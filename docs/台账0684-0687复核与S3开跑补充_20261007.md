## 2. S3 前必须补齐的实现细节

### A. 实验 Python 必须确定，禁止静默回退

`artifacts/lab_s2/run_server.sh` 在 lab `.venv/bin/python` 不存在时回退 `python3`。这会使测试环境与实际加载依赖不确定。

改为：没有实验 venv 就报错退出；若显式设置 PY，记录解释器绝对路径、Python 版本和依赖清单。主实验版本优先匹配包内 vLLM 0.26；现有 0.28 和 rebuild 里的 0.30/Omni 作为分开的兼容实验，不安装到原环境、不混写结果。Python 3.10 系统版本不能直接视为适配已验证；按该版本 wheel/包元数据选择实验 Python。

启动器还需显式指定 Linux `assets_dir` 和 `tmp_dir`，原 server 默认值为 Windows 路径；对输入布尔值进行严格校验，拼写错误应报错，不能静默当 false。当前布尔解析已正确解决 false 仍开启的旧问题。

### B. 修正真实精度日志

S2 补丁读取 `cv.model.llm.llm_engine.model_config.dtype`，而包内模型代码实际将引擎赋给 `self.llm.vllm`。当前日志很可能只输出 unknown。

应从 `cv.model.llm.vllm` 按安装版本的实际接口读取 model_config/vllm_config，并记录来源；查不到就明确 unknown，不能猜。参数存储 dtype、autocast 计算类型、vLLM 实际计算类型分开记录。当前日志位于后续补丁前，建议运行配置稳定后再补一份最终快照。

### C. 给单请求门完整的异常清理

现有补丁在多个分支手工释放 semaphore，但非流式 `_encode_wav()` 发生异常时不在这些清理路径中，可能永久占门，后续一直 429。

门的所有权应明确，采用统一 try/finally，流式响应持有门至真实任务结束。需用受控假生成器注入编码异常、生成异常、空输出、连接断开，确认后续请求可以继续。不得用“捕获重复 release 的 ValueError”替代所有权设计。

### D. 断开 HTTP 不等于后台推理结束

S2 诚实声明只执行 gen.close，尚未完成 vLLM abort。底层生成器启动了 LLM 线程；正常清理在尾部，不是完整 finally。提前关闭可能留下线程/缓存，而 wrapper 已经释放门，随后第二个请求就可能与上一请求争 GPU。

先建立取消标记、后台线程退出/引擎 abort 和缓存清理闭环，再释放门。事件循环内同步 next(gen) 也会延迟取消和 429 响应，宜改为专用工作线程/进程加有界队列。

在闭环完成前，仅允许隔离的单个正常请求冒烟；若要做断开负例，每例用可回收的独立实验进程，确认其子进程退出和显存回落后再测下一例。不能据此签署“取消生成≤500ms”。

### E. 引擎参数还没真正暴露

当前包内 EngineArgs 仍固定 gpu_memory_utilization=0.2，计划中的 max_num_seqs/max_model_len 等未通过 S2 server CLI 接线。安装前先确定实验配置格式，启动时记录实际 EngineArgs，不能把方案里的候选数字写作生效配置。

0.55 不是必须值，更不是整机显存安全保证；flow、HiFT、ONNX、OBS 还有额外占用。BNB 暂后置，先建立未量化可比较基线。

### F. 固定增益与证据口径

`--fixed-gain` 已有但启动器默认不设置，因此仍沿用 ×45。先测增益前后 PCM 和裁切比例，以同一干净参考音校准，不能未经听音直接拿这个默认值作为性能决赛配置。stats 当前跳过静音块的样本，应明确其 clip_ratio 分母为纳入统计的样本，或改为统计所有输出样本。

`midplay_cut_check.json` 同时保留粗匹配 played_s=2.0 和精细 played_exact_s=1.61；粗窗口的 post_cut 从12.29s开始，而末次有声是11.85s。字段并不推翻词中停止结论，但后续程序应使用清晰的 exact/matched 命名，并另记控制命令的对齐误差。当前这些数字不能独立支持毫秒级取消 P95 宣称；不要删除旧证据。

## 3. 推荐的下一批执行顺序

1. **先做无需 GPU 的补齐。** 修改实验启动器、精度日志、门的异常清理、配置透传；以假生成器验证错误恢复、取消状态和资源释放，不改已验收 OBS 出口。
2. **建立版本锁定的 lab 环境。** 核验 Python/wheel/CUDA/驱动组合，单独保存解析后的依赖清单和版本。安装完成先验证 import/模型配置，不立即启动推理。包内有 Omni 不意味着当前入口必须再运行 Omni 服务。
3. **协调 GPU 窗口。** 查明当前占用者及看门狗恢复行为，通过已有维护/资源调度机制让出显存。不能杀 QQ 桥，也不能在其他代理训练时强占 GPU。开始推理前再次采样；若资源仍不足，停在此处，不加载第二模型。
4. **单请求冒烟。** 使用小艺同源参考音，keepalive=false、明确预热、单并发、实际 dtype 日志。先得到完整有效音频，再测流式首 PCM；响应头和 WAV 头不算首声。保留 flow10 音质对照，再测 flow5/3。
5. **执行 S3 筛选与验收 B。** 同文本/同参考条件，与 Qwen 对照。候选短中长各10条、共30热请求，至少3次独立冷启动；完整记录 TTFA、RTF、chunk间隔、显存、失败、削波和听音结果。取消测试须采用上面的资源闭环。
6. **候选通过后推进 S4。** 再接增量 PCM / AudioWorklet，最后做 B站弹幕与 Gemma 的共存测试。CosyVoice 单独合格不等于8GB整链路合格，也不自动替换默认Qwen音色方案。

沿用 0683/0642 指标：TTFA P50≤1.5s/P95≤2.5s，RTF P95≤0.85，常态显存≤6.8GiB/峰值≤7.4GiB、OOM=失败。这些仍是目标，尚无本机 CosyVoice 成绩。

下一步的准确描述是：**S2.1 补齐可运行性和资源释放，再进入 S3 实测。** OBS 降噪问题已在 S1 收口，不需要重复返工。
