## 2. 故障分层

```text
Codex准备运行项目Python
  → 沙箱判断是否需提升
  → 自动审批请求
      → CC Switch本地代理 /responses
          → 当前提供方/分组/实际模型
          → 本次在这里返回404，操作没有执行
  → 放行后才启动Python
  → MCP initialize → tools/list → tools/call
  → Capability Registry → ledger_store提交 → 记录号回传
```

分别记录以下状态，避免混淆：

- approval_service_error：审批服务无法给出决定；本次命中这一层。
- approval_denied：审批正常完成但拒绝；不能被自动换模型重试当成服务故障。
- runtime_start_failed：解释器不能启动。
- mcp_protocol_error：stdio握手、JSON-RPC或schema出错。
- ledger_commit_failed：业务已执行但提交失败。
- ledger_ack_unknown：可能已提交但记录号回传丢失，需先查询核对，不能直接重放追加。

这些是拟议故障标签，尚未加到现有应用中。

## 3. 六段维修任务

### M0：冻结现场，不先改配置

交付：脱敏配置清单、错误样本、应用/CC Switch版本、配置作用域图、维修前备份位置。

1. 记录当前应用、代理版本、审批模式/任务实例及配置来源；分清主模型、审批角色、模型目录、别名、当前提供方和运行缓存。对照本轮“自动审批404”与“获准后同客户端读取成功”的两种执行条件。
2. 只提取model、provider、端点主机/路径、角色、错误码、request_id等诊断字段，不导出auth.json、API key或含用户prompt的完整代理日志。
3. 备份拟修改配置。CC Switch若使用SQLite数据库，需经软件导出/一致性备份机制，不能复制活动主文件就忽略WAL。
4. 记录YHLZ服务身份但不重启它、不切换Gemma适配器。维修只影响Codex/代理控制面，与数字人推理服务分开。
5. 只读查官方Codex配置文档及当前CC Switch版本的路由说明。若无法获取，明确缺项，不能猜一个approval_model配置键。

M0完成标准：能说明“审批模型在哪一层选、在哪一层改写”，或列明缺少的证据；有真实备份，不只一个hash。

### M1：确认审批角色的实际路由

交付：角色路由表与单条请求关联证据。

建议字段：role、requested_model、normalized_model、effective_provider、effective_model、endpoint_path、config_source、config_revision、response_status、request_id。日志仅存元数据，不保存审批prompt原文或凭据。

1. 用一个无敏感数据、无文件副作用的测试动作触发正常审批，记录请求入口的model和角色。
2. 比较代理收到的是gpt-5.6-luna还是codex-auto-review，以及发往提供方的实际model；由请求关联而非模型目录推断。
3. 核实当前组的可用模型。模型列表只能作线索，必须以同认证/同分组/同Responses路径的合成最小请求验证；不能用主聊天成功替代审批请求成功。
4. 查看是否存在旧配置缓存、别名未加载、提供方选择漂移。仅做必要的应用/代理刷新，记录刷新前后差异。
5. 若运行版本没有可观察的角色路由，先补代理诊断或提出上游问题，不通过捕获用户正文去猜。

不能使用成功返回固定allow的代理stub来“验证审批”；测试stub只适合离线协议测试，不能进入实际授权链。

### M2：选择一条可验证的修复路线

按M1证据选择，不同时尝试所有配置。

| 路线 | 适用条件 | 实施边界 |
|---|---|---|
| A：修正现有角色/别名配置 | 当前软件确实支持审批角色映射，且已有明确错误映射 | 只改相应项，记录requested→effective关系；不能假造官方字段 |
| B：修正当前提供方/分组能力 | 正确请求仍被当前组拒绝，提供方存在支持相同接口的可用组/模型 | 明确配置和费用变化，使用已有授权范围；若必须新凭据/新服务，停在可审阅方案等待授权 |
| C：修复或升级CC Switch适配逻辑 | 代理硬编码旧模型、错误别名、Responses转译/流式解析不兼容 | 先查当前版本官方说明，再在可回退环境验证；不改YHLZ业务代码 |
| D：修复Codex角色选择或配置刷新 | 请求在进入代理前就选了不可用角色，且无现成配置入口 | 用受支持的应用版本/配置机制或上游修复；不能推测“换主模型必有效” |

可能需要一个明确的审批角色别名，但前提是软件已有支持。若需要开发代理映射，应限定已识别的审批角色、特定提供方和确切模型；不能全局把未知模型名改成另一个模型，也不能仅靠提示词内容识别审批角色。

选择有效模型时要验证它能理解当前审批协议和输出决定，不凭“价格更低”或“普通聊天能回答”替代正确性。若软件只支持整个Codex提供方切换，方案应明确影响主任务而非假装只影响审批。

### M3：有限失败处理与观察

如果代理层确需增强，设计如下：

- 模型不存在/分组不支持：明确标记配置错误，不无限重试。
- 临时网络/5xx：仅在产品允许的范围内做有上限重试；记录是否用了已配置的备用审批路由。
- 服务正常返回拒绝：保留拒绝，不自动转另一模型争取允许。
- 响应缺失决定、格式错、流式截断：属于审批服务错误，不默认为通过。
- 若配置允许临时服务错误后转人工确认，应由Codex原生审批机制完成；代理不得把“人工可能同意”转换为allow。
- 路由切换有配置版本和审计记录。自动fallback只能使用已配置且已经验证的审批通道，不能临时添加新提供方。

健康检查使用合成最小请求。HTTP200、模型列表有名称、codex-auto-review显示在菜单都不够；要验证Responses输出/流结束/审批决定能被当前客户端解析。

### M4：验证Python与MCP真实可用

M2/M3技术检查通过后，再验证解释器和MCP，不把404消失当整体维修完成。

1. 核对`.venv/pyvenv.cfg`指定的解释器、当前Python路径及启动命令，确认Unicode路径在批准的正常执行环境能使用；不为了规避审批把解释器复制到别处。
2. 检查现有MCP客户端依赖与server启动。stdout只输出MCP协议/客户端结果，诊断走stderr，避免日志破坏握手。
3. MCP读取依次用ledger_list获取当前编号、ledger_get读取0600～0603、ledger_search用1～3关键词检索。以返回记录号/标题为证据，不直接读取台账文件。
4. 关闭客户端再开，连续三次成功，确认不是某个残留进程碰巧可用。
5. 验证不存在后台LLM推理、训练启动、真实QQ外发等附加动作。现有保护性训练标记只作资源策略，不充当真实训练观测。

MCP主调用仍走`tools/yhlz_mcp_server.py`→Registry→ledger_store。未来可让MCP/CLI共享更多结构化错误字段，但这是正常后端复用，不是审批异常时改走CLI。

### M5：真实结果追加、读回与回退

1. 维修结果使用明确标题和delivery_id，正文只写真实修改项、验证结果、限制及配置指纹。
2. 先搜索该delivery_id/标题，确保本次待登记结果尚未归档；若其他代理已登记，核对后引用，不再重复追加。
3. MCP ledger_add返回实际自动编号；再用ledger_get核对标题和内容摘要，并确认最新列表可见。
4. 若追加后响应丢失，先检索标识。找到一致内容才确认提交；无法确定就保留unknown，不盲目追加第二条。不预填0604等猜测编号。
5. 交付配置diff、恢复步骤和已知缺项。失败时先恢复对应角色/代理配置，保留诊断；不覆盖用户其他配置，不回滚已真实提交的台账结果。

## 4. 三个验收节点

| 节点 | 必须通过 | 不通过的处理 |
|---|---|---|
| J1：审批通道 | 合成审批请求连续3次正常；主模型/审批模型路由有记录；拒绝结果仍保留，坏响应不放行 | 停在角色/提供方/协议层，不改ledger_add |

| J3：登记闭环 | 一条真实维修记录经MCP追加、自动编号、再次读取一致；响应不确定先查询，不重复写 | 保留待登记与unknown，不绕过MCP |

测试异常响应/拒绝保留可在隔离的审批适配器fixture中验证，真实通道只做无副作用动作；不为测试构造破坏性系统命令。
