## 1. 计划结论

YHLZ2.0 先收敛为**模块化单体**，在验证稳定后再按需要拆成实时媒体进程和认知进程。全双工采用 NEKO 的设计原则，但不照搬 NEKO 的 Provider、生命周期、前端或记忆实现。

目标不是增加入口，而是让所有入口共享一个会话内核：

```text
麦克风 / 文本 / WebSocket
          ↓
Session Kernel
  状态、turn 所有权、事件序号、取消、恢复
          ↓
Conversation Coordinator
  ├─ Fast Path：普通聊天
  └─ Task Path：Agent / 工具 / 视觉 / 具身
          ↓
事件总线
  ├─ ASR / LLM / TTS / 播放
  ├─ Live2D / 桌宠
  ├─ 记忆 / 日志 / 指标
  └─ 外部平台适配器
```

## 2. 背景与当前约束

当前仓库是多入口、单核心倾向、外围多进程的实验性集成项目，主要存在：

- `/chat`、`/ws/stream`、`/agent/chat` 和独立 Demo 并存；
- ASR/VAD/LLM/TTS/播放之间的状态信号分散；
- Agent、视觉、具身和 Avatar 尚未通过统一会话路径接入；
- 记忆接口和存储存在重复或空实现；
- WebSocket、工具路由、插件声明和 SDK 版本存在不一致记录；
- 文档、配置、依赖和启动方式有漂移；
- 对外监听、CORS、文件工具和插件执行边界需要重新收紧。

这些问题先作为风险台账管理；未完成复核的项目不能被协议掩盖。

## 3. 工程目标

### 3.1 必达目标（P0）

1. 定义并冻结 `Session Kernel Protocol v1`；
2. 让所有生产入口经过同一会话内核；
3. 支持输入播放并行、用户抢占、旧输出失效和明确收尾；
4. 保证历史和记忆只在明确提交点写入；
5. 建立契约测试、Golden Path、故障注入和长时间运行验证；
6. 提供可回滚的版本、配置和数据恢复方案。

### 3.2 次要目标（P1/P2）

- Provider 热切换和离线降级；
- Agent/工具与实时路径隔离；
- 主动行为、视觉、具身和 Avatar 作为事件消费者接入；
- 统一插件 SDK 和能力声明；
- 进一步拆分实时媒体进程与认知进程。

### 3.3 非目标

- 一次性重写全部 `backend/main.py`；
- 立即引入消息队列、微服务或分布式数据库；
- 在核心协议稳定前扩展更多模型、平台和玩法；
- 把 NEKO 或 NachoBot 的代码直接复制进生产路径。

## 4. 目标边界与职责

| 组件 | 负责 | 不负责 |
|---|---|---|
| Session Kernel | 状态、turn 所有权、取消、超时、序号、恢复 | 模型推理、音频设备、数据库细节 |
| Conversation Coordinator | 选择 Fast Path 或 Task Path、汇总结果 | 管理播放线程和 Provider 私有状态 |
| Media Pipeline | VAD、ASR、TTS、播放、采样率和背压 | 决定人格、工具权限和记忆策略 |
| Agent/Task Adapter | 推理、规划、工具调用、任务取消 | 直接控制扬声器或修改 Kernel 状态 |
| Memory Facade | 统一读写、幂等、隐私和迁移 | 各模块直接写 SQLite/JSON |
| Avatar Consumer | 消费 `AvatarEvent`、口型、表情和动作 | 反向决定对话结果 |
| Provider Adapter | 对齐本地、云端、realtime/offline 能力 | 改变公共事件语义 |

## 5. 核心契约初稿

### 5.1 事件公共字段

```text
protocol_version
session_id
turn_id
seq
kind
actor
timestamp
trace_id
payload
```

建议事件集合：`INPUT`、`STATE`、`TOKEN`、`TOOL_CALL`、`TTS_TEXT`、`AUDIO_CHUNK`、`AUDIO_DONE`、`INTERRUPT`、`ERROR`、`COMPLETE`。

### 5.2 状态和不变量

```text
IDLE → LISTENING → THINKING → SPEAKING → DONE
                         └→ INTERRUPTED → RECOVERING
```

必须保持：

- 一个 session 同时只有一个活动 turn；
- `seq` 在 session 内单调递增；
- 取消会使旧 turn 的后续 chunk 全部失效；
- 正常结束才产生有效的 `AUDIO_DONE`；
- 中断 turn 不得重复提交 history/memory；
- 下游消费者故障不能反向破坏核心会话；
- 事件和敏感文本按权限分流、按默认策略脱敏。

### 5.3 全双工能力模型

全双工不是强制所有 Provider 使用同一种协议，而是一组可协商能力：

```text
concurrent_input
streaming_output
barge_in
cancel_generation
cancel_tts
server_vad / local_vad
tool_call_streaming
reconnect_resume
```

不具备某项能力的 Provider 必须明确降级为 offline/半双工，不得伪装成支持。

## 6. 工作分解

### WP-0：基线和冻结章程

产出：入口/功能清单、依赖和硬件矩阵、风险台账、冻结范围、责任人、回滚点。  
退出条件：基线可在干净目录复现，所有已知入口有归属。

### WP-1：协议与决策记录

产出：Session Kernel Protocol v1、状态转移表、能力矩阵、ADR-001 至 ADR-005。  
重点决策：VAD 唯一所有者、turn 提交点、取消代际、音频格式、记忆写入口。

### WP-2：特征测试与可观测性

产出：文本和语音 Golden Path、事件记录格式、`trace_id/turn_id` 日志、指标清单、回放样本。  
退出条件：当前实现的关键行为可以被自动复现并区分正常结束与中断。

### WP-3：Session Kernel 最小实现

产出：状态机、事件发布、取消/超时、会话隔离和兼容适配器。  
原则：先包裹现有链路，不先删除旧模块；禁止 Kernel 依赖具体模型或音频库。

### WP-4：媒体链路全双工

产出：输入适配器、音频格式契约、ASR/VAD/TTS/播放连接、背压、打断和收尾哨兵。  
退出条件：LLM 生成中和 TTS 播放中均可抢占，旧音频不会继续泄漏。

### WP-5：认知路径和记忆

产出：Fast Path/Task Path 路由、Agent 工具适配器、Memory Facade、幂等提交和迁移脚本设计。  
约束：Agent 不直接写历史、不直接控制播放、不绕过权限。

### WP-6：外围能力接入

产出：AvatarEvent、视觉/具身/主动行为消费者、插件能力声明和失败隔离。  
策略：外围模块可以暂时保持实验状态，但必须显式标记，不得成为默认核心依赖。

### WP-7：安全、发布和冻结

产出：认证/CORS/文件工具策略、依赖锁定、干净安装说明、压力/长跑报告、冻结标签和回滚手册。

## 7. 阶段计划与门禁

下表是初步工作日估算，实际以 WP-0 复核为准：

| 阶段 | 主要工作 | 参考工作量 | 退出门禁 |
|---|---|---:|---|
| S0 基线 | 清单、风险、环境复现 | 1–2 天 | 基线可复现、风险有负责人 |
| S1 设计 | 协议、状态机、ADR、能力矩阵 | 2–4 天 | 协议评审通过 |
| S2 保护 | 特征测试、日志、回放样本 | 3–5 天 | Golden Path 稳定 |
| S3 内核 | Kernel 和旧入口适配 | 3–6 天 | 单会话/并发隔离通过 |
| S4 双工 | 音频并行、抢占、恢复 | 5–10 天 | 中断和故障注入通过 |
| S5 认知 | Agent、工具、记忆收敛 | 4–8 天 | 无重复提交、权限通过 |
| S6 外围 | Avatar、主动、视觉、插件 | 4–8 天 | 失败可隔离、可关闭 |
| S7 发布 | 安全、长跑、文档、冻结 | 3–5 天 | 冻结清单全部通过 |

若 S1 或 S2 暴露 Provider 不具备取消/流式能力，应保留同一协议并切换到 offline 降级，不强行实现伪全双工。

## 8. 验证策略

### 8.1 自动化层次

- 单元测试：状态转移、事件序号、取消令牌、文本清洗和队列边界；
- 契约测试：HTTP、SSE、WebSocket、事件 JSON、Provider 能力协商；
- 集成测试：真实 ASR/LLM/TTS 各至少一条路径；
- 故障注入：超时、断线、重复 chunk、设备不可用、工具失败、进程重启；
- 长跑测试：连续对话、持续播放、内存/显存/线程/队列监控；
- 安全测试：认证、路径穿越、任意文件访问、插件权限、日志脱敏。

### 8.2 关键观察指标

- 首 token、首音频、首字出声延迟；
- 用户打断到播放停止的延迟；
- 过期 chunk 丢弃率和重复 turn 数；
- Provider 错误、降级和重连成功率；
- 队列深度、线程/任务数量、GPU 显存峰值；
- 记忆重复写入、隐私泄漏和事件回放成功率。

指标阈值在 S0 依据硬件和 Provider 实测后确定，不预先伪造精确目标。

## 9. 风险登记

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 双 VAD 或双状态机并存 | 重复提交、竞态 | 明确唯一所有者，旧逻辑只作适配器 |
| 本地 Provider 不支持取消 | 打断不真实 | 能力协商，丢弃旧输出并保留 offline 降级 |
| TTS/播放队列无界 | 延迟和内存增长 | 有界队列、背压、取消和长跑测试 |
| Agent 工具阻塞实时路径 | 用户体验冻结 | Task Path 隔离、超时、权限和可取消任务 |
| 双记忆存储继续写入 | 历史不一致 | Memory Facade、幂等键、迁移前禁止新写入口 |
| 前后端协议漂移 | 客户端静默失败 | schema、版本协商、契约测试 |
| 过早冻结错误行为 | 技术债固化 | 冻结不变量，已知 bug 必须修复或书面豁免 |
| 直接复用外部代码 | 许可证和维护风险 | 保留 NOTICE，逐项审查依赖和修改范围 |

## 10. 冻结验收标准

只有同时满足以下条件，才发布 `architecture-freeze-v1`：

1. 生产入口统一进入 Session Kernel；
2. 会话、turn、事件和取消语义有版本化契约；
3. 全双工和 offline 两种模式共享上层接口；
4. TTS、播放、Avatar、Agent、记忆均通过事件或明确端口连接；
5. 已知 P0/P1 路由、数据、安全问题已关闭或有批准豁免；
6. 干净环境启动、契约测试、真实链路和长跑测试通过；
7. 有版本标签、回滚步骤、数据恢复和变更审批人。

冻结后的常规开发只允许在契约内部进行。修改公共事件、状态机、权限边界、存储所有权或入口拓扑，必须重新走 ADR 和兼容性评审。

## 11. 近期执行队列

在开始业务重构前，按以下顺序完成：

1. 复核 `/ws`、工具路由、记忆接口和插件加载的实际行为；
2. 形成入口/功能/Provider/数据存储四张清单；
3. 评审 Session Kernel Protocol v1 草案；
4. 为文本 Golden Path 和一次真实语音链路定义验收样本；
5. 确定 VAD、音频时钟、turn 提交和取消传播的唯一所有者；
6. 通过 S0/S1 门禁后，才允许创建 Kernel 代码和迁移分支。

## 12. 计划变更规则

本计划是初稿。任何改变目标架构、冻结范围、Provider 能力假设、数据迁移策略或安全边界的事项，都要更新本文件版本并附 ADR；普通实现调整不必扩大计划范围。
