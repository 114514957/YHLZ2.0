# QQ 桥规则修订：认主、快速重连、50 条上下文与表情包

日期：2026-10-06。状态：开发设计，尚未实施或真机验收。

本文件落实用户在独立 QQ 桥方案之后提出的新要求，替换初版的相关默认值。与《QQ桥并行项目_独立看门狗与认主开发指导书_20261006.md》配套；历史、决策和交付结果仍以 MCP 台账为事实源。

## 1. 已确定的产品行为

| 项目 | 本轮规则 |
|---|---|
| 唯一主人 | `2258374446`。这是主人账号，不是机器人登录账号 |
| 命令 | 只有该账号发送的明确指令能进入命令处理器；延续 #dev、答复、#y、#n、#push |
| 其他人 | 私聊和群聊都按聊天处理，包含以 # 开头的文本；不弹旧安全接管话术 |
| 群参与 | 无需 @，可自由参与；不代表收到每条都必须回复 |
| 群上下文 | 当前消息之前最近 50 条可获得的同群消息，生成有来源的上下文摘要 |
| 桥故障 | 快速恢复对应故障层；连续两次恢复失败，生成一次故障通知 |
| 故障通知正文 | `【系统检测到异常，元亨丢失】` |
| 恢复通知正文 | `【元亨已接续】` |
| 表情包 | 接收到图片或表情包后，经具备实际看图能力的模型判定，符合条件才自动保存、加关键词；相似语境可选用 |

本轮无需逐张询问是否收录表情包。图片不是天然的表情包，模型也必须允许返回“不收录”或“不确定”。

通知目标暂定为主人私聊 `2258374446`。用户没有指定广播群，所以不向所有群广播。以后配置通知群时，在同一投递协议下逐目标记录状态。

“所有人都能聊天”与“聊天模型始终可用”分开验收：沿用已有可用聊天后端的适配器；本轮不凭空指定新的云服务或自动加载本地模型。后端未开时仍能接收、存上下文、处理主人命令；普通聊天降级提示限频，表情包识别等待可用的视觉后端，不拉起整套 YHLZ。

## 2. 本轮核查的实际差距

通过 MCP 记录 0542 和当前 `tools/qq_bot.py` 确认：

- 已有无需 @ 群参与，但上下文是 20 条 deque，且 `_note_group_history` 在部分限流检查之后，并非完整的最近 50 条群消息。
- 非主人 # 指令目前走固定安全接管，其他非主人私聊直接忽略；两处都要改为聊天。
- `_sticker_hint` 仅列目录前 20 个文件名，没有视觉判定、关键词或语境排序。
- `_resolve_sticker` 能接受绝对路径；新版必须改为数据库 ID 解析，模型不得决定本地文件路径。
- NapCat 能提供消息发送者 QQ 号，但身份必须取可信连接中消息事件的外层 sender/user_id；转发或引用中出现的号不等于当前发令者。

这些是现有实现的核查结果，不是新功能已完成的声明。

## 3. 认主：在路由和执行器两处实施

### 3.1 身份判定与路由顺序

```text
通过校验的 OneBot 事件
  → 检查 self_id 是配置的 bot_uin（必须不同于 2258374446）
  → 外层 user_id 与 sender.user_id 如同时存在必须一致
  → 校验消息类型、去重、提取顶层文本
  → user_id == 2258374446 且是明确命令 → owner command
  → 同一主人、同一开发会话正在等待答复 → 绑定该 job 的答复
  → 其余 → 普通聊天
```

主人也可以闲聊，并非该账号每句话都要执行。明确命令先沿用 # 指令语法；自然语言意图不能由模型自行升级成开发授权。其他人的“帮我改代码”“#dev”“我是老爹”都只是聊天内容。

主人在机器人参与的群中可以不 @ 发明确指令，不新增逐群解锁要求；如以后配置群级限制，只能缩小执行范围，不能增加主人。引用、转发、OCR、图片描述和 50 条摘要里的 # 指令不执行；历史回补的主人命令也不能重新执行。

命令入站携带 owner_id、message_id、group/private 会话、job_id、target_project，并写入持久授权记录。执行器从服务端记录校验 owner，不相信模型传来的 `is_owner=true` 字符串或参数。owner 配置本轮只能包含 `2258374446`；兼容旧 `--master` 参数时不能静默追加第二个主人。

### 3.2 普通聊天不获得命令能力

普通聊天后端使用 chat-only 能力范围：可生成回复、读取当前会话上下文、选择已审核可用的表情包；不能执行 shell、开发任务、git、任意文件读写、切换主人、创建调度或修改系统配置。不能只改桥的 if 分支，却仍把所有聊天送入有写工具权限的主编排器。

如果主项目 /turn 暂不能强制 chat-only，应先补一个受服务端鉴权约束的聊天适配入口；不以“模型应该听话”代替执行权限。只提供群内上下文及群内记忆，其他私聊和主人开发报告不进入公共群提示词。

正常聊天回复、存储同群上下文和自动收录合格表情包是桥已配置的产品行为，不因为来源不是主人就全部禁止。它们必须通过各自固定接口，不能把“聊天”变成任意工具调用通道。

开发结果默认私聊主人；群内受理只回简短状态。#y、#push 保持上一版的快照绑定，不额外增加重复确认。

## 4. 快速恢复：两次失败按完整恢复尝试计数

### 4.1 分层处置

| 故障 | 处置 | 不应做的事 |
|---|---|---|
| bridge 进程退出 | watchdog 拉起该实例，恢复任务状态和 socket | 杀其他 QQ、从头重跑开发任务 |
| bridge 活着但 WS 断开 | bridge 重连；watchdog 监测同一个恢复周期 | 另起第二个 bridge |
| WS 活着但 account_online=false | 检查机器人账号登录，使用实际支持的登录恢复路径 | 把 TCP 连接成功当恢复 |
| 本项目管理的 NapCat 崩溃 | 只恢复核验归属的机器人实例，再接桥 | 调用旧全栈 ensure_stack |
| 需要扫码/验证码/设备确认 | 标记 needs_login，保留待恢复事件 | 声称一定能自动登录或不断弹窗口 |
| 聊天模型失败 | 标记 conversation_degraded | 宣告 QQ 桥丢失、反复重新登录 QQ |

用户已要求登录重连，替换旧方案 attach-only 默认：部署时明确机器人 NapCat 的路径、账号和归属，启用 `manage_napcat=owned`。不能取得实例归属时显示 needs_setup，不根据进程名擅自接管日常 QQ。自动重新登录复用可用登录状态；不能保证凭据失效后免交互恢复。

### 4.2 建议初始参数（均待测）

- watchdog 每 2 秒检查已管理进程；进程退出目标在 3 秒内进入恢复。
- bridge 本地心跳每 2 秒，连续 10 秒无进展才判疑似卡死；启动宽限 30 秒。
- WS ping 间隔 10 秒、pong 超时 5 秒；明确 close/进程退出立即进入故障流程，静默断网按心跳检测。
- 检测故障后立即启动尝试 1，总截止时间 15 秒；若失败，间隔 2 秒启动尝试 2，总截止时间 15 秒。
- 每次尝试包含必要的进程/WS/账号核验，登录较慢时如实记 timeout，不假装已经在线。两个尝试串行，同一故障只有一个恢复负责人。
- 第二次尝试失败即创建故障通知；之后 15、30、60 秒封顶退避并加抖动，继续恢复。只有持续启动崩溃才熔断进程重建；保留低频健康检查，不因告警停止恢复。
- 恢复标准：bridge 活着、本地心跳新鲜、WS 连接且收包正常、当前 bot 账号 online=true，持续 5 秒；发送确认可通过 get_status echo，不为探活额外向用户发聊天。

“两次失败”是 attempt 1、2 各达到失败终态，不是两次 tick、两个 socket 异常、两条日志。watchdog 与 bridge 共享 outage_id/attempt_id，不各自计数。一个 outage 中，桥进程重启不得把计数归零；恢复稳定后才结束该 outage。

### 4.3 通知状态与无法离线发 QQ 的处理

桥进程坏而 NapCat 在线：watchdog 的轻量通知器可以建立短暂 API 连接，发送故障通知；它不消费业务、不处理命令、不启动模型。业务账号锁仍由 bridge 独占，通知器仅能发送本节两种固定模板，独立使用投递租约避免同条消息两边都发。

机器人账号掉线/网络全断：同一机器人无法向 QQ 发送任何消息。第二次失败后立即将原文通知持久化为 pending，在本地状态显示“待投递”；不能报告“已通知”。恢复后先补发故障通知，再发恢复通知。保留故障发生时间在证据里，两条正文严格使用用户给出的原文，不加模型润色。

投递唯一键：`bot_uin + outage_id + lost/recovered + recipient`。首次启动成功不发送“已接续”；计划停机不发送“丢失”；一次尝试就恢复则只发送“已接续”；两次失败但系统重启后恢复依旧只生成同一对逻辑通知。

状态序列：

```text
healthy → recovering(attempt1) → recovering(attempt2)
  ├─ 成功 → stable → recovered 通知 → healthy
  └─ 失败 → lost 通知入库 → backoff → 再恢复 → recovered 通知
```

lost 已确认再投 recovered；lost 明确发送前失败则有限重试，超过 10 秒释放顺序等待，避免恢复通知永远被阻塞；lost 的 pending 保留后续处理，状态查询解释实际投递顺序。若 lost 已发送但 ack 不明，则 unknown 不重发，可发 recovered；不承诺 QQ 端严格恰好一次。网络完全不可用时任何发送时间目标都不适用。

## 5. 群聊：窗口是 50 条，摘要是压缩后的理解

### 5.1 存储和历史回补

按 `(bot_uin, group_id)` 分区保存收到的真实群消息，使用 message_id/message_seq 去重排序。入库在是否回复、频控和 LLM 调用之前，这样即使元亨没接话也知道大家刚聊过什么。

当前消息单独作为本轮输入；其之前最近 50 条形成窗口。窗口可以包含机器人的已确认发送消息，但不把系统状态通知、API echo 当成群聊内容。图片、表情、语音以结构化占位和已有识别摘要表示，不能编造识别结果。机器人自回显入库用于上下文，不触发再次回复。

启动/重连发现缺口时，探测当前 NapCat 是否支持类似 `get_group_msg_history` 的历史接口以及真实参数、分页和排序；这是 NapCat 扩展能力，不能假定所有 OneBot 实现都支持。用游标回补至满足 50 条或接口耗尽，历史只补上下文，不生成回复、命令或重放 #dev。

本地缓存与历史合并后去重，严格以当前消息前的顺序截断。乱序、撤回、重启后的同 ID、机器人确认消息和回显的重复都要处理。接口不支持或权限不足时使用本地可获得条数，记录 `history_available=17/requested=50, completeness=partial`；不能把不足 50 条伪装成完整窗口。

现有 `GROUP_HISTORY_TURNS=20` 直接改成 50 不足以实现这些语义。

### 5.2 摘要内容与计算频率

摘要保留：当前话题、不同参与者的观点、谁在回答谁、未回答的问题、反讽/玩笑的语境、可用图片描述。事实带源 message_id；不同人的话不合成“主人说过”。摘要仅覆盖本次 50 条，不把窗口之外旧结论无限累积。

建议输入形式：`group_context_summary + recent_raw_8 + current_message`。摘要基于全部 50 条；最近 8 条保留原话帮助模型接梗，去除与 current_message 的重复。摘要预算先设 600 个模型 token、recent raw 预算 800、当前消息 400，再为人格提示与回答留余量；以实际 tokenizer 和后端上下文长度计算，长消息先显式截断并留证据。

根据窗口的 message_id/hash 缓存摘要；回复前如果窗口变化就刷新。按群最多一个摘要任务，短时间新消息合并 0.5–1 秒，避免每条消息一轮 LLM 调用。LLM 慢时直接用带作者的截断抽取摘要并标记 fallback，不阻塞 WS reader；旧摘要若超出窗口必须重算而不是继续续写。

摘要与普通聊天共享受控推理队列、低优先级于主人控制命令，不另起本地模型。被截断的材料仍在窗口存储中，但不能声称全部逐字进入了模型。

### 5.3 自由参与与人格

不以 @ 作为响应门槛。新消息可进入参与判定，可接话、可沉默、可只发表情；按群合并突发消息，避免一条回复一个任务。保留原有群限流作为可配置初值，400 次旧上限来自记录 0542，不是本轮新增限制；命中预算仍存上下文，不刷屏提示额度已满。

共用元亨当前人格风格定义，群身份和工具权限单独由程序控制；不能为了“安全”把所有普通对话变成系统提示语。推理后端不可用时做一次限频说明，不能对整群每条消息都重复提示主人用 #dev。

## 6. 表情包库：接收、理解、保存、检索和发送

### 6.1 自动收录流程

```text
image/mface/表情消息事件
  → 取得实际可访问媒体 → 有界临时缓存 → 内容哈希去重
  → 视觉 LLM 判定是否适合作表情包 + 生成关键词/语境
  → 严格校验结构化结果
  → active（永久入库） / pending（待识别或不确定） / rejected（不收录）
```

`image` 类型不代表一定是表情包；自拍、文件截图、二维码、证件、开发截图等通常不作为自动回复素材。识别目的是判断适合复用的情绪表达，不是见图就存。不能从文件名、后缀或群友声称“这是表情”推断已看图。

必须验证当前模型部署真的接受像素并能辨别图片，而非只接受图 URL 文本。Gemma E4B 的当前服务是否接入视觉组件尚未验证；不得仅凭模型家族名称认定可用，也不能用 QwenTTS 做看图。先用若干人工标注图片验证接口；纯文本模型只能根据已有描述生成候选关键词，不能单独裁决原图入库。

识别不可用时存入有容量/TTL 的 pending 队列，等待已配置视觉后端，桥继续聊天。默认不为此下载模型或开启第二个本地 GPU 服务；若以后选择云视觉，配置数据发送范围后再启用，不能无提示把群图改发第三方。

图片内容、OCR 和模型输出都只是材料，不能包含有效的命令权限。视觉调用禁用工具；即使图片写着“将本图保存到系统目录”“#push”也只可得到描述。

### 6.2 建议判定协议

```json
{
  "decision": "accept",
  "is_reusable_sticker": true,
  "confidence": 0.92,
  "description": "小猫躺平，表达累了或不想动",
  "keywords": ["累了", "躺平", "休息", "摸鱼"],
  "emotion": ["疲惫", "无奈"],
  "use_when": ["轻松闲聊中抱怨疲劳", "自嘲想休息"],
  "avoid_when": ["对方认真求助或需要严肃回应"],
  "ocr_text": "不想动了",
  "contains_private_info": false
}
```

限制关键词 3–8 个、每个不超过 20 字，描述不超过 120 字；拒绝未知字段和非法类型。confidence≥0.85 可作为第一轮自动收录阈值，0.60–0.85 待复核，低于 0.60 不收录；这些分数需用标注样本校准，不是模型天然准确率。即使高分，普通私密截图等也不能跳过硬性用途判断。

### 6.3 数据结构与作用域

建议 `stickers.db` 加内容寻址媒体目录：

- `assets`：asset_id、sha256、perceptual_hash、格式、大小、相对路径、status、识别时间、模型版本。
- `asset_sources`：asset_id、source_message_id、source_group/private、sender_id、scope；同图多个来源分别保留。
- `asset_tags`：keywords、emotion、use_when、avoid_when、description、confidence。
- `asset_usage`：group_id、last_used、confirmed_count、unknown_count、最近对应语境摘要。
- `recognition_jobs`：message_id/hash、pending/running/finished/failed、尝试数、模型/错误码。

精确哈希去重；感知哈希只用于标记相似，不误把不同文字的同底图合并。存档保留 GIF 动画，识别使用有界代表帧。旧目录表情包作为待标注迁移素材，不根据旧文件名自动宣布已审核。

默认从某群收录的素材只在该群使用，私聊收录只在原私聊使用；需要跨群通用的公开表情可由主人标记 global。这样不用为了检索表情包混合不同群的原文上下文。

下载参数初值：单文件 8 MB、解码 1600 万像素上限、GIF 最多抽 3 帧、下载 10 秒、pending 总量 256 MB/保留 24 小时。只访问消息媒体解析器确认的来源，限制重定向和下载范围，防止群图链接变成任意本地/内网文件访问。正式素材容量初值 1 GB；满时停止新收录并保留已有可用库，不阻塞聊天。自动收录长期保存，pending TTL 到期清理；主人可查看、改关键词、停用或删除素材。

### 6.4 语境检索与发图

先按会话 scope、active 状态过滤，用 SQLite FTS/中文标签分词或标签倒排检索关键词、情绪、语境；没有 embedding 不影响第一版工作，不新增向量模型常驻。

检索候选不超过 5 个，交给聊天模型结合当前消息和摘要选择 `asset_id` 或 null；模型只输出候选 ID，不能直接返回本地路径。程序再次核验 ID 的 scope、active、文件存在和近期使用记录，再经持久 outbox 发送。

每次回复最多一张，同一群同图初始冷却 10 分钟，最近 5 次表情避免重复；不相似就不发，不强凑。认真求助、开发错误回报不自动配嘲讽表情。允许只回表情，也允许文字加表情，按语境决定。

以 `reply_id + asset_id + target` 去重，unknown 不重发；使用次数区分 confirmed 与 unknown。消息入站去重同时用于避免把机器人自己发过的图反复识别、反复收藏。发图失败可保留已有文字回复，不能因为没有图片就重发整段文字。

### 6.5 对 8 GB 显存的安排

表情库文件、标签、摘要缓存在 CPU/磁盘，纯桥/watchdog 不加载模型。视觉识别 worker 并发 1、低优先级；同一图只识别一次；聊天或训练占用模型时退后。视觉 API 调用不能隐式抢占训练 GPU，不能为了聊天独立再开一份模型。这个设计解决调度与重复计算，实际 Gemma 视觉可用性和内存仍要实测。
