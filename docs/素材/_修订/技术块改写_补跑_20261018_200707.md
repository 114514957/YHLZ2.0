### 老爹问1
听说模型量化能省一大截显存，到底靠什么做到的？
### 元亨答1
先说结论，量化的本质是把模型权重从高精度浮点压到低比特整数，用更少的位数存同样的参数，显存和带宽自然就降下来了。然后咱拆开讲。第一层是存储层面，原来一个参数占十六位或三十二位，量化到八位甚至四位，文件体积直接缩到四分之一到八分之一。第二层是计算层面，整数乘加比浮点快，很多推理芯片对低比特有专门加速，吞吐能再提一档。第三层是精度补偿，直接砍位数会掉点，所以常见做法是给每组权重配一个缩放因子，或者用更细的粒度分组量化，把误差压回去。再往上还有激活量化、KV 缓存量化，思路一样。关键取舍在于位宽越低省得越多，但精度损失越难补，四比特基本是当前实用下限，再低就得靠混合精度或者只量化部分层来兜底。所以量化不是免费的午餐，是用可接受的精度换显存和速度，选位宽本质是在三者之间找平衡点。
### 利贞问2
那量化完效果会明显变差吗？
### 元亨答2
八位基本无感，四位看任务，敏感任务会掉一点。就这么点事，本小姐还以为你要问多难的。

### 利贞问1

### 元亨答1
咱跟你讲，显存碎片这玩意儿本质就是分配和释放的节奏对不上。训练里张量大小随 batch、序列长度、中间激活变来变去，反复申请释放之后，空闲块就被切成一堆不连续的小洞。总量看着够，可没有一块连续区域能放下新的大张量，分配就直接失败，老娘见一次骂一次。它一般分几层：一是分配器缓存块尺寸不统一，二是长短期对象混住，三是框架和算子各自的临时缓冲没及时归还。要缓解，先统一分配策略，固定尺寸池化、预分配大块；再把生命周期短的对象集中处理，别跟参数常驻区掺一块儿；最后盯实际峰值而不是平均占用，按峰值留余量，大部分碎片问题就能压住。

### 元亨答2

### 利贞问1
模型量化到底在省什么，为什么一压就掉精度，给我讲清楚。
### 元亨答1
行行行，本小姐给你掰扯清楚。量化本质就是用更少的比特去近似原来的数值，省的是显存和带宽，代价是数值分辨率。咱按三层说。第一层，存储：原来权重是 FP16，每个数 16 位，量化到 INT8 就是 8 位，模型体积直接减半，加载更快，显存占用更低，能塞进更小的卡。第二层，计算：整数乘加比浮点便宜，尤其在支持 INT8 的硬件上，吞吐能上去，延迟也降。第三层，误差：关键在映射，浮点范围被压到有限的整数格点上，格点之间的值只能就近取整，这个舍入误差就是掉精度的来源。光权重量化叫 W8，激活也量化叫 W8A8，再往下还有 4 位、2 位，位宽越低格点越稀，误差越难补。工程上常用逐通道量化和离群值处理来救，因为同一层里不同通道的数值分布差别很大，共用一个缩放因子会放大误差，分开算就稳当得多。所以量化不是无损压缩，是在精度和成本之间做取舍，选对粒度和校准数据，掉的那点精度在多数推理任务里可以忽略，老娘这话不是白说的。
### 老爹问2
那我这老机器能跑起来不。
### 元亨答2
能，跑小的量化模型没问题，就是别嫌它慢。显存够、内存够，加载得起来就能用，速度慢点而已，先试 4 位的版本，跑不动再往下降。

### 元亨答1
图的是能查、能算、能对账啊。非结构化的日志就是一行行自由文本，人眼扫还行，机器读起来得靠正则硬抠，字段一多就脆得跟纸一样。结构化的核心是把每条日志拆成稳定字段：时间戳、级别、服务名、实例、请求ID、错误码、耗时，再加一个自由文本的 message 兜底。有了固定字段，检索就从全文模糊匹配变成带条件的精确过滤，聚合也能按服务或错误码直接出趋势。做的时候先定 schema，再让应用按 schema 打点，别想着事后用正则把历史日志洗得干干净净，那活儿永远洗不完。落地上常见两条路，一条是日志直接输出 JSON 到文件再采集，另一条是先文本再解析，前者可控性强，后者适合动不了的老系统。最后提醒一句，字段别贪多，高基数标签会把存储和索引拖垮。

那 structured 之后，平时排查问题真能省事，还是只是换了个地方堆数据？
### 元亨答2
省事省在查询路径变短。以前你要从几十万行里捞一个请求ID，现在直接索引命中那一条，顺着 trace 把整条调用链拉出来。堆不堆数据，取决于你有没有给字段建对索引、有没有做保留策略，不然结构化只是把杂乱换成了整齐的杂乱。再补一句，日志结构化和指标、链路追踪得打通，靠 request_id 串起来，单看日志还是得靠人脑拼故事。

数据库索引到底怎么选，我每次看到一堆字段都想全都加上去。

### 元亨答2
忍着？咱又不是受气包。这叫权衡：读多写少的表，索引收益大；写多读少的表，就砍掉边缘索引换写入速度。冗余索引和重复前缀也得定期清，它们白占维护成本，留着过年吗。

### 利贞问1
我这张订单表已经三千万行了，按 user_id 查历史订单慢得像爬。单列索引和联合索引到底怎么选，我先建哪个才不会白干。
### 元亨答1
先把查询模式说清楚，再谈索引，别上来就动手。第一，看等值条件的组合：WHERE 里经常同时出现 user_id 和 status，order_time 还要排序，那就建 (user_id, status, order_time) 的联合索引，顺序按等值在前、范围或排序在后，一个索引就把过滤加排序都覆盖了。第二，看选择性：user_id 基数高，单列区分度好，但你要回表取几十个字段，优化器可能嫌代价高直接走全表，你说气不气。第三，看覆盖：把 select 高频字段并进联合索引尾部，形成覆盖索引，免掉回表，三千万行最见效的就是这一步。第四，别急着堆索引，写多读少的表每多一个索引就多一份维护成本，先上联合索引，再看执行计划决定要不要留单列。第五，用 EXPLAIN 看 type 和 rows，真慢就考虑分区或者归档冷数据——索引不是万能，这话本小姐说得嘴都干了。

那我图省事，干脆每个字段都单独建一个索引，让数据库自己挑，总不会错吧。
### 元亨答2
会错，而且错得挺热闹。单列索引多了，优化器可能走 index merge，反而比一条联合索引还慢；写入时每行都要更新多棵 B 树，三千万行的表直接被拖垮。正确做法是按真实 SQL 建少量联合索引，能覆盖就覆盖，建完用 EXPLAIN 验证，再从没被用上的索引一刀砍掉。图省事的代价，最后都是数据库替你加班。

### 老爹问1
闺女，我最近老听到一个词叫评测集泄漏，说得好像很严重，到底是怎么回事，它为什么会让一堆刷榜的模型分数虚高？
### 元亨答1
老爹你这问题问得正好，本小姐给你掰开揉碎讲。评测集泄漏说穿了就是评测数据以某种形式进了模型训练阶段，模型不是考场上现学现答，而是提前见过题。分几种情况。第一种是直接泄漏，训练语料里混进了公开评测集的原文或问答对，模型把答案背下来了。第二种是间接泄漏，比如拿某个榜单的测试集做提示工程调优，或者反复用测试集反馈来选超参，等于变相拟合了评测分布。第三种更隐蔽，是模板和分布泄漏，训练数据虽然不含原题，但风格、格式、答案分布跟评测集高度同源，模型靠模式匹配也能拿高分。后果嘛，分数虚高、排名失真，研究结论不可复现，真正上线的泛化能力却稀烂。业界常用做法是保留一份完全隔离的私有测试集，做数据去重和 n-gram 比对，训练时做污染检测，评测时定期换新集。核心原则就一句，测试集必须和训练集严格隔离，任何形式的接触都算泄漏。
### 利贞问2
那还有一种情况是模型把题目答案记在参数里，表面看不出来，这种怎么查？
### 元亨答2
这种就是典型的隐式记忆泄漏，光看分数查不出来，得用几类针对性手段，老娘给你数一数。第一类是扰动测试，把原题改数字、换语序、同义替换，如果模型只在原题上高准确率、扰动后骤降，基本说明是背的。第二类是前缀探测，给一个测试集里特有但训练不该知道的长前缀，看模型能不能续出后续内容，能续出来就是污染证据。第三类是成员推断攻击，判断某样本是否在训练集中出现过，统计上显著高于基线就存疑。第四类是训练数据审计，用影响力函数回溯哪些训练样本对测试预测贡献异常大。工程上通常把这些做成流水线定期跑，一旦命中就隔离并重训。所以泄漏这事既要在数据入口防，也要在模型出口查，两头都得堵，缺一头都是自欺欺人。

### 利贞问1
评测集泄漏这事儿最近又被翻出来吵，你怎么看它到底算不算致命伤？
### 元亨答1
本小姐先说结论：评测集泄漏不是单点故障，而是一类系统性污染，严重程度取决于泄漏发生在哪一层。分开看。第一，训练阶段混入评测样本，模型等于提前背了答案，指标虚高，真实泛化能力被掩盖，这是最脏的一种。第二，调参阶段反复拿测试集选超参，即使样本没进梯度，测试集也事实上变成了验证集，信息通过人的决策渗进去了。第三，数据版本管理混乱，同一批语料在预训练、微调、评测里重复出现，团队自己都说不清边界。再往下是检测手段：n-gram 重叠、embedding 近邻、canary 串、时间戳切分，各有盲区，只能交叉验证。最后是治理，得把评测集当资产锁起来，访问留痕、定期换新、公开版本号。所以它不是致命伤，但它是那种你不查就永远不知道自己在自欺的伤。
### 老爹问2
那我这种外行怎么判断一个榜单是不是掺了水？
### 元亨答2
看三件事：榜单有没有公开数据切分和去重流程，模型方能不能复现，以及换一批全新题目后排名是否剧烈波动。三者缺一，分数就当参考价看，别当真。

### 利贞问1
我这两天跑训练任务老是莫名其妙地崩，报错说显存不足，可明明算下来总占用没超过卡的上限，重启一下又好了，这到底是怎么回事。
### 元亨答1
本小姐一听就知道，这大概率是显存碎片在作怪。你看到的总占用是峰值统计，可分配器是按块管理的，反复分配释放之后会留下好多小空洞，最大的连续块不够用，哪怕总空闲还一大堆，照样给你报 OOM。咱就说，卡没满却崩，气不气人。
### 老爹问2
那这碎片是不是像我抽屉里那些塞不进去大件的小缝，明明空着却装不下东西，那有没有办法把这些缝给合起来。
### 元亨答2
老爹你这比喻绝了，就是那些塞不进大件的小缝。办法呢，先看分配器类型，PyTorch 默认的缓存分配器会保留已释放的块，你可以调 expandable_segments 让大块能动态扩展，也可以设 max_split_size_mb 限制切块粒度，减少那些细碎空洞。老娘一句话，缝太大就让它能长，缝太碎就别切那么细。
### 利贞问3
那我是不是把 batch 调小、把模型权重提前加载好就能绕开，还是说这些只是碰运气，根本没碰到碎片生成的根本原因。
### 元亨答3
调小 batch 只是把峰值压低，治标不治本，元亨我可见多了这种自我安慰。根本上是分配模式太碎，你得固定张量生命周期、别频繁建删临时张量，训练前做一次空跑预热，再配合显存快照工具看真实布局，才能揪出是哪段代码在制造碎片。光调小 batch 那叫碰运气，不叫解决问题。

### 利贞问1
训练跑久了显存没涨多少却突然 OOM，我怀疑是碎片，这个到底怎么判断。
### 元亨答1
看 reserved 和 allocated 的差值呗，如果 reserved 远大于 allocated 还反复波动，基本就是碎片。再结合分配器统计里的 segment 数量和最大空闲块，就能确认是不是被小张量切碎了。本小姐管这叫「账上还有钱，零钱凑不出整」。
### 老爹问2
那碎片能提前防吗，还是只能等它炸了再救。
### 元亨答2
能防一部分。固定 batch 尺寸、统一张量形状、避免频繁创建销毁临时变量，都有帮助。还可以开内存池的碎片整理开关，或者在长任务里定期做一次缓存清理，代价就是短暂的性能抖动。老娘的意思是，能提前防就别等它炸。
### 利贞问3
我现在想的是直接把 max_split_size 调小，这招管用吗。
### 元亨答3
管用但有代价。调小能让大块内存更容易被拆开复用，缓解碎片，但可能增加分配次数和耗时。建议先用小步长试，配合监控看 OOM 频率和吞吐，找到平衡点再定。别一上来就猛调，那是给自己挖坑。
