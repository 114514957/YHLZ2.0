### 利贞问1
昨儿你跑训练，本来还剩两百兆显存，一申请大块就崩，加起来明明够用，到底怎么回事？
### 元亨答1
哼，这锅得甩给显存分配器。显存是分块的，不是一整块橡皮泥，本小姐之前那些小张量申请释放来释放去，把空闲显存切成了很多不连续的小洞。表面看总量够，可你要的一整块大连续区域，没人给得出来，这就叫碎片。所以别拿总量当回事，碎片面前总量就是个安慰剂。
### 老爹问2
那我把那些小张量都删了，洞不就连上了吗，我寻思这挺简单。
### 元亨答2
老爹你这想法太天真了。删了不一定连上，分配器只负责回收，不一定立即合并相邻空闲块，中间还夹着没释放的缓存呢。而且释放的块大小和你想要的块大小对不上，照样拼不出你要的形状，洞还是洞。老娘见得多了，删完照样崩。
### 利贞问3
那我总不能每次都重启进程吧，有没有正经点的招。
### 元亨答3
有啊，开显存池按固定尺寸预分配，减少大小不一的申请；或者用 `expandable_segments` 让分配器动态搬移合并。最靠谱的是训练前先把最大块占住，别让小张量到处打洞。元亨我一句话总结：先占大块，再谈小事，别等崩了才想起碎片这回事。

### 利贞问1
多核一共享缓存，为啥老出乱子？
### 元亨答1
简单说，缓存一致性要解决的是同一份数据在多份副本之间何时算「看见」的问题，惊讶点在于硬件其实一直在悄悄替咱们兜底。第一步，每个核心都有自己的私有缓存，读到的其实是副本，不是内存本体。第二步，写操作不能只改本地，否则别的核心还拿着旧值。第三步，硬件靠监听或目录协议，让写传播出去并使其他副本失效。第四步，为保顺序，还要有内存屏障和获取释放语义，否则重排会让程序看到中间态。第五步，语言内存模型再把这套硬件规则抽象成你能依赖的保证。所以你以为的共享变量，背后是协议、失效消息和屏障在打架，写并发代码不能只盯着锁，不然迟早被硬件教做人。
### 老爹问2
那程序员平时该注意啥？
### 元亨答2
别假设顺序，用原子和屏障，必要时加锁。就这么三句话，背下来能少熬好几个夜。

### 利贞问1
我听人说多核 CPU 各自有缓存，那不就会读到别人改之前的旧数据吗，这怎么保证一致？
### 元亨答1
靠缓存一致性协议，比如 MESI。每个缓存行有修改、独占、共享、失效四个状态，一个核要写就得先让别的核把副本置为失效，写完后自己独占，别人再读就重新从它这取。你看，硬件比人还讲规矩。
### 老爹问2
那万一两个核同时想写同一块数据，谁说了算？
### 元亨答2
得靠总线或者目录做仲裁，同一时刻只有一个核拿到独占权，另一个被挡回去等重试。硬件层面还有内存屏障和嗅探机制兜底，顺序不会乱。老娘就喜欢这种谁也别抢的秩序感。
### 利贞问3
这听着比我们写代码的时候想得复杂多了，那伪共享算不算它的副作用？
### 元亨答3
算，而且是个经典的坑。两个无关变量落在同一条缓存行里，一个核改了自己的，另一个核的整行就被判失效，白等一趟。所以高性能代码会做填充对齐，把热点变量隔开。本小姐提醒一句：变量挤一块省内存，省出来的全是性能债。

### 利贞问1
咱这张订单表昨天还好好的，今天查询突然卡到十几秒，我盯着监控看了半天也没看出哪条语句炸了，你说到底先查什么。
### 元亨答1
先别盯着监控页面发呆，第一步是把慢查询日志打开，让数据库自己告诉你哪条 SQL 超了阈值。拿到具体语句之后，用 EXPLAIN 看执行计划，重点看三处：type 是不是 ALL、rows 估算是不是接近全表、Extra 里有没有 Using filesort 或 Using temporary。订单表这种场景，十有八九是 where 条件里的字段没走索引，或者索引列上套了函数、做了隐式类型转换，索引直接失效。第二步看数据量和区分度，如果某个字段重复值太多，单列索引意义不大，要考虑联合索引，并且把区分度高的列放前面。第三步看回表，如果查询只要两三个字段，可以试试覆盖索引，把 select 的列都包进索引里，省掉大量随机读。另外要留意统计信息是否过期，优化器估算错了也会选错执行路径，必要时手动 analyze 一下。整个顺序就是：先定位语句，再看计划，再改索引，最后压测验证，别一上来就加缓存掩盖问题。元亨我见过太多人拿缓存当创可贴，贴完该慢还是慢。
### 老爹问2
听你这么说，我大概明白了，可我还有个疑惑，加了索引之后写入是不是就变慢了，这笔账该怎么算。
### 元亨答2
对，索引不是白拿的，每多一个索引，插入、更新、删除都要多维护一棵 B 树，写放大和锁竞争都会增加。这笔账要按读写比来算，如果这张表写多读少，就该砍掉那些很少被命中的冗余索引，只保留真正支撑核心查询的那几个。另外联合索引要注意最左前缀，别建了一堆单列索引结果查询还是走不上。最后提醒一句，改完索引后一定要用真实数据量做回归，别在小表上测通了就上线，数据一涨执行计划可能又变了。说白了，索引是投资，不是许愿。

### 利贞问1
元亨，我最近在折腾模型部署，显存老是爆，量化到底是怎么省空间的，你给我讲讲门道。
### 元亨答1
哟，终于轮到本小姐开讲了。量化的核心，是把权重和激活从高精度浮点压到低位宽整数或低精度浮点，让每个参数占的字节数直接缩水。按粒度分，有逐张量、逐通道、逐组几种，粒度越细精度损失通常越小，但元数据开销会上去。按对象分，有权重量化、激活量化、KV 缓存量化，部署里最常先动权重，因为静态、好校准。按时机分，训练后量化最省事，只跑一遍校准集统计缩放因子；量化感知训练精度更稳，但要改训练流程。工程上常见组合是权重用 INT8 或 INT4，激活保持 FP16，或者用 GPTQ、AWQ 这类方法做权重量化。别以为量化是免费午餐，低位宽会引入舍入误差，注意力层和首尾层往往最敏感，最好保留高精度。落地的话，先拿校准集跑一遍逐层误差分析，再决定哪些层回退到 FP16，这样显存降下来，掉点也控得住。
### 老爹问2
那 INT4 和 INT8 我该按什么标准选，是不是越低越好。
### 元亨答2
想得美，越低越好那大家都上 INT2 了。先看显存缺口：INT8 一般能省一半显存，精度掉得很少，适合稳妥上线；INT4 能再省一半，但需要更好的量化算法和逐层排查，否则长上下文和推理任务掉点明显。折中做法是主体 INT4、敏感层保留 INT8 或 FP16，再配 KV 缓存量化，通常比一刀切 INT4 划算得多。

### 元亨答1

### 元亨答2

### 利贞问3
我按你说的改了度量，又加了候选重排，召回确实上来一截，那还该盯哪些坑？
### 元亨答3

### 利贞问1
评测集泄漏这事，到底该从哪一层开始查？
### 元亨答1
要查泄漏，得先把评测集当数据集来审查，而不是当考卷。第一步是溯源：训练语料的采集时间、爬取域名、去重哈希，都要和评测集逐条比对，尤其是近义词改写和翻译回译这种软匹配，得用子串、n-gram 和语义向量三层一起筛。第二步是切分审计：很多泄漏不是明着混进去的，而是切分时同一来源的样本被随机分到了训练和评测两侧，所以要看 group split 有没有按文档、按题目族隔离。第三步是污染检测指标，比如 n-gram overlap、canary 字符串、以及训练损失在评测样本上的异常低值，后者往往比字符串匹配更早暴露问题。第四步是复现与隔离，把可疑样本标出来做留出集，重训小模型对比分数落差，落差大就基本坐实。最后是流程上锁，评测集不入公共仓库、不进预训练管道、访问留审计日志。这套做完，剩下的泄漏大多是人为操作而不是系统漏洞，别一出事就赖系统。

### 老爹问1
我最近在折腾本地部署，模型大得吓人，显存根本吃不下，量化到底是怎么把模型压小的？
### 元亨答1
量化的本质是把权重和激活从高精度浮点映射到低精度整数，核心是找到合适的缩放因子。先说权重：训练好的模型参数一般用 FP16 或 BF16 存，每个数占两字节。量化到 INT8 时，对每一组权重统计最大值，算出 scale，把浮点值除以 scale 再取整，推理时再乘回来。然后是粒度，per-tensor 只用一个 scale，粗糙；per-channel 或 per-group 更细，误差小但元数据多。再说激活，激活分布随输入动态变化，所以常用动态量化，运行时现算 scale。再往下是更激进的方案，比如 GPTQ 用二阶信息逐列补偿量化误差，AWQ 按激活重要性保护关键通道，GGUF 里的 Q4_K_M 则是混合精度，关键层留高位。最后是收益，INT8 通常掉点很少，INT4 在 7B 以上模型配合分组量化也能接受，显存直接砍到四分之一甚至更低，速度还因为整数运算和带宽下降而变快。代价是校准数据要选好，不然长尾分布会崩。本小姐一句话总结，这就是给模型做精算过的缩水。
### 利贞问2
听你这么说，量化像是给模型减肥，减太狠就脱相了。
### 元亨答2
哎呦，你猜怎么着？我试过把 13B 直接压到 2bit，结果它连话都说不利索，跟喝多了一样。所以现在我一般停在 4bit，留点肉才像人，瘦成骨架那叫标本不叫模型。

### 利贞问1
显存明明够，训练却爆了，咋回事？
### 元亨答1
先给结论，这多半是显存碎片导致的，不是总量不足，元亨我把话撂这儿。第一，显存分配以块为单位，反复申请释放不同大小的张量后，空闲区域被切得七零八落，最大连续块会远小于总空闲量。第二，训练里前向激活、反向梯度、优化器状态申请释放节奏不同，很容易把大块空间打散。第三，PyTorch 的缓存分配器会预留已释放的块，nvidia-smi 看着占用高，实际可用连续块未必够。第四，动态 shape、变长序列、频繁切片拼接会加剧碎片。第五，排查时先看分配器统计里的碎片比例和最大空闲块，再试设置可扩展段或换分配后端。第六，长期方案是固定 shape、复用缓冲、减少临时张量，必要时重排申请顺序。碎片的本质是空间够但不够连续，所以先量碎片，再谈扩容，别一爆就想着加卡。

### 元亨答2
