# 工具块去重：一次可验证的上下文瘦身（2026-10-22）

> 结论：系统提示里那份"工具清单"与 API `tools` 传的 schema **完全重复**，实测占 **1,825 token（45 工具）**。
> 已改成默认不再重复，**用同一份上下文从"必然 400"变成"通过"**。

---

## 1. 实测数据（llama-server `/v1/chat/completions` 的 `usage.prompt_tokens`）

同一份 system + 同一个问题，只改"有没有那份文字清单"：

| 工具数 | 有文字清单 | 无文字清单 | 差值 |
|---|---|---|---|
| **45（work 模式全量）** | **8,579 token → HTTP 400**（超过 8,192） | **6,754 token → 200** | **1,825** |
| 12（CASUAL_SAFE_TOOLS） | 4,250 token | 3,823 token | 427 |

45 工具那一档是**决定性证据**：加不加上那份清单，决定请求是"直接被服务端拒绝"还是"正常返回"。

## 2. 行为有没有变差

12 工具、8 个需要调工具的问题，两臂各跑一遍：

- 工具选择 **7/8 完全相同**；
- 唯一不同的一条（"记住：老爹喜欢先看结论"）：**无清单那臂调了 `memory_save`**，有清单那臂只回了句"已记"——**无清单更好**；
- 没有任何一臂出现"该调不调"的系统性退化。

## 3. 改了什么

`backend/target_prompts.py`

- 新增 `tool_text_block_enabled()`：默认 **关**，`YH_TOOL_TEXT_BLOCK=1` 可恢复旧行为；
- `render_system_prompt()` 只在开启时才追加 `render_capabilities_tools_block(tools)`；
- API `tools` 参数、权限过滤、`allowed_tools` 契约**一律没动**——能调什么完全不变。

测试（54 项全过）：

- `test_tools_block_off_by_default`（新）：默认不出现清单；
- `test_tools_block_rendered_when_enabled`：开关打开时仍渲染；
- `test_persona_text_boundary`：把"广告集合 == 实际提供集合"的等式改成**子集 + 泄漏检查**（没被提供的工具绝不能出现在提示里），开关打开时仍断言严格相等；
- `test_render_default_preserves_full_owner_api`：改为在开关打开时验证 owner 全量 / 受限时隐藏。

## 4. 上线与验证

1. `tools/daemon_restart.py` 重启 8321：`fresh_health=yes`，新实例 pid 1672。
2. 重启后走一次 **owner 渠道**的真实回合（`/v1/chat/completions`，`user=console`）：
   llama-server 日志 task 1014 = **5,768 prompt tokens**，正常返回、无 400。
   改前同配置应约 5,768 + 427 ≈ **6,195**。
3. 单测：`backend.test_persona_text_boundary` + `backend.test_prompt_structure` + `backend.test_target_prompts` = **54 passed**。

### 4.1 一个未定性的观察（不是这次改动引起的）

同一个 owner 回合问"现在几点"，连续 4 次都回答 **"凌晨 1:45"**（错误）。

排查：直接用同一份 12 工具 schema、同样**不含**文字清单的 system 问"现在几点"，模型**正确调用 `system_time`**。
所以"去掉文字清单导致不调工具"这个解释**不成立**——问题在 daemon 那一段（多出来的 `early_context`、history 或温度 0.7）。
**留作独立问题**，别混进这次改动。

## 5. 第二次改动：work 模式只发 30 个工具

去掉重复清单后，work 模式仍有 45 个工具 ≈ **4.1k token** 的 schema。按场景裁：

- **常驻 30 个**：台账 6 / 记忆 6 / 日记 3 / 文件 4 / 知识库 2 / 任务+日程 2 / 技能 3 / 联网 2 / 系统 2；
- **默认不发 15 个**：`qq_*`（6）、`bili_*`（5）、`song_*`（3）、`member_profile`（1）；
- **按文本解锁**：出现「群 / QQ / 周报」→ 补 qq 组；「B站 / 直播 / 看片 / 弹幕」→ 补 bili 组；「歌 / 音乐」→ 补 song 组；「群友 / 成员 / 昵称」→ 补 member。
- 显式契约（`text_tool_contract`）不受影响——它只用核心工具，命中后仍取交集。

实测（同一 system、同一问题，`usage.prompt_tokens`）：

| 工具集 | 数量 | schema 字符 | prompt tokens |
|---|---|---|---|
| 旧：全量 work | 45 | 14,862 | 6,753 |
| 新：work 核心 | 30 | 10,784 | **5,523** |

**省 1,230 token（−18.2%）。** 与去重叠加：work 模式从 **8,579 → 5,523（−35.6%）**。

线上实测（重启后 owner work 回合"列出 backend 目录下的前 5 个文件"）：

- 首调 **4,603 prompt tokens**，正确调用 `file_list` 并答出目录内容；
- 工具结果回来后那一调只重算 **277 token**——前面 4,326 token 全部命中前缀缓存。**这也顺便证明了 P0-1 说的机制是真的**：前缀稳定时，第二轮几乎不花钱。

## 6. 测试

- `backend.test_target_entry`：25 项全过（新增 work 集合、按提示解锁、集合必须存在于注册表三项）；
- 8 个相关测试文件共 146 项：3 项失败，**已确认与本次改动无关**——把 `YH_TOOL_TEXT_BLOCK=1` 还原旧行为后同样失败（工具快照漂移、persona eval 两例），属于既有问题。

- 重启后 daemon 在 1 分钟内退出过一次，watchdog 已拉起；`daemon.log` 里没有本次改动相关的 traceback，判断是 restart 工具与 watchdog 同时 spawn 的竞争，未证实。
