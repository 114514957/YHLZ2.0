## 1. 实测：llama-server 的缓存命中与未命中，差 3.7 秒

YHLZ 的启动参数（`tools/yhlz_launcher.py:184-194`）：

```
llama-server -m <gemma gguf> --mmproj <mmproj> --jinja -c 8192 --port 8081 --host 127.0.0.1
```

**没有** `--cache-prompt` / `--no-cache-prompt` / `--slots` —— 走 llama.cpp 默认（prompt cache 开）。

日志里同时存在两种形态：

**命中（前缀没变）**

```
prompt eval time =  205.29 ms /     5 tokens (   41.06 ms per token)
```

只评估 5 个新 token——说明 5000+ token 的前缀是从 slot 缓存里复用的。

**未命中（前缀变了）**

```
prompt processing, n_tokens = 4649, progress = 0.90, t = 3.21 s
prompt processing, n_tokens = 4884, progress = 0.95, t = 3.42 s
prompt processing, n_tokens = 5161, progress = 1.00, t = 3.69 s
prompt eval time = 3885.51 ms / 5165 tokens ( 0.75 ms per token)
```

整段 5165 token 重新 prefill，**3.89 秒**。

`slot release` 行的 `n_tokens` 分布（最近 500 条）也印证：`81×150`、`91×28`、`1347×24`、`65`、`66`、**`5315×13`**、`56`——同一台机器上，请求的 token 规模在 60 到 5315 之间跳。

> **结论（可直接写进验收）**：在元亨这台机器上，**前缀断裂一次 ≈ 多花 3.7 秒**。而 `target_orchestrator.py:345` 正是每轮把 `early_context` 拼进 `system[0]`——这就是每轮都在断。
>
> 这也解释了为什么"首 token 有时快有时慢"：快的那些轮是前缀没变的。

**注意边界**：日志里没有逐轮的 prompt 指纹，所以"每一轮都断"是从代码推的，不是从日志逐条对出来的。要 100% 确定，得在 `PromptFrame.render()` 里加一行"静态段 hash"，跑一轮对比。这一步仍未做。

## 2. 源码核对：MemOS 的检索算法（比 YHLZ 精细一个量级）

`apps/memos-local-plugin/core/retrieval/ALGORITHMS.md` 是这份仓库里信息密度最高的文件——它逐条写了"为什么偏离论文原文"。

### 2.1 它的完整流水线

```
候选收集（多通道）
  ├─ 向量：tier1 skill / tier2 trace+episode / tier3 world，各 poolSize = topK×4
  ├─ 关键词：FTS5 trigram MATCH
  ├─ 兜底：LIKE %term%（专治 2 字中文，低于 trigram 窗口）
  └─ 标签预筛：tags_json（工具名/错误码/关键词字典），auto 模式下空则重试一次不带标签
        ↓
排序（分层的）
  ├─ tier2 内部：score = 0.6·cos + 0.4·priority
  ├─ tier1 skill：0.6·cos + 0.15·η（η 从 0.4 降到 0.15，防陈旧技能压过新技能）
  └─ priority = max(V, 0) · 0.5^(Δt/30d)   ← 30 天半衰，**读时重算**
        ↓
跨 tier 融合：**RRF k=60**（不是加权和——因为 cos 在 (0,1)，V·decay 在 (-∞,∞)，无法直接相加）
        ↓
相对阈值：丢弃 relevance < top × 0.4（默认）
        ↓
MMR 去冗余：λ=0.7，贪心；每层先"播种"一条，防 tier 饿死
        ↓
LLM 精排（小模型 few-shot）
  └─ **失败即 fail-closed**：网络/超时/坏 JSON → 用机械截断 0.7·top·maxKeep，绝不把整列倒进 prompt
```

三个我没想到但很关键的设计：

1. **RRF 不是"更好的排序"，是"不同量纲无法相加"的解法**。原文：*"we don't need to rescale the (0,1) cosine scores to match the (-∞,∞) V·decay range"*。YHLZ 现在是**拼接**（`out.extend`）——比 RRF 还退一步。
2. **相对阈值而不是绝对阈值**：`relevance < top × 0.4` 才丢。绝对阈值在查询难度变化时会全丢或全留。
3. **LLM 精排必须 fail-closed**。失败时不给"全部候选"，给机械截断。YHLZ 的 `rerank` 首次调用返回全 0（`vector_memory.py:244-268`），恰好是反例——失败时反而放行了全部候选。

### 2.2 与 YHLZ 逐项对照

| 能力 | MemOS local | YHLZ | 差距 |
|---|---|---|---|
| 候选通道 | 向量 + FTS5 trigram + LIKE 兜底 | kw 倒排 + FTS5 + PPR + 语义 | 通道数相当，**但 YHLZ 不融合** |
| 跨通道融合 | **per-channel RRF** | `extend` 拼接 | **真差距** |
| 相对阈值 | `top × 0.4` | 无（只有语义绝对阈值 0.42/0.45） | **真差距** |
| 去冗余 | MMR λ=0.7 + 每层播种 | 无 | 可借 |
| 结果奖励 | `value / alpha / r_human / priority` | `belief`（active 均值 0.452，健康） | 字段在、**未进排序**；可信度维度可立即启用 |
| 标签预筛 | `tags_json`（工具名/错误码/词典） | 无 | 可借 |
| 精排降级 | fail-closed 机械截断 | 失败返回全 0 → 放行全部 | **反例** |
| 技能注入 | 默认只给摘要 + 按需取全文 | 无此层 | 可借（对应"技能库"） |

### 2.3 schema 级 diff（`001-initial.sql` vs `l2_items`）

MemOS 的表：`sessions` / `episodes` / `traces`(L1) / `policies`(L2) / `skills` / `world_model`。

`traces` 的字段里，YHLZ **没有**的：

| 字段 | 含义 | 为什么值得有 |
|---|---|---|
| `value` / `alpha` / `r_human` | 结果奖励 / 学习率 / 人类评分 | 让"成功过的经验"能被排序，而不是只靠相似度 |
| `priority` | `max(V,0)·0.5^(Δt/30d)`，读时重算 | 与 NEKO 的 30 天半衰**独立撞车**——这是行业共识值 |
| `tags_json` | 工具名/错误码/关键词 | 召回前的低成本预筛 |
| `error_signatures_json` | 错误指纹 | 失败→修复的结构化匹配 |
| `vec_summary` / `vec_action` | **两条向量**：摘要 & 行动 | 查"说过什么"与"做过什么"是两种意图 |
| `share_scope` / `share_target` | 共享范围 | 对应"群记忆/私聊记忆"的授权维度 |
| `turn_id` | 同一用户轮的所有子步共享 | UI 分组 / 回放 |
| `agent_thinking` | 模型原生思考文本 | 可审计 |

YHLZ **有**而 MemOS 没有的：`stance`（来源分级）、`valid_at/invalid_at/superseded_by`（双时态）、`protected`、`kind`（profile/episodic）、`salience`。

> **一句判断**：YHLZ 在"来源与时间"上比 MemOS 强，在"结果奖励与多通道融合"上比它弱。**两边正好互补**。

## 3. 由此修正的三条建议

### 3.1 P1-6 的目标形态（第三次修正，这次有源码支撑）

上一轮我说"别做乘性门控、做分带"。现在有两个参照项目的源码，结论收敛成：

```
最终分 = 0.6 × 相关性 + 0.4 × 可信度
其中 相关性 = RRF 融合后的名次分（不是原始 cos，因为跨通道量纲不同）
     可信度 = belief（修好后）× stance_weight
门槛 = 相关性 < 本批 top × 0.4 直接丢
去冗余 = MMR(λ=0.7)，每通道先播种一条
```

差异点：**不是"把 relevance 当乘数"，也不是"分带"，而是加权 + 相对阈值 + RRF**。三条都有源码依据。

### 3.2 `belief` 是健康的——上一轮我读错了（更正）

上一轮我写"全库 464 条 belief=0"，这是**我的测量错误**：审计脚本用了 `ROUND(belief,1)`，所以"0.0"其实是 `belief < 0.05`。本轮精确查询：

| 群体 | 条数 | belief 均值 | 最小 | 最大 |
|---|---|---|---|---|
| active | 176 | **0.452** | 0.208 | 0.884 |
| downgraded | 239 | 0.045 | 0.016 | 0.144 |
| archive | 295 | 0.022 | 0.016 | 0.231 |
| 精确等于 0 | **0** | — | — | — |

结论反过来了：**在役记忆的可信度是健康的（0.21–0.88）**，低值恰好集中在已降权/已归档的条目上——说明衰减机制**在按设计工作**，而且与状态迁移一致。

**因此 P1-6 没有"先修 belief"这个前置依赖**：可信度项现在就能用 `belief`（归一化后）。上一轮写的那条依赖作废。

### 3.3 关于 stance 的最后一次校准

- 它**不适合**当相关性乘数（会让"相关的但来源弱"直接消失）。
- 它**适合**当可信度项的权重：`stance_weight ∈ {fact:1.0, opinion:0.85, speculation:0.6, 空:0.7}`。
- 它**必须先落库**（主写入轨不写 stance 的 bug 仍在），否则权重恒 0.7，等于没做。

## 5. 补充实验：融合与相对阈值，在本机数据上是什么结果

`research/exp_fusion.py`（只读；复制 kw 索引到临时文件，memstore 用 `mode=ro`；不实例化 `TargetMemoryService`）。10 条查询，两条**不依赖模型**的通道：kw 倒排 + FTS5/BM25。

| 查询 | kw 命中 | FTS 命中 | 重叠 | top1 不同 | 前 5 集合不同 | kw 置信度范围 | 低于 0.4×top |
|---|---|---|---|---|---|---|---|
| 麦克风 采集 | 12 | 0 | 0 | – | – | 0.50–0.91 | 0 |
| 训练 冻结 | 12 | 1 | 0 | – | ✔ | 0.59–0.65 | 0 |
| 图表 导出 | 2 | 0 | 0 | – | – | 0.42–0.99 | 0 |
| 记忆 检索 | 12 | 1 | 0 | – | ✔ | 0.42–0.86 | 0 |
| 部署 端口 | 4 | 2 | 2 | – | – | 0.50–0.65 | 0 |
| 语音 打断 | 12 | 2 | 1 | ✔ | ✔ | 0.50–0.65 | 0 |
| 人格 微调 | 3 | 1 | 1 | ✔ | – | 0.65–0.65 | 0 |
| 记忆 衰减 | 12 | 1 | 1 | ✔ | ✔ | 0.42–0.65 | 0 |
| TTS 合成 | 12 | 12 | 8 | – | – | 0.45–0.65 | 0 |
| 群聊 记忆 | 12 | 1 | 1 | ✔ | ✔ | 0.42–0.65 | 0 |
| **汇总** | 均 9.3 | 均 2.1 | 均 1.4 | **4/10** | **5/10** | — | **全 0** |

三个结论：

1. **RRF 确实会改变结果**（4/10 换头名、5/10 换集合），但**没有 ground truth，不能证明更好**。它的价值是"原理正确"（不同量纲不可相加），不是"实测更优"。
2. **FTS 通道在中文短查询上几乎不产出**（均 2.1 条；5 条查询只有 0–1 条）。唯一例外是 "TTS 合成"（12/12，重叠 8）——**拉丁词能命中，纯中文长词不行**。也就是说 YHLZ 的"多通道"实际上长期是**单通道在干活**。
3. **相对阈值 0.4 在本机是空操作**：所有查询"低于 0.4×top"的条数都是 **0**。原因是 `target_kw_index.py:343-347` 把 confidence 压成两位小数、范围窄（常见 0.65–0.65 全并列、0.42–0.99）。**阈值再低也筛不掉；要筛就得先让分数有分辨率。**

> 开放问题 #4 直接关掉：**0.4 的阈值不能照搬**。真正的动作是**先提高相关性分数的分辨率**（把 `score` 与 `coverage` 分开返回，而不是先按 0.7/0.3 合成一个粗粒度 confidence），再谈阈值。
