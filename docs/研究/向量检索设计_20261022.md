# 向量检索设计（讨论稿 v1）· 2026-10-22

> 先量后设计。下面每个数字都是在本机 `cache/embvec.db`（407 条 L2 向量）上实测的。
> **一句话结论：现在这套"向量"不是设计，是堆叠——线上默认根本没开，开了之后排序又被一个坏掉的 reranker 压平。要做的不是换模型，是把通道分开、打分归一、阈值改成相对的。**

---

## 1. 现状实测

| 项 | 实测 | 含义 |
|---|---|---|
| 模型 | bge-small-zh-v1.5，512 维，CPU，`max_length=256` | 中文短文本够用 |
| 存储 | `cache/embvec.db` 单表 `vec(id, scope, vec BLOB, text)` | 无索引，全表扫 |
| 覆盖 | L2 共 **711** 条，有向量 **407**（57%）；缺 304 = archive 295 + **active 8** + downgraded 1 | active 基本齐，但会在"关着"期间继续掉 |
| 向量新鲜度 | 用当前 `summary+keywords` 重算，与库存向量 cos **0.999–1.000**（407/407） | **没有陈旧向量问题**，不用重建 |
| `text` 列 | 407 行里 **204 行是空串** | 任何依赖它的路径（diary/未来 l1/l3）都不可靠 |
| 相似度基线 | 全库两两 cos：mean **0.501**、p90 0.616、p99 0.732 | bge 的各向异性：**随机两条就有 0.5 相似** |
| 查询分布 | 16 条真实问法：top1 0.437–0.730；全库 mean 0.27–0.41 | 阈值必须相对这条分布定 |
| 绝对阈值 0.42 的实际效果 | 保留 **2–179 条**（"工具太多"179 条，"B站直播"2 条） | **失控**：低于基线均值，等于没筛 |
| 嵌入成本 | 首次加载 **67 s**，之后 **19 ms/条** | 绝不能在回合里加载 |
| Reranker | bge-reranker-base，加载 2.6 s，**10 条 1435 ms**，打分 **0.000–0.013** | 又慢又是坏的 |

### 1.1 线上到底开没开

`semantic_model_allowed()` 只在 `YHLZ_MEMORY_SEMANTIC_MODE=cpu` 时返回真；**全仓库没有任何启动脚本设置它**（只有 `persona_live_safety.py` 显式设成 disabled）。所以线上 `_semantic_enabled = False`。

后果链条：

1. `contextual_recall` 跳过语义两路，只剩 **字面 2-gram + BM25**，且两者 `_score` 都被写成**常量 0.45**；
2. 排序靠 Python 稳定排序 → **实际顺序 = 插入顺序**；
3. `memory_save` 里的 `vec_add()` 因为模型不可用而静默失败 → **新条目不会进向量库**，覆盖率只会往下掉。

---

## 2. 现在的融合方式（`contextual_recall`，`target_memory.py:706-813`）

四路候选，分数口径互不相干：

| 路 | `_score` |
|---|---|
| 语义 L2（阈值 0.42，importance≥5，active） | 余弦原值 |
| 字面 2-gram（≥2 个共同 bigram） | **常量 0.45** |
| 日记语义（阈值 0.48） | 余弦原值 |
| BM25 | **常量 0.45** |

然后：

```python
if len(good) > 1 and self._semantic_enabled:
    scores = rerank(q, [g["summary"] for g in good])
    for g, s in zip(good, scores):
        g["_score"] = float(s)        # ← 把所有分覆盖成 0.000–0.013
```

**这一步把所有通道的分差压平成噪声，等于随机排序。** 之后只按"前 80 字相同"去重。

所以三个结构性问题，按严重度：

1. **reranker 覆盖分数**（有语义时最致命）；
2. **常量分与余弦混排**（0.45 这个数比很多真实余弦还高）；
3. **绝对阈值**（0.42 在基线 0.50 之下）。

---

## 3. 设计目标

**要**：换说法也能召回（"我不吃香菜" ↔ "别再给我推荐香菜"），且召回结果**可解释**（每条带来源分与通道），并能在 8GB 机器上常开。

**不要**：不要把它当唯一证据（词法仍是主干）；不要引入向量数据库（规模不够）；不要为了"先进"上 ANN/量化。

**规模判断**：407×512 点积 ≈ 0.2 ms；到 1 万条 ≈ 5 ms。**这个量级不需要 ANN**，等 5 万条再说。

---

## 4. 设计决策

### D1 开关：三态，默认 `auto`

`YHLZ_MEMORY_SEMANTIC_MODE = off | auto | on`（默认 `auto`）：

- `auto`：后台预热成功 → 本次运行启用；失败 → 静默降级为纯词法，并在 `/state` 里标 `semantic=unavailable`。
- `off`：绝不加载（训练/压测时用）。
- `on`：预热失败要让启动日志显式报错，不静默。

> 依据：现在"默认关"导致这个能力事实上不存在；而"默认开"又会因为 67 s 加载拖死启动。`auto` 是唯一两边都不亏的形态。

### D2 预热：只在启动后，永不进回合

daemon 起服务、`/health` 返回之后再起后台线程加载模型（67 s），**不阻塞任何回合**。回合一侧只做"已就绪？否 → 走词法"。

> 依据：67 s 是实测；一次 in-turn 加载会直接把回合拖成超时。

### D3 打分：只保留余弦；跨通道用 RRF

- 删掉所有常量 `_score = 0.45`；
- 每个通道各自排序，用 **RRF(k=60)** 融合：`score = Σ 1/(60 + rank_i)`；
- 最终分数只用于排序，不参与"重要性加权"（重要性仍单独作为过滤/展示字段）。

> 依据：MemOS 的 `ALGORITHMS.md` 明确写了 RRF 是为了解决"cos 在 (0,1)、另一路在 (-∞,∞) 无法相加"；本机实测也证明不同通道分数不可比。

### D4 阈值：相对 + 硬下限 + 截断

```
keep = score >= max(top1 - 0.08, mean + 1σ)   # 相对
       and score >= 0.50                       # 硬下限（高于全库均值 0.501 之上一点）
k <= 8
```

标定依据（16 条查询实测）：

| 规则 | 保留条数范围 |
|---|---|
| 绝对 0.42 | **2 – 179**（不可用） |
| top1 − 0.08 | 1 – 79 |
| top1 − 0.08 且 ≥ 0.50，再截 8 | 预期 1 – 8 |

> 0.50 这个下限不是拍脑袋：全库两两 cos 的均值就是 0.501，低于它的"相似"没有信息量。

### D5 reranker：暂停，不进主路径

- 成本：10 条 **1435 ms**（CPU），一个回合多 1.4 s；
- 输出：**0.000–0.013**，明显未正确使用（base 模型的 logits 经 sigmoid 后接近 0，未做 pooling 校准）；
- 决定：主路径移除；保留 `YH_RERANK_EXPERIMENT=1` 供离线对比。

> 不是"以后再修"，是"现在它在破坏排序，先摘掉"。

### D6 `text` 列：降级为缓存，读路径一律 join 源表

204/407 为空说明它从来没被当契约维护过。L2 读路径本来就 join `l2_items`，保持；`semantic_any`（diary）改成 join 日记文件/表。

### D7 覆盖：写入跟随库，启动补齐

- `vec_add` 的 scope 改用 `l2_scope(db_path)`（现在硬编码 `"l2"`，多库场景会串）；
- 启动时对 active 且无向量的条目补嵌（当前 8 条，19 ms×8 ≈ 0.2 s）；
- `memory_save` 的 hook 保留，但**失败要计数**，不再静默。

### D8 评测：固定 40 条查询，三组对比

- 查询集：从 `cache/sessions` 真实提问里取 40 条，人工标"哪些记忆应当被召回"；
- 指标：recall@5、precision@5、以及"注入段字符数"（预算约束）；
- 三组：**词法 only**（现状）/ **向量 only** / **RRF 融合**；
- 判定线：RRF 的 recall@5 比词法 only **≥ +10 个百分点**才默认开 `auto`。

## 5.1 P0 实施记录

**开关**（`backend/memory_resource_policy.py`）：新增 `semantic_mode()` → `off | auto | on`（旧的 `cpu` 视作 `on`），**默认 `off`**（老爹 2026-10-22 定）。`auto` 只有在后台预热真的加载完（`semantic_ready()`）后才返回可用；训练/微调标记仍然一票否决。

**预热**（`backend/vector_memory.py`）：新增 `semantic_ready()` / `warm_semantic()`；`_load_model(force=True)` 供预热线程绕过开关检查。预热是后台线程，**永不进回合**（冷加载实测 67 s）。`TargetMemory.__init__` 在 mode≠off 时触发预热。

**reranker**（`backend/target_memory.py`）：召回路径里的 `rerank()` 改为 `YH_RERANK_IN_RECALL=1` 才启用（默认关）；异常时**不再吞掉**，计入 `_rerank_failures`，并保留各通道原分数（fail-closed 而不是清零）。

**写入**（`backend/target_scheduler_tools.py`）：`vec_add` 的 scope 从硬编码 `"l2"` 改为 `l2_scope(svc.db_path)`——群记忆库不再往主库 scope 写。失败不再静默：新增 `vec_add_failures()` 计数（仅在语义已启用时计，避免关闭态刷假异常）。

**巡检工具**（`tools/vec_backfill.py`）：FTS5 缺行原来拿**全部**条目比（含 archive），所以永远报 295 处假漂移；改为只比"参与召回"的集合。

**覆盖补齐**：`vec_backfill.py` 补了 9 条缺失向量（8 active + 1 downgraded）。巡检结果：

```
L2 条目 711（参与召回 416）；FTS5 行 416；向量 416（scope=l2）
缺向量 0 | 孤儿向量 0 | 维度损坏 0 | FTS5 缺行 0 | FTS5 孤儿 0
```

**测试**：

- 新增 `backend/test_memory_semantic_policy.py`（9 项）：默认 off、cpu=on、auto 等预热、训练标记否决、rerank 默认关、scope 跟随库；
- `target_memory` + `target_scheduler_tools` + `memory_endurance` + `target_entry` + 新文件共 **73 项全过**；
- `test_vector_recall` 11 项在 `YHLZ_MEMORY_SEMANTIC_MODE=cpu` 下全过；不带该变量时 5 项失败——**这是既有的环境依赖**（这些用例本来就要求真模型），不是本次改动引入。

**仍未生效说明**：默认 `off`，所以**线上行为与改动前一致**；P0 只是把"打开"这条路修干净了。

**操作发现**：从这个沙箱里拉起 daemon，进程会在命令结束、作业对象回收时被一并收掉（日志只有启动 banner，无 traceback）；由 watchdog 拉起的实例才能长期存活。所以"验证重启后的稳定性"这类事，要么交给 watchdog 的自然周期，要么由老爹在正常终端里起。

---

## 6. 风险

1. **CPU 抢占**：预热 67 s、每回合 1–2 次嵌入（~40 ms）。daemon 与 llama 抢 CPU 时，嵌入会拖慢首 token——用 `auto` + 低优先级线程缓解，必要时 `off`。
2. **排序变化**：P1 会改变注入顺序，可能影响人格语气。必须先用评测集 + `tools/persona_regression.py` 跑一遍。
3. **多库串扰**：`vec_add` 硬编码 scope 是既有 bug，P0 顺手修，但会改变群记忆库的向量归属——需要单独回归。
