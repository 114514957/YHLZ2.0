# GitHub 记忆项目扫描（2026-10-21）

> 配套《记忆系统全景研究_20261021.md》§4。本篇只补"**能直接读代码/直接装**"的开源项目，不重复论文部分的结论。
> 方法：GitHub 搜索 API + 逐仓库 README 原文；**指标均为项目自报，未经复现**；星数/许可来自 README 徽章与仓库声明，可能变动。

## 0. 一句话结论

**记忆层已经商品化了**：9 个项目里有 5 个同时支持 Claude Code / Codex / OpenCode / OpenClaw / Hermes——**其中 2 个已经支持 DeepSeek Harness（MemOS 的 cloud/local 插件、Honcho 的 `@honcho-ai/dsh-honcho`）**。这意味着"给 DSH 装长期记忆"不需要自己写，装插件就行；而 YHLZ 要做的，是**元亨自己的记忆**，不是代理的工具记忆。两者可以共存，但不能混为一谈。

对 YHLZ 最有参考价值的三个：**MemOS 的分层（L1 traces/L2 policies/L3 world model + Skills）**、**memU 的"服务不做 LLM、判断留在 agent"**、**Honcho 的 (observer, observed) 双视角**。

## 2. 三个最值得读代码的（按对 YHLZ 的贴合度）

### 2.1 MemOS：分层与 YHLZ 几乎是同一张图

它的本地插件宣称：**L1 traces / L2 policies / L3 world model + crystallized Skills**，混合检索 **FTS5 + vector**，本地 SQLite，带 Memory Viewer。

对照 YHLZ：
- L1 短期 / L2 长期 / L3 认知根基 —— **同名同义**；
- YHLZ 的 `l2_fts`(FTS5) + `embvec` —— **同栈**；
- YHLZ 缺的正是它多出来的两样：**policies（可复用策略）** 与 **Skills（结晶体）**。

> 值得读的是它的 **cube 模型**：一个 cube 是"可隔离、可共享、可组合"的记忆容器。YHLZ 现在只有"一个库 + scope 后缀"，没有"共享"这一维（比如"主人记忆"与"群记忆"能否按 cube 授权共享）。这比加字段更彻底。

### 2.2 memU：服务不做 LLM，判断留给 agent

它的核心设计（README 明说）：`MemoryService` **不发起任何 LLM 或聊天调用**；它只负责**存、嵌、取**。谁来蒸馏？——**编码代理自己**。流程是：

```
定时任务把新会话日志切成 job 文件
  → agent 读已有 skill，决定：什么都不做 / 改一条 / 新建一条
  → 写成 skill Markdown（name/description/workflow/分支/坑）
  → commit 提交，服务只做 embedding 与落库
  → 下次相似任务 retrieve 回来
```

这对 YHLZ 是一个**结构性的省钱方案**：记忆抽取现在跑在 Gemma 上，占 8GB 显卡；如果改成"主对话时顺手判断、后台只做机械搬运"，就能把 LLM 成本移到本来就要发生的推理里。

> 但要注意：memU 敢这么做，是因为它的宿主是"会自己思考的编码代理"；元亨不是——她的抽取必须自己调模型。**可借的是"服务薄、判断厚"的分层，不是"零 LLM"这个结论。**

### 2.3 Honcho：双视角（observer × observed）

内部 collections 按 `(observer, observed)` 建：同一个"peer"既有"我看你"，也有"你看我"。查询面暴露 conclusions（演绎/归纳）、representations（低延迟快照）、peer cards、session context。

YHLZ 目前只有**一个视角**："元亨知道什么"。没有"元亨认为老爹怎么看她"这一层。这不是必须的，但它是**关系型数字生命**缺失的那块——`docs/元亨认知根基.md` 里的"人机关系"是静态文本，不是可查询的模型。

> AGPL-3.0：**只能读设计，不能抄代码**。

## 3. 其余四个的可用点

| 项目 | 可借的一件 | 落到 YHLZ 哪 |
|---|---|---|
| **MIRIX** | **六类记忆各配 agent** + `auto_dream(mode, dry_run)` 维护接口 | 把 `memory_review` / `reflection` / 未来 `dream` 统一成"按类型分派的维护端点"；`dry_run` 是必须的 |
| **Second-Me** | **HMM（分层记忆建模）→ 训进模型** 的流水线；8GB 内存对应的模型选型表 | 与现有 QLoRA 计划对照：记忆是先训进去还是先检索？它的答案是"两条都要" |
| **Memori** | **entity / process / session 三级归因** + 把 skills 当记忆类型 | `source` 字段可扩成三元（谁 / 哪个进程 / 哪次会话），比单一字符串强 |
| **Supermemory** | **static / dynamic 双档画像** + **临时事实自动过期**（"明天有考试"过期即失效） | YHLZ 的 profile 是 static，缺 dynamic；`valid_at/invalid_at` 已有，缺"到期自动失效"的规则 |

## 4. 一个必须说的反例

**Open-LLM-VTuber**——GitHub 上最接近"本地 AI 伴侣"的项目之一，README 原话：

> *"Although the long-term memory feature is temporarily removed (coming back soon)..."*

它保留了聊天记录持久化，但**长期记忆被下掉了**。这和 NEKO 花 293KB 写 `facts.py`、写 25+ 支记忆提示词，是同一个问题的两面：**陪伴场景的记忆，做出来容易，做对很难**。

所以看到"#1 on every benchmark"（Supermemory）和"88.83 on LoCoMo"（MemOS）时，要分清：**基准测的是问答召回，不是"她记不记得你昨天难过"**。后者没有基准。

## 5. 下一步建议

| 优先 | 动作 | 成本 |
|---|---|---|
| 1 | **读 MemOS 的 `apps/memos-local-plugin`**（SQLite + FTS5 + vector + 分层 schema），对照 YHLZ 的 `l2_items` 做一次字段级 diff | 半天，不需要装 |
| 2 | **读 memU 的 500 行核心**，看它怎么把"判断"完全隔离在服务之外 | 半天 |
| 3 | 试装 **MemOS 或 Honcho 的 DSH 插件**，体验"插件式记忆"与"内置式记忆"的差别（只装到 DSH，不碰 YHLZ） | 1 小时，可回滚 |
| 4 | 把 **MIRIX 的 `auto_dream` 语义**（含 `dry_run`）抄成 YHLZ 的维护端点设计 | 设计稿，1 天 |

**不建议**：直接接 MemOS/Honcho 进 YHLZ。它们是**代理的记忆**（面向代码任务、线程、文档），不是**人格的记忆**（面向关系、情绪、时间）。混进来会让 YHLZ 多一层不需要的抽象。
