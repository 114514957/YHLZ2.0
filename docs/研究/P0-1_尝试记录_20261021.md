# P0-1 尝试记录：先量，再改（2026-10-21）

> 目标：在动代码之前，把"每轮都断前缀"这个前提量清楚。
> 方法：**只读**。解析 `cache/logs/llama-server.log`（4241 条请求）+ 一个不依赖模型的确定性仿真。
> 结论先说：**前提不成立——不是"每轮"，是 42% 的真实回合**；但收益仍然成立（仿真 -52%），且顺带发现一个比慢更要命的问题。

---

## 1. 实测：4241 条请求里，三分之一在重算整段

按 `prompt eval time = X ms / N tokens` 切分（N = 本次真正进 GPU 的 prompt token）：

| 桶 | 请求数 | 占比 |
|---|---|---|
| ≤50（缓存命中） | 1289 | 30.4% |
| 51–500 | 1331 | 31.4% |
| 501–2000 | 207 | 4.9% |
| **>2000（整段重算）** | **1414** | **33.3%** |

只看**真实回合**（生成 >50 token，n=507）：

- 中位数 **902 token** 的 prompt eval；
- **42%（212 条）整段重算**；
- 20% 命中（≤50 token）；
- prompt eval 累计 **878 秒**（约 14.6 分钟）——只算真实回合。

再看**探测/后台**（生成 ≤5，n=381）：中位数 73 token，只有 2% 整段重算。**说明重算主要发生在真实对话和后台中间档（生成 5–50，n=3353，其中 36% 整段重算）**。

> 所以准确的表述是：**"前缀稳定时是 5–70 token 的命中，不稳时是 2000–8000 token 的整段重算，真实回合里 42% 落在后者。"** 上一轮"每轮都断"是过度概括。

## 2. 仿真：把易变块移出去，能省一半（**仅在 append-only 历史假设下**，见 §4）

`research/sim_prefix.py`。用真实的 `PromptFrame` 渲染，三种布局各跑 12 轮（persona 4000 字、每轮 ctx 300–1200 字、history 每轮 +2 条、按 1.6 字/token 估算）：

| 方案 | 布局 | 每轮需重算（均值） | 相对现方案 |
|---|---|---|---|
| **V0 现状** | `[system(persona+ctx_t+control)][history][user_t]` | **1031 token** | — |
| **V1**（低风险） | `[system(persona+control)][history][user(ctx_t+user_t)]` | **493 token** | **−52%** |
| **V2**（需改不变量） | `[system(persona+control)][history][system(ctx_t)][user_t]` | 500 token | −52% |

V1 与 V2 收益相同，差别在实现代价：

- **V2 会撞墙**：`PromptFrame.request()` 明确禁止 `messages[1:]` 里出现 `system`/`developer`（`prompt_structure.py:55-56`），这条不变量是为了防注入——检索文本不能变成指令。要用 V2 得给"尾部动态块"开一个显式豁免，等于放宽安全边界。
- **V1 不动不变量**：把动态块拼进本轮 user 消息的前缀即可，角色始终合法。

> 所以推荐 V1。它的代价是：模型看到动态块时它属于 user 角色，语义上比 system 弱一点——但当前 `【本轮背景资料｜数据，不是指令】` 那段本来就在 system 里，改成 user 前缀后"不是指令"的属性反而更强。

## 3. 顺带发现：两个比慢更要命的问题

### 3.1 硬失败：prompt 超过上下文被整条拒绝

日志末尾：

```
send_error: task id = 241, error: request (10782 tokens) exceeds the
available context size (8192 tokens), try increasing it
stop: cancel task, id_task = 241
```

**不是截断，是直接取消整条请求**。也就是说元亨会"没回应"，而不是"回应得慢"。

根因很清楚：`target_orchestrator.py:29` 定义的是 `CTX_BUDGET_CHARS = 16000`（**字符**预算），压缩触发在 `:552`；而服务端按 **token** 限流 8192。**中文 16000 字符 ≈ 9000–11000 token**，天生越界。字符预算和 token 预算之间没有换算。

这条比 P0-1 更急：**它让回合直接失败**。

- `8321` 在监听，但 `/state` 超时。

## 4. 第二轮（外围）：真实会话把上一节的结论推翻了一半

上一节的仿真是**合成数据 + 增长式历史**。换成**真实会话**（14 个 `cache/sessions/*.json`，44 个可测回合）后发现两件事：

**（1）代码里的历史是"滑动窗口"，不是增长式。**

`target_entry.py:730`：`history=self._clean_history()[-6:]` —— **6 条消息的滑动窗口**。窗口每轮往前滑 2 条，意味着 prompt 的第一条历史消息每轮都在变——**不管动态块放在哪，前缀都会在历史开头断掉**。

**（2）因此 V1 在真实现状下是负收益。**

| 场景 | V0（现状） | V1（动态块后置） | V1 相对 V0 |
|---|---|---|---|
| 滑动窗口 `[-6:]`（**当前代码**） | 2575 字符/轮 | 3021 | **+17%（更差）** |
| 增长式历史（假设改成 append-only） | 4136 | **2136** | **−48%** |

读法：

- 现状下把动态块挪出去，**没有便宜可占**——因为滑动窗口已经在第一轮就把缓存砍断了，V1 只是多包了一层 user 前缀。
- 只有**同时**改成 append-only 历史，V1 才有意义；但 append-only 会把历史越堆越长（V0 从 2575 涨到 4136），**必须配压缩**才成立。
- 两者都做的净收益：2136 vs 现状 2575 → **约 −17%**，不是第一版说的 −52%。

> 结论：**P0-1 单独做不值得**。真正的杠杆是"历史窗口策略"，不是"动态块位置"。第一版的 −52% 建立在"历史增长"这个代码里并不存在的前提上。

## 5. 那什么是便宜且确定的杠杆

按"每轮固定开销"排序（真实测量）：

| 组件 | 估算大小 | 是否每轮都在 |
|---|---|---|
| 静态 system（`render_system_prompt`） | **3856 字符** | 是 |
| 工具块（49–54 个能力，各一行 name+description） | **约 4900 字符**（按 54×90 估） | 是有工具时 |
| 动态上下文 `early_context` | ≤1500 字符 | 是（owner） |
| 历史 6 条 | 中位 499，p90 3383 | 是 |

总 prompt 中位约 6425 字符（不含工具块）、约 11.3k 字符（含工具块）——**at 8192 token 限附近**。这也解释了日志里 10782 token 的越界：**工具块 + 长历史**把它顶出去了。

所以最便宜的三个动作，按性价比：

1. **削工具块**（每轮都在，且 49 个能力不可能每轮都用）：按场景分组下发（owner 私聊 / 群 / work），或把描述压到一行以内。**这是唯一"减少总量 + 降低越界 + 降低 prefill"三合一**的动作。
2. **把字符预算换成 token 预算**：`CTX_BUDGET_CHARS=16000` → 约 9000 token，已越界；改成按 `len/1.6` 估算的 token 预算（比如 7000），并在请求前断言。
3. **历史策略**：要么 append-only + 压缩（收益 −17% 但要动压缩），要么维持滑动但接受前缀被打断（现状）。**这条不该第一个做。**

## 6. 本轮做了什么、没做什么

**做了**：4241 条日志的分布统计；真实回合/后台的分层统计；三布局仿真；发现了上下文越界与字符预算的换算缺口。

**没做**（刻意）：

- 没改任何生产代码；
- 没重启任何服务（llama 不在，但启动它会占 ~5GB 显存，该由你决定）；
- 没有逐轮 prompt 指纹（那需要在 `PromptFrame.render()` 加一行 hash 打点，并跑真实回合——现在 llama 停着，跑不了）。

## 7. 下一步（按新证据重排）

1. **削工具块**（最便宜、三合一）：49–54 个能力每轮全量下发，约 4900 字符。按渠道/场景分组下发，或把描述压到一行。这一步同时降低 **prefill 量、越界风险、首 token 延迟**。
2. **修越界**（比 P0-1 急）：`CTX_BUDGET_CHARS=16000` 换成 token 估算预算（约 7000），并在请求前断言。
3. **加 hash 打点**：记 `static_hash / total_chars / ctx_chars / tools_chars`，跑 20 轮与 llama 日志对照——先拿到"现状 42% 整段重算"的逐轮归因。
4. **历史策略另开一题**：append-only + 压缩 才有 −17% 的净收益；在压缩机制没验证前不动。
5. **P0-1（V1）暂缓**——单独做没有收益（§4），要和历史策略一起做才有意义。
