## 1. L1（短期工作记忆）

### 1.1 存在哪
- 路径由库名派生：`db_path.name + ".l1" + ("." + sha256(l1_scope)[:16]) + ".json"` — `backend/target_memory.py:401-405`。
- 默认库 → `cache/memstore/memstore.db.l1.json`；带 `l1_scope`（private/console/qq_p<uin>）→ 独立文件，**不同渠道永不共享滚动窗口**（注释 :402-404）。设计目的：主人可共享 L2 事实，但不与他人共享会话窗口。
- 内容是一份 JSON（schema 3）：`schema/scope/history_digest/archive_digest/summary/version/turns/pending` — :458-463。
- 读取 `_load_l1` 会校验 `scope` 一致、`turns`/`pending` 全部是合法 turn，否则整份作废并置 `_l1_read_blocked=True`（:419-443）。被污染时**既不读也不再写**（:448-451），宁可丢窗口也不写脏数据。

### 1.2 容量
- `L1_WINDOW_TURNS = 5`（:37），构造参数 `window_turns`（:225、:233）。
- 超出窗口的轮次**不丢**：移入 `_pending_dropped`，无上限，并记录峰值 `_summary_backlog_peak`（:531-541，注释明说"永不 cap/drop，它是 L1 压缩的持久来源"）。

### 1.3 append_turn
`append_turn(role,text)`（:525-542）：
1. 清空 `_archive_digest`（会话与档案脱钩）；
2. `_history_digest = sha256(prev_digest|role|text)` 链式摘要（:478-481、:529）；
3. append → 超过 `window_turns` 则切出 `dropped` 进 `_pending_dropped`、置 `_summary_pending=True`；
4. 立即 `_save_l1()`（原子：唯一 tmp 名 + `replace`，:457-464）。

调用点：用户轮 `backend/target_entry.py:459`（语音走 `append_voice_turn` :456-457 → :544-552），助手轮 :758，自主轮 :1383/:1390。

### 1.4 摘要怎么生成、何时压缩
- 生成器是注入的 `extractor.compress`，实现为 `MemoryLLMService.compress`（`backend/target_memory_llm.py:87-104`）：system prompt 要求"压成 ≤100 字中文摘要，保留核心实体/结论/待办，末尾一句情绪走向，禁止前缀"（:68-73）；`prev` 作为"上一段摘要（接续用，别重复）"拼接（:90）；返回 `(text[:300], int(time.time()))`（:104）。空文本直接抛 `RuntimeError`（:101-103）——**绝不把"空摘要"当成压缩成功**。
- 调度：`process_summary` 单飞、按 `summary_batch_size=40` 取前缀（:228、:599）；只有写盘成功才 `del _pending_dropped[:len(dropped)]`，写盘失败会把整段**塞回队首**并记 `l1_persist_failed`（:616-633）。版本号 `max(旧+1, provider版本)`（:620）。
- 触发时机两处：
  1. 每轮结束后若 `_summary_pending` → `MemorySummaryScheduler.kick()`（`target_entry.py:796-799`）；每次唤醒最多 4 批，每批 `asyncio.wait_for(45s)`，失败按 `2^n`（≤300s）退避（`backend/memory_summary_scheduler.py:17-24、50-67、45-48`）；`allowed()` 默认取 `memory_resource_policy().llm_enabled`（:26）。
  2. `review_once` 复盘时显式 `await process_summary()`（`target_entry.py:1048`）。
- **实测：压缩从未跑过**。四个 L1 文件的 `version` 分别为 0/0/0 与 1790681249，3 个渠道文件 `summary` 长度 0、`pending` 积压 31/9/190。原因是 `YHLZ_MEMORY_LLM_MODE` 默认 `disabled`（`backend/memory_resource_policy.py:38、90-92`），`compress` 直接抛 `MemoryWorkDeferred`，scheduler 计入 `deferred` 而不报错。这是"安全的退化"，但也意味着 L1 摘要曲线目前是空的。

### 1.5 summary_line
`summary_line()` 返回 `"[早前对话摘要] " + summary` 单行，无摘要则空串（:643-649）；只在 owner 通道注入（`target_entry.py:630-632`）。
另有 `context_block()`（:815-823）把摘要+全部窗口轮拼成多行，仅被旧推理器 `backend/llm_reasoner.py:60` 使用，主入口不用。

### 1.6 bind_archive / restore_history
- `bind_archive(history)`（:483-497）：把"**成功保存过的**、有界的档案"与当前活会话绑定。档案只保留 `history_limit` 条，所以档案 digest ≠ 全流 digest；只有当档案尾部 `[-window_turns:]` 与当前 `_turns` 完全一致时才写入 `_archive_digest`，否则写空串。调用点 `target_entry.py:1169`。
- `restore_history(history)`（:499-523）：digest 与 `_history_digest`/`_archive_digest` 都不同、或尾部不一致时，才重置窗口：`_summary=""`、`_pending_dropped=旧头部`（"更早的消息需要压缩"）。摘要运行期间禁止 restore（:513-514）。

### 2.5 L3 的写权限与证据要求（硬约束）
1. **必须 owner 逐条批准**：无 approver 时只排队（:391-397）；`owner.approve` 明确不从模型侧暴露（`target_scheduler_tools.py:1161`）。

| `semantic_any` | 跨 scope 文本召回（默认 `["diary"]`） | 直接读 `vec.text`，不 join；`min_score` 默认 **0.42**（:122-166） |

| 实际调用阈值 | — | `contextual_recall` 语义 0.42（`target_memory.py:714`）、日记 0.48（:759）；工具召回 `_semantic_hits` 0.45（:1689，注释记录了 0.496 的真命中案例）；自主 `_recall_hints` 0.42 / 日记 0.45（`target_entry.py:1287、1289`） |

### 5.1 `memory_review.py` —— S3 候选队列（不是"周期复盘"）
- 三张表与 L2 同库：`memory_candidates`、`memory_review_events`、`memory_provenance`（:33-50），所有变更 `BEGIN IMMEDIATE` 单事务（:52-64）。**故意不初始化 TargetMemoryService、不读主人 L1**（:31-32）。

- 幂等 id：`cid = 'review_' + sha256(channel|normalized_summary|replaces_id)[:24]`（:91-92）—— 模型类型或证据变了也不能"复活"同一条被拒声明。
- `decide`（:149-204）：reason 1-1000 字必填；**批准必须传入同一 db 的 service**（:154-155）；状态终态不可重开（:164-165）；`check_text` 内容闸（:168-171）；替换目标必须 `active` 且非 `protected`/非 `profile`/`tier=='L2'`（:173-177）；写入 L2 时 `importance=5`、`stance` 群聊=`speculation`/主人=`fact`、`evidence_ref='review:'+cid`（:179-188）；同时补 FTS、provenance、旧条目 `invalid_at/superseded_by`（:189-197）；事件流（:198-200）。
- 注释明说：FTS 与主表同事务提交；**全局 kw/向量镜像不参与提交，也绝不允许自动裁决新事实**（:202-203）。
- `invalidate`（:206-221）：只软失效，拒绝 `protected`/`profile`/非 L2。
- CLI `tools/memory_review.py`：`list/show/approve/reject/invalidate/propose-correction`，变更必须 `--confirm`（:34-35），db 不存在直接拒绝（:36-38）——"拼错路径不能悄悄建一个新生产库"。

### 5.2 周期复盘（真正的"复盘"在入口层）
`ConversationSession.review_once(reason)`（`target_entry.py:1001-1119`）：
1. 资源策略未开 → `{"reason":"resource-deferred"}`（:1007-1009）；忙→ `busy`；auto 且退避中→ `retry-backoff`（:1010-1013）。
2. 冻结窗口 `history[-16:]`，先落 T4 持久 review job（`review_queue_store`），首次从持久水位恢复检查点（:1016-1044）。
3. 依次做：`process_summary()`（L1 压缩）→ `submit_candidates(text=last_user, transcript, evidence_ref=f"review:{ts}", source="review")` → `adjudicate_async(local_only=True)` → `reflect()`（:1045-1083）。
4. **只有全部成功才提交水位**（:1084-1096）；否则指数退避 `5*2^n ≤300s` 并 `schedule_retry`（:1097-1110）。
5. 自动触发：`_turn_count - _last_reviewed >= 6` 且非退避（:808-814）；CLI `/review`（:1655-1658）。

### 5.3 `memory_judge.py`
LLM 裁判，`judge(new, old) -> "new"|"old"|"uncertain"`，prompt 强调"更新/更具体/更有依据者优先"（:27-33），解析失败一律 `uncertain`（:44-48）。**生产路径已不再调用**（`memory_adjudicate.py:5` 明说"replaces the old keyword-triggered memory_judge"；仓库内只剩 `test_memory_judge.py` 引用）。属于保留的辅助信号。

### 5.4 `memory_adjudicate.py`（冲突裁决，纯规则、可审计）
- 四个动作：`supersede` / `supersede_candidate`（只记方向）/ `merge` / `uncertain`（:10-14、:21-24）。
- 来源信任表（子串匹配）：老爹/owner/user-approved 1.0、memory.save 0.85、自主/agent 0.6、对话 0.5、群聊/qq 0.3、web 0.2（:27-32）。

### 5.5 `memory_policy.py` —— 名不副实

### 5.6 `memory_carriers.py`（载体证据账）

### 5.7 `memory_index_audit.py`（一致性巡检）

## 7. 台账（`docs/上下文台账.md`）

### 7.1 `ledger_store.py` 的定位
"项目唯一事实源"的唯一程序化接口（docstring :1-14）：外科式改写（只动目标记录行）、原子替换、跨进程文件锁、备份、密钥闸、写完同步索引。

- **进程内检索** `search()` 是**纯子串 AND + 标题加权**（:164-179）：`score = 1 + 3×(命中标题的关键词数)`，按 `(-score, -no)` 排序，并生成 ±40 字片段（:182-197）。这条路径**不用 FTS、不用 kw 索引**。

### 7.2 检索到底走哪条路
`ledger_search`（`backend/target_scheduler_tools.py:64-89`）：
1. `_ledger_index_fresh()`：比较 `kw_meta.ledger_built_at` 与台账 mtime（:92-104）；
2. 新鲜 → `KeywordIndex.query(q, source="ledger")`（BM25-ish + strong-term 覆盖门槛，`target_kw_index.py:248-359`）；

### 7.3 台账算不算"记忆"，会不会被注入
- **不会**。`ctx_lines` 的 12 个来源里没有任何一项读台账（§6.1）。台账只在工具层可达：`CASUAL_SAFE_TOOLS` 显式包含 `ledger_search`（`target_entry.py:44`），work 模式全量工具也含它。

- 答题 prompt：基础版"只用上下文，答不出写 unknown"（:96-100）；`--enh` 版强调方括号日期可用于 when/相对时间推算（:104-111）。
- 判分 prompt：严格三档 `CORRECT / PARTIAL / WRONG`（:113-119）。
- 指标：`accuracy = CORRECT/n`、`partial`、`by_cat` 分类统计（:178-190）；报告含类别表 + 前 30 条明细（:271-285）。

### 8.4 口径警告（代码自己写明的）
- B 模式 = 我们的答题器（DeepSeek）+ 我们的判官（DeepSeek），temperature 0、提示词固定（:61-66、:258-270）。**只能内部前后对比，不能与厂商冻结协议数字并列**。
- 评测路径与生产路径不同：灌库绕过裁决（importance 恒 5、无 `contextual_recall`、无注入、无 L1 摘要），所以它测的是"recall + 读文档"能力，**不覆盖** §6 的注入链与 L1/L3。

## 10. 交叉核对：断链与风险（按影响排序）

**R1 · stance 断链（已确认）**
`adjudicate_async` 的 INSERT 列里没有 `stance`（`target_memory.py:935、946-955`），`store_item` 有（:1204、:1231-1233 走 `infer_stance`）。实测 710 条里 **534 条 stance 为空**（fact 78 / opinion 16 / speculation 82）。同时 `contextual_recall` 返回的 dict **都不带 stance**（:720-726、748-751、763-766、781-784），而工具 `recall`（:1876）和 `_spread_hits`（:1753）带。→ 自动注入路径上看不到来源分级，"群聊传闻"和"老爹原话"在 prompt 里长得一样。

**R2 · 自动裁决只挂在一条写入轨**
`_auto_adjudicate` 仅在 `store_item` 末尾调用（:1246）。对话主轨走 `submit_candidates → adjudicate_async`，**完全跳过自动取代**。→ 只要模型不主动调 `memory.save`，聊出来的新事实不会让旧的失效，`invalid_at` 只在显式/否定路径才动。

**R3 · L1 摘要从未产出**
默认 `YHLZ_MEMORY_LLM_MODE=disabled`（`memory_resource_policy.py:38`），`compress` 抛 `MemoryWorkDeferred`；实测 3 个渠道文件 summary 空、积压 31/9/190。功能无害但等于"L1 只有窗口、没有长期弧线"，且积压无上限。

**R4 · 向量投影漂移**
active+downgraded 415 vs `vec` scope `l2` 407（缺 8）；kw `source='l2'` 465（多 50）。`_vec_upsert` 的异常被完全吞掉（`vector_memory.py:1000-1001` / `target_memory.py:969-970`），所以漂移是静默的。

**R5 · `vec.text` 半空**
`_vec_upsert` 的 `INSERT OR REPLACE INTO vec(id,scope,vec)` 不写 text（:994-996）。`semantic_any` 是唯一依赖 `vec.text` 的读路径（`vector_memory.py:144-148、162-163`），目前默认只查 `diary`（由 `vec_add` 写了 text）才没暴雷；一旦把 `l2` 加进 `semantic_any` 的 scopes，会拿到空文本。

**R6 · `vec_add("l2", …)` 硬编码 scope**
`memory_save` 直接 `vec_add("l2", …)`（`target_scheduler_tools.py:380`），绕开 `l2_scope(db_path)`。群记忆/测试库的 `memory.save` 会把向量写进**主库 scope**，正是 0499 迁移要修的同名 id 覆盖问题。

**R7 · 社区摘要全空但被缓存 24h**
`_summarize` 失败返回 `""`（`communities.py:83-84`），`build` 仍把空摘要写盘并按 `_STALE_SECONDS=24h` 复用（:87-90、:107-109）。实测 74 个社区全空 → `context_for` 恒空，注入 #8 实际上从未生效。

**R8 · L3 待批队列的两套 id 与漏记拒绝**
41 条 pending 里 33 条没有 `id`；`claim_id`（sha1[:16]）与 `reflection` 的 id（sha256[:12]）不通用（`target_persona_loop.py:61-69` vs `reflection.py:117-119`）；`approve_act` 的 no 分支不写 `record_rejection`（:1424-1428）。→ 拒绝账覆盖不全，被拒条目可能反复出现。

**R9 · 注入预算 1500 字按顺序砍尾**
`early_context[:1500]`（`target_orchestrator.py:345`）配合 §6.1 的顺序，意味着 `kb` 与 `profile` 是最先被牺牲的两个来源。当前没有按来源裁剪/配额的机制。

**R10 · 台账 kw 索引已陈旧**
`ledger_built_at` 2026-09-29 < 台账 mtime 2026-10-21 → `ledger_search` 全程走 grep 兜底（`target_scheduler_tools.py:76-77`）。功能可用（结果带 `[ledger:NNNN:line]`），但排序与召回率退化为逐行子串。

**R11 · `memory_policy.py` 与记忆无关**
名字容易被误当治理模块，实际是 GPU 显存策略（:39-80、:128-243）。真正的记忆资源闸在 `memory_resource_policy.py`。审计/交接时容易混淆。

**R12 · 图里混入运维噪声**
`relations` 头部是 `计划表→到点→09:30+daily`(35)、`老爹→需要配合→跑工具`(22)、`尝试更新计划→失败`(13)。`EXTRACT_PROMPT` 只要"明确、可复用的事实"（`entity_graph.py:29-32`），但调度/工具失败文本仍被抽进来；PPR 扩散与社区聚类会被这些节点带偏。

**R13 · `memory_judge` 已成死代码**
生产无调用点（仅 `test_memory_judge.py`），`memory_adjudicate` 的 docstring 已声明取代它（:5）。保留无害，但别在链路上指望它。

**R14 · 评测不覆盖注入与 L3**
`memory_eval` 灌库绕过裁决、不跑 `contextual_recall`/`ctx_lines`/`persona_draft`（§8.4），因此"注入顺序""stance 分级""L1 摘要"这三块当前**没有任何回归评测**。
