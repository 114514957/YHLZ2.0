## 1. 先盘现状：歌库其实是坏的

`cache/songs/songs.json` 有 **59 条**记录，`backend/song_library.py` 的 `song_path()` 只认索引里存的绝对路径。

实测：**59 条全部解析不到文件**（0/59 存在）。

原因是 2026-10-22 的目录重排：索引里存的是

```
C:\Users\ACE_WAN——PROJECT\YHLZ\音频素材\翻唱产出\…\成品_….wav
```

而文件已经移到

```
C:\Users\ACE_WAN——PROJECT\YHLZ\YH\音频素材\翻唱产出\…\成品_….wav
```

**59 条全部只差一个 `\YH\`。** 也就是说：元亨的 `song_list` 一直能列，但 `song_play`/`song_send` 一直拿不到文件——她"点歌"其实是空的。这不是这次做插件引入的，是做的时候撞见的。

### 修了两处

1. **读时兜底**（`backend/song_library.py`）：`song_path()` 找不到原路径时，尝试把 `\YHLZ\` 换成 `\YHLZ\YH\` 再试一次；命中就返回。**不改写索引**。
2. **显式迁移**（`tools/music_cli.py repair`）：把能修复的条目的 `path` 重写为新路径；**先备份** `songs.json.bak-<时间戳>`，只改确实能在新位置找到文件的条目。

已执行迁移：**59 条全部修复**，备份在 `cache/songs/songs.json.bak-20261029195644`。现在 `list` 不再显示"文件缺失"，后端 `song_path()` 返回 True。

## 2. 交付物

### 2.1 `tools/music_cli.py`（唯一实现）

```
list   [--query TEXT] [--limit N] [--json]
info   <handle> [--json]
play   <handle>
send   <handle>
repair [--dry-run]
```

- 直接按**文件路径**加载 `backend/song_library.py`（不 import 整个 backend 包，避免拖起重的初始化）；
- `handle` 支持：歌曲 id、列表序号、标题片段、标签；
- `play`：优先 `sounddevice`（与元亨同款），装不上就交给**系统默认播放器**（`os.startfile`），并说明用了哪条路；
- `send`：走 `song_library.send_qq`（NapCat `upload_private_file`）；如果文件是靠兜底解析到的，CLI 直接用解析后的路径走同一套 NapCat 调用；
- 统一以人类可读文本输出，`--json` 给插件用。

### 2.2 `plugins/dsh-music/`（DSH 插件）

```
package.json        dsh.bundle.patch + main（纯 ESM，无 npm 依赖）
cordis.patch.yml    insert 一行纯 host 插件
config.json         python / cli / 超时（相对路径按 YH 根解析）
lib/index.js        apply(ctx)：ctx.get('tools') → register × 4
lib/library.js      配置合并、调 CLI、渲染；无 DSH import，可 node 单测
test/smoke.mjs      9 项离线自检
install.mjs         装进 profile：备份 → dependency → bundle → junction → 校验
README.md           用法、配置、边界
```

四个工具：`music_list` / `music_info` / `music_play` / `music_send`。

**为什么是薄壳**：DSH 插件不该有第二份"歌库是什么"的实现。索引格式、路径解析、QQ 发送全部留在 Python 侧（`song_library`），插件只负责"把工具调用翻译成 CLI 调用"。这样元亨（daemon）和 DSH（插件）**共用同一条链路**，不会出现两边看到不同歌单。

这套形状是照着 `dsh-rofm` 学的：`ctx.get('tools')` + `tools.register(definition)`，注册包在 `ctx.effect` 里，禁用插件即卸载。

## 5. 边界与规矩

- **只有成品才能发**（元亨的操作员规矩）：插件只读索引、只发已存在于歌库的条目；生成仍然只在工作台做。
- `music_send` 需要 NapCat 在线；不在线时返回失败原因，不静默。
- 播放是"发起"不是"等待"——工具立刻返回，音频在后台线程/系统播放器里播。
- 插件只读 `songs.json`，不写；新增/删除歌曲仍走工作台。

### 6.2 抓到一个会误导人的 bug

第一次跑校验时报：

```
[dsh-music] verification failed: junction points elsewhere
```

但 `fsutil reparsepoint query` 显示 junction **建得好好的**、目标正确。原因是 Windows 的 junction 属于 mount point，
`realpathSync()` 打在它身上**返回链接自己的路径**而不是目标路径，于是"比较两个 realpath"永远不等。

**如果老爹先跑了旧版，会看到"装成功了但报校验失败"**——最难解释的那种错。已改成：

```js
// 通过链接读文件，和插件目录里的同一文件逐字节比较
readFileSync(join(linkPath, 'package.json')) === readFileSync(join(PLUGIN_DIR, 'package.json'))
```
