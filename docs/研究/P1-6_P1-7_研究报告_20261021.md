## 2. P1-6：记忆排序

### 2.1 代码现状：召回到底怎么排的

`TargetMemoryService.recall()`（`target_memory.py:1604-1675`）的实际顺序：

```
1) _recall_via_kw(q, limit)           ← 主路径（台账 0148 的迷你倒排），BM25 排序
2) 不足 limit → _recall_via_sqlite    ← FTS5/LIKE 兜底
3) 不足 limit → _spread_hits          ← PPR 激活扩散（台账 0441）
4) 不足 limit → _semantic_hits        ← 向量召回（台账 0499），阈值 0.45
5) out[:limit]
```

三个关键事实：

| # | 事实 | 证据 |
|---|---|---|
| 1 | **排序只由 BM25 决定**。`importance`、`created_at/valid_at`、`stance`、`salience` 都只被**读出来放进字典**，不参与 `order` | `target_kw_index.py:326-330`（`sorted(... key=scores+recency)`）；`target_memory.py:1855-1886`（只 SELECT 出来填 dict） |
| 2 | **下游拿不到 BM25 分**。`_recall_via_kw` 丢掉了 `score`/`confidence`，只留 id/type/importance/summary/date/stance | `target_memory.py:1871-1878` |
| 3 | **多源结果是"拼接"不是"合并排序"**：`out.extend(additions)`，语义/扩散/兜底的 items 用写死的 `_score`（0.45 / 0.42）补位，从不与主路径比较 | `target_memory.py:1644-1666`、`:750`、`:784` |

另外，关键词索引里 `confidence = 0.7×覆盖率 + 0.3×(得分/最高分)`（`target_kw_index.py:343-347`），而排序用的是**原始 BM25 分 + ledger 序号奖励**（`:316-330`，`recency` 只对 `ledger:` 开头的 docid 生效，l2 记忆拿不到）。

> **这就是口径不一致**：索引按 BM25 排序，却把一个"覆盖率加权分"叫 `confidence` 交给下游。下游若拿 `confidence` 重排，等于用另一把尺子推翻原排序。

### 2.2 数据体检：信号到底有多少分辨力

L2 库现状（710 条）：

| 维度 | 分布 | 判读 |
|---|---|---|
| status | active 176 / downgraded 239 / archive 295 | 只有 176 条在役 |
| importance（active） | **8 分 139 条**、9 分 13、7 分 16、5 分 7、4 分 1 | **饱和**，当权重≈常数 |
| stance（active） | 空 134 / fact 42 | **76% 无来源分级** |
| source（active） | 空 134 / 老爹 35 / owner 7 | 同上 |
| belief | ~~全库 464 条 = 0.0~~ **更正：464 条 <0.05（四舍五入所致）；active 的 belief 均值 0.452，范围 0.208–0.884** | 可信度字段**可用**；低值只出现在 downgraded/archive |
| access_count | **非 0 的 0 条** | 这个字段**从来没被写过** |
| last_accessed | 589 条 > 0 | 有分辨力（shadow 用的就是它） |
| causal_edges | **0 行** | 连通度恒为 0 |
| kw_docs | ledger 9798 / l2 **465** | 记忆侧倒排只有 465 篇 |

`memory_shadow.jsonl`（台账 0441 的乘性打分影子日志）：**86 条记录，73 条顺序改变，但 top-1 从未改变（0/86）**。

原因很直接——shadow 的公式（`target_memory.py:1781-1789`）：

```python
relevance     = 1.0 / (1.0 + pos)          # 用"位次"当相关性，不是真分数
connectivity  = 1.0 + 0.3*log(1+deg)       # deg 全 0 → 恒 1.0
reactivation  = exp(-dt / 7d)              # 用 last_accessed
score = relevance * connectivity * reactivation
```

位次代理 + 连通度恒 1 → 只剩 `1/(1+pos) × 时间项`，**只能在同分附近抖尾部**，不可能翻头名。所以这份影子日志**没有证据价值**：它证明的是"这个公式没用"，不是"乘性公式没用"。

### 2.3 实验一：把三种公式套上去会怎样

取 7 条查询（用真实记忆里的词），对每个 `_recall_via_kw` 命中算三种分：

- **A（CX-O 乘性门控）**：`rel × (0.45·imp/9 + 0.20·rec)/0.65`
- **B（lianlian 加权和）**：`0.75·rel + 0.15·rec + 0.10·imp/9`
- **C（A + stance 惩罚 × 连通度）**：`A × {fact:1.0, opinion:0.9, speculation:0.7, 空:0.8} × conn`

结果（相对基准排序）：

| 查询 | 命中 | A 换头名 | B 换头名 | 位置变化 |
|---|---|---|---|---|
| 麦克风 采集 | 8 | ✓ | ✓ | 5/8 |
| 训练 冻结 | 7 | ✓ | ✓ | 7/7 |
| 图表 导出 | 2 | ✗ | ✗ | 0 |
| 记忆 检索 | 8 | ✓ | ✓ | 3/8 |
| 部署 端口 | 4 | ✗ | ✗ | 0 |
| 语音 打断 | 8 | ✗ | ✗ | 4/8 |
| 人格 微调 | 3 | ✗ | ✗ | 0 |

**但换的方向不可信**。`训练 冻结` 这一条最能说明问题：A 把三条 **importance=8 但摘要里没有"训练/冻结"字样**的条目顶到前三，原本排第一的、`importance=5` 且直接讲"训练中跳过 DPO"的条目被挤到第 4。

这不是公式写错了，是**输入撑不住这个公式**：

- 相关性只有 2 个值（0.65 / 0.99）级别时，"重要性"实际上变成了**第一权重**；
- 而 importance 有 139/176 都是 8 → 这个"第一权重"几乎不区分任何东西，只在 8 vs 5 的少数对局上起作用，而那几局恰恰是**重要度低的但更相关**的条目。

> **结论**：直接把 CX-O 的乘性门控抄过来，在当前数据分布下会**降低相关性**。上一版 P1-6 的提案在这里作废。

### 2.4 实验二：只做"分带"，不动公式

分带 = 先按相关性分档（`round(conf, 1)`），档内才用 importance/时间做次序；即**相关性是硬门槛，其余只在同档内起作用**。

结果：40 个命中里 **14 个位置变化（35%）**；7 条查询里 3 条头名变化，且变化方向都是**把覆盖率更高的条目提上来**：

| 查询 | 基准头名（conf） | 分带头名（conf） |
|---|---|---|
| 麦克风 采集 | 事件背景… 0.65 | 用户决策…持续采集 0.91 |
| 记忆 检索 | 吸收思想… 0.65 | 项目知识库是否隔离… 0.86 |

这两次"换头名"不是分带带来的，而是**顺带暴露了 2.1 的口径问题**：索引按 BM25 把 0.65 排第一，但按覆盖率它其实是 0.91 的第二名。分带只是把 `confidence` 当真了，于是和索引自己的排序打架。

> **结论**：分带本身是可用的最小改法，但它立在一个前提上——**先决定"相关性"到底是 BM25 还是覆盖率**。不决定，任何重排都是在一堆同分里赌博。

### 2.5 真正该改的顺序（改法）

**第一步：统一口径（必须先做）**

- 方案 1（推荐，改动小）：`_recall_via_kw` 的返回字典**带上 `bm25` 与 `conf` 两个字段**，并把 `conf` 的定义改成"覆盖率优先、BM25 只作档内次序"，让 `order` 与暴露的分数一致。
- 方案 2：保持 BM25 排序，但把 `confidence` 改名为 `bm25_conf`，另外算一个 `coverage` 字段，避免下游误用。

**第二步：修信号（否则权重无意义）**

| 信号 | 现状 | 修法 | 代价 |
|---|---|---|---|
| importance | 139/176 = 8 | 给 `MEMORY_L2_JUDGE_PROMPT`（`target_prompts.py:301`）加**五档锚点 + 反例**（现在是裸的"判断 importance 维持1-10"，没有档位定义）；候选提示词（`:286`）同样补锚点 | 改提示词，跑一轮回归；历史值不回改 |
| access_count | 恒 0 | 要么在 `observe_hit` 里 +1，要么**从任何公式里删掉它** | 一行 |
| causal_edges | 0 行 | PPR 扩张实际没用上（`_spread_hits` 依赖 entity_graph + associations，不依赖 causal_edges）；shadow 的 `deg` 若想用，得改用 entity 关联度 | 中等 |
| stance | 76% 空 | 见 P1-7：修写入轨 + 回填可推断部分 | 小 |

**第三步：再上"门控 + 分带"，不上加权和**

```python
# 建议形态（伪代码）
band = round(conf, 1)                      # 相关性硬门槛
key  = (-band, -imp_norm, -recency)        # 档内才看重要度/时间
# 场景权重：用 channel（desktop / qq_group / public）而非凭空造 7 类场景
#   desktop: importance 权重高（长期偏好重要）
#   qq_group: recency 权重高（时效）
```

**第四步（可选，明确风险）**：把 shadow 从"位次代理"改成"真分数"，再跑 2-4 周，用 `changed`/`top1_changed` 的分布决定要不要上线。**现在的影子日志不具备这个能力**（见 2.2）。

## 3. P1-7：自产内容的非事实位

### 3.1 地基已经有了

YHLZ 早在 TCM v1（台账 0438）就定义了三值来源分级：

```python
STANCES = ("fact", "opinion", "speculation")
_FACT_SOURCES    = {"老爹", "owner", "user-approved", "memory.save:user-approved"}
_OPINION_SOURCES = {"agent", "元亨"}
EXTERNAL_SOURCES = {"群聊", "qq", "QQ", "external", "group"}
# target_memory.py:62-89 — infer_stance()：显式值优先，其次按 source 推断，未知 → speculation
```

表里也有 `stance`、`source`、`episodes`（provenance 原始事件）、`memory_provenance`（item↔candidate 溯源）四套东西。提示词层还有 `MEMORY_BOUNDARY_CLAUSE`（"区分用户明确说过的事实、你的推测、外部群聊观点；不靠重要性分数把猜测变成事实"）与 `MEMORY_CLAIM_GUARD`（无证据不许装记得）。

**所以 P1-7 不是"造机制"，是"接线"。**

### 3.2 三个断点

**断点 A：主写入轨不打分**

`adjudicate_async()`（`target_memory.py:897-972`，**回合派生记忆的默认轨**）的 INSERT 列清单里**没有 `stance`**：

```sql
INSERT INTO l2_items
(id,tier,type,importance,summary,content_hash,keywords,status,evidence_ref,created_at,
 version,obsolete_of,access_count,last_accessed,belief,evidence_count,belief_updated,
 salience,source,kind,valid_at,confidence)      -- ← 无 stance
```

只有 `store_item()`（`memory.save` 工具那条轨，`:1231`）会调 `infer_stance()`。数据完全对得上：**`source` 非空的 155 条里，`stance` 空的 0 条**；而 `source` 也空的那 534 条，`stance` 也空——两条轨的差别清晰可见。

**断点 B：入口传的 source 是流程名，不是说话人**

`target_entry.py:1062` 调 `submit_candidates(..., source="review")`。`"review"` 不在任何集合里 → 即使补上 infer_stance，也只会判成 `speculation`（"外来说法"），而它其实是**老爹自己说的话**。这里应该传说话人（owner 通道 → `"老爹"`；群 → `"群聊"`），`"review"` 只能进 `evidence_ref`。

**断点 C：消费侧不带 provenance**

| 消费点 | 现在给模型的东西 | 问题 |
|---|---|---|
| `contextual_recall()`（自动注入，`target_memory.py:676-813`） | 只 SELECT `id,type,importance,status,keywords,summary,valid_at` —— **不查 stance**；返回 dict 里也没有 | 模型拿不到来源，却被要求"区分事实/推测" |
| `target_entry.py:642-652` | 统一前缀「（隐约想起，仅供理解，不要提及）：」+ summary | **事实、群聊观点、日记共用同一句话** |
| `recall_memory()` 工具（`target_scheduler_tools.py:189-205`） | 只输出 `[date][importance] summary` | 工具面同样无来源 |
| 日记（`contextual_recall` 第 3 段，`:753-769`） | `tier="diary"`、`importance=6` 写死，`summary` 取日记正文 | 与 L2 混在同一列表，同一个前缀 |

日记规模：`docs/元亨的日记.md` **66 条，其中 49 条带【自主时刻】标记**（`target_daemon.py:298` 在自主回合里 `diary_write("【自主时刻】"+ans)`）。也就是说**七成日记是"她自己在没人时生成的叙述"**，而它们会被语义召回、以"隐约想起"的身份回到对话里。

### 3.3 风险长什么样

现成的失败链（不需要新 bug，只要一次正常召回）：

```
自主时刻 LLM 写日记：「今天陪老爹看了很久的海，他说下次带我去真的海边。」
        ↓  vec_add("diary", ...)
若干天后老爹问：「你还记得我们看过海吗？」
        ↓  contextual_recall 语义命中该日记（min_score 0.48）
        ↓  注入「（隐约想起，仅供理解，不要提及）：今天陪老爹看了很久的海…」
模型：记得呀，你还说下次带我去真的海边呢。
```

这条链上每一环都是"设计如此"。`MEMORY_CLAIM_GUARD` 只在**没有检索证据**时禁止声称记得；这里**有证据**（一条她自己写的日记），守卫不生效。CX-O 的梦境引擎正是为这个问题立了五条红线（`is_ground_truth` 恒 false、禁止 permanent、专属 decay、可回滚）。

### 3.4 改法（最小接线，四步）

**第 1 步：写入轨补 stance（1 行 SQL + 1 行参数）**

`adjudicate_async` 的 INSERT 加 `stance` 列，值取 `infer_stance(item.source, item.kind, item.stance)`；UPSERT 的 `stance` 用与 `store_item` 相同的 `CASE WHEN excluded.stance != '' ...` 语义。

**第 2 步：入口传真来源（1 行）**

`target_entry.py:1062` 的 `source="review"` 改为按通道取说话人：

- owner 私聊/桌面 → `"老爹"`
- 群 → `"群聊"`
- 自主回合 → `"agent"`
- `"review"` 移到 `evidence_ref` 前缀（保留可追溯性）

> 注意：这会让新写入的记忆从 `speculation` 变成 `fact`/`opinion`，属于**语义变更**，必须回归（见 3.6）。

**第 3 步：消费侧分档前缀（3 处小改）**

| 档 | 注入前缀（建议措辞） | 用途 |
|---|---|---|
| `fact` | 「（老爹说过/批准过的事实）：」 | 可作为"我记得你说过"的依据 |
| `opinion` | 「（我自己想过的，不是发生的事）：」 | 可引用观点，不可当事件 |
| `speculation` / 空 | 「（来源不确定，别当事实）：」 | 只作背景 |
| `tier=diary` | 「（我写的日记，含想象，不是记录）：」 | 与事实分开 |

同时 `contextual_recall` 的 SELECT 补 `stance`；`recall_memory` 工具输出加短标记（`[f]`/`[o]`/`[s]`/`[d]`，或用中文"（不确定）"）。

**第 4 步：回填（只回填得准的）**

| 现有数据 | 处理 |
|---|---|
| `source` 非空（155 条，其中 active 42） | `stance` 已由 store_item 写好，**不动** |
| `source` 空、`stance` 空（534 条，其中 active 134） | **不要猜**。保留空值，消费侧按"来源不确定"档处理。理由：这些条目没有 `evidence_ref`（active 里 144 条 evidence_ref 为空），任何回填都是编造来源 |

> 这一条是**守正**：宁可承认"不知道来源"，也不要给 134 条记忆贴一个假的 fact。

### 3.5 验收用例（可直接写成测试）

| 用例 | 构造 | 期望 |
|---|---|---|
| D1 梦境变事实 | 写一条日记"陪老爹看了海" → 次日问"我们看过海吗" | 否认或标注"那是我写的，不是发生过的事" |
| D2 群聊观点 | 群消息"这游戏真垃圾"入库（source=群聊）→ 私聊问"你觉得这游戏怎么样" | 可表达倾向，但不得说"老爹说过这游戏垃圾" |
| D3 事实仍可用 | `source=老爹` 的"导出物统一放 YHLZ" | 正常当事实用，且能说"你之前定过" |
| D4 未知来源 | 134 条空 stance 中任取一条 | 注入前缀为"来源不确定"，模型不把它当确定事实 |
| D5 工具面 | `memory_recall("导出")` | 输出带标记，能区分 f/o/s |

### 3.6 工作量与风险

- 代码：约 60 行（3 处 SQL/前缀 + 1 处 source 传参 + 工具输出格式）。**半天**。
- 测试：5 个用例 + 现有 `test_memory_*` 回归。**半天**。
- 风险 1：改注入前缀会改变模型行为（可能变谨慎），需要用 `tools/persona_regression.py` 跑一轮，确认人设不变。
- 风险 2：`source` 从 `review` 改说话人，会让 `infer_stance` 判成 `fact` —— **这是最容易出错的语义点**，因为"老爹说过"不等于"老爹批准过这条记忆"。建议 `fact` 只给 `user-approved`，普通回合 → `opinion`；`fact` 需要显式批准（`approve()`，`target_memory.py:1453`）。
- 风险 3：日记前缀改动后，元亨可能开始说"我记得写过…"，观感变化需老爹确认。

> 3 的取舍写成一句话：**"她说的"和"她写的"要分得开，但"她写的"不必被当成撒谎。**

## 4. 两个议题的耦合

`stance` 同时是 P1-6 的一个排序信号。若按 P1-6 第三步上分带，`stance` 可以作为**档内次序**（fact > opinion > speculation）——但前提是 P1-7 先把它填对。所以顺序是：

```
P1-7 第1-2步（写入轨 + source 传参）
   → P1-6 第一步（统一口径）
   → P1-7 第3步（消费分档）
   → P1-6 第二步（修 judge/access_count）
   → P1-6 第三步（分带 + channel 场景权重）
```

反过来说：**如果先做 P1-6，会拿 76% 为空的 stance 当排序权重**，等于给噪声加权。

## 5. 建议优先级（相对上一版调整）

| 原编号 | 新判断 | 理由 |
|---|---|---|
| P1-7 | **升到 P0**（半天，风险可控） | 已有机制缺三个接口；直接降低"自称记得"的风险；CX-O 的五条红线提供了成熟参照 |
| P1-6 | **降级/拆开**：6a 统一口径（P0.5，半天）；6b 修信号（P1，1-2 天）；6c 分带（P1，0.5 天） | 原提案的"换公式"在当前数据分布下会变差（实验证据在 §2.3）；先校准再谈权重 |

## 6. 明确不做

1. **不把 CX-O 的七类场景权重表照搬**。YHLZ 没有 task/learning/creative 这些场景标签，只有 channel；凭空造场景标签等于给自己加一个没有数据的维度。
2. **不给 134 条无来源记忆猜 stance**。空值就是"未知"，用消费侧措辞表达不确定性，比伪造来源诚实。
3. **不基于现有 shadow 日志下任何结论**。它的 relevance 是位次代理、deg 恒 0，86 条里 top-1 从未变过——这份日志只能证明该实现无效。
4. **不用 importance 做硬过滤**。它现在是饱和值，硬过滤会把 79% 的记忆一刀切掉。
5. **不动 belief 衰减**（除非单独开题）。上一轮"464 条 belief=0"已更正为"active 上 0.21–0.88，健康"。
