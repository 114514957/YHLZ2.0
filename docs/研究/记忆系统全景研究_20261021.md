## 0. 摘要：十条结论

1. **记忆系统的分歧不在"存哪"，在"按什么分层"**。NEKO 按**用途**分（facts=原子观察 / reflections=解释 / persona=身份），Trae 按**回合用途**分（intent/actions/outcome/**learned**），Codex 按**阶段**分（stage1 蒸馏 → 阶段二合并），YHLZ 按**时间尺度**分（L1/L2/L3）。时间分层解释不了"这条记忆拿来干什么"，这可能是 YHLZ 的 importance 全挤在 8 分的结构性原因。
2. **importance 不该进检索公式**。NEKO 的 `memory_settings.py:25-26` 明确写着"所有评分计算都以净用户确认次数为单位（**§3.1.2 偏离 task spec 原公式——去掉 importance 项**）"；importance 在 NEKO 只用于**候选截断/排序**（`:104, :526, :946`）。这与上一轮 YHLZ 实测（importance 139/176 全为 8）互相印证：**重要性是筛选旋钮，不是相关性权重**。
3. **Generative Agents 其实是加权和，不是三项相乘**。官方 `retrieve.py` 默认 `gw=[0.5, 3, 2]`（recency / relevance / importance 顺序），源码注释还留着 `gw=[1,1,1] tends to work decently`。很多复现写成"相乘"，与原文不符——**这直接推翻了我上一轮"乘性门控"的表述**。
4. **写入闸的行业共识是"用 LLM 当闸门"，学界前沿是"用作用域和可验证性当闸门"**：前者=Mem0 的 ADD/UPDATE/DELETE/NOOP、Graphiti 的 dedupe/resolve（同源错误，验证者与被验证者是同一模型）；后者=CASK 的 discourse ownership + commit rule、CogMem 的 Claim/Fact 认识论分离、SEMV 的 verification-gated consolidation（负迁移 5.7% → **0.2%**）。**"提取后再验证为真"几乎是空白**。
5. **双路径是共识**：自动注入**不做全库语义搜**（NEKO `memory-system.md:77`），工具召回才混合（BM25+向量+**RRF k=60**，`hybrid_recall.py:50`）。YHLZ 的 `contextual_recall` 把语义、2-gram、BM25、日记四路混进自动注入（`target_memory.py:709-787`），**与自己 v2 设计 §3.4 相反**。
6. **管理闭环要有"游标+租约+幂等"**。NEKO：`outbox.ndjson` + `events.ndjson` + `cursors.json` + at-least-once + 幂等 handler（`memory-system.md:188-193`）。Codex 更极端：`jobs` 表带 `lease_until / ownership_token / retry_remaining / input_watermark`，另有 `consolidation_progress(singleton, max_thread_count)` 做**水位驱动的二次合并**。YHLZ 这两样都没有。
7. **遗忘是 2025-2026 的显学，但没定论**：FSFM(2604.20300)、Oblivion(2604.00131, token −73%)、MemDream(2609.34545)、ScrapMem(2605.03804)、REM(2610.27377)…；Bemula(2610.18052) 指出**没有系统端到端通过 >1.5% 的删除请求**。YHLZ 的"零删除"反而是保守正确的选择。
8. **provenance 是公开的空白**。做得最实的是 Graphiti（episode 即 ground truth 流）、CogMem（Claim/Fact 分离、source-attributed）。**没有看到"来源分级 + ground-truth 标记"的成熟标准**——YHLZ 已有 `stance ∈ {fact, opinion, speculation}`，只要接通就能领先，而不是追赶。
9. **检索质量的瓶颈常在评测口径**。跨论文数字不可横比：Mem0 重跑 A-Mem 得 J=39.79，而 A-Mem 原文只报 F1/BLEU；ZenBrain 自陈 LoCoMo 的 substring F1 偏袒 BM25。YHLZ `tools/memory_eval.py` 自己标注 "B-mode = 自家答题 + 自家裁判，不可与厂商数字横比"——这个自觉是对的，要保留。
10. **最先该做的不是算法，是三个接口**：① 主写入轨补 provenance（上轮已定位）；② 自动注入与工具召回分离（v2 §3.4 已设计未落地）；③ 给后台整理加 outbox+游标（NEKO/Codex 都有，YHLZ 没有）。

## 2. 参照系 A：NEKO —— 目前最完整的开源"角色记忆流水线"

### 2.1 五层 + 一本原始账

| 层 | 载体 | 是否进新会话上下文 |
|---|---|---|
| Working context | `GET /new_dialog/{name}` 渲染结果（不是一个库） | 它就是上下文本身 |
| Recent memory | `recent.json`（有界轮次 + 就地 `SystemMessage` 摘要 memo） | ✅ |
| Facts | `facts.json`（原子观察，带 subject/importance/event time） | ❌ 供反思与显式召回 |
| Reflections | `reflections.json`（由 fact 组综合出的解释） | 部分（pending + confirmed） |
| Persona | `persona.json`（master / neko / relationship 三实体） | ✅（受预算与抑制规则约束） |
| 原始账本 | `time_indexed.db::time_indexed_original` | ❌ 只做抽取/时间扫描/间隔计算的**底账** |

（`memory-system.md:9-19`）

### 2.2 写入流水线（五步，每步都有失败隔离）

**前台零 LLM**：每轮的 `POST /cache` 只做两件事——把回合写进 recent、把原文写进 `time_indexed_original`，**不跑抽取**（`app/memory_server/routes.py:741-749`）。抽取交给后台批循环：累计 ≥10 个"有用户发声"的回合，或空闲 ≥5 分钟，40 秒轮询（`config/memory_settings.py:67-69`）。

1. **落盘**：主服务 POST 到 memory-server(48912)；写 recent + 原始表 + **`outbox.ndjson`**（可重放的回合后操作）→ 抽取放到后台（`:23-32`）。
2. **就地压缩 recent**：超阈值时把旧条目换成一条 `SystemMessage` memo 放在最前，最新轮保持原文；超大输入走 map-reduce；**硬上限**兜底（`:34-38`）。
3. **抽 fact + 去重**：hash/文本检索常开；有 embedding 时后台找同义改写送 LLM 仲裁；被反思消费过的标 `absorbed`，旧的移 `facts_archive.json`（`:44-48`）。
4. **综合 reflection**：**id 由源 fact ids 派生 → 重试幂等**；成功后源 fact 标 absorbed（`:52-56`）。
5. **晋升 persona**：证据驱动 + correction-tier merge（新条目 / 合并 / 拒绝 / 进矛盾队列）；角色卡条目 **protected**，不参与衰减与清扫（`:58-62`）。

### 2.3 证据算术（可直接抄的具体数值）

`config/memory_settings.py`：

```
EVIDENCE_CONFIRMED_THRESHOLD = 1.0     # score ≥1 → confirmed
EVIDENCE_PROMOTED_THRESHOLD  = 2.0     # ≥2 → promoted
EVIDENCE_ARCHIVE_THRESHOLD   = -2.0    # ≤-2 → 归档候选
WEAK_MEMORY_AUTO_CONFIRM_DAYS = 7 / AUTO_PROMOTE_DAYS = 7 / EVIDENCE_ARCHIVE_DAYS = 14
IGNORED_REINFORCEMENT_DELTA  = -0.2    # 被忽略要扣分
USER_CONFIRM_DELTA = 1.0（直接）   USER_FACT_REINFORCE_DELTA = 0.5（间接）
USER_FACT_REINFORCE_COMBO_THRESHOLD = 2 / COMBO_BONUS = 0.5   # 间接信号累计后补到 1.0
```

设计要点（`:25-56` 注释）：**评分单位 = "净用户确认次数"**；直接信号（用户显式确认/否认）权重 1.0，间接信号（Stage-2 LLM 推断）0.5 且要"累计补偿"；**importance 已从公式中移除**。

**双时钟的精确式子**（`evidence.py:125-160`，比 v2 的设计描述更具体）：

```
score = rein·0.5^(age_rein/30d) − disp·0.5^(age_disp/180d)
```

正证据半衰 30 天、负证据半衰 180 天——**负证据衰减得慢**，所以"否认过的事"比"确认过的事"记得更久。importance 只作为**初始种子**（10→0.8 / 9→0.6 / 8→0.4 / 7→0.2），此后由证据接管（`evidence.py:79-84`）。
归档：`score < 0` 时按自然日累计 `sub_zero_days`，**累计 ≥14 天**才进分片归档；`protected`（角色卡）的 score 视为 **inf**，永不归档（`evidence.py:155-159`）。

生命周期：`facts → pending → confirmed → promoted/merged`；负证据 → `denied → archive candidate → sharded archive`（`:110-135`）。**mention suppression 与证据分离**：只抑制反复提及，不删条目（`:137`）。

### 2.4 两条召回路径（关键设计）

| 路径 | 触发 | 候选 | 排序 |
|---|---|---|---|
| **自动上下文**（新会话） | `GET /new_dialog` | persona（protected+active，2000 tok 预算）+ reflections（pending+confirmed，2000 tok）+ recent memo/原轮 | **不做全库语义搜**（`:66-91`） |
| **工具召回**（`recall_memory`） | 对话模型主动调 | active facts + active reflections + archived facts（**persona 被故意排除**，因为它已在上下文里） | BM25 4 条 + cosine 4 条 → **RRF(k=60)** → 最多 8 条；**不加 LLM rerank**（`hybrid_recall.py:48-61`、`memory-system.md:81-93`） |

工具召回的细节（`hybrid_recall.py:1017-1266`）：BM25 与 cosine 各有**独立阈值 0.1 / 0.3**，各取 4 条；只给 `query` 走语义、只给 `time` 走事件时间邻近、两者都给时**先按时间窗硬过滤**再检索。渲染格式是：

```
1. [事实/关于用户] 老爹不吃香菜  (2026-05-01, 23 天前)
```

单条 400 tok、整段 2204 tok 封顶（`recall_render.py:119-190`）。

**recent 压缩的具体阈值**：保留 10 条原文 + 1 条 `SystemMessage` 备忘；**>20 条触发压缩**；输入 >8000 tok 走 map-reduce；摘要 >1000 tok 再压一次；最多 3 轮；失败不 splice、保留原文；硬上限 60000 tok（`recent.py:788-1194`）。

第三条路：**内部维护召回**（`MemoryRecallReranker`）只服务证据检测与反思综合，与工具召回**不是同一个池**（`:97-106`）。三种消费者、三套降级：向量挂了 → 工具召回退 BM25-only、维护召回退证据分、反思锚点退空块。

### 2.5 韧性

`outbox.ndjson`（至少一次投递 + 幂等 handler）、`events.ndjson` + `events_applied.json`（先写事件再改视图，启动对账）、`cursors.json`（扫描进度）、每角色锁、有限重试/退避、存储不安全时返回 409 限流模式（`:188-202`）。

> **可借鉴 TOP3**：① 自动注入与工具召回彻底分离；② 证据分用"净确认次数"而非 importance；③ outbox+cursor+事件日志的闭环。

### 2.6 被低估的一层：25+ 支记忆专用提示词

`config/prompts/prompts_memory.py` 有 **338KB**，按阶段分成独立提示词（每个都多语言）：

`RECENT_HISTORY_MANAGER` / `DETAILED_RECENT_HISTORY_MANAGER` / `FURTHER_SUMMARIZE` / `SETTINGS_EXTRACTOR` / `HISTORY_REVIEW` / `EMOTION_ANALYSIS` / **`FACT_EXTRACTION`** / `FACT_EXTRACTION_BATCH` / `FACT_EXTRACTION_AI_AWARE` / **`SIGNAL_DETECTION`** / `REFLECTION` / `REFLECTION_FEEDBACK` / **`PROMOTION_MERGE`** / `PERSONA_FUSION` / `PERSONA_CORRECTION` / **`FACT_DEDUP`** / `MEMORY_RECALL_RERANK` / `RECALL_MEMORY_TOOL_*` / `MEMORY_REFINE` / `SCOPED_*`…

两个具体可抄的点：

1. **importance 五档锚点 + 反饱和指令**（`prompts_memory.py:1409-1414`）：

```
10   ：关键长期信息（姓名/昵称/生日/身份/核心关系；用户说"请记住 X"）
8-9  ：长期稳定的核心偏好 / 固定习惯（不是一时兴起）
6-7  ：普通偏好、日常习惯、近期动态
5    ：次要但有记录价值的观察
1-4  ：弱相关或不确定（**仍请返回**，下游按场景过滤，不要在此处丢弃）
—— "请按此打分，不要泛泛都打 7"
```

> YHLZ 的 `MEMORY_L2_JUDGE_PROMPT`（`target_prompts.py:301`）只有"判断 importance 维持1-10"，**没有档位**——这正是 importance 79% 挤在 8 分的最可能原因。

2. **相对时间编码 `event_when`**（`:1416-1423`）：不写绝对日期，写 `{"start":{"offset":-1,"unit":"day"},"end":null}`，unit ∈ minute/hour/day/week/month/year。好处：不受会话当时时钟影响，跨机器/跨时区可重放。YHLZ 只有 `valid_at` 时间戳，没有"话语里的相对时间"这一层。

3. **提示词水印**（`:1434-1437` 注释）：`======以下为对话======` 这一对定界符在所有语言里都保持简体字面量，是**运行时匹配的安全水印**，不是给人看的文案——防止注入时被本地化改掉。

### 2.7 NEKO 相对 YHLZ 独有的五个机制

| # | 机制 | 为什么值得看 |
|---|---|---|
| 1 | **双时钟证据**（正 30 天半衰 / 负 180 天）+ 自然日 `sub_zero_days` 累计 + 14 天才归档 | 用"两个半衰期"表达"否认比确认更持久"，比单标量 belief 有信息量 |
| 2 | **LLM 反思中间层** + `temporal_scope` 三档 TTL + 独立"过去记忆"渲染块 | 把"解释"与"事实"分开存，过期解释不删而是降级展示 |
| 3 | **提及抑制（mention suppression）与证据解耦**：5h 窗口、>2 次触发、5h 冷却；用户显式禁话题 3 天 TTL | "不想被反复提"≠"这条是假的"——两件事分开管 |
| 4 | **群聊 subject 隔离 + 平台中立 speaker_trust 账本 + per-subject 渲染预算与总闸（16000 tok）** | 多人群场景下防止某个 subject 吃掉全部预算 |
| 5 | **outbox + events.ndjson 至少一次重放 + 启动 reconciler**（视图仍可手改） | 不是完整事件溯源，但足以在崩溃后对账 |

> 这五条里，YHLZ 已经有的：无（1）、部分（2，有 L3 但无 TTL 分档）、无（3）、部分（4，有 QQ 群隔离但无 trust 账本）、无（5）。

**但反向也有一条**：YHLZ 有 `valid_at / invalid_at / superseded_by` + `recall(as_of=…)` 的**时点回溯**（bi-temporal 完整），NEKO **没有**——它只有"事件时间 vs 写入时间"，没有失效时间轴，历史时点召回只能靠事件时间窗近似。**这一点别丢**：上一轮 YHLZ 的 `_filter_as_of` 与 `test_memory_m1` 已经覆盖了它，是本项目少数领先 NEKO 的地方。

### 2.8 一条可以直接搬的工程原则：**信任值不能来自模型输出**

NEKO 的 `speaker_trust` 是**服务端配置**（四档初值 admin 1.0 / trusted 0.8 / normal 0.5 / none 0.3，仲裁 margin 0.15），**从不取自模型输出**（`config/memory_settings.py:248-266`、`memory/speaker_trust.py`）。

这条与 provenance 同构：**来源可信度必须由"谁说的/从哪来"决定，不能由模型自己判断**。YHLZ 的 `stance` 目前正是按 `source` 推断（`infer_stance`），方向对；要守住的是——别哪天让 LLM 在抽取时顺手输出一个 `stance` 字段。

## 3. 参照系 B：这台机器上的四个编码代理

### 3.1 Trae CN：**按回合用途的结构化记忆 + 按日分桶**

真实落盘结构（一手）：

```
.trae-cn/memory/
  user_profile.md                      # 412 B · 2026-09-26 · 沟通与协作偏好 / 工作流
  projects/<slug>/
    project_memory.md                  # 仅 Desktop(556B) 与 NEKO(981B) 有；YHLZ 没有
    <YYYYMMDD>/
      session_memory_<id>.jsonl        # 当日记录（增量，不是全量快照）
      topics.md                        # 当日主题摘要（较新的一天才有）
```

`project_memory.md` 的三个小节值得抄：**Hard Constraints / Engineering Conventions / Lessons Learned**。真实片段（NEKO）："Heavy assets (torch, model weights, dependencies) must be stored on C: drive due to D: drive space limitations (only 4GB free)"——一条环境约束，写一次，以后不用再踩。

会话记录每条形如：

```json
{"intent":"...","actions":["...","..."],"outcome":"...","learned":["...","..."],
 "message_summary_time":"...","message_id":"...",
 "compact_summary_meta":{"trigger":"auto","mode":"async","server_history_id":"...",
                          "summary_digest":"<sha256>","created_at_ms":...}}
```

三个可迁移点：

1. **四字段 schema**：`intent / actions / outcome / learned`。`learned` 是**可复用的结论**（例："全参继续预训练需 ≥100B token，当前 346M token 不适配；base+LoRA SFT 是当前路线"），不是"发生过什么"——这是程序性/语义记忆与情景记忆的分野。
2. **digest 去重**：`summary_digest` 是内容哈希，重复摘要不重复入库。
3. **增量按日分桶**：同一个 session 会跨 9/14、9/15、9/18、9/24、9/26 多个日期目录，**每天只写当天那几条**（5683→2796→4789→777→2004 字节，不累积）。日期是天然分区键，TTL 与回溯都便宜。

写入**不是编码 agent 自己做的**。`ai-agent.dll`（v3.3.104）里能找到 `extract_topics_and_update_memory` / `fetch_topics_memory` / `build_chat_memory_context` / `inject_core_memory_flag` / `core_memories` / `no_update` / `new_memory{...}` / `postcompact` / `memory_content truncated` 这些字符串，可还原出：

```
辅助模型判断 → 返回 "no_update" 或 "new_memory{...}" → 覆写 user_profile / project_memory → 追加 topic
消息级摘要异步写 session_memory（trigger=auto, mode=async）
注入走 context enricher 的 core_memories 渲染变量
```

> `no_update` 这个协议值得单独记：**给模型一个"这次没什么值得记"的合法出口**。YHLZ 的抽取没有这个出口，模型每轮都得产出点什么，这是幻觉提取的一个结构性诱因。
>
> 与 YHLZ 对照：YHLZ 的 L1 摘要只有一条滚动 memo，没有"每天一份主题"；L2 的 `event` 类型不区分 intent/outcome/learned。**Trae 的 schema 可以直接映射成 YHLZ 的 episode 结构。**

### 3.2 Codex：**rollout 事件流 + 增量投影 + 两阶段蒸馏（未启用）**

三层结构（`sessions/YYYY/MM/DD/rollout-*.jsonl[.zst]`）：

1. **事件流**：append-only JSONL。`session_meta` 带 `base_instructions`、`history_mode:"paginated"`、`context_window`（本机 **997,500**）；`world_state` 带 `agents_md:{directory,text}`；首条 `response_item` 就是 `# AGENTS.md instructions for <cwd>`；`event_msg` 里有 `token_count`。
2. **投影**：`thread_history_1.sqlite`（**189 MB**，364 turns / 21,078 items）——`thread_turns`、`thread_items(item_json)`、`thread_history_projection_state(next_rollout_byte_offset)`、`thread_realtime_items`。**按字节偏移从 rollout 增量投影**，是查询/UI 索引，不是语义召回。另有 `state_5.sqlite`（23 threads、4 projects、tokens_used）与 `session_index.jsonl`（18 行）。
3. **记忆（设计有、本机没跑）**：`memories_1.sqlite` 0 行：

```sql
stage1_outputs(thread_id, source_updated_at, raw_memory, rollout_summary, rollout_slug,
               generated_at, usage_count, last_usage,
               selected_for_phase2, selected_for_phase2_source_updated_at)
jobs(kind, job_key, status, worker_id, ownership_token, lease_until, retry_at,
     retry_remaining, last_error, input_watermark, last_success_watermark)
consolidation_progress(singleton, max_thread_count)   -- 实测 0
```

读法：阶段一每 thread 产 `raw_memory` + `rollout_summary`；阶段二用 `usage_count/last_usage` 选留（**这是"巩固/遗忘"的现成骨架**）；`jobs` 用租约防双跑、用水位做幂等重放。

**AGENTS.md 的注入语义**：项目 `YHLZ/AGENTS.md`（1261 B）被自动注入；10-15 更新时出现过一句 *"These AGENTS.md instructions replace all previously provided AGENTS.md instructions."*——**指令是可版本控制、可人工编辑、且显式声明替换的**。全局 `~/.codex/AGENTS.md` 是 0 B。

### 3.3 Claude Code：append-only 事件流（本机基本没用）

`projects/<slug>/<uuid>.jsonl` 每行一个事件：`permission-mode` / `file-history-snapshot`(trackedFileBackups) / `user`(parentUuid/uuid/promptId/cwd/sessionId/version/gitBranch) / `attachment` / `assistant` / `system` / `last-prompt`。`history.jsonl` 只是输入历史；`sessions/` 为空；`settings.json` 只有 `{"env":{}}`。

本机样本是 2026-07-30 v2.1.143，assistant 记录内容是 *"Not logged in — Please run /login"*——**基本没真正用过**；`.claude.json` 已不存在（只剩 5 份 backup，里面有 per-project allowedTools / lastSessionId）。**`CLAUDE.md` 在 PROJECT 与 YHLZ 下都不存在**（递归 3 层也没有）。

> 结论要谨慎：**不能从本机数据推断 Claude Code 的记忆设计**，只能说"这台机器上没有它的记忆产物"。可借鉴的只有形态本身：**append-only + `parentUuid` 串链 + `file-history-snapshot`**——把"经历"与"可编辑的项目记忆文件"分开。

### 3.4 DSH（当前运行环境）：分层指令 + 显式压缩阈值 + 写前 checkpoint

- **会话**：`sessions/--<normalized-cwd>--/<session-id>/session.v4.jsonl.zstd`，append-only，zstd 独立帧拼接（本会话 1032 帧 / 1698 条 / 解压 5.48 MB）。记录类型：`turn/start`、`step/start`、`system/message`、`user/message`、`request/context`、`assistant/message`、`tool/call`、`tool/result`、`job/registered`、`subagent/catalog`、`deliverables/presented`、`workspace/changes` 等。
- **系统提示词写在历史里**：`request/context` 记录 `contextWindow: 1000000`、`systemPromptUpdate: "in-history"`，`system/message` 把系统提示词当历史消息存——**不是单独的 API 字段**。
- **投影**：`storages/session_projcache/sessions/<id>.json` 里有 `contextPressure{surfaceTokens: 308576, contextWindow: 1e6, pressureTokens: 446773}`、`contextBreakdown{systemTokens, toolsTokens, messageTokens}`、`turnOutline`。
- **AGENTS.md 注入**（`dsh-agent-instructions`）：`$DSH_HOME/AGENTS.md` → `~/.agents/AGENTS.md` → 项目链根→cwd；候选 `AGENTS.md`/`CLAUDE.md`，叠加 `.local.md`；`.git` 定根；**maxBytes 65536，单文件 1 MiB**；作为持久 `user/message` 的 `<system-reminder>` 在第一次 pre-step 注入，后续读写到更深目录再补；**预算先丢宽泛文件、最后才截断最具体的文件**。
- **人格**（`dsh-agent-md`）：三层 `<项目>/AGENT.md` > `<DSH_HOME>/agents/projects/<目录名>-<hash>.md` > `<DSH_HOME>/AGENT.md`；渲染成 user 角色尾消息，**只在文本变化时追加，下一回合生效**（本机 inject-log 140 行）。
- **压缩**（`dsh-compaction-basic`）：`thresholdRatio 0.8`、`headroomTokens 65536`、`retainRatio 0.16`，阈值 `floor(min(W×0.8, W−O−65536))`。本会话 W=1,000,000、O=256,000 → 阈值 **678,464**，当前 pressure **446,773**，**尚未压缩**。摘要替换最旧一段、保留近期尾部逐字、包 `<compacted-summary>` + 固定 checkpoint 前导；只存摘要文本，原始在 `compaction/summary` 事件里。
  - **checkpoint 是固定章节的**：Primary Request / Key Technical Concepts / Files and Code / Errors and Fixes / Pending Jobs / Current Work / Next Step / Critical Context。**这比"压成一段话"强得多**——它是可被下一轮直接消费的结构。
  - 配套还有 `tool-result-pruner`（先修剪超大工具输出，不调模型）与 `image-offload`。
- **持久性**：`dsh-session-checkpoint-policy` 在**模型请求前、顶层工具副作用前、下一 step 前**flush；未完成工具调用恢复为 `TOOL_OUTCOME_UNKNOWN`。
- **检索**：无自动语义召回；`dsh-session-query-sqlite` 是手动查询工具；`dsh-experimental-session-search` 只有 11 字节（空壳）。
- **`profiles/` 不是用户画像**：desktop/web/headless 是 Cordis 插件组合清单（`dsh.profile.bundles`）。

> 四个代理的共同点：**记忆 = 文件 + 事件流 + 约定，没有向量库、没有衰减**；检索是"全量/回放"，不是语义召回。它们解决的是"跨会话接续工作"，不是"长期人格"。
>
> 但 DSH 有一样 YHLZ 该抄：**压缩是一个带具体参数的系统**（0.8 / 65536 / 0.16 + 阈值公式），而不是"超了就摘要"。以及**写前 checkpoint**——这一点 NEKO 的 outbox 也是同一思路。

### 4.3 三个横切判断

1. **写入闸**：主流只有四类——LLM 自决 op、结构化输出校验、作用域/权限门（CASK 2610.09008）、验证门（SEMV 2609.27175）。**"提取后再验证为真"是空白**。
2. **检索公式**：加权和是默认（GA、MemoryOS 的 cos+Jaccard、路由式）；图扩散只有 HippoRAG 与 Graphiti 认真做；**乘性门控在论文里罕见**（多在工程复现里，且与 GA 原文不符）。
3. **provenance**：Graphiti（episode 级）、CogMem（2610.11314，Claim/Fact 分离、source-attributed）、2026 治理线（2609.04875 provenance graph、2604.16548 综述主张"存储时带 provenance/versioning"）。**没有成熟标准。**

### 4.4 provenance 与门控：一个可下手的空白（本轮最重要的外部发现）

| 工作 | 做到了什么 | 没做到什么 |
|---|---|---|
| **Graphiti/Zep** | Episode 被定义为 *"the ground truth stream"*，每条事实可回溯到产生它的 episode；失效不删 | 只有**结构级指针**，没有"这条有多可信"的**分级** |
| **CogMem**（2610.11314, EMNLP'26） | PEC²F 图式：**Claim 节点保留"谁说的、对谁说"**，只有 Fact/Event 才是客观知识；有 semantic-collapse 探针 | 是**分类**（claim vs fact），不是**分级** |
| **CASK**（2610.09008） | **discourse ownership**：一句话属于哪个世界/分支/说话人；commit rule 决定能否进持久记忆 | 需要形式化，成本高 |
| **SEMV**（2609.27175） | **verification-gated consolidation**，显式保留冲突 | 单个实验，未成标准 |
| **治理综述**（2604.16548, EMNLP'26） | 结论：**LTM 安全无法只在检索/执行时补救，必须锚定在存储时的 provenance/versioning/策略化保留** | — |

**战略判断**：YHLZ 已有 `stance ∈ {fact, opinion, speculation}`，这比 CogMem 的二分更细，比 Graphiti 的指针更有信息量——**这是领先位，不是追赶位**。

但用法要分清（避免自我矛盾）：

- ❌ **不要**把 `relevance × importance × time` 相乘——上一轮实验已证明会降低相关性，且 GA 原文本来就是加权和。
- ✅ **要**把 **provenance 做成乘性门控**：`最终分 = 相关性分 × stance_weight`（fact 1.0 / opinion 0.85 / speculation 0.6 / 未知 0.7），**只门控来源可信度，不参与相关性排序内部的加权**。这正是 §4.4 里"没人做过"的那件事——把 provenance 从指针升级成带权标签。

### 6.3 设计文档与实现的四个偏离

1. **v2 §3.4 要求"自动注入严格、工具召回宽"，实现里自动注入已经是四路混合**（语义 0.42 阈值 + 2-gram + BM25 + 日记），比设计更"宽"。

### 6.5 值得记一笔的实现细节（正面）

- **L3 写入是三重防线的**：`persona_versions.py` 先落 prepared 意图再改文件（`:92-113`）、三重陈旧检查（文件仍等于 expected_before、版本号未重用、来源仍 active）、recover 幂等前滚、revert 只能回滚未变的顶端。这比多数论文的实现更严谨。
- **L1 的 scope 隔离**是正确的：`.l1.<scope>.json` 按渠道分文件，注释明确"owner 的 L2 可以共享，滚动窗口不能"（`target_memory.py:401-405`）。
- **载体写入有账**：`carrier_events` 先 `begin(pending)` → 变更 → `finish(committed/refused/failed)`；实测 committed 44 / refused 105，失败只报"不要自动重试"。
- **向量实现干净**：bge-small-zh-v1.5 / CPU / **DIM=512** / mean-pool + L2 norm / max_length 256；scope 分 `l2` 与 `l2@<stem>`。
- **PPR 参数明确**：`alpha=0.85`、networkx 默认 100 次迭代 / 1e-6、`top_k=8`、排除种子（`associations.py:34-38`）。
- **注入侧有硬不变量**：`PromptFrame.request()` 强制首条必须是 system，且 `messages[1:]` 里**出现任何 system/developer 就抛异常**（`prompt_structure.py:51-58`）——检索到的记忆文本**永远不能变成指令消息**。这条防线比很多论文的"trust boundary"更硬，别拆。

## 9. 如果只做一件事
**把 `stance` 接通，并让它在检索时做乘性门控。**

理由是三重的：

1. **它是空白的对面**。2026 年所有主流系统都停在"时间戳"或"episode 指针"；CogMem 的 Claim/Fact 分离是最接近的，但它只做**分类**，YHLZ 的 fact/opinion/speculation 是**分级**。做出来就是领先位，不是补课。
2. **它一次修三个病**：注入侧看不出真假（R1）、自产日记被当事实（上一轮 P1-7）、以及"重要度挤掉相关性"（有了 provenance 门控，权重就不必压在 importance 上）。
3. **成本最低**：一行 INSERT 列 + 一处 source 传参 + 四处前缀改写，约 60 行，不需要新表、不需要模型。

**验收只有一条**：那条"我梦见陪老爹看了海"的日记，第二天不能变成"我们确实看过海"。

> **第二轮补强后的修正**：门控不该是"相关性 × stance"，而该是"0.6·相关性 + 0.4·可信度，可信度里含 stance 权重"，且前置 `relevance < top×0.4` 就丢、跨通道用 RRF 融合。依据是 MemOS local-plugin 的 `ALGORITHMS.md`（§2/§3/§7）与 NEKO 的实践。另：一轮误读已更正——`belief` 在役记忆上是健康的（0.21–0.88，均值 0.45），低值集中在已降权/已归档条目，**不存在"先修 belief"的前置依赖**。见《证据补强_第二轮_20261021.md》。
