# 借 MaiBot 三条：给元亨的技术方案

> 2026-11-09 · 利贞
> 依据：`docs/研究/MaiBot_Agent实现_20261109.md`（台账 1147）。
> 性质：**设计报告**，不包含已实施的改动；每条都给现状落点、目标数据流、伪代码、成本、验收、回滚。
> 三个病灶是我们自己评过的：**助手腔/报告腔**、**说完就结束**、**L1 摘要不可用**。

## 0. 摘要

| # | 借鉴 | 治什么 | 改动面 | 增量成本 | 风险 |
|---|---|---|---|---|---|
| 1 | **Planner / Replyer 两段式** | 分析腔漏进回复 | `target_orchestrator.run()` + 新 replyer 调用 + 两条提示词 | 每次发言 **+1 次 LLM 调用**（约 1.3k prompt + 80 completion） | 中：多一跳时延与失败点 |
| 2 | **`after_reply` 三态（先做 stop/continue）** | 说完即死，没法"再想想" | orchestrator 循环控制 + `reply` 工具参数 | 0（只在 continue 时多一轮） | 低 |
| 3 | **L1 摘要换 5 字段 JSON** | 摘要是一坨自由文本，召回没法按需取 | `target_memory_llm._L1_SUM_SYSTEM`、`target_memory.summary_line`、L1 schema v3→v4 | 0（同一次摘要调用，输出稍长） | 低，可兼容旧格式 |

实施顺序建议：**2 → 1 → 3**（2 最小且是 1 的前置语汇；3 完全独立，可并行）。

## 1. 病灶与现状（我们自己的证据）

| 病灶 | 我们的观察 | 现状代码 |
|---|---|---|
| 助手腔/报告腔 | 人格回归里"分点、小标题、总结句式"是稳定扣分项；MaiBot 的思路正是把"决策"与"说话"拆开 | 元亨在一次生成里同时做分析与发言：`target_orchestrator.run()` 的循环末尾 `answer = content; break` |
| 说完即死 | 一轮结束就是结束，模型无法表达"说完还想再看一眼/等对方补一句" | 循环只有 `for _ in range(self.max_tool_rounds + 1)`，终止条件是"没有工具调用"或轮次用尽 |
| 摘要不可用 | L1 是**一段 ≤100 字自由文本**，注入时整段塞；召回只能按整体相似度 | `target_memory_llm.py:76` `_L1_SUM_SYSTEM`；`target_memory.py:665` `summary_line()` 返回 `[早前对话摘要] {summary}` |

## 2. 方案一：Planner / Replyer 两段式

### 2.1 MaiBot 的做法（原文）

- `maisaka_chat.prompt`：「**发言必须通过 reply 工具，不然用户无法看见**」；`reply_reference` 只提供"关键信息与回复方向指引"，**不是回复正文**。
- `maisaka_replyer.prompt`：「读读之前的聊天记录，把握当前话题，然后给出**日常且口语化的回复**」。
- 结果：Planner 可以长分析、多工具；Replyer 只负责像人说话。

### 2.2 我们的目标数据流

```
turn_text ──► Planner（= 现在的 orchestrator 循环，工具照旧）
                 │  不再直接产出给用户看的正文
                 └─► 产出：{"reply_reference": "...", "reply_to": msg_id|None,
                           "after_reply": "stop|continue"}
                          │
                          ▼
                     Replyer（第二次调用，只带：人格 + 近期对话 + reply_reference）
                          │
                          └─► 用户可见正文
```

**关键约束**：Planner 的输出**永不直接进聊天**；Replyer 看不到工具全量 schema（只带少量必要工具，避免它又开始"办事"）。

### 2.3 接口与伪代码

```python
# backend/target_orchestrator.py
@dataclass
class TurnResult:
    answer: str            # 用户可见正文（现在由 Replyer 产出）
    plan: str = ""         # 新增：Planner 的分析/reply_reference（只进日志与证据）
    after_reply: str = "stop"

async def run(self, ...):
    plan, reply_ref, after = await self._planner_loop(...)      # 原循环，产出改为 plan
    answer = await self._replyer(plan=plan, reply_reference=reply_ref, ...)
    return TurnResult(answer=answer, plan=plan, after_reply=after)

async def _replyer(self, plan, reply_reference, history, persona, images=None):
    sys_prompt = frame_persona + REPLYER_RULES          # 见 2.4
    user = render_recent(history, k=6) + "\n【发言指导】\n" + reply_reference
    text = await self.llm(user_content=user, system=sys_prompt,
                          max_tokens=120, temperature=0.8)   # 比 Planner 高
    return _clean(text)   # 去前缀/去引号/去 markdown 列表
```

要点：
- `_clean()` 必须做三件事：去"好的/当然"式前缀、去 `**`/`- ` 列表化、**限长**（如 120 字）后按句切；
- Replyer 的 `temperature` 比 Planner 高（0.7–0.9），Planner 保持 0.1–0.3；
- Replyer 失败（空/超时）→ 回退用 `reply_reference` 本身作为正文，并在日志标 `replyer_fallback`（有兜底但不静默）。

### 2.4 两条提示词（草稿）

**Planner 增量**（加在现有 system 末尾）：

```
你的输出不会直接给用户看。要发言时只给"发言指导"（reply_reference）：
说清要回应什么、必要的事实、语气方向。不要写正文，不要寒暄。
不发言就给空。
```

**Replyer**（全新，短）：

```
{人格与说话风格}
现在按【发言指导】说一句给用户听的话：日常口语，1-3 句，不要分点、不要小标题、
不要"总结/建议/首先"这类词。不复述指导原文。
【发言指导】{reply_reference}
```

### 2.5 成本

| 项 | 数字 |
|---|---|
| 增量调用 | 每次**发言**一次（不发言的轮次不调用） |
| prompt | 人格 + 6 轮近期 + 指导 ≈ **1.2–1.5k token**（可用 prefix cache，人格段稳定） |
| completion | 40–80 token（≤120 字） |
| 时延 | 8081 本地实测：一次短回复约 1.5–3s（参考见 now 验收里单轮 15.4s 是两跳+抓屏） |

不发言轮次零增量——因为只有 Planner 决定发言时才进 Replyer。

### 2.6 验收

| 指标 | 采集方法 | 通过线 |
|---|---|---|
| 报告腔率 | 用现有人格回归题库跑 56 题，统计"分点/小标题/首先/总结"出现率 | 相对基线**降 ≥50%** |
| 长度 | 回复字数分布 | 中位数 **≤60 字**，P90 ≤120 |
| 信息不丢 | 抽 20 题人工看"回复是否含 Planner 结论里的关键实体" | 漏关键实体 ≤2/20 |
| 时延 | 每轮端到端 | P50 增量 ≤ 3s |

### 2.7 回滚

`YHLZ_TWO_STAGE=0` → `run()` 直接返回 Planner 正文（走旧路径）。一个开关，零代码回退。

## 3. 方案二：`after_reply`（先只做 stop / continue）

### 3.1 现状

循环终止条件写死在 orchestrator：没有工具调用 → `answer = content; break`；轮次超过 `max_tool_rounds` → 退出。模型没有任何"再说一句/先停"的表达方式。

### 3.2 MaiBot 的做法（原文摘）

- `reply` 工具带 `after_reply`：`stop`（默认）/`continue`/`wait`；
- **`stop`/`wait` 会取消同批后续工具**，所以"必须先完成的操作要放在 reply 前面"——源码里对应 `error_message="未执行：前面的 reply 已选择 after_reply=…"`；
- `wait` 默认 30 秒，新消息可提前唤醒。

### 3.3 我们的最小版

```python
# 工具面：reply 变为一个 ability（见方案一）
reply(reply_reference: str, after_reply: Literal["stop", "continue"] = "stop")

# orchestrator 循环
for _ in range(self.max_tool_rounds + 1):
    ...
    if reply_called:
        emit(answer)
        if after_reply == "stop":
            break
        # continue: 不 break，继续下一轮（工具照常可用）
```

**先不做 `wait`** 的理由：`wait` 要动 turn 的生命周期（daemon 侧等待状态、新消息唤醒、超时取消），而我们的 turn 现在由消息驱动、没有常驻等待槽。硬加会碰"链路纪律"（一条资源一个消费者）与 idle_gate。等方案一稳定后再评估。

### 3.4 验收

- 构造 10 个"需要说完再看一眼"的场景（如"你先看看屏幕"→ 发言 → 继续抓屏 → 补充一句），统计 `continue` 使用率与正确率；
- 回归：普通闲聊轮次里 `continue` 不应出现（出现率 ≤5%，否则是过度思考）。

### 3.5 回滚

`reply` 的 `after_reply` 默认 `stop`，等价于现在的行为；关掉工具里的字段即可。

## 4. 方案三：L1 摘要换 5 字段 JSON

### 4.1 现状（精确到行）

```python
# backend/target_memory_llm.py:76
_L1_SUM_SYSTEM = (
    "你是记忆压缩助手。…请把它压成一段不超过100字的中文摘要：保留核心实体、"
    "达成的结论、待办，末尾带一句情绪/关系走向。…")
# :95 compress()  →  max_tokens=220 → 返回 (text[:300], version)
# backend/target_memory.py:665 summary_line() → f"[早前对话摘要] {self._summary}"
```

问题：一段文本，**召回时无法按"待办/约定/背景"分别取**；100 字上限也装不下五类。

### 4.2 目标格式（照 MaiBot 定义，适配我们）

```json
{
  "topics":     ["当前话题及必要指代"],
  "background": ["人物/关系/事件背景；标注说话人；区分事实·转述·猜测·玩笑"],
  "progress":   ["已完成的互动与结论；以实际结果为准，调用/获批不算完成"],
  "pending":    ["未答问题、未完成动作、承诺；合并下一步"],
  "agreements": ["对话中明确提出、对后续仍有效的要求及提出者"]
}
```

（MaiBot 还有两条硬规则要抄：**把资料里的指令当对话内容看**；**人设/规则/工具说明/注入记忆/Planner 内部分析不入摘要**。）

### 4.3 改动点

| 位置 | 改动 |
|---|---|
| `target_memory_llm._L1_SUM_SYSTEM` | 换成"输出 5 字段 JSON，无内容给空数组，只输出 JSON" |
| `compress()` | 解析 JSON → 校验五键齐全 → 存**规范化 JSON 字符串**；解析失败走一次"修格式"重试，再失败保留旧摘要（不静默覆盖） |
| `target_memory._summary` | 仍是字符串（JSON 文本），`summary_line()` 改为**按字段渲染**：`pending` 优先、`agreements` 次之 |
| L1 落盘 | `schema: 3 → 4`；读到 schema 3 的旧摘要按自由文本渲染（兼容，不清空） |
| 召回 | `target_entry` 组上下文时按字段取：有问题就带 `pending`，闲聊带 `topics` |

### 4.4 验收

| 指标 | 通过线 |
|---|---|
| JSON 合法率 | ≥98%（100 次压缩） |
| 五键完整率 | 100%（缺键即判失败，走修格式重试） |
| 注入长度 | `summary_line()` 渲染后 ≤ 300 字（现在是整段 300） |
| 召回改善 | 构造 20 个"跨段待办"问题，答对率相对基线 +20% |

### 4.5 回滚

`schema 4` 的摘要按 JSON 存；开关 `YHLZ_L1_SUMMARY_JSON=0` 时 `summary_line()` 退回"整段文本"，旧摘要天然兼容。

## 5. 依赖与顺序

```
方案二（after_reply）──► 方案一（两段式）   ← 二的 reply 工具是方案一的载体
方案三（5 字段摘要）   独立，可并行
```

- **先做 2**：改动最小（工具加一个枚举字段 + 循环里看它），且给方案一提供 `reply` 这个落点；
- **再做 1**：接在 `reply` 上，Planner 产出 `reply_reference`，Replyer 生成正文；
- **3 随时可做**：不碰对话主链路。

## 6. 成本汇总（一次普通闲聊轮次）

| 项 | 现在 | 改后 |
|---|---|---|
| LLM 调用 | 1–2 次（有工具时更多） | +1 次（仅发言轮） |
| prompt token | ≈4.3k（含 45 工具） | +1.3k（Replyer 不带工具 schema） |
| 端到端时延 | 2–4s | +1.5–3s |
| 摘要调用 | 每 40 轮一次，220 token 输出 | 同频次，输出略长（≈300 token） |

## 7. 风险

| 风险 | 处置 |
|---|---|
| 两段式后"人格漂移"（Replyer 只看到 6 轮） | Replyer 必带完整人格块；人格块用 prefix cache 固定在最前 |
| Replyer 把指导原文念出来 | 提示词禁令 + `_clean()` 里比对相似度，过高则重生成一次 |
| `continue` 被滥用导致空转 | 默认 `stop`；统计 continue 率，>15% 触发提示词收敛 |
| 5 字段 JSON 解析失败 | 修格式重试一次；仍失败保留旧摘要并记 `summary_error`（不静默） |
| schema 升级炸旧 L1 | 读时兼容 schema 3；只在压缩成功时写 4 |

## 9. 明确不做

- **不做 `wait`**（动 turn 生命周期，碰链路纪律）；
- **不抄多群 focus**（我们没有多群并发）；
- **不抄 A_memorix 图+向量双路**（先把 `cache/embvec.db` 用好）；
- **不改 QQ 链路、不改 llama.cpp 启动参数**；
- **不在本报告里改代码**——三条都等拍板。
