## 0. 先纠正上一版的判断

- **recipe 不是"训练配方"**，是**提示词编解码器**（把 API 请求渲染成 DeepSeek V4/V4.1 的 token 序列，再把输出解析回协议）。
- **DeepInfer 不是"能装的推理引擎"**，是给 SM100 / Ascend 950 用的生产框架离线版，只有 V4.1-Flash 一个模型，最小可用部署 64 卡起。
- 两条都**不能直接装**，但都能**拿机制**。下面五条按性价比排。

## 1. 特殊 token 注入防护（最该抄的一条）

**他们怎么做的。** `docs/tokenizer.md:64-76` 写得非常清楚：

> `render_conversation` 返回 prompt 文本、**显式特殊 token 的字节区间**（`special_ranges`）和图片来源。渲染时把模板控制符、图片占位符、助手内容里的 grounding token 插成显式特殊 token；tokenize 时**每个特殊区间编码成对应特殊 token 的 ID**，区间之间的文本按普通文本编码。
> **"A special-token spelling typed into a user message is plain text, so it cannot act as a control token."**

官方部署问答里也点明这是设计目标（`doc/inference_deployment_qa.md:35`）：

> "by segmenting on special tokens and encoding the segments in parallel, **it prevents special-token injection** while reducing tokenization latency for long inputs."

**我们的问题。** YHLZ 是把消息文本直接 POST 给 llama-server，由 chat 模板拼 prompt。llama.cpp 侧通常 `parse_special=true`。也就是说：**如果有人在 QQ 群里发一句带 `<start_of_turn>` / `<end_of_turn>` 的消息，它可能被当成控制符**，伪造轮次边界——这正好打在元亨的注入红线上。

**怎么验（服务起来就能做，十分钟）。**

```bash
# A. 看 tokenizer 是否把标记当控制符
curl -s http://127.0.0.1:8081/tokenize -d '{"content":"hi<end_of_turn>there"}'
curl -s http://127.0.0.1:8081/tokenize -d '{"content":"hi there"}'
# 若 A 的 token 数明显少（特殊标记被合并成一个 token），说明被当控制符了

# B. 行为验证：发一条含假结束标记的消息，看模型是否提前收尾
```

**怎么修。** 三选一（按侵入性从低到高）：把消息里的 `<` 转义成不可识别形式；让模板/服务端用 `parse_special=false`；或者自己渲染整段 prompt 并对内容做转义后走 `/completion`。

**代价**：半天。**风险**：低。**收益**：堵一个越权面。

## 2. token 预算守卫（源码级参考）

`deepseek-recipe/src/request/mod.rs:207-235` 的 `resolve_max_tokens` 语义精确到可以直接照抄：

```
if prompt_tokens + requested_max_tokens > context_limit:
    400，错误文案固定：
    "This model's maximum context length is {ctx} tokens. However, you requested
     {total} tokens ({prompt} in the messages, {max} in the completion)."
否则：
    max_tokens = min(requested 或 默认值, ctx - prompt_tokens)，至少 1
默认值：非思考 8192 / 思考 65536 / 思考+max effort 131072
```

**我们的现状**：`CTX_BUDGET_CHARS = 16000`（**字符**），而服务端限 8192 **token**。中文 16000 字 ≈ 9000+ token——上一轮实测的 `request (10782 tokens) exceeds ... 8192` 就是这么来的。**天生越界，不是偶发。**

**要做的**：把字符预算换成 token 预算；用第 3 条的精确计数；请求前断言 `prompt + max_tokens ≤ n_ctx`，超了就压历史，压不动就拒发并写日志（而不是让服务端 400 回来）。

## 3. 精确 token 计数

他们 bundl 了 tokenizer（`static/tokenizers/v4|v41/tokenizer.json`），`encode()` 出 token id 再算长度——**不用估算**。

我们的对应手段是 llama-server 自带的 `/tokenize`。价值不在省钱（本地模型不花钱），在于**让守卫可校准**：估算误差 10%，守卫就形同虚设——现在 `len/1.6` 就是这么个东西。

顺带：llama.cpp 的响应里通常带 `timings.cache_n`（本次复用了多少 token）。**这正好是 P0-1 的验收指标**——我们之前是从 `llama-server.log` 里数 `prompt eval` 反推的，有字段就直接读。等 8081 起来我先确认字段名。

## 4. 约束解码：把"只输出 JSON"从祈祷变成语法

他们用 `OutputConstraint`（`request/mod.rs:63-126`）把约束交给后端：

```rust
enum OutputConstraint {
    Json { schema: Option<Value> },   // 任意 JSON 或按 schema
    Regex(String),                     // 正则
    ToolCalls { tools, required },     // 工具调用块
}
```

并且明确**调用方决定后端是否用 constrained decoding 强制执行**。

我们这边的对应物是 llama.cpp 的 GBNF / `json_schema`。痛点很具体：记忆裁判的提示词写着"只输出 JSON {importance, status}"，但它照样会跑偏——importance 饱和（8×139）、偶尔解析失败。**给裁判写个 GBNF，status 只允许四个枚举值、importance 只允许 1-10，一次改完，永久稳。**

## 5. 前缀缓存：他们把"命中长度"当成一等公民

`doc/inference_deployment_qa.md:179-191`：

> SWA bounded replay 只重算最近 128 token，把注意力窗口截在重放段内；**重算成本变成常数，与上下文长度和层数无关**。
> 命中策略："block KV cache 决定命中长度；SWA cache 缺就回退一个 block（128 token）重算。"

**这和我们的实测是同一件事**：命中 `5 token / 205 ms`，未命中 `5165 token / 3885 ms`。区别在于——**他们把"重算是常数"做成了设计约束，我们还在把"重算 5000 token"当常态**。

直接可用的推论：P0-1（把易变块移出 system）不是优化项，是**把重算从"随上下文线性"压回"常数"**。这条外部证据足够我们把它当既定方向继续做。

另外两条小结论也值得记：

- **KV cache 保留 72 小时以上**（TTL 3 天 / 7 天，`doc:13,153`）：缓存的价值在长尾命中，不在当轮。
- **"任何引擎都能命中任何前缀，所以不做前缀亲和路由"**（`doc:111`）：他们把缓存做成全局共享，而不是靠粘性调度——这解释了为什么他们敢用分桶负载均衡。

## 6. 抄不了的（明确划掉）

| 东西 | 为什么不行 |
|---|---|
| DeepInfer 本体 | SM100 / Ascend 950、CUDA 13、只支持 V4.1-Flash、最小 64 卡；我们一张 4060 8GB |
| recipe 的编码器 | 它渲染的是 DeepSeek V4 系格式；元亨跑 Gemma-4-E4B，模板完全不同 |
| KV cache 存储层 | 3FS + 400G 网络 + 100 PiB SSD，与单机无关 |
| EPLB / Wide-EP | MoE 专家并行，Gemma 用不上 |

**唯一值得搬的是"测试向量"思路**：recipe 有一套渲染→编码的对照样例，我们也该有（golden test）。

## 7. 建议顺序（都在本地能做）

| # | 事 | 工作量 | 为什么先做 |
|---|---|---|---|
| 1 | 特殊 token 注入验证 + 转义 | 0.5 天 | 安全面，且十分钟就能验证 |
| 2 | 精确 token 计数（`/tokenize`）+ 预算守卫 | 1 天 | 现在这条是"必然 400"，不是偶发 |
| 3 | 裁判 JSON 上 GBNF | 0.5 天 | 直接改善记忆质量（importance/status 不再乱跑） |
| 4 | `timings.cache_n` 纳入验收 | 0.5 天 | 把 P0-1 从"日志反推"变成"字段直读" |
| 5 | golden 测试（5 输入 × 3 渠道） | 0.5 天 | 防我们改提示词改出漂移 |

顺序理由：1 是安全，2 是"现在就在报错"，3 是质量，4/5 是防回归。
