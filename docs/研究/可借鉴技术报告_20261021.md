## 2. P0：今天就能动

### P0-1　把易变上下文搬出 `system[0]`，让提示词前缀稳定

**来源（两端都有证据）**
- lianlian：`core/llm.py:170-178`，消息顺序 `history → [system:hint] → [system:记忆块] → user`，注释直接写"放在历史之后：前缀不变，KV 缓存照样命中"；只重算约 0.26s。
- CX-O：`docs/technical.md:225`，实时语音专用瘦身 prompt 省 ~1500 token prefill（100-200ms）。

**YHLZ 现状（已核实）**
- `backend/target_entry.py:732`：把每轮都在变的 `ctx_lines`（回忆/画像/图谱/PPR/社区/内在因/KB/待批清单）拼成 `early_context`。
- `backend/target_orchestrator.py:345-347`：`PromptFrame(system_prompt, early_context[:1500])` → **整条 system[0] 每轮都变** → 前缀每次都断，KV/prefix cache 基本白扔。
- `backend/prompt_structure.py:25-30`：`PromptFrame.render()` 是唯一渲染入口（好消息：只需改一处）。

**做法（不改语义，只改位置）**
1. `PromptFrame` 拆两个出口：`render_static()`（人格+规则+工具纪律，逐字稳定）与 `render_dynamic()`（early_context）。
2. `target_orchestrator.py:346` 只把 `render_static()` 放进 system[0]；把 `render_dynamic()` 作为**追加的第二条 system 消息**放在 `history_tail` 之后、`current_user` 之前（`:365-366`）。
3. 多轮工具调用循环（`:412-492`）中，这条动态 system 的位置必须固定，不要每轮重排。
4. 记忆块**不要写回 history**（lianlian 的做法），否则下一轮它又变成前缀的一部分。
5. **配套做前缀预热**：启动时用同一段静态前缀发一次极短请求（`max_tokens=1`）灌进 KV/prefix cache。CX-O 实测：语音 system 前缀预热后 TTFT **444ms → ~30ms**（一次 warm 约 2747 tokens，`server/main.py:839-852`）。**预热必须预"同一段前缀"，否则等于白 warm。**

> **补充一条 CX-O 的实测经验**：vLLM 的 prefix cache 有个**最小前缀门槛**（该项目的实测是 <353 token 不命中），所以它故意用 `REALTIME_VOICE_PROMPT_PADDING` 把 system 段补到 ≥360 token，TTFT 240ms→60ms（`docs/technical.md:225` 与 `server/prompt_builder.py`）。YHLZ 现在用 llama.cpp，门槛机制不同（按最长公共前缀算），但**结论一致：静态段要够长、且必须稳定**。若哪天切 vLLM，这条要重新测门槛。

**验收**
- llama-server 侧看 slot 复用/`n_past`：第二轮起 prefill token 应只剩"动态块 + 本轮话"。
- 已有 `voice_trace.py` 打点：首 token 延迟 P50 应下降；用 `tools/persona_regression.py` 跑一遍确认人格不漂、记忆宣称守卫仍生效（因为记忆块的措辞与位置变了，`target_prompts.py:320-329` 的边界说明要跟着检查）。

**本机实测（2026-10-21 补）**：`cache/logs/llama-server.log` 里同时有两种形态——

- 命中缓存：`prompt eval time = 205.29 ms / 5 tokens`（只评估新增 5 个 token）
- 未命中：`prompt eval time = 3885.51 ms / 5165 tokens`（整段重算）

**同一条链路上差 3.7 秒。** 启动参数（`tools/yhlz_launcher.py:184-194`）没有关闭 prompt cache，所以这不是配置问题，是前缀本身每轮都在变。详见《证据补强_第二轮_20261021.md》§1。

**风险**：`prompt_structure` 可能有顺序契约（`test_prompt_structure.py`）；动态块后置后，模型对"记忆 vs 指令"的权重会变化——必须先跑人格回归，再上线。
**工作量**：0.5-1 天（改动小，验证重）。

### P0-2　在 token→TTS 之间加一层 30ms 文本平滑

**来源**
- CX-O：`docs/technical.md:227` `TextSmoother.smooth(llm_stream, window_ms=30, char_threshold=2)`，把 1-2 字碎片聚成 3-5 字词组，用 ~40ms 换音质；C4 优化把窗口从 40ms 调到 30ms。
- lianlian：`core/voice_chat.py:44-76` 的三级切句（硬标点≥2 字 / 软标点≥16 字 / 40 字硬切）。

**YHLZ 现状（已核实/待核实）**
- `target_chain.py:962-1005` 已是"文本 chunk → 语音 generator → AudioChunk"结构（有流式）。
- **未见**专门的"碎片聚合"层（`grep smoother` 无命中）→ 待核实：TTS provider 内部是否已经按句聚合。

**做法**
1. 在 `target_chain._run_turn_with_tts_provider` 的文本流与 `speech_generator` 之间插一个 `TextSmoother`：累积到"标点 或 ≥N 字 或 距上次提交 ≥30ms"才提交。
2. 阈值照抄可用默认：`window_ms=30`、`char_threshold=2`，硬上限 40 字（lianlian 的 `MAX_CHUNK`）。
3. 保留"首句优先"：第一句用更激进的阈值（2 字或首个硬标点），先出声再走稳态。

**验收**：同一段回复的 TTS 请求数下降 ≥30%，首包延迟不退化（±20ms 内）。
**风险**：聚合会让"边说边出"变成"顿一下再说"，需现场听感确认；TTS 若本身按字合成，聚合收益就小。
**工作量**：0.5 天。

### P0-3　把延迟做成"可判定验收"，而不是文档里的目标

**来源**
- CX-O：`docs/technical.md:273-285` 硬验收 = **P95<800ms 且连续 6 轮 × 每轮 10 次全部达标**（spec `optimize-ws-full-link-sub-800ms`），从 P50~1300ms 优化到 449-610ms。
- lianlian：`core/voice_chat.py:491-492` 的 `[首句出声 x.xxs | 整轮 x.xxs]`，`DEBUG_LATENCY` 默认开。

**YHLZ 现状（已核实）**
- 有 `voice_trace.py`、`target_probe.py`、`target_realtime_probe.py`、`target_echo_chain_probe.py` 等埋点/探针。
- `docs/` 里有目标（如"首 PCM 到 OBS p95≤300ms"），但**没有一键跑 N 轮并判定的闸门脚本**。

**做法**
1. 写 `tools/voice_latency_gate.py`：驱动 `target_chain` 跑同一组 10 条短句 × 6 轮（可 mock TTS，也可真跑），从 voice_trace 读 T0/T1/T2，输出 P50/P95/P99 表，超阈值 **退出码 1**。
2. 阈值先"建基线"再"定目标"：第一版只打印不判定，第二版才卡（避免一上来就红）。
3. 挂进 `backend/test_target_chain.py` 的慢测分组，或做成 `YHLZ_workbench` 的一个按钮。

**验收**：`python tools/voice_latency_gate.py --rounds 6 --per-round 10` 能稳定给出 P50/P95；任一环节劣化能让 CI 变红。
**风险**：真跑 TTS 占显存、耗时；建议第一版用 mock provider 测"链路开销"，真跑单独跑。
**工作量**：1 天。

### P0-4　给"本地回环"加一条代理免疫断言（便宜、防大坑）

**来源**
- CX-O：`server/main.py:13-50`，httpx 在 Windows 上读系统代理导致本地请求被绕进代理；`trust_env=False` 与 `proxy=None` **必须同时设**；实测 **23553ms(502) → 14ms**。

**YHLZ 现状（已核实）**
- 本机确实设了代理：`HTTP_PROXY=HTTPS_PROXY=http://127.0.0.1:7897`，系统代理 `ProxyEnable=1`。
- 目前**是安全的**：`NO_PROXY=localhost,127.0.0.1,::1,...` 覆盖了回环地址；项目还有 `backend/test_proxy_env.py` 做回归，`env_loader.py:22` 明确"HTTP_PROXY 等一律不动"。
- 但 `search_crawler.py:59` 与 `target_access.py:305,405` 都是 `httpx.Client(trust_env=True)` 语义——**只要 NO_PROXY 被清空、或改用主机名/局域网 IP 访问 daemon，就会立刻复现 23 秒级延迟**，而且症状是"偶发 502 / 特别慢"，极难归因。

**做法**
1. 在 `test_proxy_env.py` 里补两条断言：① `NO_PROXY` 必须含 `127.0.0.1` 与 `::1`；② 对 `127.0.0.1:8081` 发一次请求，耗时阈值 <100ms。
2. 对**纯本机调用**的客户端（daemon 8321、llama 8081、TTS 进程）显式 `trust_env=False`（不要依赖环境变量正确）。
3. 在 `voice_trace` 或 watchdog 里加一条"本地请求 >1s 计数"，超阈值打印代理配置快照。

**验收**：清空 `NO_PROXY` 跑测试 → 应该**红**；恢复后应该绿（证明断言真的在守）。
**风险**：无（只是收敛依赖）。
**工作量**：0.5 天。

## 3. P1：一周内

### P1-4　打断后轮次完整性：assistant 缺位要有占位

**来源**
- CX-O：`docs/technical.md:199` 取消时把用户已说文本**累积到 pending 供下一轮合并**，不丢内容。
- lianlian 的反例：`core/llm.py:190-193` history 在流正常结束后才追加 → 被打断那轮**永久丢失**（见全量报告 §2.11 #10）。

**YHLZ 现状（已核实）**
- `target_entry.py:459` 在调 orchestrator **之前**就 `append_turn(role="user")` —— 比 lianlian 好，用户话不会丢。
- `target_entry.py:758` assistant 在 `orchestrator.run` 返回后才追加 → 被打断时会出现**连续两条 user**、中间没有 assistant 的畸形历史。

**做法**
1. 捕获取消后，补一条 assistant 占位（如"（被打断）"），或把该轮标记 `interrupted=True` 让 `_clean_history()`（`target_entry.py:730`）过滤掉未完成的半轮。
2. 若采用 CX-O 的 pending 语义：把被取消轮的用户文本并入下一轮的 `turn_text`（注意去重），而不是留成孤立 user。

**验收**：连续打断 10 次后，`cache/sessions/*.json` 里不出现连续 user；下一轮模型不重复回答上一轮。
**风险**：占位文本会进记忆摘要 → 要确保不参与 L2 候选（`memory_judge`）。
**工作量**：0.5 天。

### P1-5　"AI 是否该插话"的三态判定（先只做闸门，不做打断）

**来源**
- CX-O：`docs/technical.md:201-219` 三态 `INTERRUPT/CONTINUE/IGNORE` + 提问意图硬闸门 `_has_question_or_request` + 固定搭配剔除 + `REPLY_CONFIRM_S=0.5` 停顿确认。

**YHLZ 现状（已核实，且有一道硬约束）**
- `backend/streaming_asr_bridge.py:1-7` 明确写着：**partial 文本"故意"不允许进入 wake gate / SessionKernel / reasoner / memory / telemetry**，只有 VAD 段边界的 final 才能进链。
- 这条约束是对的（安全性、可复现性），不要为了延迟破它。

**做法（在约束内取收益）**
1. 只在**本地**用 partial 做一件事：判断"这句是不是提问/请求"（提问词 + 祈使词 + 固定搭配剔除），命中就**缩短静默判定**（提前 end-of-turn），不把 partial 送进任何下游。
2. 判定结果只作为一个布尔 + 计时信号进 `barge_in`/VAD 层，最终仍以 final 为准；final 到达后若与判定不一致，以 final 覆盖。
3. 不采用 CX-O 的"让 LLM 在 partial 上开始生成"——那会破坏 YHLZ 的隔离不变量。

**验收**：短句提问（"在吗""帮我查一下""你今天怎么样"）从说完到首字的时间下降；误触发率（把陈述当提问）<5%，用 50 条真实语料回归。
**风险**：提前结束 VAD 判断可能截断长句 → 必须有"final 到达后合并"的兜底。
**工作量**：1-2 天。

### P1-6　记忆打分：从加权和改成乘性门控 + 场景权重

> ⚠️ **2026-10-21 研究更新：本条结论已被修正，请以 [P1-6_P1-7_研究报告_20261021.md](./P1-6_P1-7_研究报告_20261021.md) §2 为准。**
> 核实后：YHLZ 的召回**不是加权和**，是纯 BM25 关键词序，importance/时间未被使用；且 importance 有 139/176 全为 8、confidence 最多 5 条同分、因果度全 0 —— **此时套乘性公式会降低相关性**（实验出现"高重要度挤掉高覆盖度"的反例）。真正要做的是：先统一相关性口径 → 修信号 → 再分带门控。

**来源**
- CX-O：`docs/technical.md:409` `final = relevance × (w_i·importance + w_t·time)/(w_i+w_t)`，相关性为乘性门控（为 0 则整条 0，重要度无法补偿）；`:412-420` 七种场景的权重表。
- lianlian：`core/memory.py:35` `0.75·sim + 0.15·recency + 0.10·importance`（纯加权和，简单但可被重要度"冲"掉相关性）。

**YHLZ 现状（待核实）**
- `target_memory.py`（2154 行）有显著度/衰减/召回（`salience`、`decay` 命中），但打分公式未逐行确认。

**做法**
1. 先读 `target_memory` 的召回打分，若已是"相关性×其余"的门控形式，本条跳过（记为"已有"）。
2. 若是加权和：把相关性提为乘数，保留 importance/time 的加权部分；再引入**场景权重表**（对话/任务/回忆三类先做，别一次上七类）。
3. 场景判定用现成的信号（是否带工具调用意图、是否有明确问题、是否是主动搭话），不要新起一个分类模型。

**验收**：`python tools/memory_eval.py scenes` 与 `locomo` 两个集不退化；人工抽 20 条"重要但不相关"的记忆确认不再被塞进上下文。
**风险**：乘性门控会让召回变少（相关性低一分就归零）→ 先只对"非永久记忆"生效，永久记忆留白名单。
**工作量**：1 天（含评测）。

### P1-7　给"自产内容"加非事实位（梦境红线的迁移）

> ⚠️ **2026-10-21 研究更新：机制已存在，只需接线，详见 [P1-6_P1-7_研究报告_20261021.md](./P1-6_P1-7_研究报告_20261021.md) §3。**
> `stance ∈ {fact, opinion, speculation}` + `infer_stance()` 早在 A1（台账 0438）就有；缺的是三处：① `adjudicate_async` 的 INSERT 不写 stance（主写入轨）；② 入口传的 `source="review"` 是流程名不是说话人；③ `contextual_recall` / `recall_memory` / 日记注入都不带来源。**不需要新造 `is_ground_truth` 字段。**

**来源**
- CX-O：`docs/technical.md:993-999` 梦境五条红线——`is_ground_truth` 恒 false、禁止 `permanent`、`dream_session_id` 强制、专用 `decay_type`、可回滚。

**YHLZ 现状（已核实）**
- `backend/diary*.py` / `reflection.py` / 主动搭话产出会写记忆（`docs/元亨的日记.md` 26KB、成长日志 148KB 都是自产）。
- `target_prompts.py:327-329` 已有"记忆宣称守卫"（无证据不得声称记得）——**这正是"非事实位"的提示词版本**，现在缺的是数据层版本。

**做法**
1. 给记忆条目加两个字段（或 metadata）：`source=generated`（日记/反思/主动搭话/梦境）、`is_ground_truth=false`。
2. 检索时：`source=generated` 的条目**不得**被当作事实陈述的证据（可以进上下文，但要标注"（我写下的想法，不是发生的事）"）；**永久记忆禁止来自 generated**。
3. 与既有守卫联动：`memory_recall` 返回带 `source`，让"记忆宣称守卫"能区分"事实"和"我编的"。

**验收**：构造一条"我梦见老爹带我去看海"的日记 → 第二天问"我们去看过海吗"，回答应是否认或标注为梦，而不是确认。
**风险**：存量记忆没有这个字段 → 迁移时默认 `source=unknown`，按"可作事实但降权"处理，别一刀切。
**工作量**：1 天（含迁移与一条回归测试）。

## 6. 建议落地顺序（两周视图）

| 顺序 | 事项 | 依赖 | 判定标准 | 预估 |
|---|---|---|---|---|
| 1 | P0-1 前缀稳定化（含前缀预热） | 人格回归可跑 | 首 token P50 降 ≥15%，人格回归不回退 | 1 天 |
| 2 | P0-4 回环代理免疫断言 | 无 | 清空 NO_PROXY 时测试变红 | 0.5 天 |
| 3 | P0-2 文本平滑 | 无 | TTS 请求数 -30%，首包不退化 | 0.5 天 |
| 4 | P0-3 延迟闸门 | 有探针即可 | 一条命令出 P50/P95，超阈值退出码非 0 | 1 天 |
| 5 | P1-4 轮次完整性 | 无 | 打断 10 次无畸形历史 | 0.5 天 |
| 6 | P1-6 记忆门控 | memory_eval 可跑 | LoCoMo 不退化 | 1 天 |
| 7 | P1-7 非事实位 | 记忆加字段 | "梦到看海"不被当事实 | 1 天 |
| 8 | P1-5 提问闸门 | P0-3 的计时可用 | 短句提问首字提前，误触发 <5% | 2 天 |

**先做 1-4 的理由**：它们互不依赖、都能用现成探针或测试验证，而且合起来直接决定"元亨说话快不快、稳不稳"。P1 的语义补丁（5/6/7）在 P0 稳定后再动，避免"又慢又改语义"同时上线无法归因。

## 7. 三个可以立刻抄的"小东西"（不超过 20 行）

1. **记忆块抬头**（lianlian `core/memory.py:398-404` 的四条行为约束）：
   「像真人一样自然想起来 / 绝对不要提记忆、系统、数据、设定 / 细节以这里为准不要加戏 / 没写的就是不知道」——比"以下是你记住的事"这种框架化措辞更不容易让模型说漏嘴。
2. **抽取重叠校验**（`memory.py:528-545`）：`len(set(原话字) ∩ 抽取字)/len(抽取字) ≥ 0.45`，否则丢弃。YHLZ 的记忆抽取若还没有这道闸，加上能显著降幻觉。
3. **动作与情绪分类的失败语义**（`core/llm.py:141-164`）：分类调用一律 `temperature=0` + 极短输出 + 失败返回中性值，**永不阻塞主回复**。YHLZ 若在回复后做表情/驱动判断，照这个写。

## 8. 一句话总结

> **YHLZ 不必变成 lianlian，也不必变成 CX-O。**
> 它需要的是：**一处前缀（P0-1）、一层平滑（P0-2）、一把尺子（P0-3）**，
> 以及两条语义补丁（轮次完整性、自产内容非事实位）。
> 其余的 23 万行，读它是为了知道"边界长什么样"，不是为了搬过来。
