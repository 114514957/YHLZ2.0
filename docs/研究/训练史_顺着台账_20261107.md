## 二、三段式看：每次"换条路"的原因

### 阶段一：QAT 期（09 月，v4–v7b）
- 起点很扎实：先解决**基座同源**（0388），再跑 SFT+DPO，v6 就把工具发射率做到 **10/10**。
- **v7b 是这段的顶点：41/56，而且 adapter 有 133 MB（训了 MLP 7 个模块/层）。**
- 短板也很清楚：**风格 0/8**。

### 阶段二：Qwen 期（10 月底–11 月初，v9t–v9t4）
- 换 Qwen3-4B 做**全参微调**（不是 LoRA）：473 步 → v9t 30/56，v9t4 到 36/56。
- 这段解决了**风格**（3/8→5/8）和**工具**（7→13），但人格/关系一直上不去。
- 代价：全参 7.5 GB，本地跑不动，只能云端。

### 阶段三：gemma 期（11-01 至今，v9t5–v9t8 + blend）
- 回 gemma，**但踩了 1049 记下的那个坑**：在普通基座上 PEFT 只认 attention，训不了 MLP。
  - 于是 gemma v1/v2/v3 三连败（**25 → 21**），比 QAT 期的 v7b（41）差一大截。
  - 1049 已经把根因写清楚了：**v7b = QAT 基座 + MLP；我们 = 普通基座 + 只有 attention**。
  - **但之后没有回去补这一课**——v9t5/v9t6/v9t7/v9t8 全部只训 attention（adapter 都是 36,346,288 字节）。
- 在这条"缺 MLP"的路上，做到的最好是 **v9t6 的 46**（人格 19/20）。
- 之后两版（v9t7 45、v9t8 42）都是"修一个病、掉另一处"。

## 三、三个反复出现的模式

1. **换基座 = 重新开始**
   三次换基座（QAT→普通 gemma→Qwen→回普通 gemma），每次都把已有的进展作废一遍，
   而"基座必须与部署同源"这条（0388）只有 QAT 期真正执行过。

2. **修一个病、掉另一处**
   v9t7 修 g09 → 身份回退；v9t8 修 g18 → 工具掉 2。
   机制上：每版都是**全量重训 1 epoch**，没有 replay、没有正则，新样本必然挤掉旧能力。

3. **判据一直在动**
   判据从 v1 改到 v6。台账里至少 3 次"进步"是尺子变了：
   v9t6 42→46、v8 43→37、v7b 35→34。**跨判据比分数等于比两把尺子。**

## 四、⭐ 一个被记下来、但没被执行的发现

1049（11-01 晚）已经写清楚：

> v7b 训了 MLP（7 模块/层，133 MB）；我们只训 attention（4 模块/层，34.7 MB）；
> 而且基座不同（QAT vs 普通），PEFT 拒普通版的 `Gemma4ClippableLinear`。
> **"今天三次尝试方向都对，但基座选错了。"**

1049 的"下一步"第 1、2 条就是：**下 QAT 版基座 / target_modules 含 gate_up_down**。

**但 v9t5 → v9t8 四版全部没有做这两条。** 四版 adapter 大小一模一样（36,346,288 字节），
说明 target_modules 一直是 attention-only。

**这是整条链上最值得回头补的一步**——不是"再调数据配比"，而是"把 MLP 训上"。
