# 训练公式审计（2026-11-08）

> 触发：老爹「我们用来训练模型的参数公式是否合理，loss、学习率公式等是否合理，别拿错公式或者老旧技术」
> 方法：读 `finetune_train.py` 的实现（不是读配置），再用 v9t10 的 6909 条真实数据量一遍。

---

## 一、结论汇总

| 项 | 现状 | 对不对 | 依据 |
|---|---|---|---|
| loss | 标准因果 LM 交叉熵，`ignore_index=-100`，只算 assistant | ✅ 对 | 代码走 HF 默认，没有自造公式 |
| **样本权重 weight** | **字段被丢弃，从未参与训练** | ❌ **完全失效** | `_slim()` 只保留 `messages_json`/`source` |
| mask_prompt 边界 | 用"单独 tokenize prompt"求长度 | ⚠️ 有 0.8% 错位 | 实测 400 条里 3 条前缀对不上 |
| 截断 | `truncation=True` 默认**右侧**截 | ❌ 错的方向 | 超长 1.5%，正好把回答尾巴砍掉 |
| 全 -100 样本 | 1.5%（约 100 条） | ❌ 会产生 0/0 | 实测 400 条里 6 条 |
| 结束符 | 训练侧以 `<turn|>` 收尾（不是 `<eos>`） | ⚠️ 需保证推理侧 stop 一致 | 实测末 token 是 `<turn|>` |
| lr / 调度 | 2e-4，cosine，warmup 3%（22 步） | ✅ 合理 | 1 epoch 742 步，短训正常 |
| 优化器 | **adamw_torch（32 位状态）** | ⚠️ 不是错，但不是 QLoRA 惯例 | 惯例是 `paged_adamw_8bit` |
| weight_decay | 0.0 | ✅ 可接受（LoRA 常用 0–0.01） | — |
| bf16 + NF4 | 4bit nf4 双量化，计算 bf16 | ⚠️ 可能与 eval NaN 有关 | bnb 4bit+bf16 有 NaN 报告 |
| 梯度裁剪 | max_grad_norm 1.0 | ✅ | — |
| eval_loss | **连续五版全 NaN** | ❌ | 见 §四 |

## 二、⭐ 最严重：`weight` 从来没生效过

### 证据

```python
def _slim(rows):
    out.append({
        "messages_json": json.dumps(r["messages"], ensure_ascii=False),
        "source": str(r.get("source", "")),
    })          # ← 只保留这两个字段
```

数据里 weight 分布：`0.3: 4110 条、1.0: 1669、0.6: 766、0.4: 287、0.8: 77`。
**但训练器根本不读 `weight`**——没有加权 loss、没有采样权重、`remove_columns` 里也没有它。

### 这意味着什么

1. **1113 那条"Σw 预算"分析对模型没有任何影响**。
2. v9t10 把 `material_full` 从 0.8 调到 0.4，**在训练里等于没调**。
3. v9t8→v9t10 的提升，**只能归因于 MLP（加了 25.8M 参数）和数据内容**，不能归因于权重。
4. v9t8 掉工具那 2 道，也不能再用"287 条 @0.8 稀释"解释——那是错的解释。
   （真正原因更可能是：加进来的 287 条没有工具调用，**条数上**把比例摊薄了，与 weight 无关。）

### 修法（二选一）

- **A. 真加权**：自定义 Trainer 的 `compute_loss`，按样本 weight 加权 CE。
- **B. 按权重重采样**：`weight` 当重复次数用（0.3 → 30% 概率抽到），简单、稳、不用改 Trainer。

**推荐 B**：不碰 Trainer 内部，效果等价于加权，且能直接控制总步数。

## 三、截断方向错了

`tokenizer(full, truncation=True, max_length=1536)` 默认从**右边**截——
正好把 assistant 的回答尾巴切掉，甚至整段切掉。

实测：中位 568、p90 873、最大 2190，**超 1536 的只有 1.5%**，和"全 -100 样本 1.5%"是同一批。

### 修法

- 超长样本改为**从头部截 system**（保 system 尾 + 完整 user/assistant），或
- 直接**丢掉**超长样本（只 1.5%，损失可忽略），或
- 把 `max_seq_len` 提到 2304（A800 80G 显存充足，代价是慢 30%）。

**推荐**：先丢超长（1.5%），把 NaN 一起消掉；再考虑提到 2304。

## 四、eval_loss NaN 的真因（五版未解）

三个嫌疑，按可能性排：

1. **全 -100 样本 → 该 batch 有效 token 数为 0 → 0/0 = NaN**
   实测 1.5%（978 条 val 里约 15 条）。HF 的 CE 在 batch 内对有效 token 求均值，
   一个 batch 里只要有 1 个有效 token 就不会 NaN——所以要求**整批都无效**。
   batch=8 时概率极低，所以这条**不足以解释每次三连 NaN**。

2. **bnb 4bit + bf16 计算的数值问题**（已知会偶发 NaN）
   训练 loss 正常、只有 eval NaN，可能的差别是 eval 不走 `train()` 的 dropout 路径和
   `no_grad` 下的累加方式。**把 compute dtype 改成 float32 是最常见的解法**。

3. **`load_best_model_at_end=True` + `metric_for_best_model="eval_loss"`**
   指标是 NaN 时，比较永远为 False → **"最优 checkpoint"的选择是失效的**，
   最终加载哪个 checkpoint 不可控。**这条无论 NaN 怎么来都必须修**。

### 修法（一起上）

- 过滤/修复全 -100 样本（见 §三）
- `bnb_4bit_compute_dtype=torch.float32` 试一版
- 把 `load_best_model_at_end` 关掉，或改用可判定的指标（如 val 上的固定小评测）
- eval 端加护栏：`if not torch.isfinite(loss): 记录并跳过`

## 五、其他（不算错，但可以更好）

| 项 | 建议 | 理由 |
|---|---|---|
| 优化器 | `paged_adamw_8bit` | QLoRA 惯例；34.9M 参数省不了多少，但**分页能防显存尖峰** |
| lr | 2e-4 可保留；若换 MLP 后不稳，降到 1e-4 | 加了 MLP 后参数量 ×3.8，同一 lr 下的有效步长更大 |
| 序列长度 | 1536 → 2304（可选） | p90 才 873，只有 1.5% 超，性价比一般 |
| packing | 不做 | 短样本多，packing 会把不同对话拼一起，Chat 模板下容易串味 |
| 结束符 | 确认推理侧 stop 含 `<turn|>` | 训练以它收尾，推理若不停在它上面会续写 |

## 六、我的判断

**公式本身没写错**——loss 是标准 CE，lr 是标准 cosine+warmup，LoRA 的 α/r=2 也没问题。
**错在三个工程细节**：权重没接上、截断方向反了、eval 指标 NaN 让 checkpoint 选择失效。

其中**权重那条最伤**：它让 1113 那条"教训"和之后所有围绕 Σw 的调整，**在训练里都是空的**。
这条必须记进台账，并且**把先前基于 Σw 的解释全部标记为"未经模型验证"**。
