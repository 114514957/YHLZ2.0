# 台账检索/写入改进调研（2026-11-13）

> 触发：老爹「现在的上下文台账的检索，写入还是太原始了，你上社区找开源项目，看有什么改进」。
> 结论先行：**问题不在“要不要上大框架”，而在索引粒度与写入结构**。用 SQLite FTS5 把索引从「逐行」改成「记录级 + 中文 bigram」，实测建库 0.44 s、查询 0–1 ms、Top-3 相关性全面好于现网；语义检索（sqlite-vec + 本地 embedding）作为第二阶段。

---

## 一、现状诊断（读代码 + 实测，不是印象）

**写入**：`ledger_add` → 追加 `docs/上下文台账.md`；随后 `index_ledger_*` 把**每一个非标题行**切成一条文档：

```
docid = ledger:<记录号>:<行号>
summary = 该行正文[:500]
tokens = 拉丁词 + 中文 2/3-gram（无 jieba）
```

**检索**：MCP `ledger_search(query, limit)` 只有这两个参数；`KeywordIndex.query()` 用 `idf * tf` 相加，**没有 BM25 的长度归一化、没有短语、没有字段权重、没有过滤、没有语义**；返回的是“行”，不是“记录”。

**规模**（2026-11-13 实测）：台账 1,170 条记录 / 21,184 行；索引 16,785 docs / 1,392,770 terms。

**具体毛病**：
1. **粒度错**：一条记录被拆成十几行，检索结果是一堆行片段，要自己拼上下文；记录标题不参与打分。
2. **没有过滤**：不能按时间、记录号、类型（决策/结论/踩坑）、状态过滤；想查“最近一周的训练结论”只能靠关键词碰运气。
3. **没有语义**：同义/改写查不到（“黄金样本”能中，“训练样本库”未必）。
4. **写入无结构**：没有标签、实体、链接、内容哈希；重复/被推翻的结论靠人读。
5. **维护脆弱**：全量重建曾是 O(n²)（11/07 修过，60 min → 46 s）。

## 二、社区项目调研（一手 README，2026-11 拉取）

| 项目 | 核心做法 | 可借的点 | 备注 |
|---|---|---|---|
| [basic-memory](https://github.com/basicmachines-co/basic-memory) | Markdown 是唯一事实源；observations + wikilink 组成知识图谱；SQLite 索引；MCP-native；向量/混合检索带 cross-encoder 重排 | **markdown 原文 + 派生索引**的分层；“链接即关系”；MCP 工具体验 | AGPL v3；有云服务，但本地 OSS 可用 |
| [mem0](https://github.com/mem0ai/mem0) | 写入时一次 LLM 调用做 **ADD-only 抽取**（不 UPDATE/DELETE，记忆累积）；实体链接；**语义 + BM25 + 实体三路并行融合**；时间感知 | 写入期抽取“事实/偏好”而不是存原文；多信号融合 | 平台版有闭源优化，OSS 效果“方向一致但不等同” |
| [graphiti](https://github.com/getzep/graphiti) | **时间上下文图**：episode（原始事件）→ 实体/关系/事实，每条事实带 `valid_at / invalid_at`；混合检索（语义+关键词+图遍历）；增量更新 | 决策的“何时为真/何时被推翻”；`episode` 溯源 | 适合“项目状态”这类会变的结论 |
| [LightRAG](https://github.com/HKUDS/LightRAG) | 图 + 向量双路检索；多种切块策略（Fix/Recursive/Vector/Paragraph）；文档删除自动重建图；接 RAGAS 评估 | 记录级/段落级切块；可评估 | 依赖 LLM 做实体抽取，成本高 |
| [sqlite-vec](https://github.com/asg017/sqlite-vec) | 纯 C 的 SQLite 向量扩展（`vec0` 虚拟表），跨平台、可嵌入 | **不引入服务**就能做本地语义检索 | pre-v1，注意 breaking changes |
| [letta](https://github.com/letta-ai/letta)（MemGPT 血统） | 有状态 agent + 分层记忆（core/archival/recall）；README 现指向 `letta-code` | 分层记忆的 API 设计 | 本项目只借鉴概念，不引入 |

**一句总结**：社区共识是 **“原文/日志是源，检索层是派生的多路索引（关键词 + 向量 + 图）+ 写入时结构化”**；没有谁靠“逐行倒排”硬扛。

## 三、实测对照（拿真台账做的原型）

原型：把 1,170 条记录按“标题 + 正文”整条入 FTS5（中文先切 bigram 写 tokens 列，`tokenize='unicode61'`），查询用 FTS5 `bm25()`。

| 项 | 现网（逐行 kw_index） | 原型（记录级 FTS5） |
|---|---|---|
| 建索引 | 全量 ~46 s（修复后） | **0.44 s**（1,170 条，内存） |
| 单查询 | 57–201 ms | **0–1 ms** |
| 返回粒度 | 行（记录号 + 行号） | **记录**（标题 + 正文 + 命中片段） |

Top-3 对照（越大越相关；FTS 的 bm25 为负值，越小越好）：

| 查询 | FTS5 Top-3 | 现网 Top-3 |
|---|---|---|
| 黄金样本 | **1141**（素材盘点）、382、865 | 1141、865、1142（行片段） |
| 翻唱 投产 | **1120**（投产验收）、**1066**（交接待办）、**1064**（复刻成功） | **464**（不相关）、1120、843 |
| 显存 5GB | **1135**（显存口径）、419、427 | 1135、49（单行噪声）、114 |
| v9t10 闸门 | **1133**（48/56）、1146（DPO）、1153（破纪录） | 1133、1115、1153 |

> 说明：现网 `old_ms` 含“取 80 行再按记录聚合”的 Python 开销；即便扣掉，逐行查询本身也比 FTS5 慢一个量级。FTS5 表名不能与列名同名（原型踩到，已记）。

## 四、建议方案（分三层，按投入排序）

### P0：先换索引层，不动业务（1–2 天，低风险，收益最大）
- **记录级文档**：`records` 表（rec/title/ts/status/tags/hash）+ `chunks` 表（记录级 + 章节级）；FTS5 建在 `tokens` 上，`body` 原样存用于展示。
- **真 BM25**：直接用 FTS5 `bm25()`，可给 title/body 设权重；替代现在的 `idf*tf`。
- **过滤**：`since/until`、`record`、`kind`（决策/结论/踩坑）、`status`（active/superseded）、`tags`。
- **写入结构化**：`ledger_add` 增加可选 `tags/kind/status/links`；落盘仍是 markdown（front-matter 或行内 `tags:`），索引器解析。
- **MCP 兼容**：`ledger_search(query, limit, *, mode="bm25", since=None, until=None, kind=None, tags=None)`——旧调用不变。
- **验收**：20 条真实查询，recall@5 ≥ 现网；延迟 < 10 ms；全量重建 < 5 s。

### P1：本地语义检索（约 1 周，中风险）
- `sqlite-vec` + 本地中文 embedding（bge-small-zh / gte-small，ONNX，约 100 MB；不联网、不占 GPU 也行）。
- 记录级向量；**混合检索 RRF**（BM25 + 向量），可选 bge-reranker 重排 Top-20。
- 增量：新记录只 embed 新增/变更块（内容哈希）；夜间批量。
- 验收：同义查询（“训练样本库”→“黄金样本”）能召回；recall@5 再提升；延迟 < 50 ms。

### P2：时间图 + 写入期抽取（2–3 周，按需）
- Graphiti 式：事实带 `valid_at/invalid_at`，`episode` 指回记录；决策被推翻时旧事实自动失效。
- mem0 式：写入时抽“事实/偏好/决定”，ADD-only 累积，实体链接。
- MCP 新工具：`ledger_related(record)`、`ledger_timeline(topic)`、`ledger_ask(question)`（带引用）。
- 只在 P0/P1 的召回还不够时做，不提前上。

## 五、迁移与回滚

1. 新建 `cache/search/ledger_v2.db`（FTS5 + 元数据）；不动现有 `kw_index.db`。
2. 双写/双读开关：`YHLZ_LEDGER_INDEX=v2` 切检索；旧索引保留一个版本周期。
3. 索引器按记录 `hash` 增量；全量重建从 markdown 重放（可随时重建，无单点）。
4. 回滚：改回环境变量即可；markdown 台账始终是事实源，不受影响。

## 六、风险与边界

- FTS5 内置分词对中文不友好 → 用 bigram 预切（原型已验证）；英文/代码词直接保留。
- FTS5 表名与列名不能相同（原型踩坑）。
- 语义检索需要 embedding 模型文件（约 100 MB），要接受一次下载；本地 CPU 推理即可。
- 图/时间层依赖 LLM 抽取时，成本与误差都会上来，先不做。

## 八、P0 已落地（2026-11-13 晚）

**文件**
- `backend/ledger_index_v2.py`：记录级 FTS5（中文 bigram 预切）、`records` 元数据（ts/kind/status/tags/hash/行号）、`ensure_fresh()` 按台账 mtime+size 自动重建、`search()` 支持 since/until/kind/tags。
- `backend/target_scheduler_tools.py`：`ledger_search(query, limit, since, until, kind, tags, mode)`；`YHLZ_LEDGER_INDEX=v1` 一键回滚。
- `tools/yhlz_mcp_server.py`：MCP 工具暴露同样的可选过滤参数（`since/until/kind/tags`）。
- `backend/test_ledger_index_v2.py`：6 项测试（bigram、构建、记录级检索、重号去重、过滤、自动重建），已进 `ci_check`。

**验收（真台账 1,172 条记录，10 条查询）**

| 指标 | v1（逐行） | v2（记录级） |
|---|---|---|
| Top-5 命中 | 5/10 | **10/10** |
| 平均查询 | 43.2 ms | **4.5 ms** |
| 全量重建 | ~46 s | **0.59 s** |
| 库大小 | 139 万词条 | 10.1 MB（记录+索引） |

过滤实测：`since=2026-11-08 until=2026-11-09` 只回 11-08/09 记录；`kind=决策` 全为决策类。
