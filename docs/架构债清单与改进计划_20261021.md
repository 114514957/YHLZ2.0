## 0. 结论（三句）

1. **主链是活的**，但「三区划分」（live / test-only / archive）只写在 `STRUCTURE.md` 里，代码里没有任何强制——所以老东西能一直挂在 live 链上。
2. 最贵的债不是「文件大」，是**同一件事有两条路**：两套 HTTP 派发、五个监督者、四个 venv、两条 QQ 链共用同一批模块。
3. 训练期间只该动**文档对齐、日志与快照、测试补边界**；结构性拆分（P1/P2）等训练跑完再动，否则抢资源且难回滚。

## 2. 债清单

每条格式：**现象 → 证据 → 为什么算债 → 改法 → 成本 → 验收**。

### A. 入口与监督

**A1｜入口名不副实：文档说「唯一开机自启」，实际有 14 个启动脚本**
- 证据：6 个 `YH_*.bat`（boot / workbench_normal / 全家桶 / test_start / TTS_test_start / voice_dialog）+ 6 个 `YHLZ_*.bat`（106–165 字节的转发壳）+ 2 个 `qqwatch-*.bat`。
- 判据：入口是"谁能改状态"的边界。入口越多，越没人能回答"现在这套是谁拉起来的"——今天 QQ 桥那条 `10296→13776→6684→33300` 的四层链就是例子。
- 改法：定三个入口（`YH_boot` 自启 / `YH_workbench_normal` 手动 / `qqwatch-*` 装 NapCat），其余标 `deprecated` 并加打印告警；兼容壳设删除日期。
- 成本：2 h · 验收：根目录脚本 ≤ 5 个，且每个头部写明唯一职责。

**A2｜五个监督者，职责靠注释区分**
- 证据：`yhlz_launcher.py`（拉 ollama/gemma/daemon）、`yhlz_watchdog.py`（自愈）、`qq_bridge_watchdog.py`（QQ 链）、daemon 内部 autonomy 循环、`schedule` 计划表。
- 判据：今天实测 `watchdog_state.json` 写「NapCat 在运行但端口不可达 84917s」，而 NapCat 进程其实早退出了（pid 28448 不存在、3001 无监听）——监督者自己的状态不可信，是最危险的一类债。
- 改法：**先不合并**。先给每个监督者加"判活口径"声明（进程 / 端口 / 端口属主链），并在状态文件里写 `evidence` 字段；收敛留到 P2。
- 成本：4 h · 验收：任一状态文件都能回答"你凭什么说它活着"。

**A3｜四个 venv，同一个服务出现两种解释器的两层进程**
- 证据：`.venv` / `venv-dsh` / `venv-gsv5` / `venv-train`；今天 QQ 桥实测 venv 起壳、system python 干活，四层链 `10296→13776→6684→33300`。
- 判据：排查时无法一眼分清"这是重复进程还是父子链"——我今天就差点按重复进程去杀。
- 改法：`venv-dsh`（利贞 SDK）独立保留；`.venv` 与 `venv-gsv5` 合并评估；`venv-train` 明确只给训练；在 `STRUCTURE.md` 写"哪个 venv 跑哪条链"。
- 成本：1 d · 验收：任一进程 PID 能通过命令行唯一映射到 venv 与职责。

**A4｜YHLZ→YH 迁移没有收口标准**
- 证据：`YH` 是指向 `YHLZ` 的 junction（实测 target + 相同 File ID）；`YHLZ_*.bat` 兼容壳为 2026-10-21 21:57 新建；模块名仍是 `yhlz_launcher.py` / `yhlz_paths.py` / MCP `serverName: yhlz`。
- 判据：兼容层没有截止日就会永久化——三年后没人敢删。
- 改法：写迁移台账：保留项（MCP serverName、历史台账路径）与待删项（bat 壳、`yhlz_*` 文件名）分列，设截止日期与"删除前检查清单"。
- 成本：2 h · 验收：文档里每一项兼容都有 owner 和到期日。

### B. 运行边界

**B1｜`console_server.py` 2115 行，一个 handler 管九件事；被 daemon 继承再叠一层**
- 证据：2115 行 / 64 函数 / `do_GET`@1202、`do_POST`@1363；`target_daemon.py:956` `class _Handler(ConsoleHandler)`，`console_do_GET/POST` 委托 + 自己的 `do_GET`@1034 / `do_POST`@1053。历史上评估文档记 38 条精确路由。
- 判据：UI 静态、聊天 SSE、TTS、控制、设置、QQ 二维码、日志、歌曲、Live2D 全在一个类里；167 个测试只有 7 个碰它——**最忙的边界，覆盖最低**。两套派发的顺序还决定路由结果。
- 改法（P1）：按域拆 mixin/模块：`static` / `chat_sse` / `control` / `media`，`daemon._Handler` 只做组合与鉴权；每个域一个路由表常量，路由清单可快照测试。
- 成本：3–5 d · 验收：单文件 ≤ 800 行；路由清单由测试锁定；拆完 167 个测试仍全绿。

**B2｜`target_daemon.py` 1128 行，五种职责**
- 证据：生命周期 + 调度 + autonomy + 记忆维护 + HTTP 装配；`make_server`@1192、`serve_forever`@1249。
- 判据：daemon 是组合根就该只做装配；现在它还会"干活"。
- 改法：把 autonomy / 记忆维护搬到 worker 模块，daemon 只保留「装配 + 生命周期 + 信号」。
- 成本：2–3 d · 验收：daemon ≤ 500 行，且不再 import 业务模块（只 import 装配目标）。

**B3｜`target_scheduler_tools.py` 2334 行 / ~45 条能力定义**
- 证据：2334 行，80 个 def，约 50 条能力声明行。
- 判据：注册表抽象是对的，但"所有能力写一个文件"等于把注册表变成第二个上帝对象；改一条能力要动 2300 行的文件。
- 改法：按域拆 `tools_memory.py` / `tools_voice.py` / `tools_qq.py` / `tools_dev.py`，注册表只收 `list[Capability]`。
- 成本：2 d · 验收：每文件 ≤ 600 行；导出工具数不变（有快照断言）。

**B4｜三个 HTTP/协议面，错误格式与鉴权各写各的**
- 证据：`target_daemon`（8321，继承 console）、`tools/dsh_worker.py`（8347 自建 HTTP）、`yhlz_mcp_server.py`（stdio MCP）。
- 判据：同一个客户端要处理三种错误形状；鉴权一个有一个没有。
- 改法：抽一个 200 行以内的 `http_contract.py`（错误体、状态码、日志字段），三处共用；MCP 侧只统一错误文本。
- 成本：1 d · 验收：错误体 schema 唯一，测试覆盖。

### C. 旧代码与文档漂移

**C1｜`qq_bot.py` 2215 行：文档说"旧 Full 链已收掉"，实际是 17 个模块的依赖**
- 证据：`STRUCTURE.md` L56 称其为旧 Full 链；实测被 17 个非测试模块 import，含 `console_server.py`、`qq_bridge_service.py`、`qq_bridge_watchdog.py`、`yhlz_launcher.py`、`yhlz_watchdog.py`。
- 判据：**文档与现实相反**比单纯的旧代码更危险——下一个人会按文档去删它，然后炸掉桥。
- 改法三步：① 冻结（新增 import 加 lint 拦截）② 抽共享库（onebot 配置发现/消息解析）③ 删 Full 链运行部分。P2 执行。
- 成本：3–5 d · 验收：非测试 import 数 17 → 2（只剩薄共享库）。

**C2｜`opencode.json` 已退役却仍入库**（✅ 2026-10-21 已处理）
- 证据：台账 0497 标注退役；实测除 `.archify` 生成物外无 live 引用。
- 已做：移入 `archive/2026-10-21-retired/opencode.json`，`STRUCTURE.md` 同步。

**C3｜`STRUCTURE.md` 落后于现状**

- 改法：本轮盘点后同步一版，并加"文档过期检查"——每次大改在台账里勾选是否更新结构文档。
- 成本：1 h · 验收：三区表与入口表与实测一致。

**C4｜备份目录在仓库里**（✅ 2026-10-21 已处理）

### D. 数据与资源

**D1｜快照把 30–80 MB 的索引整份复制**
- 证据：`cache/snapshots/` 0.4 GB，其中 9 份 `kw_index.db`（17.5 / 29.4 / 30.9 / 39.6 / 48.6 / 58.2 / 58.4 / 82.6 MB…）。
- 判据：快照的目的是回滚，不是囤积；索引是可重建派生物，不该进快照。
- 改法：快照白名单（只存记忆库/配置/关键 json），索引改为"记录版本 + 需要时重建"；保留最近 3 份。
- 成本：3 h · 验收：`cache/snapshots` ≤ 0.1 GB，回滚演练一次成功。

**D2｜`kw_index.db` 82 MB 单文件，被 6 个 live 模块依赖**
- 证据：`ledger_store.py` / `memory_index_audit.py` / `snapshots.py` / `target_entry.py` / `target_kw_index.py` / `target_memory.py` / `target_scheduler_tools.py`。
- 判据：重建成本与快照策略耦合；一旦损坏，记忆检索与台账检索一起瘸。
- 改法：增量重建 + 校验和；快照不复制（见 D1）；加"索引可重建"的验收脚本。
- 成本：1 d · 验收：删库后 10 分钟内可重建且检索结果一致。

**D3｜两套 outbox 实现并存，命名相同、语义不同**（原判「重复产物」有误，2026-10-21 更正）
- 证据：`backend/qq_outbox.py` 用 `outbox.jsonl`（proactive 消息，peek/ack 至少一次投递）；`backend/qq_delivery_store.py` 用 `outbox.db`（投递状态存储）。两者都在 live 链上，不是死文件。
- 判据：同名不同物最容易在排查时串线；真正的问题是**边界没写下来**，不是文件多余。
- 改法：在 `STRUCTURE.md` 的 QQ 一节写清两者分工（jsonl=待发队列，db=投递记录）；暂不删任何文件。
- 成本：30 min · 验收：文档能回答"消息现在走到哪个文件"。

**D4｜根目录日志与素材**（日志部分 ✅ 2026-10-21 已处理；素材**不动**——翻唱在用）
- 证据：`backend.log` 14.9 MB 的最后写入是 **2026-09-01**（`YH_boot.bat` 早已改写到 `cache\logs\boot.log`，这份是陈账）；根目录 wav 在 22:19–22:32 之间从 19 个 / 181.5 MB 涨到 **21 个 / 197.3 MB**——翻唱正在产出，文件是活的。
- 已做：`backend.log` 移至 `cache/logs/legacy/backend.log`。

### F. 测试与验收

**F1｜最忙的 HTTP 边界只有 7 个测试**
- 证据：167 个测试，7 个提及 `console_server`；12 个依赖本机端口（会随服务状态飘）。
- 改法：先补 5 条"路由清单快照 + 错误体"契约测试（不依赖端口，直接调 handler 或 mock socket）；把 12 个 live 测试单独标记。
- 成本：4 h · 验收：HTTP 边界面覆盖 ≥ 15 条，且可在无服务时跑绿。

**F2｜没有端到端冒烟**（✅ 2026-10-21 已补：`tools/smoke.py`）
- 证据：验收靠人；今天 QQ 桥断 23 小时没有任何自动告警（watchdog 只提示一次）。
- 已做：`tools/smoke.py`，只读检查 5 项（daemon 8321 / worker 8347 / QQ 桥状态与心跳年龄 / NapCat 3001 / DSH GUI 61447），输出 OK/WARN/FAIL 与一行结论，`--json` 机读，FAIL 退出码 1。
- 实测：`0 fail, 2 warn`——NapCat 未监听、桥在重连（QQ 离线），与人工判断一致。
- 验收：一条命令 10 秒内给出通过/失败。✅

### G. LLM 与上下文

**G1｜双轨回退 + 8k 上下文，没有统一预算层**
- 证据：历史 709 次上下文超限 400、Ollama 1261 次 false（台账 0944 引用的日志统计）；`_compact_for_local` 属于补丁式压缩。
- 改法：抽 `context_budget.py`（token 估算 + 截断策略 + 调用方标识），所有发往 8081 的入口强制走它；超限先拒后压。
- 成本：2 d · 验收：72 小时内 8081 的 400 = 0，且日志能看出是谁超的。

**G2｜LLM 模块多，Port 抽象只用了一部分**
- 证据：`llm_engine.py` 384 / `llm_provider_port.py` 104 / `llm_vllm_provider.py` 219 / `llm_hybrid_provider.py` 150 / `llm_stream.py` 118 / `target_orchestrator.py` 520。
- 判据：Port 有了，但调用点还是直接摸具体实现——等于抽象没生效。
- 改法：先画一张"谁调谁"的调用图（只读），再决定是否统一；不急着删模块。
- 成本：4 h（图）+ 评估 · 验收：调用图落档，违规调用点列清单。

## 3. 分期

### P0（训练期间可做，合计约 1.5 天，全低负载）

| 顺序 | 项 | 说明 |
|---|---|---|
| 1 | C3 + C1 文档对齐 | 先把"文档说谎"止住，成本最低、收益最大 |
| 2 | D4 日志/素材归位 | 纯文件移动，不动代码 |
| 3 | D1 快照策略 | 省 0.3 GB，且降低备份耗时 |
| 4 | D3 outbox 定唯一来源 | 30 分钟 |
| 5 | C2 + C4 | 清退役配置与备份目录 |
| 6 | F2 冒烟脚本 | 补上"断了能发现"的能力 |
| 7 | F1 契约测试 5 条 | 需要写代码但无 GPU/CPU 压力 |

### P1（训练结束后，约 1.5–2 周）

B1 路由分域 → B2 daemon 瘦身 → B4 统一错误/鉴权 → A3 venv 收敛 → G1 上下文预算 → A2 监督判活口径。

顺序理由：先拆最忙的边界（B1），因为后面的 B2/B4 都依赖它先有清晰的路由表。

### P2（季度级）

C1 `qq_bot` 三步剥离 → B3 能力定义拆分 → D2 索引治理 → A2 合并监督者 → A4 兼容层删除。

### 不做

- 不换前端、不引新框架（架构评估 2026-10-21 的结论仍然成立）；
- 不动人格 / 记忆 / 语音的语义，只动边界与装配；
- 不在训练期间做 B1/B2 这类跨文件重构（抢资源、难回滚）；
- 不为"看起来整洁"重命名 `yhlz_*` 模块（MCP serverName 与历史台账都依赖它）。
