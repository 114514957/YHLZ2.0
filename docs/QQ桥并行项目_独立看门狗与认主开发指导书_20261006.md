# YHLZ QQ 桥并行项目：独立看门狗、常驻运行与认主开发指导书

日期：2026-10-06  
适用项目：YHLZ / 元亨 QQ Bridge / 利贞远程开发

交付状态：方案已完成，代码尚未实施。本轮仅核对代码与 MCP 台账，没有切换启动项、重启生产进程或进行真实 QQ 收发。本文中的参数是首轮验收目标，不是已测结果。

## 1. 这次要解决什么

当前 QQ 桥已经有三项可复用能力：

1. NapCat/OneBot WebSocket 接入与断线重连。
2. 认主后的 `#dev`、`#devstatus`、`#y`、`#n`、`#push` 远程开发入口。
3. `qq_delivery_store`、统一发送适配器和 outbox 持久投递。

但现在的运行方式仍然和 YHLZ 全栈绑在一起。`tools/yhlz_watchdog.py` 发现任何服务掉线后会调用 `yhlz_launcher.ensure_stack()`，它会检查或拉起 Ollama、Gemma/llama-server、8321 daemon、QQ 桥和 NapCat。这样一来，用户只是想让 QQ 桥常开，却可能被带起整套项目；项目开发期间也可能被旧看门狗重启或误杀。

本方案的目标是建立一个独立的 **QQ Bridge Lite 并行项目**：

```text
QQ Bridge Lite
├─ 独立启动器
├─ 独立看门狗
├─ 独立锁 / 日志 / 状态 / 投递数据库
├─ NapCat/OneBot 连接检查
├─ 认主安全边界
└─ 利贞远程开发入口

YHLZ 全栈（按需启动）
├─ daemon 8321
├─ Gemma/llama-server 8081
├─ Ollama 11434
├─ 记忆、调度、知识库、语音等后台能力
└─ UI/工作台
```

最终采用同级独立项目 `C:\Users\ACE_WAN——PROJECT\YHLZ-QQBridge`，有自己的虚拟环境、依赖清单、版本与启动项。YHLZ 只作为可选对话后端和开发目标。实施初期可在现仓库中分步提取，但不能把“共享整个 YHLZ 环境、运行时 import 主仓库代码”作为最终验收。下文 tools/config/cache 路径在提取完成后均相对于新 QQ 项目；旧路径明确指 YHLZ 现有文件。

### 2.2 当前最重要的耦合

| 位置 | 现状 | 独立项目的处理 |
|---|---|---|
| `tools/yhlz_watchdog.py` | `tick()` 进入 `ensure_stack()`，会管理全栈 | 新增 QQ 专用 watchdog，禁止导入和调用 `ensure_stack()` |
| `tools/qq_bot.py::run()` | 启动时无条件预热 SenseVoice ASR | Lite 默认不预热；Lite 默认禁用语音；显式启用可选插件后才允许按需加载 |
| `tools/qq_bot.py::_daemon_turn()` | 普通消息依赖 8321 daemon | daemon 健康才转发；不可用时返回降级提示，不能触发全栈启动 |
| `tools/qq_bot.py::_dev_report()` | 完成后会尝试写主项目记忆 | Lite 默认只写桥自己的开发日志；记忆写入必须显式打开 |
| `tools/dev_runner.py::commit()` | `git add -A` 后提交 | 改成基线差异保护和明确范围提交，禁止吞并他人工作树改动 |
| `tools/qq_bot_restart.py` | 按命令行杀掉所有 `qq_bot.py` | 改成按 profile、PID、启动时间和工作目录识别，只操作自己拥有的实例 |
| 状态和锁 | 使用 `cache/tmp/qqbot.lock` 等共享路径 | 使用 `cache/qq_bridge/<profile>/`，全栈和 Lite 互不覆盖 |

## 3. 目标运行模式

### 3.1 Lite 模式

Lite 是默认常驻模式，允许以下依赖：

1. Windows Python 环境和项目代码。
2. NapCat/OneBot WebSocket 已经在运行，或明确配置了由 QQ profile 管理的 NapCat 实例。
3. `tools/qq_bot.py` 所需的基础 Python 依赖。
4. `opencode` 或 dsh worker 只在主人发起 `#dev` 时启动。

Lite 不自动启动以下内容：

- Ollama 11434；
- Gemma/llama-server 8081；
- YHLZ daemon 8321；
- UI、工作台、记忆复盘、调度、知识库索引；
- ASR 模型预热；
- TTS/语音模型常驻加载。

### 3.2 Full 模式

Full 模式仍由原 `yhlz_watchdog.py` 管理，给需要完整数字人能力的场景使用。完整 YHLZ 与独立 QQ 桥应能同时运行；互斥的是“同一个机器人账号的收发管理权”，不是整个项目。迁移后旧 Full launcher/watchdog 配置 `qq_management=external`：照常管理模型与 daemon，但跳过 QQ bridge、NapCat 和 napcat_watch 的启动、重启与通知。

Full 看门狗不得被改造成 Lite 的后门。Lite 检查不到 daemon 时，结果必须是“普通对话暂不可用”，而不是调用 Full 启动器。

### 3.3 Owner Dev 模式

Owner Dev 是 Lite 下的核心能力，不依赖 8321：

```text
主人私聊 #dev 任务
  → QQ 桥验证 user_id 在 owner allowlist
  → 利贞开发运行器启动
  → 第一轮只询问和给方案
  → 主人普通私聊答复
  → 继续原开发会话
  → 结果写入桥自己的事件日志和 outbox
  → 主人发送 #y 才允许提交，#push 才允许推送
```

普通消息仍可尝试走 8321，但它是可选能力。主人开发通道和普通对话通道必须分开，daemon 挂掉不能影响 `#dev`。

## 5. 看门狗职责边界

### 5.1 只检查四类状态

每次巡检只做这些检查：

1. Lite bridge PID 是否仍是同一个进程，且工作目录/profile 匹配。
2. bridge 状态文件是否更新，WebSocket 是否已连接、最近收发时间是否合理。
3. OneBot/NapCat WebSocket 是否可连接；只读检查，不默认启动 NapCat。
4. 是否有正在执行的远程开发任务；开发任务异常只记录并通知，不能自动重启或重复执行任务。

### 5.2 明确禁止

QQ Lite 看门狗禁止：

- import `yhlz_launcher.ensure_stack`；
- 调用 `_spawn_ollama`、`_spawn_llama`、`_spawn_daemon`；
- 扫描和杀所有 `target_daemon`；
- 扫描和杀所有 `qq_bot.py`；
- 因 8321 不健康而重启 QQ 桥；
- 因一次心跳失败而重放开发任务或发送未知结果的消息；
- 自动执行 `#y` 或 `#push`。

### 5.3 恢复规则

```text
bridge 进程消失
  → 等待短退避
  → 只启动同一个 Lite profile

WebSocket 断开但 bridge 还活着
  → 由 bridge 自身重连
  → watchdog 只记录，不另起第二个 bridge

NapCat 不可达
  → watchdog 状态为 dependency_unavailable
  → 不拉起全栈；若 manage_napcat=false，不自动拉起 NapCat

daemon 不可达
  → 普通消息进入降级分支
  → #dev 继续允许
  → 不启动 daemon
```

恢复必须有最大重试间隔和熔断：连续 5 次启动失败后进入 `blocked`，每 10 分钟再试一次，防止启动风暴。

## 6. 认主和开发安全设计

### 6.1 认主来源

在已校验的 OneBot 连接中，主人身份只来自本地 allowlist 的数字 QQ 号，不能来自消息内容、昵称、群名、模型输出、`[[dev:...]]` 标记或任何远端回报。allowlist 变更需要本机配置变更并重启 profile。

### 6.2 指令规则

| 指令 | Lite 行为 |
|---|---|
| `#dev <任务>` | 只允许主人；启动独立开发会话 |
| `#devstatus` | 只返回当前 profile 的任务状态 |
| 主人普通私聊答复 | 仅在开发状态为 awaiting 时作为利贞答复 |
| `#y` | 显示待提交摘要；经过差异检查后提交 |
| `#n` | 清除待确认动作，不撤销工作树改动 |
| `#push` | 独立确认后推送；目标仓库和分支明确才可执行 |
| 非主人 `#...` | 固定安全接管提示，不执行、不进模型 |
| 普通消息 | daemon 可用才转发；不可用则降级提示 |

### 6.3 开发工作树

默认在独立 QQ 项目的 `cache/qq_bridge/lite/dev_workspace` 下创建目标 YHLZ 仓库的专用 worktree 和 `codex/qq-dev-<job_id>` 分支（仅建分支不能隔离文件），避免远程 agent 触碰主工作树中其他 agent 的在途改动。兼容旧流程时可提供 `YHLZ_QQ_DEV_WORKSPACE=main`，但必须在状态和日志中显式标明 `shared_workspace=true`，并且禁止 `git add -A`。

提交前必须记录：

1. 开工时的 `HEAD` 和工作树摘要。
2. 本任务新增/修改的文件清单。
3. 提交前与开工基线的差异。
4. 提交目标分支和提交信息。

如果检测到基线之外的他人改动，`#y` 只能返回“发现外部改动，暂停提交”，不能自动合并、覆盖或提交。新 worktree 默认从选定提交建立，不自动包含主工作树未提交改动；任务确实需要这些改动时，先列出所需文件及来源并显式形成任务基线，不能把整个脏工作树复制过去。

## 7. 代码改造清单

### 阶段 P0：冻结边界，先不切换生产

- 新增 `qq_bridge_lite.json` 示例和本指导书。
- 为 bridge 所有状态路径增加 `YHLZ_QQ_STATE_DIR`/profile 解析，不改变默认 Full 路径。
- 记录现有启动命令、OneBot config 路径、bot UIN 和 master UIN 的指纹，不记录 token 明文。
- 明确当前只允许一个账号消费者；旧 `qq_bot_restart.py` 暂时不能用于 Lite。

通过条件：仅新增配置/设计，不影响当前运行；离线测试可加载 Lite profile，且不会 import Full watchdog 的启动函数。

### 阶段 P1：独立 service wrapper

- 新增 `tools/qq_bridge_service.py`。
- 启动时只建立 profile 目录、锁和日志，然后运行桥。
- 传入 `--profile lite`、`--config`、`--master`、`--conversation optional`。
- 将 bridge 状态写到 profile 状态文件，包含 pid、create_time、profile、ws_state、last_rx、last_tx、dev_state。
- 禁止启动时 `_warm_asr()`；Lite 收到 record 默认提示使用文字。显式启用可选语音插件时才首次懒加载，不改变原 Full 语音链路。

通过条件：隔离测试中让 11434、8081、8321 均不可用（不结束正在训练或评测的生产进程），Lite 仍能启动并连 OneBot fake transport；启动日志没有拉起全栈的命令。

### 阶段 P2：独立 watchdog

- 新增 `tools/qq_bridge_watchdog.py`。
- 使用独立 `watchdog.lock`，按 PID + create_time + profile 校验实例归属。
- 只恢复 Lite service，不调用 `ensure_stack()`。
- watchdog 启动、停止、恢复和熔断状态都写到 profile 日志。
- 支持 `--once`，支持 `status`，支持 fake checker 注入。

通过条件：人为结束 Lite bridge 后 watchdog 能恢复它；人为结束 daemon 或占用/关闭 8321 时，watchdog 不启动任何主项目服务，也不杀其他进程。

### 阶段 P3：认主开发隔离

- `dev_runner` 增加 profile/state/workdir 参数，不能和全栈 `cache/dev/state.json` 混用。
- `#dev` 使用专用 worktree；dsh worker 只在需要时启动，并绑定该 worktree。
- `#y` 删除无范围的 `git add -A`，改成基线检查 + 文件清单提交。
- 开发回报写入 QQ profile outbox；断线后沿用已有 unknown 不盲重发策略。
- `_dev_report` 默认不写主项目 memory；需要时由配置显式启用，并写入独立证据。

通过条件：主人发 `#dev` 时，8321 不在也能进入利贞流程；非主人同样消息不会启动 worker；断线重连后不重复启动同一任务。

### 阶段 P4：普通对话可选接入

- bridge 启动不检查 daemon 是否存在；收到普通消息时再做短超时健康检查。
- daemon 健康：按现有 `source=qq_bridge` 调用。
- daemon 不健康：回复一条固定降级提示，建议主人使用 `#dev`，不自动重试、不拉起 daemon。
- TTS、ASR、图片和文件能力按 profile 开关；Lite 默认仅保留文本和主人开发。

通过条件：主项目全停时，普通消息不会卡住数分钟，也不会启动模型；打开 daemon 后无需重启 QQ bridge 即可恢复普通对话。

### 阶段 P5：启动项迁移和长稳验收

- 新建 Windows 启动快捷方式或任务计划，启动 `qq_bridge_watchdog.py --profile lite`。
- 旧 `yhlz_watchdog.py` 可以继续管理 Full，但必须设为 `qq_management=external`。旧 QQ 自启/旧 napcat_watch 同时退出，只有新桥管理该账号。
- 提供 `qq_bridge_control.py start/stop/restart/status`，所有操作只针对 profile 归属 PID。
- 真机验证 NapCat 掉线、WS 断开、QQ bridge 崩溃、daemon 停止、电脑重启和网络恢复。

通过条件：30 分钟故障注入通过、2 小时常驻无重复实例、系统重启后仅 QQ Lite 自动恢复；主项目按需启动不被干扰。

## 8. 验收节点

### Gate 0：静态隔离门

- Lite 入口能加载配置。
- 代码搜索和运行时 trace 证明没有调用 `ensure_stack`、`_spawn_ollama`、`_spawn_llama`、`_spawn_daemon`。
- Full 与 Lite 锁、状态、日志目录不同。
- 没有全局杀进程逻辑。

### Gate 1：QQ 桥常驻门

- 在隔离环境证明 11434、8081、8321 均不可用时 Lite 能启动；不为验收强停生产训练。
- NapCat/OneBot fake transport 能连接。
- bridge 断开后自身重连；watchdog 不创建第二实例。
- watchdog 只恢复 bridge，不改变主项目进程状态。

### Gate 2：认主开发门

- 主人 `#dev`、答复、`#devstatus` 全流程通过。
- 非主人 `#dev` 永不启动 opencode/dsh。
- `[[dev:...]]`、模型返回文本和引用/转发消息不能改变认主判断；主人在许可群的显式命令按下文兼容规则处理。
- `#y` 检测外部改动；没有明确文件范围时拒绝提交。
- `#push` 不自动发生。

### Gate 3：普通对话降级门

- daemon 关闭时普通消息在短超时内收到降级答复。
- daemon 关闭时不启动全栈、不加载 Gemma、不预热 ASR。
- daemon 启动后普通文本可恢复；桥不用重启。

### Gate 4：投递与重连门

- 发送前断线：进入 retryable，有限重试。
- 发送后无 ack：进入 unknown，不盲重发。
- reconnect 后 outbox 可继续处理可安全处理的项目。
- 相同 job_id/result_version 只生成一条逻辑回报；网络投递遵守 unknown 规则，不承诺 QQ 端严格恰好一次。

### Gate 5：长稳门

- 30 分钟注入：WS 断开、NapCat 不可达、bridge kill、8321 停止、重复 watchdog、网络短断、开发任务运行中断线。
- 2 小时空闲常驻：没有重复 bridge、没有内存持续增长、没有主项目服务被拉起。
- 系统重启后：Lite 看门狗恢复；Full 服务仍保持按需，不被顺带启动。

## 9. 可量化标准

| 指标 | 目标 |
|---|---:|
| Lite 冷启动到开始监听 | ≤ 20 秒（不含 NapCat 登录） |
| bridge 崩溃到恢复尝试 | ≤ 60 秒 |
| WebSocket 断线到重连尝试 | 1、2、5、15、30、60 秒退避 + ±20% 抖动 |
| watchdog 同时存活实例 | 1 个 Lite bridge + 1 个 Lite watchdog |
| 8321/8081/11434 被 Lite 自动启动 | 0 次 |
| 非主人开发任务启动 | 0 次 |
| unknown 投递自动重发 | 0 次 |
| 空闲 2 小时重复进程 | 0 次 |
| `#dev` 首次确认回报 | ≤ 10 秒；模型实际执行时间另计 |

## 12. 执行顺序建议

先做 P0、P1、P2，证明“全栈关闭仍可常驻”；再做 P3，证明“主人能开发且不污染项目”；之后才接 P4 普通对话和 P5 启动项迁移。每个 Gate 形成 JSON 证据、日志摘要和台账记录，未通过时不切换生产启动项。

## 13. 实施前必须补齐的细节（本次代码复核新增）

### 13.1 真正的独立项目，不依赖正在被修改的 YHLZ 代码

最终目录是 `YHLZ-QQBridge`，开发目标仍是 `YHLZ`。把前者理解为“永远开着的远程控制台”，后者是它能接入的一个项目。

提取策略：

1. 复用 `qq_connection.py`、`qq_delivery.py`、`qq_delivery_store.py` 的协议、状态机和有价值的测试，形成独立包；记录提取源文件 SHA256、源 HEAD 和实际工作树差异。现有文件有未提交代码，不能只凭 HEAD 声称完整继承。
2. 将 `yhlz_paths` 替换成桥的配置，不通过 `sys.path` 引用 YHLZ 的 backend；不要复制整个 backend。
3. 最小依赖是 Python、websockets、进程管理依赖；SQLite 使用标准库。torch、funasr、transformers、TTS 等不进入默认安装集。opencode 为独立外部程序；dsh 为按需可选组件。
4. 主项目连接使用 HTTP 适配器，开发连接使用显式目标目录和 worker 协议，不能靠导入 daemon 实现。
5. 桥采用固定发布版本运行，开发修改在另一个工作目录里进行。开发 YHLZ 不改变正在运行的桥文件；开发桥自身也要先做测试、切换 release，不能运行中覆盖模块。
6. 开发助手若需要 YHLZ 台账，仍通过现有 MCP 工具访问；QQ 常驻核心不为此启动 YHLZ MCP 或其他主项目服务。工具服务器仅随开发任务按需使用，其自身副作用应独立审计。

新增 `pyproject.toml`、锁定的依赖文件、README、配置 schema、单元测试和发布清单。P1 验收必须包含干净虚拟环境安装；把 YHLZ 目录临时设为不可访问的测试替身时，桥核心仍可启动并处理状态命令。不要重命名真实生产仓库做测试。

### 13.2 收包循环与业务处理必须分离

当前 `qq_bot._read_loop()` 在收到 message 后直接 `await self.handle(ws, ev)`。`handle()` 内会调用 `_say()`，发送路径又等待由 `_read_loop()` 处理的 echo 回执；耗时 `_daemon_turn` 即便放在线程里，其外层 await 仍会阻止该 reader 继续收包。

这是结构性阻塞风险，本轮通过代码确认，尚未进行真机复现。不能因为 ping/pong 心跳仍正常，就宣称业务链健康。

新桥采用：

```text
唯一 WS reader
  ├─ echo → 立即唤醒对应 Future
  ├─ heartbeat → 更新在线/登录状态
  └─ message → 有界 inbox 队列，立即继续收包

inbox worker → 鉴权/幂等/路由 → 提交任务或调用可选 daemon
独立 sender → 持久 outbox → 当前 WS transport → reader 回收 ack
```

初始参数建议：inbox 上限 128；同一会话顺序处理；普通对话并发上限 2；同一个开发项目同时只有 1 个执行任务；状态查询走轻量控制通道，不被模型调用堵住。队列满时记录 busy，不能无限创建 asyncio task。reader 不等待发送 busy 提示，而是将提示入独立 outbox。

加两项必测：业务模型故意慢 60 秒期间，echo、心跳、`#devstatus` 仍能处理；开发确认回报立即收到 fake echo 时不能超时。所有后台 task 有取消和异常回收；网络重连不会重新执行已接收的 #dev。

### 13.3 谁拥有 QQ 账号：跨 profile、跨仓库也只有一个管理者

profile 独立锁只防止同目录重复实例，不能防止旧 YHLZ 与新项目分别开一个消费者。必须增加本用户共享的账号级操作系统锁，例如 `Local\YHLZ_QQ_<bot_uin>` 的命名互斥量；账号级锁由实际消费消息的 bridge 持有，watchdog 另持有自身锁。两套入口都遵守同一账号锁；拿不到锁时明确退出，不删除别人的锁、不抢占连接。

锁失败时 fail closed，不能沿用旧 watchdog 外层异常时“照常运行”的逻辑。停止进程前校验 PID、创建时间、可执行路径、入口绝对路径和 instance_id；PID 已复用或归属不符时拒绝结束进程并报告冲突。

迁移时清点：Windows Startup 快捷方式、任务计划、`qq_bot_start.bat`、`qq_bot_restart.py`、`yhlz_launcher`、`yhlz_watchdog`、`napcat_watch`。旧 Full 模式新增 `qq_management=external` 后只管主项目，不启动/停止桥或 NapCat，不再由旧 watcher发送恢复通知。

回滚顺序：暂停新任务 → 导出未完成任务/unknown 投递状态 → 停新桥并确认账号锁释放 → 恢复旧配置和指定版本 → 启动一个旧桥。不要删除投递数据库，也不要因回滚把 unknown 改回 queued。

### 13.4 NapCat 与真正在线是两回事

WebSocket 连上，只证明 OneBot 服务能连接；QQ 账号是否登录必须读取 heartbeat 的 `status.online` 或受支持的 get_status 回应。健康状态拆成 `process_alive / event_loop_alive / ws_connected / account_online / dev_available / conversation_available`，允许 unknown，不能统一写一个 online=true。

每 5 秒写本地事件循环心跳；30 秒未更新可判 stalled，启动宽限 30 秒。无 QQ 聊天消息不算故障；QQ 用户一小时没发消息也不能触发重启。长时间断网只退避重连，不能每分钟杀桥。

默认 NapCat attach-only，桥不管理已存在的 QQ 登录客户端。若后续启用 `manage_napcat=true`，只管理自己启动且记录归属的实例；登录过期进入 needs_login，不无限重启、不反复弹窗。Windows 登录会话下运行看门狗，避免把依赖桌面登录的 NapCat 错装成 Session 0 后台服务。

### 13.5 保留原来的认主使用习惯，但上下文要绑定

记录 0226 明确支持主人在群中不 @ 使用 # 指令，因此不能把“全禁群命令”当作已有用户要求。建议默认主人私聊，并提供配置明确允许的 owner_command_groups；白名单群里仍须校验真实发送者 QQ 号。群模式是可配置兼容能力，不把群全体变成主人。

开发 job 固定记录 owner_id、入口会话、target_project、workspace、backend、session_id、状态。等待答复时仅接受该主人在原会话的答复；跨会话使用显式 `#answer <job_id> <答复>`，避免把主人另一个群的闲聊当成执行确认。群里启动可回一个受理摘要，详细文件路径、diff 和错误回报默认送主人私聊。

`#y` 保留原来的“一条命令明确确认提交”，不是要求主人重复确认：DONE 回报先给出 job_id、目标分支、文件清单与 diff 摘要；同一上下文 #y 确认这份快照。快照变化则原确认失效；存在多个任务则要求 `#y <job_id>`。#push 同理绑定分支及待推送 commit，执行前后检查 exit code，失败不能报告已推送。现有 `commit()` 未校验 git 返回码，也需一起修复。

### 13.6 开发 worker 存活和任务状态不能只靠桥进程

当前 `_spawn()` 使用 daemon thread；桥退出会失去回报调度，子进程却未必退出。当前 `_run()` 在读取 stdout 行时才检查超时，子进程完全不输出或 stderr 堵塞时，超时可能不生效。

P3 要做的最小修正：独立 worker 进程 + 持久 job 表；stdout/stderr 同时排空；独立定时器控制总超时；保存进程归属信息。bridge 重启只重连任务状态，不再次 start。看门狗不会因为开发时间长而杀任务。

job 状态：accepted → running → awaiting_owner / completed / failed / interrupted；每次外部执行前先持久化 execution_id 和状态。进程崩溃后的 running 标为 interrupted 并复核进程，不自动从头重做。#n 仅表示不提交，不代表停止正在运行的 agent；需要取消时使用独立 `#cancel <job_id>`，终止已核验归属的 worker 子树并保存已改文件清单。

dsh 不能只凭 8347 /health 返回 200 就复用：应核对 worker instance_id、profile、工作目录与后端。独立监听端点必须有本机认证，日志不打印认证值。没有可恢复的 SDK session 时要报告会话中断，不能编造跨进程续接能力。opencode/dsh 不得与 Full 共用 state.json/backend.txt；一个任务开始后固定 backend，#backend 只影响后续任务。

远程 agent 的 cwd 及文字提示不构成操作系统沙箱。工程首期用专用 worktree、无自动提交/推送、任务互斥和范围审计减少干扰；如果需要强制限制任意 shell 的访问范围，必须另做受限执行环境，不能宣称现有 prompt 已提供强隔离。

### 13.7 持久投递必须存得下“要发什么”

当前普通回复经 `DeliveryManager`，其存在不等于所有回复已写入 SQLite；实际 `_relay_outbox` 才明确接入 `qq_send_adapter` 和持久库。不能根据统一适配器的注释宣称全链均已持久化。现适配器默认 transport 可返回成功占位，生产装配必须强制要求真实 transport，缺失时启动失败，防止假成功。

现有 deliveries 表侧重状态和 payload_ref/hash，不会自动把完整 params 保存起来。新桥必须持久保存受限 payload（或数据库事务内 payload 表），再生成 outbox；仅保存 payload_hash 无法在重启后恢复消息。正文存储仅限当前 Windows 用户可访问；普通诊断仅返回摘要。

开发结果和待发送 outbox 在同一事务提交；事件唯一键为 bot_id + job_id + result_version + target。入站 #dev 使用 bot_id + channel + sender_id + message_id 做跨重启持久去重，不能只复用当前进程内 15 分钟字典。

明确区分：执行成功但消息 unknown、执行失败但回报 confirmed。QQ 没有可靠远端幂等保证时，unknown 保留供 `#devstatus` 查询，不盲重发。离线很久后的过期提示不集中刷屏；任务最终状态始终保留，恢复通知按离线事件合并一条。日志轮转建议 10 MB × 5，详细事件保留 7 天，任务结论和 unknown 默认 30 天，清理策略可配置且不删仍未解决的活动任务。

### 13.8 资源与响应时间验收的正确量法

纯桥/watchdog 空闲显存目标为 0 次 CUDA/模型初始化；NapCat 图形渲染可能占用显存，必须单列，不能把 QQ 整体承诺成零显存。桥与 watchdog 合计私有内存暂定 ≤200 MB、10 分钟平均 CPU ≤1%（按整机总 CPU 归一化），超标先记录和归因；NapCat、opencode/dsh、模型不混在这个分母内。

受理时间从 OneBot event 到 outbox 入队记录；QQ 可见回报另测发送与 ack，网络不可用不可能保证 10 秒用户可见。在线正常链路目标为 #dev 受理回报 p95 ≤2 秒、上限 10 秒（至少 30 个 fake 事件样本，再真机少量确认）；不包含模型生成方案的耗时。

首次投产前先跑 30 分钟故障注入、2 小时实机常驻；“可以长期常开”的后续证明使用 24 小时观察。保存各进程树、启动命令指纹、CPU/内存时序、重连次数、任务数、投递终态分布。此前提到的 492/0 等是其他批次结果，不作为本项目验收成绩。
