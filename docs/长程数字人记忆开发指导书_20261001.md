## 2. 架构与各层职责

| 层 | 存什么、做什么 | 已实现的保护 | 仍需关注 |
|---|---|---|---|
| 人格提示词 | 角色表达、已批准认知和行为边界 | 群候选不直接固化、人格版本与冲突检查 | v8 的风格与工具调用需实测 |
| L1 短期 | 默认最近 5 条消息，滚出原文进入 pending，另有摘要 | 按渠道持久化、损坏/异 scope 拒绝覆盖、成功落盘才确认摘要消费 | 不是 5 个对话往返；写盘失败后新原文可能仅在 RAM |
| L2 中期/长期事实 | 既有 SQLite 中的事实、经历、状态与关联 | 状态过滤、群隔离、失效/纠错、可重建派生索引 | 记忆质量取决于抽取和审核，不能只看索引绿色 |
| L3 认知/人格根基 | 审批后的稳定认知与方法 | prepared 版本、哈希冲突拒写、恢复/撤回保留历史 | 生产版本表尚未初始化；未做真实人格审批 |
| 载体 | 桌面/QQ 工具入口、日记、计划、KB | 来源证据、写前 pending、写后 committed/refused/failed | 后台直接调用旧 Python 函数的路径未全部统一 |

复用既有 cache/memstore/memstore.db 与 backend/yuanheng_kb.py。FTS、关键词、向量是检索投影，不另造一份“真实记忆”。日记记经历，计划记承诺，KB 记通用知识，它们不会因为被写入就自动成为人格。

来源与身份是两个问题：CarrierOrigin 的 channel 表示路由，不能代替 QQ 主人认证。群消息只能通过群记忆/候选审核路径流转，不能因自称主人就取得 owner 权限。

设计依据沿用台账 0311、0179、0518、0519、0499、0546、0548/0550；本轮状态更新以 0562 为准。

## 4. 已实现机制与故障处理

### A：8GB 显存下的资源分配

默认 YHLZ_MEMORY_LLM_MODE=disabled。两个训练标记任一为真都优先禁用后台 LLM；关闭训练标记并不会自动开启模型。embedding/reranker 也不会因检索自动加载；语义召回须独立显式选择 cpu 模式，训练标记仍优先禁止。

闸门覆盖记忆 hooks、实体三元组提取、技能学习、主人反思、复盘、群知识晋升等本轮发现的后台入口。它是进程环境策略，不是全系统 GPU 仲裁器；别的 shell/服务必须继承同样环境。MCP 辅助客户端已显式传递父进程环境。

### B：长会话与摘要

滚出窗口的原文保留为 pending。摘要模型异常、取消、确认写盘失败均不应把旧 pending 当成已处理。L1 文件损坏或 scope 不符会阻止覆写原件；先保留故障现场，再人工恢复。

MemorySummaryScheduler 每次唤醒默认最多 4 批，每批默认 40 条；同一调度器只有一个任务，默认超时 45 秒，失败指数退避，后续事件才再次唤醒。没有常驻空闲定时器，因此不能保证用户停止聊天后积压自动清空。更没有把 pending 静默丢弃以换取固定文件大小。

文字会话现在清理完成的后台任务，保留未完成任务；异常仅记类型，避免长时间运行无限保留 done tasks。耐久测试包含 1200 轮与 1197 条 pending 重启恢复；这是临时目录测试，不是掉电硬件验证。

### C：召回路径、预算与索引

当前召回主顺序为 keyword + SQL 基线，随后在预算允许且结果不足时做 spread，再做 semantic；shadow 等可选阶段也受准入预算限制。最终条数受 limit 硬上限限制。关键词 SQLite 异常时保留 SQL 降级能力。

默认 100ms 是可选阶段准入预算，不能中断已经开始的慢调用，因此不是 100ms 硬实时 SLA。部分读连接使用 50ms busy timeout，避免锁库时默认等待 5 秒；多个阶段合计仍可能超过单次 timeout。故障回归验证退化行为，不把 CI/本机耗时当作全部硬件的性能保证。

自定义 L2 默认使用相邻独立 .kw.db，避免临时/群库误用主人关键词库。索引审计以只读 URI 打开文件；缺文件报告异常，不悄悄新建空库。向量残留 31 条已于台账 0558 无模型清理，旧文“待处理”已失效。

### D：人格审批与撤回

L2 候选不等于 L3 人格。保存版本时先有 prepared 记录，再核对当前根基哈希与目标版本；冲突时拒绝覆盖外部编辑。恢复和撤回都保留历史，撤回产生新版本。模型不能批准自己提出的根基变更。

管理入口 tools/persona_versions.py 提供 list/show/recover/revert。recover/revert 需要版本 id、reason、confirm。注意：list/show 会构造 PersonaVersions，可能初始化表，并非严格零写；如只需要巡检，使用 memory_health。正式库当前 persona.initialized=false，不要把 0 个 pending 解释为“已经全面部署且审核完成”。

### E：载体写入证据与待核对事件

已绑定 memory_save、diary_write、task_plan、kb_add 的主要会话工具入口；MCP 首次调用这些写工具才懒绑定。MCP 的服务 scope 为 mcp，owner channel 为 owner_local；只查询台账不触发该记忆服务构造。

写入流程是先留 pending 意图，再执行载体变更，最后确认状态。证据账保存来源、内容指纹与关联信息，不另存原文。如果载体已写成功但状态确认失败，保留 pending，必须核对目标再处理；禁止看到 pending 就自动重放，以免重复写日记或计划。这不是跨所有文件/数据库的原子事务。

主人 reflect 经绑定 memory_save 写入证据，公共/群 reflect 不写主人洞察。其他后台直接调用旧日记/计划/KB 函数的路径仍需逐条迁移；本轮不宣称全项目所有写路径都已覆盖。

## 6. 正式库只读快照

来源：artifacts/memory_longrun_20261001/delivery_check_mcp.jsonl，YHLZ MCP memory_health。

- resource：disabled / training-active；semantic_enabled=false。
- L1：3 个有效文件，每个窗口 5 条消息、pending=0；巡检只看计数和结构，不输出原文。
- L2：active=246，archive=295，downgraded=161。
- 应参与投影的权威记录=407；FTS、keyword、vector 的 missing/stale/duplicates 全为 0。
- carrier/persona：initialized=false，正式新表尚未建立；automatic_replay=false。

407 是索引使用的权威集合数量，不是把全部 702 条状态记录删除至 407 条。健康快照是当时状态，不表示并发运行后永远不变。

## 7. 可重复执行的命令

在项目根目录 PowerShell 执行。Agent 查询台账/记忆仍必须走 MCP，不得 grep 台账全文。

~~~powershell
$env:YHLZ_TRAINING_ACTIVE='1'
$env:YHLZ_FINETUNE_ACTIVE='1'
$env:PYTHONUTF8='1'
.\.venv\Scripts\python.exe -B tools/memory_offline_regression.py --output artifacts/memory_longrun_20261001/operator_recheck
.\.venv\Scripts\python.exe -B tools/memory_health.py --kw-db cache/search/kw_index.db --vec-db cache/embvec.db
~~~

离线回归返回码应为 0，JSON 的 ok=true，failures/errors=0，guard_violations=[]。第二条只读健康命令不会启动模型、创建记忆服务或修复数据。新建 MCP 会话也可调用 memory_health 获取同类结果。

索引异常先 audit，再依据缺失类型选择修复；不要把 rebuild 当作日常健康检查。实际生产修复需记录具体目标与前后计数。人格 pending/prepared 必须核对证据，不自动恢复或回放。

## 8. 下一阶段：复用 v8 的隔离真机验收

此阶段是实施安排，本轮没有执行。

1. 确认并行训练/评测进程已结束，记录当前端点实际模型 id；只复用既有 8081，不额外拉起模型。训练状态解除后显式配置 YHLZ_MEMORY_LLM_MODE=local；默认模型名 gemma-4-e4b，端点若有别名则以实际 id 覆盖。语义模式暂继续 disabled。
2. 使用临时 L2、临时日记/计划/KB、假 QQ transport，跑 v8 工具契约：正确工具名、合法参数、拒绝虚构成功、公共入口拒写主人。先修模型输出/解析契约，再谈自动人格成长。工具 8/16 是台账已有风险，不能用自由聊天正常掩盖。
3. 准备 30 条合成事实与 10 组纠错、多渠道身份案例。测抽取后可回忆、换一种说法检索、过期/纠错后不把旧值当现值；明确期望 id/状态，禁止把关键词命中率充当完整记忆质量。
4. 积压 200 条消息，在允许模型的隔离会话触发多次唤醒，记录每批耗时、剩余 pending、失败/取消后的队列。用户不再发消息时若仍有积压，明确呈现未完成，不能假定 idle timer 已存在。
5. 统计 100 次预热后 lexical 召回 P50/P95、端到端记忆阶段耗时、RAM、进程 GPU 峰值。建议验收目标是 lexical P95 ≤100ms；它是待测目标而非已达成指标。8GB 合格至少要求无 OOM、无第二 GPU 模型、记忆后台不挤占前台到不可用；真实数值填台账。
6. 假 transport 验证桌面与 QQ 主人共享、群隔离。人格候选逐条展示证据后审批，测试纠错与版本撤回。确认这些后才讨论受控生产启用与长期观察；音频链继续按冻结状态处理。

## 9. 遗留与后续优先级

P0：v8 工具调用契约与真实记忆质量；正式部署前的数据备份、版本表初始化与可恢复性核验。

P1：迁移剩余直接 Python 载体写入；补统一 pending/prepared 人工核对入口；按需增加可关闭的空闲摘要调度，保留预算和单飞。

P1：长期积压的大文件写入成本与磁盘故障恢复；当前保留原文换取可恢复性，尚未把无限积压转换为分段日志。

P2：向量 CPU 模型按需加载与真实语义检索评测；完整数字人的外观/动作、长期主动行为与最终一体化体验。它们不在此次记忆离线通过的结论内。
