## 2. 最值得迁移到数字人核心的四项

### 2.1 把“未知”作为正式任务状态

来源：QQ技术记录0004、0012-D，`backend/qq_delivery.py`。

当前状态包括queued、sending、confirmed、rejected、retryable、unknown、expired。核心价值是区分“还没送出去就失败”和“可能已执行但确认丢了”：前者有限重试，后者先保留未知，避免重复效果。

应用到记忆/任务：把工具handler接受、载体提交、独立读回和用户可见确认分开。请求超时不能自动当作未执行，更不能让模型用一句“好了”替代提交证据。

不要直接把QQ confirmed名称复制为业务完成：它表示OneBot接口确认，不代表用户已读；记忆完成必须由目标载体独立核对。

### 2.2 持久待办 + 确认后推进

来源：记录0004、0009，`backend/qq_outbox.py`及`backend/qqextract.py`。

outbox先peek、后ack的顺序，和抽取游标只推进已处理范围的原则，都适合复盘队列。下一阶段可据此设计：稳定源消息→持久任务→模型处理→事务提交→检查点确认→新进程恢复。

复用的是顺序和确认原则，不建议原样复制JSONL当高并发事务队列。当前outbox使用进程内锁，push错误会被吞掉，坏行在重写时可能丢弃；若多个进程同时追加和ack，仍需事务数据库或可靠跨进程协调。新记忆任务必须保留来源、租约、失败原因和幂等效果键。

### 2.3 身份与渠道在检索之前确定

来源：记录0008、0012-F，`backend/channel_auth.py`、`tools/qq_bot.py::handle`。

当前桥先过滤主人私聊，群使用qq_g渠道；channel_auth校验来源与渠道格式。这个分层可沿用到L1/L2/L3：先判用户/群与可见范围，再检索，不能检索后再靠模型决定哪些秘密不该说。

边界：is_owner_channel把合规qq_p形式视为owner，前提是桥已执行真实主人校验且daemon验证调用方。它本身不验证QQ账号所有权；不能让一个外部HTTP请求自称qq_bridge和qq_p就获得主人权限。该接线需验收，不能由字符串前缀证明安全。

### 2.4 知识抽取采用有来源的小批次

来源：记录0009、0012-G，qqwatcher/QCE→qqextract→yuanheng_kb及专题游标。

适合把QQ里的技术讨论变成可检索的候选知识，而不是直接改人格。保留群/消息来源、提炼版本、时间和审阅状态；模型输出是候选结论，不是来源内容必然正确。

8GB环境下建议复用既有候选文件、游标和知识库，把推理并入统一排队；前台有请求时后台不再领新批次。采集可持续，提炼可以暂停，二者不必同速。当前部分调用未接统一闸门，这属于后续改造，不是已具备的整机调度。

## 3. 目录与代码不一致、不能直接照抄的地方

1. **群渠道命名**：记录0003含qq_<gid>，当前handle用qq_g<gid>；身份校验也要求qq_g。新方案用当前规范，不照搬旧通道名。
2. **是否必须@**：记录0003说群需@，记录0007及当前handle已经有无@接话。要以当前策略和预算决定，不能把两种模式都当默认。
3. **确认码**：台账写status=ok且retcode=0；classify_response实际也接受retcode缺失。需明确这是兼容约定还是缺口，不能把严格协议检查说成已完全实现。
4. **主动消息绕过投递管理器**：_relay_outbox直接_request，并仅检查status=ok。发送后断连会保留条目，重连后可能再次发送；unknown不重试未覆盖这一条路径。首要优化是统一效果状态并持久化未知结果。
5. **持久队列不是全链路恰好一次**：出站条目存在不表示发送状态跨重启可恢复；入站_seen_events也只是内存。必须分别处理入站重复、任务重复、出站确认丢失。
6. **去重指纹不是消息身份**：qqexport_ingest._fp按群、用户和去空白后前300字符生成指纹，没有消息时间/ID。适合部分技术内容去重，但可能合并不同时刻的相同话语，不能拿来记录偏好变化和任务时序。
7. **心跳不代表业务在线**：WS pong只能证明socket可响应；QQ账号掉线、模型故障、daemon积压仍可能存在。重启daemon只是现场恢复手段，不是排队问题的根治。
8. **默认限额不等于性能目标**：群日400条、outbox每小时2条等需按主动程度、模型耗时与前台需求重新配置，且当前部分计数随进程重启重置。

以上是静态观察或技术视图中的限制，本轮没有复现故障、没有运行回归，不能当新生产实测结论。

## 4. 推荐采用顺序

| 优先级 | 做什么 | 为什么 |
|---|---|---|
| P0 | 把普通回复和主动outbox统一到投递状态协议；unknown持久化 | 先解决重复发送与虚报完成风险，给任务通知打底 |
| P0 | 统一可信身份、群渠道名、消息ID和效果ID | QQ入口接记忆前先保证不串人、不重复业务效果 |
| P1 | 复用游标与确认顺序建立持久复盘任务 | 让长期记忆能断点恢复，而非只看最近16条 |
| P1 | 收拢QQ提炼、反思、技能学习的LLM调用 | 让8GB下前台优先、训练时可暂停后台 |
| P1 | 分层健康状态 + 脱敏trace | 区分WS/QQ/daemon/model/发送效果故障，减少盲目重启 |
| P2 | 可配置无@接话、表情、主动频控、远程开发入口 | 核心可靠后再增加数字人参与感 |
| 冻结 | 语音发送、TTS、全双工 | 遵守当前范围；媒体编码可记作后续技术储备 |

这批资料最有价值的不是再选一个新框架，而是现成的状态机、确认机制、身份隔离和断点处理方式。先复用这些，再补持久化与统一接线，能直接服务现在的记忆长程任务。
