# OBS 噪声归因与 CosyVoice 低延迟复核：下一阶段方案

日期：2026-10-07。依据：MCP 台账 0680–0682、0642；当前音频服务与播放器源码；本机 OBS 保存配置；夸克镜像内源码只读检查。

## 1. 先说结论

1. TTS → OBS 已通过十句录音匹配，但“只走 OBS、不经扬声器、无环境声”尚未全部验收。当前最先处理的是音源串入，不是给 TTS 叠降噪。
2. 用户记得的夸克包已经找到：`下载物象/引进技术/cosyvoice-vllm-full.tar`，18,748,762,112 字节（约 18.75 GB / 17.46 GiB）。它是 CosyVoice3 0.5B 的 Docker/OCI 镜像，含 vLLM、vLLM-Omni 环境及专门的加速补丁。
3. 它具备降低首段语音等待的实现，但没有本机性能证据，不能称为“超级压缩延迟”。当前入口走 CosyVoice 内嵌 vLLM，不是 vLLM-Omni 的完整服务管线。
4. 当前 YHLZ 的两处整句缓冲会抵消流式收益。必须同时改 TTS 适配器和 OBS 播放器，单换引擎不够。
5. 本轮不需要训练模型。先修启动参数、音源路由和数据流，再测速度与音质。人格微调独立推进，不能指望它解决音频延迟。

本轮仅检查、编写方案和登记台账；未运行下载镜像、未启动推理测试、未修改 OBS/生产服务配置、未公开推流。

## 3. 降噪问题：先分离声音来源

无人主播的正常出口应当是：

```text
本地 TTS → 数字音频 → OBS 浏览器源 → OBS 混音/编码 → B站
                         不需要麦克风或扬声器参与
```

洗衣机是房间里的声音，纯数字 TTS→OBS 本来不应采到它。OBS 麦克风通道若开着，即使 TTS 输出完全干净，最终录音也会有环境声。

### 3.1 下一次本地录制操作

1. 复制现有场景集合，命名 `YHLZ-VoiceOnly`，保留原场景作回退。不要在 OBS 运行时直接修改 JSON。
2. 设置 → 音频：在测试场景集合中禁用桌面音频、麦克风/Aux 和其他非必要音频设备；确认应用音频采集源也未加入录音轨。
3. 打开 YuanhengVoice 属性，明确启用“通过 OBS 控制音频”；高级音频属性设“监听关闭”，只分配到测试录音轨。
4. 系统扬声器保持可用，避免靠系统总静音掩盖错误路由。检查 Windows“侦听此设备”关闭。浏览器页面必须只在 OBS 内加载。
5. 先录 10 秒空白，再播放原来缓存的三句 WAV，再录 10 秒空白。复用原音频，避免重新合成导致对照内容变化。
6. 查看只有 YuanhengVoice 电平随语音动；本机扬声器应无元亨声，录音应有三句。若关闭桌面音频后录音也没声音，说明旧链路依赖了桌面捕获，应修浏览器路由后重测。

### 3.2 如何判断修复

- 原 WAV、旧 OBS 录音、VoiceOnly 录音分别留存，写清采样率、录音轨、音源列表与 OBS 版本。
- 空白段只计算固定时窗 RMS/dBFS、峰值与频谱；不能把此前“-25dB”直接当作同口径测量。
- 建议门槛：10 秒空白段 RMS ≤ -60 dBFS，或数字静音；若不满足，检查播放器输出和编码器，而不是直接放行。
- 固定三句完整、顺序正确，无双声；人耳确认扬声器无声。`started` 回执不能替代录音和人工确认。
- 如果原 WAV 已有底噪，再查参考音频、音量增益、克隆合成；如果原 WAV 干净、OBS 脏，查混音路由；如果只开麦克风才脏，再做输入降噪。

以后确实需要真人插话时，再单独启用麦克风轨，先测一种抑噪方法，随后按需加轻量噪声门。不要把现有 audio_enhancer 的 RNNoise、谱减、AGC、压缩、归一化全部叠到 TTS 输出。

## 4. 夸克包到底怎么加速

镜像真实 image manifest：`sha256:4c5b1b2f2758094ad9410b48debfeb37ed1a560fe90800ebfb353a6c87915da3`。

模型路径为 `/workspace/models/Fun-CosyVoice3-0.5B-2512`。源码快照在 `artifacts/obs_cosy_review_20261007/`，只是提取文本，不运行这些文件。

| 实现 | 能降低哪段等待 | 代价/限制 |
|---|---|---|
| vLLM 解码 | TTS 内部语音 token 的生成 | 不是对话 Gemma 的加速；显存分配与版本需要适配 |
| `stream=true` | 一段音频生成就往外发，不等全句 | 默认请求 stream=false；下游必须增量消费 |
| `stream-hop-len=10` | 较早触发首段 token→音频 | 数值是语音 token 数，不是毫秒；还要等待 lookahead 和参考音频补齐 |
| `flow-steps=3` | 减少 flow matching 求解工作 | 相比更多步可能损失音质、韵律；需 3/5/10 同文本对照 |
| 声纹缓存、预热 | 避免每次重算参考条件，移走首次初始化开销 | 冷启动与热请求必须分开统计 |
| HiFT CUDA graph 等补丁 | 减少部分声码器派发开销 | 补丁按 shape 命中，失败可能回退；需记录实际命中 |
| BNB 4bit 候选 | 主要降低权重存储显存 | 反量化有成本，不保证更快；未证明本包当前入口启用 |

“量化存储、计算时恢复 FP16”更准确的说法是：低位权重存储，按内核实现做分块反量化并以指定计算类型参与运算，不代表把整个模型永久恢复成 FP16，也不保证端到端延迟下降。

### 4.1 必须修正的包内问题

**A. 跳过预热的布尔参数错误，已做独立 shell 验证。**

镜像环境是 `NO_WARMUP=false`，CMD 却用 `${NO_WARMUP:+--no-warmup}`。POSIX shell 判断的是“非空”，因此实测展开为 `--no-warmup`。同理，`VLLM=false` 和 `BF16=false` 也不会关闭相应开关。实验启动器应显式解析 true/false，采用确定的参数数组；禁止原样用字符串布尔展开。

**B. `--bf16` 名字不等于 BF16 全链路。**

`server.py:1063` 实际传 `fp16=args.bf16` 给 AutoModel；模型使用 autocast，vLLM 提示嵌入又转换为 bfloat16。应分开记录 LLM、flow、HiFT、vLLM engine 的真实 dtype，不能只记一个 BF16 标签。0642 中“BF16 基线”应改为“实际精度核验后的半精度基线”。

**C. 不是开一个 BNB 参数就完成量化。**

所检查的 server CLI 未提供 quantization/BNB 参数；`official_model.py:285` 的 EngineArgs 没有显式 quantization。底层模型包装存在 quant_config 透传，但不能证明实例已经使用 BNB。需另查导出配置、加载日志、权重模块类型和显存。默认入口也没有调用 Omni 编排，只调用 `AutoModel(load_vllm=True)`。

**D. 隐含 GPU 保活会干扰其他工作。**

`server.py:1168` 无条件启动保活；内部重复做 4096×4096 BF16 矩阵乘，仅在本 TTS 请求事件置位时暂停。它不知道 Gemma、训练或 OBS 正在用 GPU。实验副本必须增加开关、默认关闭；单列保活开启/关闭的延迟、功耗、温度，不能把耗电换来的成绩写成无成本优化。

**E. 流式增益可能制造失真。**

`server.py:128/152/160` 给非静音块固定 ×45，再硬裁到 ±0.98。原振幅 0.03 放大后就是 1.35，必然被裁；“没有 int16 溢出”不等于“没有削波失真”。先保存增益前后 PCM，统计裁切比例并听音，校准参考音色的增益，不能靠降噪掩盖。

**F. 不是双向流式文本接口。**

`official_model.py:105` 明确禁止 vLLM 路径接收 generator 文本；HTTP 接口接收完整字符串。当前可行方案是“LLM 稳定短句 → 一次 TTS 请求 → 流式音频”，不是把每个 LLM token 原样喂进同一 CosyVoice 请求，也不等于麦克风全双工。

**G. 取消与事件循环尚不完整。**

流式 wrapper 内直接遍历同步推理 generator，阻塞段结束后才 `await`；finally 只复位保活事件。所读生成链未见完整断线→取消 token→vLLM abort→线程/缓存回收的闭环。应改成单工作线程/进程产出、有界队列传递，补显式取消与清理。只断开 HTTP 不足以宣称 GPU 已停止。

**H. 0642 的参数有些还没有接线。**

包内 EngineArgs 写死 `gpu_memory_utilization=0.2`，CLI 未暴露计划中的 0.55、max_num_seqs=1、max_model_len=1024。应先在实验副本加配置透传并打印生效值。0.55 是候选值，不是照搬即可安全；同进程还有 flow/HiFT/ONNX 和 OBS 的显存。

**I. 分段长度实际会增长。**

本包 CosyVoice3 初始化 hop=25、max_hop=100、scale=2；覆盖首 hop=10 后仍用 max(100,40)，所以下一阶段可能为 10→20→40→80→100。实际首段还包含 prompt padding 和 lookahead。源码注释与实际代码有出入，应记录每段实际 token/样本数，不能把 hop=10 写成固定 10ms 或固定长度音频。

## 5. YHLZ 需要一起改的地方

当前实际路径：

```text
完整文本 → daemon /tts → 完整 WAV → audio_sink 写文件入队
        → OBS fetch.arrayBuffer() → decodeAudioData(完整文件) → 播放
```

`backend/live/audio_sink.py:334` 全量 response.read；`web/live_output/player.html:181` 全量 arrayBuffer。播放器在计划未来播放时立即上报 started，且 `at_client_ms` 使用 performance.now()*1000（实际微秒），不能直接当真实首声毫秒。

目标路径：

```text
弹幕选择 → Gemma 产出稳定短句 → TTS 单请求流式生成
       → PCM 适配器 → 有界音频队列 → OBS AudioWorklet → OBS 编码
```

具体契约：

- 保留当前完整 WAV 路由作回退，新增实验流式接口；在实验验收前，默认仍为 Qwen/小艺克隆音色。
- 每块附 request_id、segment_id、generation、seq、sample_rate、channels、sample_count、final。保持顺序；generation 不匹配立即丢弃。
- 包的 stream 输出为 WAV 头后续 PCM，RIFF/data 大小使用未知长度标记。适配器要跨网络分片解析头部并处理半个 sample，不可假设每个 HTTP chunk 就是一段 PCM。建议向 OBS 发送明确帧格式的 PCM，而非让 decodeAudioData 解析未结束 WAV。
- 24k mono s16le 每秒约 48KB；本机传输无需为了带宽先加有损 codec。按 20–40ms 传输 PCM 只改变发送粒度，不能让模型提前产出尚不存在的首段。
- AudioWorklet 使用有界环形缓冲，初始缓存候选 100–200ms，按实测抖动调节；必须做有状态的采样率适配，不能把 24k 样本按 48k 直接播放。
- 文本首段候选 8–16 汉字、后续 20–40 字，优先句读；400–700ms 等待上限是实验参数。不得切断数字/单位/英文单词或朗读未闭合工具 JSON。短句输入不是模型原生双流式，韵律要单独验。
- 初版 TTS 并发=1，只预取一段；同时限制待播总秒数。积压时丢弃过时的未播弹幕回复，不加速播放已有语音来追赶。
- 取消覆盖合成中与播放中。当前 say 在合成完成后读取 generation，有旧合成跨 stop 后进入新代际的风险；应在请求进入时固定代际，入队前再次比较。
- started 改成渲染侧首样本回执，scheduled 单独保留。真正进入 OBS 音轨仍通过录音定位验证。

## 6. 六段任务与三个验收节点

### S1：清理音源，收口 L1

执行第 3 节的 VoiceOnly 三句对照；继而复测播放中 stop、合成中 stop、OBS 页面重载、服务断连。不得重播旧段，不得回落扬声器。

产物：音源配置摘要、原/新录音、逐句起止位置、取消和断线事件日志。完成 **验收 A：纯数字路由成立**。只做了十句匹配不能替代本节点。

### S2：整理隔离实验副本

沿用 0642 的 `/opt/yhlz-cosyvoice-lab`，端口 18094/18095/18096；原 `/opt/yhlz-vllm` 不覆盖。提取最小模型与源码，核验配置与哈希，再选择匹配依赖版本。首个可比结果优先复现包内版本，现有 0.28 作为单独兼容实验，避免与 0.26 结果混写。

修复布尔参数；显式默认预热；关闭保活；增加生效参数/dtype/补丁命中日志、单请求门与取消。参考音频必须干净且与小艺音色方案一致。此 server 缺 ref_audio/voice 返回 422，因此“0 秒参考”只能作为负例，不能当成功基线；另测 3s/10s 参考及同参考缓存命中。

### S3：小矩阵筛选，再做稳定性确认

先固定同一组文本、参考音频、语速、增益，使用默认 Qwen 作基线。CosyVoice 依次测原生/内嵌 vLLM、flow=10/5/3、首 hop=10/15/25；每次只改一个因素。筛选后才测 hop=6/8 和 BNB，避免一次铺开全部组合。

每个候选先 5 请求查崩溃、空音频、杂音；决赛配置使用短/中/长各 10 条，交错顺序、30 热请求，至少 3 次独立进程冷启动。报告全部失败，不只报告最快一句。P95 的小样本误差需明示。

完成 **验收 B：候选模型确有可用收益**：0 OOM、30/30 有效音频；首个有效 PCM 的 TTFA P50≤1.5s、P95≤2.5s；RTF P95≤0.85；听音无明显漏字、参考文本回声、削波与拼接爆音。以上为计划门槛，尚未达到。相对 Qwen 的收益必须在相同文本/音色条件下报告，不能假设必然更快。

### S4：改造 OBS 增量播放器

在新实验出口接 PCM 分帧与 AudioWorklet，维持武装、租约、代际、TTL 和急停契约。先用固定 PCM 模拟断片/抖动/重连，后接真实模型。验收首个音频块到达后开始播放，后续合成仍在进行，不能仅凭 HTTP 使用 chunked 判定流式。

### S5：接 B站弹幕与 Gemma，控制回复节奏

承接台账 0679 的弹幕适配设计：标准化事件、去重、聚合、选择少量可回复消息、绑定当前话题 → Gemma → 稳定短句 → TTS。弹幕是聊天内容，不能授予开发工具执行权限。

首版先做本地弹幕回放，不公开开播。Gemma 的等待、分句等待、TTS 等待分别计时。单模型隔离结果不能代表 Gemma+TTS+OBS 同时运行结果；8GB 若不能稳定容纳，应调整 GPU 层数/缓存或选择较轻 TTS。每句卸载再加载模型会产生很大等待，不应当成低延迟解决方案。

### S6：整链路演练与准入

30 分钟本地回放，加断网/OBS 重载/取消/队列积压/模型错误；通过后 2 小时稳定运行。完成 **验收 C：能长期运行的 OBS 主播出口**：无旧段重播、无扬声器回落、无 OOM、无明显音频断裂；本地取消到渲染静音 P95≤200ms，生成停止 P95≤500ms；首个 PCM 到本地 OBS 录音首声的附加延迟 P95≤300ms。

上述取消门槛也只是目标。B站转码/CDN/观众播放器延迟另测，不混入 TTS 指标。全部通过后才讨论替换默认 TTS 和正式推流。

## 7. 怎么计时，防止测出“假低延迟”

每个请求至少记录：进入选句队列、首个 LLM token、首个稳定短句、TTS 提交、HTTP 响应头、首个非空 PCM、首个可听音频样本、最后 PCM、浏览器首样本渲染、OBS 录音首声、取消发起、取消完成。

- 首包不能拿 44 字节 WAV 头冒充；首个非空 PCM 与首个可听内容也要分开，防止前导静音掩盖等待。
- 包内 first audio 日志从 generator 起算，没包含全部 HTTP/参考音频处理；必须由客户端从请求提交重新计时。
- RTF=合成耗时/最终音频时长；与首声延迟是两个指标。更快完成全句不代表更早说出第一字。
- 后端和浏览器各用单调时钟计本地跨度；Windows/WSL/浏览器时钟不能直接相减，需校准往返偏移并报告误差。OBS 首声用录音中的已知探针/样本对齐。
- GPU 总显存约束沿用 0642：常态≤6.8GiB、峰值≤7.4GiB、OOM=失败；100ms 采样，同时记录推理进程峰值、OBS 占用、温度/功耗/频率。采样峰值可能漏掉短暂尖峰。
- 实验开始前记录正在运行的模型与训练；通过现有调度/看门狗维护状态让 GPU 互斥，不杀 QQ 桥、不让看门狗自动拉回已让出 GPU 的模型。
