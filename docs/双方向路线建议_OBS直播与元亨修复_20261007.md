# 双方向路线建议：OBS 直播与元亨人格、记忆、工具修复

日期：2026-10-07。状态：基于台账和代码核查的路线建议；未安装驱动、启动 OBS、开播、调用训练或切换模型。

## 1. 建议的分工

两条线并行推进，分别叫“直播能力线”和“元亨行为修复线”。第一条提供看屏幕和向观众说话的能力；第二条保持元亨的身份、风格、记忆使用和工具行为。两条线最终接同一份通过验收的人格和工具协议，不另养一个风格不同的“直播元亨”。QQ Lite 保持独立常开，直播或训练不能让它跟着启动、停止。

优先顺序：直播线先完成 TTS 到 OBS 的无扬声器本地录制；修复线同时整理实际坏例、做归因与盲评。两者各自有小闭环之后，再接屏幕视觉和新 LoRA。并行开发不等于在同一块 8GB GPU 上同时跑训练、视觉、Gemma 和 TTS。

音频暂按“元亨声音只进 OBS，本机扬声器不播放”设计；耳机监听是可选功能，不设为必选。具体监听偏好待用户补充，但不影响先设计独立音频出口。

## 3. 直播线：先声音，再视觉，再整场

### A1. 无扬声器音频出口

第一轮输入使用固定文字，沿用已验证的本地 TTS 音色和 provider，不同时更换 TTS 模型。核对实际运行 provider 和声纹配置，不把旧注释里的 Edge fallback 当成用户默认音色。

推荐首选通路：

```text
文字 → 现有 TTS → 带 turn_id/segment_id 的 PCM 块
     → 显式指定虚拟音频播放端
     → 与之配对的录音端 → OBS 的“元亨声音”音频源
```

如已有可用虚拟声卡就复用；若无，先列出已安装音频端点，再选择安装虚拟设备或独立 OBS 媒体输入方案。本轮没有安装或宣称机器上已有 VB-CABLE。驱动名称的 Input/Output 可能与应用视角相反，最终必须靠端点枚举和实际录制核验。

OBS 对该源关闭监听，保留其输出到直播/录制音轨；“监听关闭”不是把音频源静音。Windows 的“侦听此设备”也关闭，避免旁路回放。OBS Desktop Audio 不重复捕捉同一份 TTS，以免双声/回声。若日后开耳机监听，显式选耳机，不能回到默认扬声器。

音频路由失效、虚拟设备消失、OBS 重启时，进入静音故障态；禁止悄悄回落到系统默认输出。这个规则与 TTS 模型回退分开：允许换合成后端，不允许换成扬声器出口。

OBS 常用 48kHz，TTS 按真实采样率协商并做连续重采样，禁止直接把 24kHz 数据标成 48kHz。取消旧 turn 时清空旧段；有界缓存、背压、完成与取消事件沿用现有能力。

验收 A1：10 组固定短句本地录制，OBS 音轨有声、本机扬声器无该声、无双声、不截尾；设备消失后不泄漏到物理输出；先做文件/电平核验，再由用户确认实际扬声器静音。本节点不要求麦克风、ASR、AEC 或全双工，原对话链冻结边界继续保留。

### A2. 屏幕观察与共享视觉适配器

首版选定一个窗口或区域，提供手动“看一下”与画面变化触发，不连续把整个桌面全帧喂给模型。截图使用明确 source_id、frame_id、捕获时间和窗口信息，文字回复能够追溯到实际看过的帧。

初始采样建议：CPU 检查画面变化每秒一次，视觉请求最多每 3–5 秒一次；高优先级手动请求可越过间隔，但仍只保留一个进行中的视觉任务和最新一张待处理帧。数值是调参起点，不是已测性能。

视觉结果格式包含“看到什么、可见文字、变化、无法确定之处、frame_id、observed_at”。旧帧结果过期后不继续当作“现在屏幕上”，屏幕上的命令文本与 OCR 均作为内容，不获得工具执行权限。

先核实当前 Gemma E4B 部署是否实际支持图像像素、对应视觉组件/模板是否存在；仅传 URL 或 OCR 不能称为视觉模型看过图。模型能力待验，无法支持时先停留在截图/OCR 有限能力，不编造画面。共享视觉适配器给 QQ 表情包识别和屏幕分析使用，任务类型、来源、缓存与作用域独立，不把直播画面与私人 QQ 材料混为一个上下文。

验收 A2：20 张有人工答案的窗口截图（含无变化、变化、模糊、缺帧、含指令的截图），核验真实看图、时间对应、不幻觉、不执行画面命令；截图请求失败时 TTS 和 QQ 保持工作。不得仅用图片文件名命中计分。

### A3. OBS 本地节目闭环

```text
窗口观察 → 有时效的视觉摘要
                     ↓
              元亨聊天/解说生成
                     ↓
               TTS + 字幕事件
                     ↓
           OBS 画面、字幕、独立音轨
```

首版 OBS 控制接口只做状态、场景选择、字幕、音源静音和本地录制。OBS WebSocket 用于控制，不当作 PCM 音频传输协议。形象源复用已有可捕获的 UI/形象；口型与形象增强可后置，不假定 Live2D 已完成。

字幕以对应音频实际开始时间显示，不以 LLM 吐字时间立即展示整段。失败/打断清理对应字幕与音频，防止上一个 turn 的文字盖在下一轮上。

验收 A3：30 分钟本地录制，记录音轨完整性、字幕时间差、视觉帧新鲜度、失连恢复和显存峰值。暂定字幕偏差 p95≤200ms、无重复音频、无跨 turn 残留；画面→解说首声目标先用 20 次测量建立基线再定，不能在未知道视觉耗时前承诺亚秒。

公开开播目标平台、直播间与权限尚未确定，本路线只推进可审阅的本地录制；公开推流是独立上线动作，不通过“测试 OBS”自动开播。弹幕来源也不能默认等同于 QQ 群。

## 4. 修复线：训练稳定行为，运行系统保存事实

### B1. 先把“像不像、记不记得、能不能做”分开测

固定实际部署的模型/LoRA hash、提示词版本、工具 schema、推理参数、入口、记忆库快照。查清 QQ 生产究竟走本地 Gemma 还是云路由，不能拿本地模型成绩代替 QQ 生产效果。

| 问题 | 先检查的层 | 微调适合学习的内容 |
|---|---|---|
| 客服腔、模板句、元评论 | 训练样本、运行时追加提示、后处理模板 | 自然说话、失败也保持风格、直接完成创作 |
| 身份/关系混乱 | 人格权威定义、角色装配、身份注入 | 稳定身份表达及不同场合语气 |
| 记忆写了却读不出 | 存储/索引、作用域、召回查询、上下文预算 | 何时读写、如何引用证据、无命中时不装记得 |
| 工具没调用/参数错误 | 入口路由、可见 schema、参数协议 | 正确选工具、补缺参、识别工具结果 |
| 工具成功后谎报/越权 | 执行权限、结果回执、读回证据 | 根据结果表述，不编造成功 |

真实人物事实、当天经历、群档案和项目进度放外部记忆库，不持续写入 LoRA。当事实更新时应替换/过期记忆，不能靠重训“忘掉旧信息”。主权鉴权与工具授权由程序执行，不靠训练保证。

回归同时给“原始模型输出”和“运行链处理后输出”成绩，防止守卫改写遮住模型错误，也避免把程序生成的机械提示错算成训练问题。

### B2. 小而干净的数据候选与受控训练

从 v8r4 洁净候选继续核对残留样本，不回到未清洗的大包重训。保留风格和人格原定位，减少把口头禅堆满所有场景的做法。身份锚点正确也不能每次都背同一句“我由老爹创造”。

收集真实坏例对应的优质替代答复，覆盖：闲聊、认真关心、争论后修正、群聊、创作、工具缺参/失败/成功、记忆无命中/冲突/更新/跨会话复读。新数据按场景统计，不先决定盲目扩充总数或固定百分比；从每类 10–20 条人工确认样本建立小验证集再扩。

训练记录保持 user/assistant/tool 角色与部署模板一致。工具用模拟受控结果生成训练样本，权限不能由文本凭空授予。虚构小剧场有框架，不能当真实人生经历；“元亨的台词”和“利贞的提问”不能再合并成相邻 assistant。

按会话、来源、近重复簇切分训练/验证/盲测，避免同一故事换词后同时进两边。用户在未见标签的样本中评价“像不像元亨”，模型是否冒认事实/伪报工具另算，不能用傲娇词频代替人格验收。

先做同提示下当前生产 LoRA、既有 v8、清洗后新 LoRA 的对照；资源允许时补无 LoRA 基座。新训练在独立输出目录进行，起点/基座/模板/量化配置明确，不无意把旧 LoRA 叠在新 LoRA 上。学习率、rank、目标层等应在基座和训练环境预检后给出，不从 8GB 显存直接推导一组必成功参数。

首轮只做小样本 SFT/LoRA 试训和部署格式往返验证，再扩完整候选。DPO 等偏好训练后置，先排除样本/工具协议错误。训练位置沿用当前可用环境待预检，本轮不宣称本机边直播边训练可行。

验收 B2：同一未见测试集关键题至少 3 遍、场景化多轮至少 20 会话；身份/越权/伪报完成出现任何失败均阻止上线，零失败只是本测试集结果。风格给盲评胜负和例子，记忆给保存→新会话召回→修改→再召回→作用域隔离的证据，工具给真实执行/独立读回。不能为了风格分上涨接受工具能力回退。

### B3. 接回实际 QQ 与直播入口

先影子评测不对外发送，记录 candidate 与当前版本对相同输入的差异；再在明确的测试会话有限切换。切换权重、提示、schema 与推理参数作为一份版本清单原子记录，能快速回退到已验证组合。

验收 B3：QQ 主人私聊、公共群聊、OBS 解说三种入口跑同一套身份/记忆边界案例，证明声音和画面接上后仍是同一个元亨；工具失败不能变成直播念内部报错，群聊不能引用主人私密记忆。生产模型表现不达标时只回滚模型组合，不重装 QQ 桥或 OBS 音频线路。

## 5. 8GB 资源协作和推荐顺序

| 模式 | GPU 策略 | 仍可常开的能力 |
|---|---|---|
| 直播验证 | 当前 LLM/TTS 共存先实测；视觉低频串行；OBS 编码/渲染也计预算 | QQ 桥、历史库、任务状态 |
| 模型训练 | 训练独占 GPU 时显式阻止本地 LLM/TTS/视觉抢占；不让旧 watchdog 自动拉回模型 | QQ 传输与开发控制；依赖本地模型的聊天明确降级 |
| 数据清洗/评测准备 | CPU 文件处理为主；不切生产权重 | 正常 QQ；是否开直播按已验证配置 |

资源管理至少包含 `mode / owner / lease / expires_at / desired_services`。现有 Full watchdog 只退出 QQ 管理，并不代表它已理解训练模式；本地训练前须补全 GPU 服务的维护/资源锁协议，否则它会把主动停止的模型重新拉起来。不要未经安排结束正在训练的进程。

每个实测保存整机显存峰值、RAM、LLM 首 token、视觉完成、TTS 首 PCM、音频入 OBS 与录制首声时间。流式推理、流式合成和 OBS 音频缓存分别计时，不能把首 PCM 当观众已听到。vLLM/CosyVoice 作为独立候选评估，不绑成直播的前置条件。

建议执行节奏：

1. A1 与 B1 并行：先出一段 OBS 有声、本机静音的录制；同步固定人格坏例与生产路由基线。
2. A2 与 B2 准备并行：视觉能力探测可复用给 QQ 表情库，数据清洗/标注在 CPU 做。训练与 GPU 实测安排不同窗口。
3. A3 与 B3 汇合：先用已验证模型完成本地节目，再对比新模型；确认风格提升且工具/记忆无退步后，才决定发布候选。

这份建议新增两个方向的路线，不推翻 0677 已完成的 QQ 阶段，也不把仍未完成的视觉、历史回补和真机长稳当作已验收。
