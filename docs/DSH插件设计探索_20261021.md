# DSH 插件/扩展设计探索：方法、优势、技术支持与边界

日期：2026-10-21 · 目的：为元亨新架构选型，先弄清 DSH 插件到底能做什么、怎么做、能依赖到什么程度。
结论：**DSH 的插件契约值得学，部分能力值得用；但它是“Agent 运行时内的扩展”，不是“长驻服务/实时身体的宿主”。**

> **2026-10-21 老爹决策**：**不把元亨接入 DSH**，不做元亨的 DSH 插件/面板试点。DSH 的插件与设置能力只用于利贞（她本来就是 DSH 原生 agent）；元亨的架构改造留在 YHLZ。

## 1. 一句话模型

DSH 是 Cordis 上的“一切皆插件”运行时：没有特权核心，模型适配器、工具注册表、会话日志、Agent 循环本身都是插件；插件向共享 `ctx` 贡献 service、类型化事件和**可逆 effect**，卸载时自动回卷（[官方架构](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)）。

- **Profile**：一次启动的插件树，`$DSH_HOME/profiles/<name>/package.json` 里按顺序列 bundles。
- **Bundle**：可分发的配置层，`package.json` 的 `dsh.bundle.patch` 指向 `cordis.patch.yml`。
- **Patch**：按 `id` 覆盖/插入行；`config` 是整段替换，不是深合并。
- 组合顺序：profile bundles → profile patch → home patch → `--patch`。

本地证据：桌面 profile 只有 4 个 bundle 插件（`dsh-agent-md`、`dsh-chat-wallpaper`、`dsh-global-prompt`、`dsh-startup-secret`），全部用 `cordis.patch.yml` 的 `insert` 行挂载。

## 2. 三种插件形态

| 形态 | 用途 | 必须怎么写 | 不能怎么写 |
|---|---|---|---|
| **函数式插件** | 绝大多数：工具、命令、HTTP、事件、UI | `export const name` / `inject` / `Config` / `apply(ctx)` | `export default`（会被当服务类解析而失败） |
| **服务插件** | 给别的插件提供能力 | `export default class extends Service`，构造器 `super(ctx, 'serviceKey')` | 普通函数导出 |
| **组合包 bundle** | 只把已有插件装到一起 | 只有 `package.json` + `cordis.patch.yml`，`dsh.bundle.patch` 指向它 | 写 JS/TS、`src/` |

UI 插件不是第四种形态，是“函数式插件 + 浏览器半侧”。

## 3. Host / Client 双半

| 半边 | 跑在哪 | 能做什么 | 不能做什么 |
|---|---|---|---|
| **Host** | DSH 的 Node 进程 | 文件、进程、HTTP 路由、工具、服务、设置、事件 | 直接画界面 |
| **Client** | 浏览器/桌面 WebView | slot 组件、设置卡片、浮层、对话节点 | 直接读文件/起进程；必须经 Host 服务 |

本地 `dsh-agent-md` 是完整例子：

- Host：`export const inject = ['systemPrompt', 'webServer']`，用 `ctx.effect(() => ctx.systemPrompt.context({ text: (context) => ... }))` 注入人格，用 `ctx.webServer.register({kind, path, handler})` 暴露同源 API。
- Client：`window.__ModuleLoader__.load({ id, factory(require) { ... } })`，`require('react')`，用 `ctx.slots.inject('settings.section', () => ctx.slots.register({...}, Component))` 注册设置页。
- 名称三处一致：`package.json#name` = patch 的 `id`/`name` = client ModuleLoader `id`。

## 4. 扩展点地图（按需求选）

| 你要加什么 | 用什么 | 关键约定 |
|---|---|---|
| 模型可调用的能力 | `ctx.tools.register(defineTool({...}))` | schema 进系统提示；`execute(args, exec)` 用 `exec.signal`；返回一个 canonical JSON；长任务走 `ctx.jobs.start` |
| 人类可敲的命令 | `ctx.commands.register({...})` | 不经过模型轮次 |
| HTTP 接口 | `ctx.webServer.register({kind:'exact'|'prefix', path, handler})` | 包在 `ctx.effect` 里；重复 (kind,path) 会抛错；显式缓存头 |
| 系统提示/上下文 | `ctx.systemPrompt.context()` / `section()`；`agent.inject()` | 不要把大段内容硬塞；`agent.inject` 是下一轮可见，不是唤醒 |
| 设置页/配置 | `export const Config` + `ctx.settings.register(NS, Config)`；`Volatile` 字段 | schema 校验、默认值、非法值拒绝；`role('secret')` 隐藏敏感值 |
| 网页 UI | `ctx.slots.inject(key, () => ctx.slots.register({...}, Component))` | 只能注册到已声明 slot；owner 卸载自动消失；不要 fork 整个 UI |
| 拦截/观察 Agent | `agent/request`、`agent/pre-step`、`tools/pre-execute`/`execute`/`post-execute` | waterfall 必须 `await next()` 并透传；串行事件没有 `next()` |
| 后台长任务 | `ctx.jobs.start({ kind, label, owner: exec.agent, run })` | **in-process**；进程死则 job 死；owner 会话隔离 |
| 定时提醒 | `ctx.schedule`（`schedule_create/list/update/delete` 工具） | 持久化跨 Host 重启；到点作为原会话 follow-up，不是推送 |
| 周期任务 | `ctx.interval(cb, delay)` | 不是 `ctx.setInterval`；要可清理 |
| 接外部系统 | MCP（`@deepseek-ai/dsh-mcp-client`）或 HTTP 工具 | 外部进程自己管生命周期 |
| 给别的插件用 | `ctx.provide` / Service Definition | 扩展插件依赖 Service Definition，不依赖具体 provider |

## 5. 合同不变量（装不上/没反应，八成是这些）

1. `package.json`：`type: "module"`、`main: "lib/index.js"`；`exports["."]` 与 `exports["./package.json"]` 必备。
2. Bundle：`dsh.bundle.patch` 指向 `./cordis.patch.yml`，且 `exports["./cordis.patch.yml"]` 与 `files` 都有。
3. UI：`dsh.client.platform: "web"` 与 `exports["./client"]` 必须成对；缺一个客户端半侧不组装。
4. **名称三处一致**：包名 = patch 的 `id`/`name` = client ModuleLoader `id`。
5. 禁止声明 `@deepseek-ai/*` 依赖（profile 已提供）；client bundle 里 React/ReactDOM 必须 external（打第二份 React 会崩 hooks）。
6. `inject` 只放必需服务；可选服务用 `ctx.get('x')` 或 `ctx.inject([...], child => ...)`；未声明就访问会 PENDING 或崩。
7. 所有长生命周期资源（route、timer、watcher、DOM、React root、socket）必须放进 `ctx.effect()` 并返回 disposer。
8. 改 `src/` 后构建；不要手改 `lib/`。

## 6. 生命周期与生效边界

- **配置 patch**：YAML 里 `config` 改动可热替换（HMR 开启时）。
- **插件代码**：默认必须重启；想免重启要开 HMR，且依赖 timer 插件，缺了会 PENDING。
- **Client**：需要构建 watcher 持续重写 `lib/client.js`；只改 `lib/` 不重建不生效；刷新页面后才加载新 bundle。
- **安装/卸载**：`dsh plugin --profile <name> add/remove` 只是转发 pnpm；profile 的 bundle 列表由启动器/plugin-manager 对账。
- **Plugin Manager**：Web 侧边栏和 `plugin_manager` 工具可启停行、装/卸 bundle；安装 Host 代码**在进程内、workspace 沙箱之外**执行；版本不兼容可走 `compatibility.json` 的 per-package/per-runtime 豁免，需显式接受风险。

## 7. 优势：它到底解决了什么

| YHLZ 旧问题 | DSH 插件的对应机制 |
|---|---|
| 单体 `console_server` 38 条路由、2128 行 | 一个插件一个能力面；HTTP 用 `webServer.register`，UI 用 slot，设置用 Config |
| 自维护 668 行前端、改一处回归全部 | 设置卡片/侧边栏/浮层按 slot 增量挂载，owner 卸载自动消失 |
| 手写进程/线程生命周期，重启收掉子进程 | `ctx.effect` disposer + `ctx.jobs` owner 语义；但 job 是 in-process，关键任务仍需外部 supervisor |
| 可选依赖（Ollama）被当必选，启动反复等待 | `inject` 只声明硬依赖；可选服务 `ctx.get`/惰性 `ctx.inject`，缺失降级而不是阻塞 |
| 启动链/新旧两套并存 | profile + bundle + patch 层是**单一组合**；`--dump-config` 可审计 |
| 上下文被塞爆（709 次 400） | 工具 schema/系统提示由框架装配；compaction 插件；工具输出有界；但插件自己仍要控制注入量 |
| 版本漂移、API 改动靠猜 | 官方 developer preview 明确“会破坏兼容”；peer 版本、version exemption、源码探针 |
| 重复造桌宠/主题/搜索 UI | 社区已有 Live2D 桌宠、壁纸、启动动画、market 插件，可直接组合 |

**最大的优势不是“功能多”，是“契约化”**：依赖声明、schema、effect、profile 分层、安装/回滚、真实组合测试。这些正是 YHLZ 现在缺的。

## 8. 技术支持：能依赖到什么程度

### 官方
- 文档站：<https://deepseek-harness.github.io/deepseek-harness/>；仓库 `docs/architecture.md`、`docs/development.md`、`docs/subsystems/*`、`docs/cookbook/adding-a-tool.md`、`adding-a-settings-card.md`、`docs/tool-catalog.md`、`docs/config-catalog.md`、`docs/event-producer-consumer.md`。
- CLI：`dsh --profile <name> --dump-config`、`--dump-config-schema`、`--patch`、`headless`；`dsh plugin` 转发 pnpm。
- Plugin Manager：Web 插件页 + `plugin_manager` 工具，支持安装/卸载/启停/检查/版本豁免/日志。
- 测试：仓库自带 keyless smoke、`mock:llm` HTTP/SSE 测试服务器、headless 真组合；client 有 jsdom/SlotTestRuntime。
- 社区：GitHub Discussions、Discord、`dsh-plugin` topic。

### 社区/第三方
- 白皮书：`dsh-handbook`（15 章，含插件开发、上下文、MCP、Windows 坑）。
- 插件开发 skill：`liupengyang-1008/dsh-plugin-development`（12 模板、23 坑、版本闸门、探针脚本）；`NanmiCoder/dsh-agent-teams` 的插件开发 skill（合同/验证矩阵）。
- 目录/市场：`awesome-dsh-plugin`、`dshbase`、`dsh-market` 等；质量参差，安装前看源码。

### 版本与稳定性（必须知道）
- 官方 README：**developer preview，会有兼容性破坏**；`packages/README` 明确“public APIs remain pre-stable”。
- 社区版本闸门实测：tag 间隔中位数约 1 天，破坏性变更频繁；所以**锁版本、跑探针、以目标版本源码为准**，不能把教程当契约。
- 本机 DSH 是桌面 App 自带的 runtime + 独立 profile；插件 peer 依赖要匹配目标 runtime。

### 安全
- `SAFETY.md`：未做安全审计，不可当生产安全边界；可执行模型生成的代码、加载第三方插件、访问网络/进程/凭证/文件。
- Plugin Manager 文档：安装的 Host 代码**在进程内、workspace 沙箱之外**执行；审批不沙箱插件代码。
- 结论：插件 = 以你的用户权限运行的第三方代码；只装审查过的源，敏感 profile 不装来路不明插件。

## 9. 不能拿 DSH 做什么（对元亨尤其重要）

1. **实时语音/打断/VAD/AEC**：DSH 是 turn-based agent runtime，没有原生实时音频。
2. **长驻服务宿主**：`ctx.jobs` 是 in-process，进程死 job 死；`ctx.schedule` 持久化的是提醒，不是服务。NapCat、llama、B站浏览器 worker 都不该塞进插件进程。
3. **桌宠/Live2D/直播/OBS 的“身体”**：社区有 Live2D 桌宠插件，但绑定 DSH 客户端生命周期；不能替代元亨的实时身体。
4. **QQ 协议桥**：没有 OneBot/NapCat 集成；应保持外部桥，插件只做状态/控制面板。
5. **替代系统级 supervisor**：DSH 不负责拉起/重启 Windows 服务；那是 launcher/NSSM/计划任务的活。
6. **多用户/多租户隔离**：插件代码同进程同权限；不要拿它当安全边界。

## 10. 给元亨新架构的 10 条规则（吸取旧设计教训）

1. **一个模块一个能力**，显式依赖；可选依赖必须能降级，不许阻塞启动。
2. **所有长生命周期资源有 disposer**；禁止裸线程/裸 timer；卸载要回卷。
3. **配置 schema + 默认值 + 校验**；端口、模型、路径不许硬编码。
4. **进程边界**：实时/外部服务在 supervisor；插件/面板只做状态、控制、工具。
5. **单一组合入口**：一份 profile/bundle/启动链；禁止新旧两套并行。
6. **契约测试 + 真组合烟雾**：`--dump-config`、真实 profile 安装、一条命令/一个 UI 可见面。
7. **前端用 slot/panel，不 fork 整个 UI**；聊天/设置/状态各自独立挂载。
8. **任务语义分清**：in-process `jobs` 只做可丢的后台；关键任务用外部持久队列 + 独立 worker。
9. **版本门**：锁 DSH/插件版本，升级前跑源码探针；不接受“最新版应该兼容”。
10. **安全默认**：插件同权限，最小暴露、来源审查、敏感数据不进插件。

## 12. 结论

- **设计方法值得照搬**：显式依赖、schema、effect/disposer、profile/bundle、slot、真实组合测试。
- **运行时只用在合适的地方**：DSH 插件只服务利贞；元亨不接入、不做 DSH 面板、不做 DSH 插件试点。
- **不要为了“插件化”而插件化**：如果能力需要独立进程/实时性，就留在外部，用 HTTP/MCP 连接；DSH 只做控制面。

> 下一步建议（仅利贞侧）：如确需一个利贞自己的面板，在独立 `lizhen-lab` profile 做只读插件验证安装、slot、HMR、卸载四条链路；元亨侧继续走 YHLZ 内部的 P0 稳定化与拆层。
