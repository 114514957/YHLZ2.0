## ⭐ 一、Gemma/QLoRA 必须显式开的四样（"那个东西"就是这里）

以前我们靠库的默认值，现在**全部写死并打印**。

| # | 开关 | 值 | 为什么必须显式 |
|---|---|---|---|
| ① | `attn_implementation` | **`sdpa`**（可切 `eager` 对照） | Gemma 系列在注意力实现上有已知差异；默认值随 transformers 版本变，**不写就等于随机**。我们装的是 5.15.1 |
| ② | `use_cache` | **False** | 开梯度检查点时 HF 强制要求；留着 True 会警告并可能行为异常 |
| ③ | **`gradient_checkpointing_kwargs={"use_reentrant": False}`** | 必传 | **最像"那个要开的东西"**：旧式 reentrant 检查点会**跳过不需要梯度的段**，典型症状是 **loss 在动、LoRA 学不到东西**（"训练完了但没效果"） |
| ④ | **`enable_input_require_grads()`** | 显式调用 | 让输入侧也带 `requires_grad`；PEFT 只在"没传 use_reentrant 或传 True"时才帮你调——**一旦传了 False 它就不调了**，所以必须自己开 |

附：`tokenizer.padding_side="right"`（训练侧，避免左侧 padding 干扰 causal 掩码）。

> 这四条**不是"优化"，是"通路"**。开着它们，梯度才到得了 LoRA；关着，跑完 742 步也是白跑。

## 二、新增的第五道保险：**梯度自检**（本次流程的核心新增）

**不问"开关开没开"，直接看梯度有没有到 LoRA。**

训练器在第 `grad_check_step`（默认 10）步做：

```
LoRA 参数 256 个，拿到非零梯度 256 个
   q_proj ‖g‖=3.2e-03
   v_proj ‖g‖=2.8e-03
   ...
```

- **非零为 0** → 当场 `RuntimeError` 中止，并提示去查 ③④②。
- 这样"白训 742 步才发现没效果"的成本从 30 分钟降到 **30 秒**。

## 二、⚠️ 权重配比硬规则（2026-11-14 v13 事故后新增，**开训闸门会拦**）

**教训**：v13 工具题 16 道挂 13 道，答案全是「我记着」「好，任务已添加」「查过了，没有」——
**不调工具，用话糊过去**。而它的工具样本 **条数只少了 64 条（900→836），看着完全正常**；
真因在**权重**：口述故事抢到 26%，工具样本被稀释到 **6.9%**。

> **只看条数会骗人，必须看权重占比。**

| 类 | v9t10（48 分） | **v13（38 分）** | v14（已修） | 闸门要求 |
|---|---|---|---|---|
| 工具/格式类 | 8.9% | **6.9%** ❌ | **16.9%** | **≥ 12%** |
| 口述/口味类 | — | **26.1%** ❌ | 13.4% | **≤ 18%** |
| 单来源上限 | — | personality 25.6% | — | **≤ 30%** |

`tools/train_preflight.py` 已把这三条做成硬检查，**违反直接拒绝开训**：

```
v13 → ❌ 工具/格式类权重仅 6.9% < 12%｜口述/口味类 28.4% > 18%
v14 → ✅ 通过（工具 16.9%）
```

**配方前必做一步**（1 分钟）：

```bash
python experiments/measure_tool_weight_share.py    # 打印各类权重占比
```

### 判断口诀

1. **工具类不许低于 12%** —— 低于它，模型会"用话糊过去"而不是真调工具。
2. **口味/故事类不许超过 18%** —— 它是"调味"，不是主菜。
3. **调整权重用纯乘法**（`w × k`），不要写 `max(w, 1.0) × k` ——
   那会把原本 0.3 权重的行全抬到 1.0，实测把工具类从 17% 冲到 **36%**（过头）。
4. **一类题整类下滑 ≥30% 时，先查该类权重占比**，再怀疑数据量或 lr。

## 三、五阶段（命令照抄）

### 阶段 1 · 素材就绪检查（无卡，1 分钟）

```bash
python tools/build_material_v13.py          # 可重跑，确定性
python tools/train_preflight.py --config dist/material_v13/config/finetune.gemma4.v13.json \
    --n-train 5641 --changed "数据 v13" --smoke-done
```

要点：**素材里已按老爹禁令清洗过**（破折号 507 处改句号、543 条禁令命中整条删），
词表与线上同一份 `config/style_bans.json`。

### 阶段 2 · 冒烟（GPU，~10 分钟）

```bash
python dist/material_v13/train_v13.py --config config/smoke60.json
```

smoke60 配置 = v13 全套超参，**只改三样**：`train_file`（60 条子集）、`epochs=6`、`lr=1e-4`。

**三条判据全过才继续**：
1. loss 从 ~5 起，末值 ≤ 起点 **60%**
2. `[gradcheck]` 打印的"非零梯度"个数 **= LoRA 参数个数**（不是 0、不是一半）
3. 拿这 60 条原样推理，能**逐字背出**；与基座直接推理**明显不同**

### 阶段 3 · 正式训练（GPU，~30 分钟）

```bash
python dist/material_v13/train_v13.py --config dist/material_v13/config/finetune.gemma4.v13.json
```

预期：742→**706 步**（5641/8=706）｜warmup 22 步｜lr 2e-4 → 0｜loss ~5 → ≤3
日志里必须看到三行：`attn_implementation = sdpa`、`enable_input_require_grads() 已显式开启`、`[gradcheck] ... 非零梯度 N/N`

### 阶段 4 · 转 GGUF + 评测（本地 CPU，~10 分钟）

```bash
python llama.cpp/convert_lora_to_gguf.py <adapter_dir> --base <base_hf> --outfile v13.gguf
llama-server -m <base.gguf> --lora v13.gguf -ngl 99 -c 8192 --parallel 1 -rea off --jinja --port 8093
python experiments/eval56_28.py --tag v13 --port 8093
```

**同一 GGUF 必须跑两遍，分数完全一致**（不一致＝环境问题，不是模型）。

### 阶段 5 · 上线 + 记账

- 超基线（当前 **56 题 49 / 群聊 27**）才换 `backend/yhlz_paths.py::YH_LORA_GGUF`
- 重启一律走 `tools/restart_daemon_safe.py`（翻唱在跑会拒绝）
- 台账记：变量、条数、lr/epochs/eff_batch、loss 起终、gradcheck 结果、56+28、闸门、是否上线

## 四、故障判读（新流程专用）

| 现象 | 先看什么 | 多半是 |
|---|---|---|
| `[gradcheck]` 非零梯度 = 0 | 有没有 `use_reentrant=False` | ③ 没传 |
| 非零梯度只有一半（如 128/256） | 是不是 `k_proj/v_proj` 没挂上 | target_modules 写错 |
| loss 不动 | `trainable params` 是否 34.88M | ④ 没开，或 LoRA 没挂上 |
| loss 动但效果差 | 是否 3 epoch；素材是否被稀释 | 见台账 1211 |
| 显存 OOM | 是否开了 `fp32` 计算精度 | 换 `bf16`，或降 batch |
| 训练完 adapter 无变化 | GGUF 是否真被 llama-server 加载 | `/health` 的 `llm` 字段 |
