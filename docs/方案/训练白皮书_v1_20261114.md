## 1. 数据层

### 1.1 来源构成（v11 为例）

| 类别 | 占比 Σweight | 说明 |
|---|---|---|
| 口述故事（老爹亲讲） | 约 3.5× | 权重最高，风格最纯 |
| 自有对话/日记/关系样本 | 主体 | 人格与关系事实 |
| 工具轨迹 | 5.5× 已迁出 | 分给 Gemini 做工具训（台账决策） |
| LCCC 等开源对话 | **0.15×** | 只做"别太机械"的稀释，多了变助手 |

### 1.2 权重如何生效（关键机制，曾长期失效）

**【代码】不是把 weight 乘进 loss，而是重采样**：

```python
_idx = rng.choices(range(n), weights=[w/Σw for w in ws], k=n)   # 总数不变
ds = ds.select(_idx)
```

- 2026-11-08 审计发现：`_slim()` 只保留 `messages_json/source`，**weight 字段被丢弃，从未参与训练**【代码前 v11 注释】。
- 修复后实测"平均 weight 0.963 → 实际生效 0.958"，接近说明重采样生效。
- **推论【推断】**：2026-11-08 之前所有"加权"实验，权重其实都是 1.0——那些实验的结论要打折看。

### 1.3 清洗与检查（必须过的五道）

| 检查 | 做法 | 为什么 |
|---|---|---|
| 结构 | 每条必须有 `messages` 且至少一条 assistant | v11 曾把 949 条**工具样本**误判为"结构坏"（assistant content 空 + tool_calls），要显式放行 |
| 截断 | **从右侧截**，保留开头 | 左侧截断会把 assistant 段切光，标签全 `-100` |
| 全 `-100` | 有则**丢弃该条** | 否则单批全坏时 loss = 0/0 = **NaN** |
| 重复 | `_repetition()` 检测复读 | 复读是最常见退化 |
| 工具字段 | `tools`/`weight`/`safety_labels` 异构字段先摊平 | Arrow 推断类型会直接抛错 |

### 1.4 数据量结论

| 数据量 | 版本 | 分数 |
|---|---|---|
| 5659–6155 | v9t7/t8/t10 | 42–48 |
| 7586 | v10u | 48 |
| **13189** | v11 | **44** |
| 318（补丁） | stylepatch4 | 46（在 dpo2 上 -3） |

**【实测】结论**：本项目在 **5.9k–8.9k** 区间最稳；**过 1.3 万开始负收益**（且与 lr 改动混淆）。

## 2. 训练层

### 2.1 基座与量化

| 项 | 值 | 依据 |
|---|---|---|
| 基座 | `models/gemma4-hf/gemma-4-e4b-it`（bf16，15.99 GB ≈ 8.00B 参数） | 【代码】safetensors 头 |
| 量化 | 4bit NF4（`bnb_4bit_quant_type=nf4`） | 【代码】 |
| 特别注意 | `prepare_model_for_kbit_training` 会做 fp32 upcast，**8G 卡会 OOM**（需 10.5 GiB）→ 用 `skip_kbit_prepare` | 【实测】 |
| 张量并行/多卡 | 单卡即可（A800 40G 充裕） | 【实测】 |

### 2.2 LoRA 挂载

```python
LoraConfig(r=16, lora_alpha=32, lora_dropout=0.05, bias="none",
           target_modules=["q_proj","k_proj","v_proj","o_proj",
                           "gate_proj","up_proj","down_proj"],
           task_type="CAUSAL_LM")
```

- **【代码】可训练参数 34,881,536 / 7,975,982,368 = 0.4373%**。
- **【代码】文本塔就是 `nn.Linear`**：`Gemma4TextMLP` 无 `ClippableLinear`；该类只出现在
  `Gemma4AudioFeedForward` / `Gemma4AudioLightConv1d` / `Gemma4VisionMLP`。
  → 外部传的"必须写 `q_proj.linear`、否则挂不上"**对本模型不成立**。
- **【代码】全模型只有 1 个 bias**：`model.audio_tower.output_proj.bias`；**没有 lm_head**（tied embedding）
  → `bias="lora_only"` 与 `modules_to_save=["lm_head"]` 都是空操作。

### 2.3 损失

标准 causal-LM 交叉熵，prompt 段置 `-100`：

```python
labels = [-100] * n_prompt + ids[n_prompt:]
loss   = CrossEntropy(logits[:-1], labels[1:])      # 无 label smoothing
```

- 不做 loss 加权（权重走 §1.2 重采样）。
- **【实测】本项目 loss 量级 5.3 → 1.6**；外部所谓"E4B 正常 13–15"与我们的分词器/掩码/序列长度不同，
  **不可横比**。

### 2.4 学习率与调度

```
warmup_steps = max(1, int(warmup_ratio(0.03) × steps_per_epoch × epochs))
lr(t)        = cosine 衰减，峰值 lr，末值 ≈1e-8
steps_per_epoch = ceil(n_train / eff_batch)
eff_batch       = batch_size × grad_accum  = 8（本项目恒定）
max_grad_norm   = 1.0
```

| 版本 | lr | 调度字段 | 备注 |
|---|---|---|---|
| v9t5–v9t10 | 2e-4 | **None（吃默认）** | 【代码】配置里没显式写 |
| v9t11 起 | 2e-4 | cosine + paged_adamw_8bit | 显式 |
| v11 | 1.5e-4 | cosine | 与数据量同改，未归因 |
| 补丁类 | 3e-5 | cosine | stylepatch |

**【实测】建议**：1 epoch 下 lr **1.5e-4–2e-4** 都可用；不要为了"更稳"降到 5e-5（我们这代数据上几乎不动）。

### 2.5 梯度

| 版本 | gn 均值 | p95 | max |
|---|---|---|---|
| v9t10 | 2.43 | 3.36 | 4.50 |
| v11 | 3.73 | 5.74 | 9.43 |

**【实测】** 无 NaN、无 100+；clip=1.0 未频繁触发。梯度抬升与"数据更杂 + 分数下降"同向。

## 3. 评测层（分数可复现的根本原因）

### 3.1 两套题库

| 题库 | 题数 | 构成 | 闸门 |
|---|---|---|---|
| `tools/persona_bank.py` | **56** | 人格 / 关系 / 工具遵循 / 风格 四类 | **r07, r08, s06**（【代码】`GATE_IDS`） |
| `tools/group_bank.py` | **28**（g01–g28） | 多人 / 短回合 / 关系冒认 | `entry["gate"]` 为真的题（【代码】`is_gate`；实测 g09 曾破闸） |

### 3.2 判分是**确定性规则**，没有 LLM 判官

**【代码】`persona_bank.verify()` 的判定项**：

| 项 | 含义 |
|---|---|
| `all_keys` | 全部子串必须出现 |
| `keys` | 至少一个出现 |
| `negative` | 任一子串**不得**出现（助手腔/撇清/旧人设/规则泄漏） |
| `no_tail_question` | 结尾不得是问号 |
| `max_len` / `min_len` | 字数上下界 |
| `expect_any_tool` / `forbid_tools` | 必须/禁止调用指定工具 |
| `_repetition()` | 复读检测 |

`JUDGE_VERSION = 6` 指**规则集版本**。
**这解释了两件事**：① 同一版本重测分数完全一致；② 分数低不等于"感觉差"（判据死板）。

### 3.3 验收口径

| 层 | 判据 |
|---|---|
| 通过 | **56 题 ≥ 49** 且 **28 题 ≥ 27** 且 **闸门全过** |
| 稳定性 | **同一 GGUF 双跑分数完全一致**（否则环境有问题，不是模型） |
| 主观 | 老爹听/读，**只用来看质感，不替代分数** |

> ⚠️ 历史教训：评测脚本漏传 system prompt 导致"客服腔 4/25"的**假结论**（实际 0/25）。
> **任何评测先确认提示词注入路径与生产一致。**

## 5. 标准作业流程（SOP）

### 阶段 0 · 立项（30 分钟，无卡）
1. 写清**假设**：这次只改哪个变量、期望什么变化
2. 翻台账（`ledger_search`）确认不是重复劳动
3. 备份当前生产 adapter（回滚点）

### 阶段 1 · 冒烟测试（必做，~10 分钟卡）
**目的**：证明"能背下来"，即训练通路健康。

| 项 | 值 |
|---|---|
| 数据 | 从正式集抽 **60 条**（固定种子） |
| epochs | **6**（约 45 步） |
| lr | **1e-4** |
| batch / accum | 8 / 1 |
| seq | 1536 |

**判据（三条全过才进阶段 2）**
1. loss 从 ~5 持续下降，末值 ≤ 起点 60%
2. 拿这 60 条原样推理，输出**逐字贴近**目标
3. 与基座直接推理**明显不同**（证明 adapter 生效）

### 阶段 2 · 单变量正式训练（~15 分钟卡）
- 只改一个变量，其余锁定并**写进台账**
- 1 epoch、cosine、clip 1.0、eff_batch 8
- 训练后**立刻**导出 `train_log.csv` + `train_summary.json`

### 阶段 3 · 验收（~6 分钟 CPU）
1. 转 GGUF
2. 起独立 llama-server（**不碰生产 8081**）
3. 跑 56 + 28 各两遍，**分数必须完全一致**
4. 闸门必须全过
5. 分数 ≥ 基线（当前 49/27）才谈上线；否则**记录为负结果**

### 阶段 4 · 上线与回滚
1. 换 `yhlz_paths.YH_LORA_GGUF` 指向新 adapter
2. 重启 llama 与 daemon（**先看 `/sing/status`，勿在翻唱中重启**）
3. 观察 24h：回复长度、复读率、群聊闸门
4. 出问题 → 改回旧 adapter 路径即可（无需重新训练）

| 反模式 | 后果 | 证据 |
|---|---|---|
| 3 epoch 起步 | 分数腰斩（25 vs 42） | 【实测】 |

## 7. 故障排查

| 现象 | 先查什么 | 常见真因 |
|---|---|---|
| loss 不降 | 标签是否全 `-100`；数据条数是否 0 | 右截断 bug / 结构过滤误杀 |
| loss 出现 NaN | 单批是否全 `-100` | 已加过滤，若再现查 tokenizer |
| loss 降但效果差 | 是否 3 epoch；分数是否与 loss 反向 | 过拟合风格模板 |
| adapter 加载后无变化 | 是否真换成新 GGUF；`/health` 的 `llm` 字段 | 路径没改 / daemon 未重启 |
| 分数两跑不一致 | 采样是否 greedy；提示词是否一致 | 温度/种子/上下文 |
| 群聊表现与 56 题不符 | 是否只跑过 56 题 | **评测口径≠部署口径**（56 题单人 vs 群聊多人） |

## 9. 未解问题（诚实清单）

1. **P7 稳定性**：从未验证"同配置重跑是否同分"（只验过评测双跑一致）。
2. **数据红线的精确位置**：6k 好、13k 差，**拐点在哪不知道**（8.9k 是好的，1.3 万是差的）。
3. **lr 与数据量的交互**：v11 把两者混在一起，无法判断"数据多"本身是否有害。
4. **KL 锚定未试**：`CE + λ·KL(当前‖dpo2)`，λ 0.02–0.05，理论上能缓解遗忘，本项目**一次都没跑过**。
5. **`use_cache=False` 是否真无副作用**：源码看无特殊分支，**未做前向 logits 对比**。
6. **群闸门清单**：`group_bank` 用 `entry["gate"]` 标记，但**未逐题核对哪些是闸门**。
