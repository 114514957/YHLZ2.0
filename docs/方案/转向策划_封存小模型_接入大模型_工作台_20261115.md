### 阶段 2 · 大模型接入（P0，1–2 天）

**前提动作**：拿到 key（环境变量或 `config/llm.local.json`，**不入 git**），定一个主力模型。

**架构**：新建**唯一出口** `backend/llm_router.py`

```
LLMRouter.chat(messages, tools=None, stream=True, profile="chat")
   ├─ cloud : OpenAI 兼容（base_url + api_key + model）  ← 默认
   ├─ local : llama.cpp 8081（保留，作兜底与离线评测）
   └─ 策略 : cloud 连续 2 次失败 → 切 local；60s 复核后回切（复用 0114 语义）
```

**配置全走环境**（不入库）：

| 变量 | 例 | 说明 |
|---|---|---|
| `YHLZ_LLM_PROVIDER` | `cloud` / `local` / `hybrid` | 默认 `hybrid` |
| `YHLZ_LLM_BASE_URL` | `https://api.deepseek.com/v1/chat/completions` | OpenAI 兼容端点 |
| `YHLZ_LLM_MODEL` | `deepseek-chat` | 模型名 |
| `YHLZ_LLM_KEY` | `sk-…` | 密钥 |
| `YHLZ_LLM_TEMP` / `_MAXTOK` / `_TIMEOUT` | `0.7` / `800` / `120` | 采样与超时 |

**改造方式**：13 处生产现场**只改一行**——把 `build_openai_compatible_llm_turn(base_url=…)`
换成 `llm_router.turn(profile=…)`；离线脚本统一读 env，不再写死 8081。

**验收（四条，缺一不可）**
1. `/health` 显示 `provider=cloud:<model>`，`/props` 能查到
2. **三渠道同测**：工作台一句、QQ 群一句、QQ 私聊一句，**都走大模型**（看服务端日志的 request id）
3. **断网演练**：把 cloud 端点指向死地址 → 自动切 local，回复不断；恢复后 60s 内回切
4. 成本与延迟有数：单轮 token/费用、TTFT/P50/P95 记进工作台

**风险与对策**

| 风险 | 对策 |
|---|---|
| 成本（按 token 计） | 设日预算上限 + 提示词瘦身（见阶段 4）+ 缓存命中（稳定前缀放前） |
| 延迟（历史 TTFT 0.9–2.2s） | 流式；群聊短上下文；超时分级 |
| 隐私（对话出厂） | 明确"哪些内容不许出本机"（记忆原文/台账/密钥），在 router 层做**出口脱敏** |
| 工具调用格式差异 | 大模型 function calling 更规范，但仍要适配 43 个工具 schema + 失败兜底解析 |
| 人设漂移 | 大模型没有"训练出来的人格"，**全靠提示词**——这正是阶段 4 的重点 |

### 阶段 4 · 提示词工程（P1，与大模型同步）

继承历史结论：
- 分块 + 覆盖（1193）、A/B 开关、**35/42 层 512 可见窗**（1221）、去 AI 味硬规则（1208）
- **硬约束放末尾**、**只搬不复制**（1221：锚点式重复会掉分）

大模型带来的新手段：
1. **系统提示瘦身**：目标 ≤1500 token（现在 5009 字 ≈ 3400 token）；成本与延迟都随长度线性
2. **few-shot 放进系统提示**：大模型吃示例比小模型好，尤其语气/收尾
3. **结构化输出**：工具调用让大模型自己规范化，减少 `<call:...>` 伪调用
4. **前缀缓存**：稳定段（身份/口径）放最前，变动段（用户轮/上下文）放最后 → 命中缓存省钱
5. **每版提示词必回归 152 题**（现在基线 125/152，群聊 74/75）

**验收**：任改一次提示词，能在工作台一键出分，并与上一版逐题对拍。

### 6.4 阶段 1.5 · 记忆修整（**插在大模型接入之前**，台账 1234/1235）

**为什么插在最前面**：recall 确实在生产路径上（`target_entry.py:681/699`），但实测**有效命中仅 ~25%**；
不修就接大模型 = 上线第一天把工程流水账当她的记忆，还烧 token。

**现状数字（只读实测，台账 1232/1233/1235）**

|---|---|
| 记忆总量 | **1022 条**（active 474 / archive 305 / downgraded 243） |
| 分层 | **her 157｜owner 51｜engineering 347｜unknown 467** |
| 现在会注入的条件 | `type∈{preference,event,decision}` 且 `importance≥4` → **529 条** |

**五步（顺序即优先级）**

| 步 | 做什么 | 产出 | 验收 |
|---|---|---|---|
| **0** | **建"记忆召回评测集" 30–50 条**：问句 → 应命中的记忆 id / 应"无命中" | `data/eval/memory_recall.jsonl` | 人工抽检通过；能给出精确率/召回率 |

| 2 | **召回加严接线**：3-gram ≥2、碎片过滤、只取 her+owner、相关性门槛 | 改 `contextual_recall`（或旁路新函数） | 用第 0 步评测集：**精确率 ≥80%**，召回不低于现状 |
| 3 | **注入可观测**：每轮记 `{turn_id, 命中id[], 注入/未注入, 原因}` | `cache/recall_trace.jsonl` | 工作台能回看"这一轮喂了什么" |

**安全边界（自定，必须遵守）**
- 第 0–2 步**只读或副本上跑**；**任何 UPDATE 前先备份** `memstore.db`（带时间戳）并记路径。
- 任何一步异常 → 回滚备份，不凭"应该没事"。
- 第 1 步是**唯一会改数据结构**的动作，做之前单独找老爹确认。

**与阶段 2 的接口**
- 大模型接上后，注入的仍是"记忆块（历史之后）"；本次修整保证**喂进去的是 her/owner，不是工程流水账**。
- 大模型上下文更长，但**注入量不膨胀**（仍 limit=2/3），省 token 也防跑题。



**"记忆块"在本项目有确切含义**（记录 0920，学 lianlian-bot）：
> **记忆块是注入到提示词里的一块记忆内容，放在"历史之后"，以保住 KV 前缀**（缓存友好）。

所以"继承"不是重写，而是**把存量记忆原样接上，并保持注入位置与结构不变**。

| 存量资产 | 规模 | 继承方式 |
|---|---|---|
| L2 记忆条目（`cache/memstore/memstore.db`） | 962+ 条（QQ 来源 225） | 检索接口不变；注入块结构不变 |
| 认知根基（`docs/元亨认知根基.md`） | 5.8 KB | 作为固定块（放在稳定前缀里） |
| 成长日志 | 194 KB | 检索式注入（不全量塞） |
| 日记 / 任务 / 计划 | 27 / 50 / 7 KB | 按需检索 |
| 问句式记忆样本 | 借 235 个 keep 记忆块改写而来 | 仅作历史参考（685 条已删，1087） |

**三件事（验收即完成）**
1. **清点**：按类型/来源/时间出一张表（条数、均长、最近使用）
2. **注入不变**：记忆块仍在**历史之后**；稳定段（身份/口径）在前、变动段在后 → 吃满前缀缓存
3. **召回验证**：用真实问题测"大模型能不能读到她自己的记忆块"——
   沿用 1186 的四层验收思路（阈值 / 排序变化 / 时间窗 / 端到端）
