## 1. 结论与已经明确的方向

用户已经明确 V9 从预训练 base 开始；不再将客服腔成因或 IT/base 对照列为开训必经门。Gemma 是否继续使用是另一个独立问题。base 仍含预训练权重，不是随机初始化。

建议把 Qwen/Qwen3.5-4B-Base 列为第一替代候选；若 LLM 原生接收音频是本次必须保留的能力，google/gemma-4-E4B 仍是重点候选。Qwen/Qwen3-4B-Base 是纯文本、结构较简单的备用；Qwen3-8B-Base 与 Qwen3.5-9B-Base 暂不作为本机 8GB 语音陪伴主线。

这是基于资源、模态与工程路径的选型建议，尚不能证明 Qwen 中文人格质量优于 Gemma，也不能将 IT 排行榜分数当作 base 微调后效果。未完成 base 小试时，不承诺任何模型会自动消除客服腔。

## 2. 对原建议的必要修正

| 原说法 | 修正 |
|---|---|
| 再做 IT/base 四臂对照，base 是待检验方向 | 用户已决定从 base 开始；比较应聚焦 base 候选的部署成本与 SFT 后表现，旧 IT 只保留回滚/历史参照，不再为成因验证租卡 |
| DAPT 只有 100B token 以上才值得，少量语料占预训练比例低所以无效 | 没有此通用阈值。域内/任务适应研究曾在低资源条件见收益，但不是元亨人格实验，不能据此保证本项目收益。0559 跳过 V8 DAPT 的事实保留；其中技术理由不作为跨模型定律 |
| QLoRA 风格必然打折、一定更慢 | 不成立。QLoRA 论文的实验中可维持 16-bit 微调表现；速度/效果取决于模型、内核、序列与数据。优先 BF16 LoRA 是为了减少量化变量，不是宣布 QLoRA 劣质 |
| 80GB 上 BF16 LoRA 轻松，language 全参一定 50–60GB | 长上下文、激活、优化器状态和实现决定峰值显存；旧短序列显存不能保证新长块可训。资源估算必须留空间做峰值测量 |
| 2 万条以上才可全参，4,047 条一定练歪 | 条数不是通用门槛。应看有效监督 token、独立场景、重复、质量和未见题退化；也不能因 LoRA 某次失败就断言参数方式触顶 |
| base 无对话先验，统一多训几轮即可 | base 没有完成目标指令对齐，不等于没有对话相关预训练；要检查格式和监督覆盖，不能以加 epoch 弥补缺失行为 |
| 必须先大量通用 SFT，再单独人格 SFT | 可分阶段或混合训练，也可先用高质量目标对话小试；需补的任务覆盖由失败用例决定。通用保留样本应避免把客服腔重新教回来 |

以上纠正旧报告与此前对话里过度确定的技术判断。LoRA 优先、SFT 主线、DPO 后置仍是本轮工程建议；DAPT 维持不自动启动，另有明确目标和许可语料才评估。

## 4. 本地证据与迁移门槛

- 2026-10-11 nvidia-smi 只读快照：RTX 4060 Laptop，8,188 MiB 总显存，当时 4,493 MiB 已用。该占用只是瞬时，不归因到某个进程，不杀进程或加载候选。
- `dist/local_serve/README_本地部署.md` 有旧 Gemma IT/QAT、2,048 上下文的速度与内存记载；这是已有资产，不是候选 base 的新实测。
- 本地 `models/llama-cuda/src/llama.cpp-b10991/conversion/qwen.py` 已注册 Qwen3 与 Qwen3.5 模型类；`src/models/qwen35.cpp` 有 DeltaNet 层的 LoRA 运算。这消除了“源码完全不支持”的猜测，但不能代替完整 adapter 的导出/加载证明。
- 云端 `sft_train.py` 多模态类与 LoRA 目标正则为 Gemma 专用；默认 `--seq 2048`，旧控制台脚手架是1,024。换 Qwen 必须核对模型类、语言层模块路径、DeltaNet 投影、数据模板和监督区间，不只改 MODEL_ID。旧七个 projection 名在混合结构上并不表示覆盖全部语言层。
- `backend/session_audio_reasoner.py` 有音频进入 session 的分支，目标 composition 也有 ASR 路径。改成无原生音频的 LLM 需要明确选择哪条输入路径；语音服务接口不能因换权重而被假定自动兼容。
- 对 Qwen3.5 候选先验收：HF adapter 转换与 GGUF 挂载、或在高精度同源 base 上合并后再转 GGUF；合并输出是新部署权重，应保留 base 与 adapter 回退。图像 processor/投影器、消息边界、工具格式、结束 token、量化前后输出均要核对。
- 本轮不下载/运行任何候选；没有候选速度、显存、中文自然度或工具回归成绩。

## 5. 这一次怎么做

1. 先回收 V8 的 trainer_state、日志、超参与底座修订。MCP 记录0559中的1.86 s/it、38.6G、645步是当时作业记载，不能作新base长序列成本承诺；原日志 `/root/autodl-tmp/sft.log` 也加入回收目标。
2. 选型聚焦一个主候选和一个备用。若原生听音频非必需，优先 Qwen3.5-4B-Base，备用 Qwen3-4B-Base；若必须保留 LLM 直接听原始音频，优先评估 Gemma4-E4B base。生产仍保持现状直到训练与整链验收通过。
3. 冻结批准素材、按故事/来源分组隔离测试；统计输入 token、有效 assistant labels、上下文/监督覆盖与任务类型，不只数 JSONL 行。当前可用数据能做小试，不宣称已经足够正式定稿。
4. 长块先按各 tokenizer 测长度：>20问答轮、>=400字发言不能在旧2,048 token处静默截断。确定一个能容纳样本且兼顾部署的训练窗口；太长时用连续窗口保留必要前文与有效监督，不能把非相邻轮拼成新的对话。
5. 首次小试用 BF16 LoRA，批大小/梯度检查点按真实长块的峰值显存定；QLoRA 保留为长上下文超显存时的选项。初始超参不是承诺效果，不按固定3–5 epoch硬训到底。
6. 把人格、任务执行、工具、记忆、群聊身份分开评分；必要时补一般任务样本，但先按目标行为审核，避免大批通用助手答案把人格稀释。验证集loss辅助判断优化与过拟合，不取代行为评测。
7. 没有明确领域适应目标就先SFT；若决定DAPT，独立数据/预算/保留checkpoint/基线，不因原书堆得多或预训练占比小直接下结论。DPO仍以后续真实偏好坏例为前提。

### 训练与陪伴要求

- 不能靠纯文本人格LoRA把Gemma补出不存在的原生语音输出；缺失的语音生成模块需另建并对齐或选已有Omni架构。DAPT读书不等于音频编码/语音输出/双工训练。
- Omni继续训练不仅看文字答案：应验证音频输入和同题文本输入的人格一致、语音输出是否对应答案、声线与情绪，以及图像理解、轮次/工具/记忆/诚实行为。不能只用文本测完就宣称全部通过。
- “思想”按有理由的判断、分歧、修正、未知时不编来评估；“陪伴”按记忆延续、关系分寸、自然回应和打断后的承接评估，不以thought标签或语音功能代替。

## 8. 本地部署与本地训练：轻量候选补查

用户追问“就没我能本地部署训练的吗”。纠正：官方默认配置下的9–11GB或BF16视频峰值不能证明所有本地配置不可行；CPU分担/量化/短输入可能改变边界，但能加载不等于能实时、能推理不等于能训练。用户原先云上训练回本机部署的计划仍然保留，未确定改成全程本地训练。

### 新增可研究候选

- **MiniMind-O（jingyaogong/minimind-o）**：公开视听说架构、权重和训练数据；dense可训练主体113.13M、冻结外部模块424.70M，运行总模块537.83M。具备语音/图像特征直接入隐藏空间、Talker生成语音code的路线；训练脚本可分all/audio_proj/vision_proj。作为8GB本地训练研发候选优先于大Omni，尚无本机训练峰值/耗时实测，不保证默认batch或长块可训。
- 作者的3090两小时mini训练是英文、无视觉子集；不能说两小时得到中文视听说元亨。中文/视觉需full或自建相应数据。训练用llm_768.pth的具体训练阶段还须核清，不仅凭“基座”称呼就当纯预训练base；冻结编码器/codec有既有权重，不能说所有组件都从零学成。
- 技术报告自述小模型在语音自然度、长回答稳定与视觉能力上有明显局限，未证明能胜任元亨哲学、主见、长期人格；适合先复现闭环、学习模块对齐，不签收替代正式认知底座。
- **sensenova/InteractiveOmni-4B**：本轮新核官方HF和GitHub，支持图像/音频/视频输入与文字/语音输出、中文语音；完整模型HF标约6B。列入本地量化推理预检候选，与Qwen2.5-Omni-3B并列研究；未证实8GB完整链路能实时、未找到明确pure-base、未核完整微调脚手架。不用名称4B推导全部内存，不批准正式训练。
- **Mini-Omni2**：公开视听说/打断推理架构，但FAQ明确仅英文输出，训练脚手架并未完整放行；不作为中文元亨现成主选。
- **MiniCPM-o2.6 int4**：官方模型卡说约9GB，属于特定推理配置。未实测CPU分担路线，不因略超8GB就宣布整个项目本地不可行，也不因量化权重小就承诺全功能可跑。

### 当前执行建议

1. 若目标是强认知base云训后本地部署：保留Gemma base+已有声音组件的系统路线，明确不是原生单模型语音生成；E2B是更小的视听输入base候选但同样不原生出语音，不因变小就保证人格质量。

3. 若目标是全程本地训练视听说：MiniMind-O可做小规模研发路线，从模块/数据/起点阶段核验开始；先短序列小batch峰值再决定是否进入完整中文训练。QLoRA可减少训练权重占用，但激活、梯度、优化器仍需空间；device_map=auto等推理卸载不视为可训练证明。
4. 本轮只补查与记录，未下载权重/语音数据、安装依赖、加载模型、停止后台服务或跑训练；能力与部署可行性均未验收。

## 9. 用户现役体验补充：Gemma视觉与哲学表现

用户反馈现役Gemma E4B支持视觉、哲学效果不错。此为用户实际体验，不是本轮新跑的盲评；当前没有候选在相同问题/配置下胜过现役的实测证据，不应仅凭Omni功能表建议抛弃已经工作的认知核心。

- 官方Gemma4模型卡确认E4B原生图像/音频输入与文本输出；多模态预训练包括文本、图像、音频，提供PT/IT两类权重。能看图和讨论哲学符合其能力方向；无法将用户哲学表现精确归因到预训练、IT、LoRA、提示词或记忆中的某一部分，本轮未做此实验。
- 本地V8 adapter_config明确源为gemma-4-E4B-it-qat-unquantized；部署README记载QAT-Q4_0 4.80GB、mmproj 0.92GB、8GB设备上的旧视觉/音频转写与速度记录。这些解释为何现役可本地部署；不声称已实测新base或当前实时性能。
- 纠正此前对需求的过度收窄：用户说“语音链路端对端”，未明确要求所有模态/语音生成必须同一套权重。单模型原生语音输出是可选路线，不能被当成已确认硬要求并自动否定Gemma+声音模块的系统路线。流式延迟、打断、并发与恢复仍需整链验收。
- 建议暂不为了“原生语音输出”单项就换掉认知底座；优先保留Gemma4-E4B系列，按既有base方向准备同家族PT的V9人格/行为SFT，并保留现役IT+adapter回退。用户并未在这次消息中正式选择新底座，本文是更新建议，未替用户下开训决定。
- base具有同家族预训练模态能力，现役IT的回答效果不能保证自动迁移；新的processor/投影器/权重需同源、V8 IT adapter不直接复用，SFT后看图/听音频/哲学与陪伴均要回归。
- 语音输出可以继续由现有声音模块承担，系统能否达到用户的端到端目标以实际交互验收为准，不因画出串联链就声称已满足。若用户以后明确必须原生音频到音频，另评估Omni或语音输出模块训练，base起点仍不撤销。
