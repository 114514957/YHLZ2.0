## 1. 新增两族 CoT（`cot_deep` 400 → 600）

| 族 | 形态 | 样例 |
|---|---|---|
| `cotdeep:switch` | **中途改条件**：先一个方案、后来换成另一个，按新条件算 | "兜里 500，本打算买 60 的，后来换成 140 的，又拿 25 配件，还剩多少？" → 500−140−25=335 |

两族各 100 条，答案由代码算出并 assert；drill 强制 `total > mi + 60`，保证一定跨小时借位。

## 3. 评测判分收紧

- 新增 `final_claim()`：优先取**最后一个断言**（"答案/结果/应当得"后面的值），
  没有断言才退化成"最后一个数字"；
- 数值族改为"断言里含期望值"——避免模型说"不是 48"却被判对（**高估**风险）；
- 请求层加 **1 次重试**（3 秒退避），抗瞬时 503；
- 评测族扩到 **10 族**（含 switch / drill）。

## 4. 评测跑不完的真实原因（已定位）

llama-server 日志：

```
E srv send_error: request (11118 tokens) exceeds the available context size (8192 tokens)
```

- 服务是 `-c 8192 --parallel 1`，**单槽**；
- 元亨主链路（daemon/桥）会发上万 token 的请求，直接把槽位占满并触发 5xx；
- 我的评测请求在排队/超时后表现为**空回复**，脚本按"连续 3 次失败"中止。

**结论**：不是评测脚本的问题，是**评测与生产共用同一个 8192 上下文单槽服务**。
两条路：
1. 把 llama 上下文提到 16384（显存够的话），或
2. 评测单独起一个实例（另一端口/另一份模型）——更干净，但要占两份显存。

本轮只记录问题，没有擅自改生产参数（改 `-c` 会影响元亨主链路，需你点头）。
