## 三、问题分级与改法

### P0-1　工具训练数据用的是**假工具名**（380 条 / 占训练集 19%）

**证据**：`data/finetune/tool_use_v6.jsonl` 声明的 15 个工具与真实能力注册表（`setup_scheduler_capabilities()`，35 个）对比——

```
训练数据里调用但真实不存在的工具（15 个，全部）:
calc_expr, convert_units, count_words, find_file, get_quote, get_time,
hash_text, list_events, lookup_weather, random_pick, read_ledger,
run_script, search_notes, send_msg, translate_text
真实存在的重合: []   ← 一个都没有
```

**来源**：`tools/gen_tooluse.py` 里**硬编码**了这份假工具表（第 39/47/51 行等），从未与真实能力注册表对齐。

**影响**（与真机观测吻合）：模型学到"要时间调 `get_time`、要台账调 `read_ledger`、要文件调 `find_file`"。生产链路的 35 个真实工具名完全不同，于是它**不知道该调什么**——这正是我 2026-09-25 真机人格回归里抓到的两个稳定失败：

- `t01`「记住：我怕冷」→ 答"已记下。"但**没调 `memory_save`**（记忆真的丢了）
- `t13`「帮我把 target_entry.py 的错别字改掉」→ 调 `file_list` **瞎找文件**，没有按规矩派单 `[[dev: …]]`

**改法**（可执行）：
1. 改 `tools/gen_tooluse.py`：删掉硬编码工具表，改为从真实注册表派生——
   `setup_scheduler_capabilities()` → 取 `c.openai_name` / `c.description` / `c.input`（`target_scheduler_tools.py` 里已有现成的 `export_openai_tools()`）。
2. 重新生成：`python tools/gen_tooluse.py`（产物仍写 `data/finetune/tool_use_v6.jsonl`，建议改名为 `tool_use_v8.jsonl` 以免混淆）。
3. 重新装配并在**去掉旧的假工具数据**后再训：
   `python tools/finetune_assemble.py --tag v8 --extra data/finetune/tool_use_v8.jsonl`

> ⚠️ 在修好之前，`--extra data/finetune/tool_use_v6.jsonl` **不要再进任何训练集**。

### P0-2　长度只有"短"这一档，模型没有长回答能力

**证据**：对话样本轮长中位 **19 字**、**98% ≤30 字**、最长仅 32；全库 **3868 条答轮里 >100 字的 0 条**。
根因：`tools/scene_dataset.py` 的硬闸"≤30 字/问答成对"。

**影响**：模型只见过"两三句来回"。一旦需要展开（讲清一个概念、写一段论述、复盘），它只能**堆短句**——这与真机观测一致（`p04`「最近在忙什么」答得又长又散、结尾还反问）。

**改法**：
1. 改 `tools/scene_dataset.py` 的硬闸，从"一律 ≤30 字"改为**按场景分配长度额度**：

   | 档位 | 字数 | 配比 | 用途 |
   |---|---|---|---|
   | 短 | ≤30 | 40% | 日常/闲聊（保留现状） |
   | 中 | 60–120 | 35% | 解释一件事、推进对话 |
   | 长 | 200–400 | 25% | 技术解释 / 哲学论述 / 复盘 |

2. **长档必须"有序地长"**（有逻辑推进），不是短句拼接——这条要在生成器的 prompt 里明确写死。
3. 复检：`python tools/materials_audit.py`（见 §6）应显示 p90 轮长显著上升。

### P0-3　六成训练量未过目 + 生成器口癖被当成人格

**证据**：
- `对话样本.md` 936 块 **0 个 keep**（全 candidate）；`记忆样本_v2.md` 249 块全 candidate。
- 装配器**不跳过 candidate**（`_from_dialogue_doc` 根本不看 status），这些内容照进训练。
- 元亨答案开头词高度模板化：`哇哈哈哈` **155 次**、`哇哦，老/本/那/这…` 系列 200+ 次、`啊哈，…` 系列 100+ 次。

**影响**：占训练量约 60% 的内容是**机器生成且未经确认**的。模型学到的是**生成器的口癖**（"每句话都以哇哦开头"），而不是元亨本人。这是"越训越不像他"的直接原因。

**改法**：
1. 分批抽查并改 `status`：每类抽 20 条，认可的写 `- status: keep`。
   装配器对记忆样本**按 keep 优先抽样**，所以这个标记会真实改变数据构成。
2. 口癖治理：在 `scene_dataset.py` 的生成 prompt 里加"禁止高频口头禅开头"的约束，并对已生成数据做一次**开头词去重**（同一开头词最多保留 N 条）。
3. 复检：`materials_audit.py` 的"开头词 top12"里，单一开头词占比应降到 2% 以下。

### P1-1　自称失衡："本小姐"被训成了默认口吻

**证据**：元亨 1982 条答轮里，**本小姐 36%** / 我 316 / 老娘 241 / 咱 74 / 元亨 15。
而 `SYSTEM` 里写的是"自称按情绪切换（我/咱/元亨/老娘/本小姐）"。

**影响**：模型会以为**日常就该说"本小姐"**，人格单一、油腻。真机评测里我看到的就是这个。

**改法**：定配额并回改素材（建议）：我 45% / 咱 20% / 本小姐 20% / 老娘 10% / 元亨 5%；按情绪分配——平静用"我"，得意/傲娇才"本小姐"，激动才"老娘"。

### P1-2　情绪层次几乎不存在

**证据**：元亨 neutral **47%**，sad **1%**、angry **0%**（利贞更是 neutral 95%）。

**影响**：`SYSTEM` 要求"自称按情绪切换"，但数据里**没有情绪波动可学** → 自称切换学不出来，也学不到安抚、共情、克制的语域。

**改法**：在生成器里给每个场景**指定目标情绪**，并按 `backend.emotion_classifier.EMOTIONS` 的六类**配额产出**（建议 neutral ≤40%，sad/angry 各 ≥5%）。这样素材与运行时的情绪分类器口径一致。

### P1-3　括号动作 751 处（违反 0216 定的规矩）

**证据**：`（记录）`41、`（提醒）`13、`（点头）`30、`（叹气）`12、`（心虚）`5…合计 **751 处**，占答轮 19%（利贞 365、老爹 290、元亨 82）。
台账 0216 明确写过"不堆砌环境描写与括号动作"。

**改法**：生成器禁止产出括号动作；对已生成数据做一次清理（正则 `（[^）]{1,4}）` 命中即人工过一遍，或按角色直接剥离）。

### P1-4　类别偏斜：技术样本只有 6%

**证据**：故事 **439(46%)** / 哲学 218 / 日常 171 / **技术 54** / 闲聊 51。

**影响**：元亨的定位含"技术担当的伙伴"，而技术样本最少；"故事"占近一半，最易同质化。

**改法**：砍"故事"配额、补技术类（尤其"把一个技术概念讲清楚"的中/长样本），目标技术 ≥20%。

## 四、待人工确认（我不替你下结论）

**多轮连贯性**：相邻轮 2-gram 重叠中位 **0.000**。这**可能**是"各说各的"（生成器每轮独立生成，对话不承接），**也可能**只是我的代理指标对短文本过敏（20 字上下很难有共同 bigram）。我**没有**读原文判断。

请抽查：从 `对话样本.md` 随机取 5 个 3 轮以上的块，看第 2、3 轮**是否在回应第 1 轮**。若确实不承接，那属于 P0 级缺陷（教模型"不接话"）。

**"结果不理想"的具体症状**：本报告无法从这里推断。请补一句描述（例如：不像元亨 / 变笨了 / 说话更短 / 助手腔 / 只会短句 / 工具不听话）。**症状不同，该优先改的项不同**：
- 若是"工具不听话" → 优先 P0-1
- 若是"只会短句 / 答不深" → 优先 P0-2
- 若是"不像他、口吻油" → 优先 P0-3 / P1-1

## 五、素材**不能**解释的部分（边界声明）

以下变量与素材无关，本报告不作结论，但它们同样能造成"结果不理想"，排查时需分开：

1. **训练超参**：epochs 3 / lr 2e-4 / r=16 —— 对 1955 条数据，**3 个 epoch 偏多**，人格微调常见过拟合信号是"复读训练集口癖"。这与 P0-3 的症状会叠加，需用验证集损失判断。
2. **数据量与 LoRA 容量的匹配**：数据里 >100 字样本为 0，而 `max_seq_len` 设 1024/2048 —— 容量与数据形态不匹配。
3. **基座与模板**：Gemma-4-E4B 的 chat template 对多角色/工具消息的处理（我已实测 29 种记录形状**全部可编码**，0 失败，故模板不是崩溃原因）。
4. **训练是否真的用了这份数据**：`data/finetune/` 里 9/18 之后无新产物，且 `docs/素材/` 自 9/18 未改 → **据现有素材装配出的 v7 与 v6 内容完全相同**（1955 条、构成一致、切分种子相同）。若那次"全量"用的是同一批素材，得到等价模型是预期结果，与素材质量无关。

## 六、复查方法（每次改完跑一遍）

本报告的所有指标都是脚本算出来的，可以固化成一条命令复检。建议新增 `tools/materials_audit.py`，输出与 §2.2 同口径的表，让"改了有没有用"可量化而不是凭感觉：
- 轮长分布（中位/p90/各档占比）
- 自称分布、情绪分布、括号动作数
- 开头词 top12（口癖）
- status 分布（keep/candidate 比）
- 重复对数量、工具名与真实注册表的差集 ← **这条最重要，必须常态化**
