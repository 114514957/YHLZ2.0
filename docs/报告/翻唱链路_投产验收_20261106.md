# 翻唱链路投产验收（2026-11-06）

> 依据：`docs/报告/翻唱链路_投产设计_20261102.md`（台账 1064/1066）、台账 1106。
> 范围：设计里的四项待办——正式入口、端到端验收、工作台接线、依赖回归。
> 结论：**四项全部完成**；端到端与 11/01 参考产物按设计判据逐项比对通过。

---

## 1. 改了什么

| 项 | 落点 | 说明 |
|---|---|---|
| MDX 分轨改 audio-separator 原版 | `tools/svc_mdx_karaoke.py` | 默认走 `audio-separator`（corr 与验收一致）；自写 onnx 版退到 `tools/svc_mdx_karaoke_legacy.py`，用 `--legacy` 才启用 |
| 正式入口 S1–S7 | `tools/cover_produce.py` | 规范化 → Kim → MDX → Seed-VC → 柔化 e → 三轨混回 → 归档+说明；出口 JSON 带 `sep` |
| 工作台接线 | `backend/console_server.py` | `_COVER_ENGINE=produce`（`YH_COVER_ENGINE` 可回滚 seedvc/soulx）；新增 `_job_produce`，`SING_STATE` 增加 `sep` 并回传 |
| 依赖回归 | `venv-gsv5` | torch 2.7.1+cu128 / torchaudio / soundfile / librosa / numpy 2.5.4 / onnx 1.23.2 / onnx2torch / torchvision 0.22.1 / demucs 4.1.0 全部可导入 |

顺带修掉一个跨链事故：`gpu_window` 原来按镜像名 `llama-server.exe` 杀进程，
把**实验站的 8093 llama** 一起带走、还让生产的 8081 在窗口后永远拉不起来（`_proc_alive` 把 8093 当生产）。
现在 `backend/gpu_window.py` 与 `tools/yhlz_launcher.py` 都只认 `--port 8081` 那一个 llama。

## 4. 工作台入口（真入口，不是只调脚本）

用 15 s 样本走 HTTP：

```
POST /sing {"target": "...mdx_probe.wav", "voice": "bright"}
→ {"ok": true, "status": "running"}
GET /sing/status 轮询：104 s 后 status=done
→ sep="native-kim+mdx"，result=成品_mdx_probe_清亮嗓.wav，song_id=song_20261106231751
```

`SING_STATE.sep` 已回传；日志里保留完整 stage JSON，降级会显式标注（不再是静默 demucs）。

## 5. 复现

```bat
:: 全链（约 6-7 分钟，会自动开合唱窗）
.venv\Scripts\python.exe -X utf8 tools\cover_produce.py "音频素材\翻唱投入\黑夜梦想家.m4a"

:: 只验分轨（S1-S3，约 1 分钟）
.venv\Scripts\python.exe -X utf8 tools\cover_produce.py "…\x.wav" --dry-run

:: 判据比对（需要参考产物目录）
.venv\Scripts\python.exe -B cache\tmp\_cover_accept.py
```

## 6. 边界

- 整首会短暂停生产 llama（唱窗机制），跑完由 `close_window()` + 看门狗拉回；实验站 8093 现在不受影响。
- onnxruntime 的 CUDA 13 与 torch 12.8 不一致，MDX 仍跑 CPU（202 s 歌 84 s），未提速。
- 听感验收要老爹本人；代码侧判据已全过。
