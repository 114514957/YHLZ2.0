# 台账索引修复（2026-11-07）

> 触发：老爹「补台账索引」。
> 结论：索引覆盖面本来就是全的（20,012 行 / 15,388 文档），但**全量重建是坏的**——
> 60 分钟跑不完、WAL 涨到 116MB 不提交。修完后重建 **46.4 秒**完成。

## 一、先量清楚

| 项 | 值 |
|---|---|
| 台账正文 | 20,012 行（2,536,268 B） |
| `kw_docs` | 15,804（ledger 15,388 + l2 416） |
| `kw_index` 词条 | 1,305,274 |
| 已索引最后一行 | 20,012（= 总行数，**没有缺行**） |

> 插曲：第一次用 PowerShell `Measure-Object -Line` 数成 7,524 行，误判「台账被压缩、增量空转」；
> 实际用 Python `splitlines()` 是 20,012 行，索引与台账本来就对齐。

## 二、真正的病：全量重建 O(n²)

跑 `tools/ledger_cli.py index --all` 后：

- 进程 CPU 1,133 秒（单核 93%）、WAL 116 MB、`kw_docs` 一直是旧值 15,804；
- 60 分钟后仍未提交，只能杀掉。

读 `backend/target_kw_index.py::bulk_upsert_docs` 找到原因：

```python
if clear_source:
    con.execute("DELETE FROM kw_index WHERE docid IN (SELECT docid FROM kw_docs WHERE source=?)")
for docid, ... in prepared:
    con.execute("DELETE FROM kw_index WHERE docid=?", (docid,))   # ← 每条一次
```

`kw_index` 只有 `(term, docid)` 主键和 `term` 索引，**没有 docid 索引**；
`clear_source` 已经把整源清空了，循环里再按 docid 删一次，每次都全表扫 130 万行 × 15,388 条 → O(n²)。

附带一个坑：建索引时 SQLite 默认 `temp_store` 落盘，报 `unable to open database file`
（TEMP 被重定向/权限边界），改成内存排序后 2.6 秒建完。

## 三、修了什么

| 文件 | 改动 |
|---|---|
| `backend/target_kw_index.py` | schema 增加 `idx_kw_docid ON kw_index(docid)`；`_init_schema` 设 `PRAGMA temp_store=MEMORY`；`bulk_upsert_docs` 在 `clear_source` 时跳过逐条 `DELETE` |
| `backend/test_target_kw_index.py` | 新增回归：`clear_source` 重建后旧 doc 必须消失、新 doc 可查（11 项测试 OK） |

## 四、验证

```bat
.venv\Scripts\python.exe tools\ledger_cli.py index --all
:: 全量重建台账索引：15388 行   (46.4 s)

:: 检索新记录
yhlz ledger_search "v9t10"
:: → ledger:1128:19984 … 20003，行号与台账一致
```

`kw_docs` 15,804 / `kw_index` 1,305,274 与修复前一致；重建耗时 **60min+（未完成）→ 46.4s（完成）**。

## 五、边界

- 索引是「可重建缓存」，重建期间检索看到旧快照，不丢数据。
- 新增 docid 索引会让 `kw_index.db` 略大（+约 30 MB 量级），换重建速度值得。
- 下次台账追加仍走增量（`_sync_index("incremental")`），只有台账被重写/压缩时才需要 `--all`。
