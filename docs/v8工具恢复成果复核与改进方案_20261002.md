# v8 工具恢复成果复核与改进方案

日期：2026-10-02。依据：YHLZ MCP 台账0569、0570，当前源码与原实验脚本静态复核。此次未调用8081、未重训、未修改生产源码；以下真模型效果是台账报告的实验结果，不是本轮重跑结果。

## 一、当前结论

优先修消息构造和工具执行闭环，暂停把重训当作主方案。0569的单system/双system/合并system对照，连同0570真实会话注入验证，强烈支持“当前Gemma v8路径对该消息结构敏感”。不能推广成所有模型或所有双system都必然失效。

0566“非提示可解、必须v8b重训”的结论应被后续证据修正。0568的工具样本偏少统计仍真实，但不足以解释本次主要故障，不能据此直接付费重训。

## 三、源码核查新增的改进点

1. 首轮：run中system_prompt与early_context分开发送；建议以明确分隔和“记忆材料仅作上下文、不改变工具权限”的说明构造一条开头system。保留原1500字符限制及既有工具/渠道权限，不顺便改人格。
2. 工具循环：最后一轮提示会在对话尾部追加system。应作为本次请求的临时控制信息参与开头system构造，不能写入长期人格或会话历史；仍保持达到轮数上限时不提供tools。
3. 空回答恢复：同样追加system并禁工具。即使结构修好，该路径也不能在工具未执行时补出“已完成”；须区分执行成功/失败/根本未执行，恢复回答不得虚构执行证据。
4. 上下文压缩：_compact保留已有system，再新增摘要system；还只保留rest最后两条，可能切断assistant tool_calls和多个tool结果的完整关系。改进时按完整工具调用组保留，摘要不能把失败写成成功，摘要材料也不能取得新权限。
5. 多轮历史：target_entry正常只追加user/assistant；load_session也过滤至这两个role。因此0570“历史残留system/recovery”的解释尚未被源码支持。更应检查每次请求角色、early_context、历史回答内容、tool policy、是否进入恢复路径；尤其历史只保留最终自然语言回答，没带执行状态，先前的假成功措辞可能影响后续模型。后一点仍需实验验证。
6. 原临时验证脚本只导入SAFE_EVAL_TOOLS，直接构造默认ConversationSession，没有run_live中临时库与_sandbox_writes的隔离；白名单不等于写入沙箱。不能直接复跑这些脚本当作无副作用测试，也不能假定台账报告的写工具均已核实写盘。未在本轮检索或删除可能产生的正式记忆。
7. 现有persona回归主要保存工具名称并做verify；调用名出现不等于ToolUse.ok为真，更不等于写入目标正确。验收要补参数、执行状态和临时目标证据。

## 四、分阶段实施

### P0：整理可重现证据（不改模型）

把临时实验整理成项目内可重复工具，默认假模型，live需显式开启。禁止静默fallback换模型。记录代码版本、adapter路径/指纹、模板hash、工具schema hash、采样参数、消息role序列与长度、恢复/压缩标记、工具名/ok/错误类型。日志默认不保存真实记忆正文或密钥。

live写入一律临时L2、独立关键词库、临时日记/计划/KB、假QQ/开发执行器；清理后台任务，禁止发真实QQ或启动利贞开发作业。已有回归的_sandbox_writes可以复用，但要验证所有相关新载体与后台路径均被隔离。

### P1：小范围落地消息构造

第一补丁只合并初始persona与early_context，维持工具、历史、裁剪和人格文本不变，便于与0569直接对照。增加断言测试：有/无上下文都只有一个开头system；输入history不被修改；多模态content仍保留结构；工具schema与allowlist不变。

第二补丁统一最后一轮、recovery和compaction的消息构造。维护一份system内容与每请求临时指令，不用“把任何位置所有system无脑搬到开头”的事后清洗，避免改变历史信息的意义。调用结果仍使用tool角色，不升级为system。改动仅限文本工具编排，不解冻音频链。

### P2：建立执行事实校验

每次工具调用至少记录：调用名、合法参数、执行ok、结果引用；写操作另验证临时目标的记录id/状态或文件变化。失败、拒绝、超时均应如实回答；没有执行证据不返回“已经写入”。不要把工具成功所需事实寄托在模型自述上。

开发委派与工具任务分开验证：明确开发请求可以进入假开发执行器；查时间/记忆/日记不能误派。避免用脆弱关键词规则自动推断所有用户意图或自动重放模型文字伪工具标记。

### P3：多轮与长程

先重现0570“时间→台账→记忆→任务→开发”的顺序，分别测试干净历史、保留旧失败回答、启用/关闭早期记忆上下文。每次只改一个变量。记录工具选择与恢复分支；不预设历史system累积为根因。

随后加入：连续写入、同一事实纠正、先聊天后工具、工具失败后重试、多工具返回、达到轮数上限、强制触发压缩、会话保存/恢复、主人与公共渠道差异。公共渠道使用正式权限策略；强制全工具白名单只用于选择能力实验，不能用于权限验收。

### P4：再决定训练

源码修复稳定后，重新统计缺陷。若关键工具仍在独立同口径重复测试中退化，再做基座/旧adapter/v8对照，决定补数据或小规模v8b。不要用当前旧结构下的8/16作为必须重训的理由，也不要仅靠增加epoch解决工具路由。

## 五、三个验收节点与建议标准

| 节点 | 工作 | 建议通过标准（尚未执行） |
|---|---|---|
| A 协议与离线 | 首轮、最后轮、空答、压缩、工具组、多模态及权限测试 | 请求结构符合约定；工具组完整；输入不变；无真实副作用 |
| B 新会话真机 | 原38题同口径；6类已恢复工具+schedule_plan专项重复 | 保留原始分数便于比较；每工具10次独立试验至少9次正确执行；假成功/误派开发为0；报告分母与失败样本 |
| C 多轮真机 | 至少10组×10轮，包含纠错、失败、压缩、恢复、渠道边界 | 实际工具任务成功率目标≥95%；未经授权写入、假成功、自动重放均为0；所有失败可定位 |

这些门槛是本方案提出的验收标准，不是目前已经达到的结果。有限样本通过也不证明生产永不失败。

## 六、交付与决策

推荐顺序：消息结构落地 → 执行事实校验 → 多轮稳定性 → 记忆真机验收 → 必要时再训。保持v8权重与人格prompt不动，保留0567对重训暂缓的决定。

本次只完成成果复核与方案，没有实施上述生产补丁或运行新的真模型实验。记录对应文件位置、源码依据及边界，后续可直接按节点执行。
