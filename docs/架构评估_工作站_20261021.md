# 工作站架构评估：继续 WebUI、集成 DSH，还是拆层

日期：2026-10-21 · 约束：**元亨的人格、模型、记忆、语音链路不动**；只改架构与进程边界。
结论：**不建议全量迁 DSH；也不建议继续维护当前单体 console_server。推荐把 YHLZ 拆成「核心 / IO / UI / 监督」四层，DSH 只做运维面板。**

> **2026-10-21 老爹决策（覆盖本文 P3）**：**不把元亨接入 DSH**，不做元亨的 DSH 面板/插件试点。DSH 原生能力只服务利贞；元亨的架构改造全部留在 YHLZ 内部。

## 1. 现状量化（本机日志/代码）

| 指标 | 数值 | 含义 |
|---|---:|---|
| `console_server.py` | 2128 行，64 个函数，38 条精确路由 | 一个 HTTP handler 同时管静态页、聊天 SSE、TTS、设置、控制、QQ 二维码、日志、歌曲、Live2D |
| `assets/webui/console.js` | 668 行 / 28 KB，无前端测试 | 自维护 UI |
| 后端测试 | 166 个 `test_*.py`，仅 **7 个**引用 `console_server` | 最忙的边界测试覆盖最低 |
| `daemon.log` | 92 次 daemon 启动；48 次 schedule 错误；176 次 autonomy skip | 进程重启与自主回合失败频繁 |
| `llama-server.log` | 107 次 listening 启动；**709 次上下文超限 400** | 8k 上下文被反复打爆，请求失败/重试 |
| `launcher.log` | `'ollama': False` **1261 次**；`'gemma': False` 24 次；`'daemon': False` 13 次 | Ollama 永远起不来，却被当必选服务反复等待 |
| 实时/IO 代码 | `qq_bot.py` 2215 行；voice 模块 20+ 个；live 管线多个 | 这些是“身体”，DSH 没有对应能力 |

## 2. 根因判断

1. **可选依赖被当成必选**：Ollama 一直 500，launcher 每次 `ensure_stack` 都等它，日志 1261 次 false，启动被拖慢、状态永远“未就绪”。
2. **没有本地模型上下文预算**：709 次 400 是请求超过 8192；不是模型坏，是调用方把整段人设+45 工具+历史原样塞进去。
3. **进程监督是手写的**：launcher/watchdog 用循环和端口探测；daemon 重启会把子进程（B站 worker）一起收掉，任务卡死。
4. **单体 HTTP 服务**：`console_server` 把 UI、API、音频、控制、静态资源混在一个 handler，改一处要回归全部；38 条路由、7 个测试，维护成本高。
5. **双轨回退复杂**：DeepSeek 主 + 本地回退（原 Ollama，现 Gemma）逻辑分散；出错信息曾只报 `dual-rail failed`，难定位。
6. **8 GB 共享显存**：Gemma、TTS/ASR、浏览器、daemon 抢资源；llama 进程会消失，靠看门狗拉起。

**重要判断**：换前端不会解决 1/2/3/6。先修监督与上下文，再谈 UI，否则新 UI 一样“不稳定”。

## 3. 方案对比

### A. 拆层：YHLZ 核心 + IO + UI + 监督（推荐）

```
Electron 桌宠 ─┐
Web SPA ───────┼─ HTTP/SSE ─ yhlz-api (FastAPI) ─ yhlz-core (session/persona/memory/LLM)
DSH 运维面板 ──┘                              ├─ yhlz-io (voice/QQ/live workers)
                                              └─ llama/Gemma (supervised)
```

- API 只做协议：`/api/v1/chat/stream`、`/state`、`/control`、`/history`、`/tts`；不直接碰 UI 静态文件。
- 前端换成薄 SPA（React/Vite 或 Svelte；只保留聊天/历史/设置），Electron 只做桌宠/语音浮层。
- 监督换成明确的 supervisor（NSSM/Windows 服务或单一 supervisor 进程）：Ollama 可选、llama 有重启策略、IO worker 独立。
- 人格/模型/记忆/语音实现不动，只包一层 API。
- 工作量：P0 稳定 1-2 天；P1 API 抽取 5-7 天；P2 新前端 5-7 天；P3 IO/监督 3-5 天。风险中等，可增量回退。

### B. 前端迁 DSH，后端留 YHLZ

- DSH client 插件做状态/控制/日志面板，聊天仍用 YHLZ。
- 工作量 3-5 天；能减少运维页面，但**不减少聊天 UI 的维护**，还多一层 DSH rc 依赖。
- 适合作为 A 的补充，不适合当主架构。

### C. 用成熟聊天前端（Open WebUI / LobeChat / Chatbox）

- 优点：聊天/历史/移动端由社区维护，UI 维护量骤降。
- 硬伤：现有 `/v1/chat/completions` 走的是 **public 通道**（隔离记忆、只读工具），不是主人 console 会话；直接用会改变元亨的记忆/工具行为。要保留人格/模型，必须新写一个“owner OpenAI 适配器”，并处理历史双写。
- 语音/桌宠/直播/QQ 仍要单独存在；等于多一个重依赖，不是一体化。
- 结论：可作为 A 的 P2 备选（若不想写 SPA），但不作为首选。

### D. 全量迁 DSH

- 不接受：DSH 是 turn-based agent runtime，无原生实时音频/打断，不能托管 NapCat/模型/直播；rc 阶段插件权限全开。
- 只有在 DSH 提供稳定实时音频、长驻服务宿主、沙箱后才重估。

## 4. 推荐路线（按顺序）

### P0 稳定化（1-2 天，先做）
1. **Ollama 移出关键路径**：launcher 不再等待/要求 Ollama；健康状态标 optional；失败不阻塞启动。
2. **本地模型上下文预算**：所有调 8081 的入口统一截断/估算 token；> 7000 拒绝或压缩；记录调用方。
3. **worker 独立**：B站 worker、QQ 桥不再做 daemon 子进程；用计划任务/独立服务，daemon 重启不影响。
4. **监督明确化**：一个 supervisor 管 llama/daemon/IO，指数退避 + 重启上限 + 日志；不再靠 60 秒轮询刷屏。
5. 基线：72 小时内 llama 400 = 0、Ollama 不阻塞、daemon 非计划重启 ≤1 次。

### P1 API 抽取（约 1 周）
- 新建 `backend/api/`（FastAPI，已有 fastapi/uvicorn 依赖），把 `console_server` 的聊天/状态/控制/历史抽成版本化路由；旧 handler 保留做兼容层。
- 为 API 加契约测试（SSE 帧、错误码、鉴权、超时）。
- 前端暂时不动，先让新旧入口并存。

### P2 前端替换（约 1 周）
- 薄 SPA：聊天（SSE）、历史、设置、状态灯；语音/桌宠留给 Electron。
- 旧 WebUI 保留一个版本做回退；用 feature flag 切换。
- 不做 iframe 复制；不做 DSH 聊天。

### P3 运维面板（已取消）

## 5. 验收标准

- 连续 72h：无 UI 不可恢复白屏；daemon 非计划重启 ≤1；llama 上下文 400 = 0；Ollama 不影响启动。
- API：聊天 SSE 首字节 p95、断线重连、错误可读；契约测试覆盖 ≥80% 路由。
- 人格/模型回归：现有 166 个测试 + persona regression 全过；同一组 prompt 的回答风格/记忆行为无变化。
- 维护：新增一个功能只改 API + 一个前端页面，不再动 2000 行 handler。
