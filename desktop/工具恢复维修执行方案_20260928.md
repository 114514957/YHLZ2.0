## 2. 执行纪律

### 2.1 台账检索纪律

- 查询项目历史、决策、编号、方案、适配器结论时，只使用 `ledger_search`。
- 查询用户偏好或记忆条目时，只使用 `memory_recall`。
- 获取当前时间时，只使用 `system_time`。
- 不要亲自全文读取、全文 grep、复制整份 `docs/上下文台账.md`。
- 搜索关键词使用 1 到 3 个短词，例如：`全双工`、`适配器`、`MCP`。
- 结果必须保留原始 `ledger:编号:位置` 来源标识。

### 2.2 修改纪律

- 本方案默认是恢复和验证，不是大规模重构。
- 不得执行：
  ```powershell
  git reset --hard
  git checkout -- ...
  git clean -fd
  ```
- 不得覆盖用户现有修改。
- 改动前先记录 `git status --short`。
- MCP stdio 服务的 stdout 只能输出协议数据，普通日志必须走 stderr。
- API key、token、密码、设备密钥只允许记录指纹或“已配置/未配置”，不得写入台账、方案、日志或探针报告。
- 未实际执行的检查不得写成“已通过”。

### 2.3 语音链路纪律

工具恢复完成后再继续语音链路。语音部分必须遵守：

- 不新建第二套 `SessionKernel`、`TargetVoiceChain`、Runtime、turn/generation 状态、播放队列或历史系统。
- Target 必须显式选择，legacy `/voice` 默认行为不能被偷偷改掉。
- 扬声器路线需要真实 AEC 证据；RMS 门限、VAD、ducking 不能被写成 AEC。
- “发出取消请求”不等于“播放已经停止”，必须有 playback stop evidence。
- 蓝牙耳机可以先作为低回声验证路线，但最终主路线仍是扬声器。

探针当前重点验证 `system_time` 和 `ledger_search`。DeepSeek 接入前还需要单独调用 `memory_recall`。

### 成功判定

- 工具名称稳定；
- 参数名和默认值稳定；
- 成功、未找到、异常三种状态可区分；
- 返回中保留来源记录号；
- 没有把记忆、日记和台账混写。

1. 主路线：扬声器 + 麦克风；
2. 兼容路线：蓝牙耳机；
3. 蓝牙耳机先作为较容易观察全双工行为的验证路径；
4. 扬声器路线必须补真实 AEC 或至少明确降级为安全半双工。

Target 请求示例：

```json
{
  "pipeline": "target",
  "continuous": true,
  "audio_route": "speaker_mic"
}
```

蓝牙耳机验证示例：

```json
{
  "pipeline": "target",
  "continuous": true,
  "audio_route": "headset"
}
```

### 8.3 不能伪称为全双工的情况

以下情况只能叫“软件抑制/半双工降级”或“全双工实验骨架”：

- 只有 RMS 门限，没有声学回声参考；
- 只有 VAD，没有 AEC；
- 只有 cancel 请求，没有播放停止证据；
- 只有接口字段，没有真机录音、播放和插话报告；
- 只有蓝牙耳机通过，扬声器还未验证，却宣称主路线通过。

### 8.4 语音阶段验收顺序

1. 固定文本单轮播放；
2. 固定文本流式播放；
3. 播放中取消，确认实际停止；
4. 蓝牙耳机输入输出路由；
5. 麦克风采集与 ASR；
6. 插话检测；
7. 全双工状态机；
8. 扬声器播放 + 麦克风回采；
9. AEC/回声风险统计；
10. 超阈值自动降级为安全半双工。
