## 一、这一阶段要解决什么

上一阶段已经解决了“空闲后连接死掉但进程还在”的问题：

- 主动 ping/pong 保活；
- 心跳失败主动断开旧连接；
- 指数退避重连；
- outbox 消息发送成功后才删除。

但现在还剩一个可靠性问题：**普通 QQ 回复发出去以后，主桥没有统一等待 OneBot API 确认，也没有统一处理发送超时、重复发送和重连中断。**

本阶段的目标不是盲目“重试越多越好”，而是让每条出站消息明确处于以下状态之一：

```text
queued       已入队，尚未发送
sending      正在发送
confirmed    OneBot 明确确认成功
rejected     OneBot 明确拒绝，通常不应重试
retryable    明确属于临时错误，可以重试
unknown      请求结果不确定，不能盲目重发
expired      超过有效时间，不再发送
```

特别注意：OneBot 的 `echo` 能确认“桥收到了 API 响应”，但不天然提供业务层幂等。**如果请求已经被 NapCat 执行，只是响应丢了，盲目重试可能造成 QQ 重复消息。** 因此本阶段必须把“确认成功”和“结果不确定”分开。

## 二、最终要达到的效果

### 2.1 普通回复链路

```text
QQ 入站消息
    ↓
对话处理
    ↓
生成逻辑回复 delivery_id
    ↓
进入统一发送管理器
    ↓
发送 OneBot send_msg + 唯一 echo
    ↓
等待 API 响应
    ├─ status=ok / retcode=0 → confirmed
    ├─ 明确权限/参数错误 → rejected
    ├─ 连接断开/超时 → unknown
    └─ 明确网络暂时失败且确认未执行 → retryable
```

### 2.2 主动消息 outbox

继续使用上一阶段的安全边界：

```text
peek
  ↓
发送
  ↓
确认 status=ok
  ↓
ack
```

本阶段不允许恢复“先 drain、后发送”的模式。

### 2.3 断线重连期间

- 不创建多个读循环；
- 不创建多个发送循环；
- 不重复消费同一个入站 `message_id`；
- 不丢失尚未确认的 outbox；
- 对普通回复的未确认请求不自动盲重试；
- 重连成功后只恢复确定安全的队列消息。

## 四、设计方案

### 4.1 出站消息统一封装

新增内部消息对象，建议字段如下：

```python
{
    "delivery_id": "本地唯一 ID",
    "kind": "reply|proactive|face|image|file|voice",
    "target": {
        "message_type": "private|group",
        "user_id": 123,
        "group_id": 456
    },
    "payload_hash": "正文或媒体参数的 SHA-256 前缀",
    "attempt": 0,
    "status": "queued",
    "created_at": 0,
    "last_attempt_at": 0,
    "expires_at": 0,
    "last_error": ""
}
```

日志和状态文件只记录 `delivery_id`、目标类型、哈希、状态、次数和错误类型，不记录完整聊天正文。需要重发的正文仍保留在受控的本地队列中。

### 4.2 API 响应分类

| 响应情况 | 状态 | 默认动作 |
|---|---|---|
| `status=ok` 且 `retcode=0` | `confirmed` | 完成；从可重发队列删除 |
| 参数错误、权限错误、目标不存在 | `rejected` | 不重试；记录错误类型 |
| 连接在发送前失败 | `retryable` | 按退避重试 |
| 连接在发送后断开 | `unknown` | 不立即重发；进入待核查状态 |
| API 响应超时 | `unknown` | 不立即重发，避免重复消息 |
| 队列消息超过有效期 | `expired` | 丢弃发送动作，但保留统计记录 |

### 4.3 普通回复和主动消息分开处理

#### 普通回复

普通回复通常是用户刚刚触发的实时回答。建议默认：

- 发送超时不盲重试；
- 记录 `unknown`；
- 如果仍有连接，可以执行一次非发送型健康检查；
- 只有明确判断“发送动作未提交”时，才允许一次重试；
- 超过 30 秒的普通回复不再自动补发。

原因：普通回复的重复发送比漏发一条更影响用户体验，也可能造成两次指令执行感。

#### 主动 outbox

主动消息本身已经是持久队列，继续：

- `peek` 不删除；
- `status=ok` 后 `ack`；
- 暂时性连接错误保留；
- 每小时最多发送数量继续受限；
- 同一 `delivery_id` 不重复 ack。

### 4.4 发送顺序和并发

采用两级约束：

1. 同一个目标（同一私聊或同一群）按入队顺序发送；
2. 不同目标可以有限并发，但全局发送并发先限制为 1，稳定后再评估是否放宽。

第一版不要为了吞吐量引入并发发送。先解决“状态正确、重连正确、不重复”。

### 4.5 Echo 与 delivery_id 的关系

两者不能混用：

```text
echo       OneBot 请求响应匹配用，一次 API 请求唯一
 delivery_id 本地业务消息生命周期用，一条逻辑消息唯一
```

重试时可以生成新的 `echo`，但不能生成新的 `delivery_id`。这样可以追踪：

```text
同一条逻辑消息尝试了几次
```

同时必须明确：`delivery_id` 只是本地追踪，不代表 NapCat 已实现幂等。

## 五、分阶段执行顺序

### Phase 2A：只加状态，不改变发送行为

目标：先知道消息到底卡在哪里。

工作项：

- 把普通回复发送封装为统一 delivery 对象；
- 记录 `queued/sending/confirmed/rejected/unknown`；
- 保留现有发送时机；
- 暂时不自动重试；
- 增加脱敏状态文件和计数器；
- 为每次发送记录耗时、错误类型、是否发生重连。

完成标准：

- 普通回复可以看到明确结果状态；
- 日志不出现 token 和完整聊天正文；
- 现有普通回复行为不回退；
- 隔离测试通过。

### Phase 2B：接入 API ack

工作项：

- 所有 `send_msg` 请求都使用统一 `_request()`；
- 读循环统一消费 echo 响应；
- 判断 `status`、`retcode` 和错误字段；
- 发送成功才进入 `confirmed`；
- API 明确拒绝进入 `rejected`；
- 连接断开时将 pending 请求标记为 `unknown`。

完成标准：

- 不再把“调用了 ws.send”当成“发送成功”；
- API 响应和业务消息可以通过 `delivery_id` 对应；
- 一个 WebSocket 只有一个读循环。

### Phase 2C：有限重试与队列恢复

工作项：

- 只对明确的 `retryable` 做重试；
- 默认最多 2 次重试；
- 退避建议：1 秒、3 秒；
- 普通回复有效期默认 30 秒；
- 主动消息继续持久化，不设置过短有效期；
- `unknown` 不自动盲重试；
- 重连完成后只恢复安全队列。

完成标准：

- 网络短暂断开不会导致主动消息丢失；
- API 超时不会自动制造明显重复回复；
- 重试次数有上限；
- 队列不会无限增长。

### Phase 2D：观察模式和真机前置

先不立即自动重试，增加观察指标：

```text
qq_delivery_total
qq_delivery_confirmed
qq_delivery_rejected
qq_delivery_retryable
qq_delivery_unknown
qq_delivery_expired
qq_reconnect_total
qq_heartbeat_failure_total
```

观察时间建议：

- 开发环境 fake transport：完整测试；
- 本机不发消息空闲观察：至少 30 分钟；
- 真机小范围灰度：先只允许主人私聊；
- 真机稳定后再恢复群聊主动回复。

## 六、必须覆盖的测试

### 6.1 单元测试

1. `status=ok` → `confirmed`；
2. 参数错误 → `rejected` 且不重试；
3. 发送前连接失败 → `retryable`；
4. 发送后连接断开 → `unknown`；
5. API 响应超时 → `unknown`；
6. 重试最多 2 次；
7. 退避时间符合 1 秒、3 秒；
8. 普通回复超过 30 秒不再补发；
9. outbox 发送失败后仍保留；
10. outbox 确认成功后才 ack；
11. 旧消息没有 `id` 时可以兼容读取；
12. 两条同目标消息保持顺序；
13. 一个连接不会出现两个读循环；
14. 重连后旧 pending future 全部结束，不泄漏任务；
15. delivery_id 不重复；
16. 日志不含 token 和完整消息正文。

### 6.2 集成模拟测试

使用 fake WebSocket，模拟：

```text
正常连接 → 收到 ack
正常连接 → 空闲 → ping/pong
发送中断线 → reconnect
重连后收到消息
ack 丢失
NapCat 返回 retcode 错误
outbox 多条消息
```

禁止使用真实 QQ 做这些测试。

### 6.3 真机验收

真机阶段才允许连接实际 NapCat，但要分级：

#### A 级：只观察

- 不主动发送；
- 空闲 30 分钟；
- 检查 ping/pong 是否持续；
- 检查连接是否自动恢复。

#### B 级：主人私聊

- 发送一条普通文本；
- 发送一条主动 outbox；
- 确认不重复、不丢失；
- 断开网络后恢复网络，确认状态回到 `connected`。

#### C 级：群聊

- 最后进行；
- 先限制一个测试群；
- 不先开启高频主动消息；
- 观察频控、发送顺序和重复消息。

## 七、验收指标

### 必须满足

- 空闲 30 分钟，连接仍能通过心跳维持；
- 心跳失败后能进入 `reconnecting`；
- 连接恢复后回到 `connected`；
- outbox 发送失败不丢消息；
- 明确失败不被无限重试；
- 一个入站 `message_id` 不重复处理；
- 普通回复发送失败时日志能说明是 `rejected`、`retryable` 还是 `unknown`；
- 不出现双读循环、双发送循环；
- 不泄漏 token 和聊天正文；
- 不影响语音链路。

### 暂不作为本阶段指标

- 还不要求达到 Neuro 风格全双工；
- 还不要求 QQ 语音低延迟；
- 还不要求无限吞吐；
- 还不要求跨进程分布式队列；
- 还不要求 NapCat 端具备真正的业务幂等。

## 八、回滚方案

每个子阶段都单独提交或保留补丁，不修改整个工作区。

如果真机出现重复消息：

1. 关闭自动重试；
2. 保留 ack 记录和 `unknown` 状态；
3. 恢复上一阶段只发送一次的策略；
4. 不删除 outbox；
5. 导出脱敏状态文件后再分析。

如果真机出现消息丢失：

1. 暂停普通回复自动发送；
2. 只保留主动 outbox；
3. 检查 `peek/ack` 边界；
4. 不清空 `cache/qq_outbox.jsonl`；
5. 通过台账记录具体 delivery_id 和时间，不记录消息正文。
