## 2. 目标效果和术语：什么才叫有效流式、什么才叫全双工

### 2.1 四种流式必须分开记录

| 名称 | 含义 | 本阶段是否必须完成 |
|---|---|---|
| LLM token 流式 | Gemma 不等整段答案，持续吐出 token/delta | 必须 |
| 文本分段流式 | 把 token 按标点、短语和等待时间切成可说片段 | 必须 |
| PCM 音频 chunk 流式 | QwenTTS 产生一块 PCM 就送入有界播放队列 | 必须 |
| 真正声学级端到端流式 | 音频输入直接驱动连续语音输出，模型内部不依赖完整文本 | 本阶段不强行承诺 |

当前 QwenTTS 适配器的 `text_stream=False` 意味着：不能把 `push_text` 当成真正声学级流式。我们的第一版应该叫：

> **低延迟分段流式全双工**，不是未经验证的“纯语音端到端”。

### 2.2 全双工的可验收定义

全双工至少同时满足：

1. 播放时麦克风仍持续采集；
2. 播放参考信号可提供给 AEC/回声抑制；
3. VAD 能区分用户语音和扬声器回声；
4. 用户插话后可以抢占当前播放；
5. 插话会取消当前 Gemma 生成；
6. 插话会取消当前 QwenTTS 生成；
7. 播放队列会丢弃旧回合剩余 PCM；
8. 新 turn 立即获得唯一所有权；
9. 旧 turn 迟到事件按 `generation` 丢弃；
10. 不必等上一轮播放自然结束才能开始下一轮。

### 2.3 状态机

```text
IDLE
  ↓ speech_start
LISTENING
  ↓ partial / speech_end
THINKING
  ↓ Gemma first token + first text segment
SPEAKING
  ├─ barge_in → BARGE_IN
  ├─ answer_end → IDLE
  └─ provider_error → RECOVER
BARGE_IN
  ↓ stop_and_wait（播放/TTS/Gemma/队列）
LISTENING

RECOVER
  ├─ 可降级 → LISTENING
  └─ 不可恢复 → ERROR（保留诊断，不死循环重启）
```

每个事件至少携带：

```text
session_id
turn_id
generation
trace_id
sequence
monotonic_timestamp
```

旧事件判断规则：事件的 `generation`、`turn_id` 或 `sequence` 不匹配当前活动回合时，直接丢弃并记一次 `stale_event`，不能再进入播放队列。

## 3. Gemma E4B 与 QwenTTS 的分工设计

### 3.1 Gemma E4B：负责“快而可取消的对话决策”

#### 优点

- 本地 4B 级模型适合常驻，避免每轮加载；
- Q4 量化后资源压力相对可控；
- 在 CUDA 全 offload 条件下有机会达到足够的 token 速度；
- 可以通过 token stream 尽早给出短反馈；
- 适合做短句确认、插话后快速响应、人格化语言生成；
- 可以通过 KV cache、短上下文、输出上限降低首 token 延迟。

#### 限制

- 长上下文、复杂工具调用和过多记忆会增加首 token 延迟；
- token 流式不代表语义已经完整收束；
- 每个 token 都送 TTS 会导致碎片化、频繁重启和断句；
- Ollama 的 chat template 与特定 GGUF 不匹配时可能出现空回复；
- 取消必须真正终止底层请求或让所有迟到 token 被丢弃，不能只把 UI 状态改成停止。

#### Gemma 适配要求

建议新增：

```text
C:\Users\ACE_WAN——PROJECT\YHLZ\backend\gemma_e4b_provider.py
C:\Users\ACE_WAN——PROJECT\YHLZ\backend\test_gemma_e4b_provider.py
```

Provider 最小接口：

```python
async def stream_chat(
    messages: list[dict],
    *,
    max_tokens: int,
    temperature: float,
    turn_id: str,
    generation: int,
    cancel: CancellationSignal,
) -> AsyncIterator[LLMDelta]: ...

async def cancel(turn_id: str, generation: int) -> None: ...
```

接入时必须记录：

- `model_load_ms`；
- `queue_wait_ms`；
- `first_token_ms`；
- `token_interval_ms` 的 P50/P95；
- `generated_tokens`；
- `cancel_requested_at`；
- `provider_terminal_at`；
- 是否还有迟到 delta。

#### Gemma 两条生成档位

**快速档**：用于“嗯、我听到了、稍等一下、确认性短句”。

- 上下文只放必要摘要和最近一轮；
- `max_tokens` 建议 32–64；
- 禁止工具调用；
- 目标是快速开口，内容不追求复杂。

**正常档**：用于完整回答。

- 由记忆门面提供受限上下文；
- `max_tokens` 建议先控制在 160–256，再根据实测放大；
- 复杂工具调用必须有超时和降级；
- 语句先经过文本分段器再交给 TTS。

#### Gemma 部署选择

先做两个适配实验，不要直接改变生产默认：

1. 当前 Ollama 路径：验证自定义 Modelfile/chat template 后是否稳定吐字；
2. llama.cpp server 路径：使用与模型匹配的 Jinja 模板、CUDA offload、较短上下文，作为低延迟候选。

选择标准不是“哪个能回答一次”，而是连续 20 轮满足：首 token、取消、无空回复、无旧 token 污染。

### 3.2 QwenTTS：负责“音色稳定、自然、可分段播放”

#### 优点

- 当前项目已经有 `tts_qwen_provider.py` 与 `tts_qwen_process.py` 适配基础；
- 可以复用本地模型、音色、取消控制和 PCM chunk 事件；
- 音色自然度和自定义音色能力适合作为默认语音输出；
- 生成结果可以进入现有 `TargetPlayback`，不必重建播放系统。

#### 限制

- 当前适配器的能力声明为 `text_stream=False`；
- 不能把每一个 Gemma token 直接送入 QwenTTS；
- 太短的片段会导致断句、尾音和音色稳定性变差；
- 太长的片段会增加首音等待；
- 生成速度必须高于实时播放速度，否则播放队列会逐渐见底；
- 旧回合取消后必须等生成 worker 到达终止边界，并由播放端确认停止。

#### QwenTTS 第一版策略

采用“两级流式”：

```text
Gemma token stream
      ↓
TextChunker（标点/短语/最大等待时间）
      ↓
QwenTTS 分段合成
      ↓
PCM chunk
      ↓
有限播放队列
```

初始参数建议：

- 遇到 `。！？；` 等句末标点立即提交；
- 无标点时累计等待最多 300–500ms；
- 第一段尽量控制在 8–20 个汉字或一个完整短语；
- 后续段尽量控制在 15–45 个汉字；
- 播放队列目标保持 200–500ms，不允许无限增长；
- 当队列超过上限时对 Gemma 施加背压，不能继续无条件生成；
- 当 QwenTTS 速度低于实时 1.0 倍时，进入降级：缩短回答、暂停复杂工具或切换预设短反馈。

建议新增：

C:\Users\ACE_WAN——PROJECT\YHLZ\backend\tts_stream_scheduler.py
C:\Users\ACE_WAN——PROJECT\YHLZ\backend\test_text_chunker.py

### 3.3 两个模型的正确协作方式

```text
ASR final
  → Gemma 快速生成 token
  → TextChunker 等到安全边界
  → QwenTTS 生成第一段
  → 播放第一段
  → Gemma 继续生成
  → QwenTTS 继续排队
```

不能采用：

```text
一个 token → 一次 TTS
```

也不能采用：

```text
等 Gemma 完整回答 → 整段 QwenTTS → 一次性播放
```

前者会碎，后者会慢。正确目标是“短段尽快开口，后段连续补充”。

## 任务五：低延迟优化、资源预算和设备路由

### 目的

把“偶尔很快”变成 P50/P95 稳定，解决长时间运行后延迟累积和设备切换问题。

### 优化顺序

不要一上来同时改所有参数，按下面顺序逐项测量：

1. Gemma 常驻和 warmup；
2. Gemma KV cache、短上下文、输出上限；
3. 记忆召回只读且限量，不让全量记忆阻塞首 token；
4. ASR、Gemma、QwenTTS、播放使用独立 worker；
5. 减少音频重复复制和无意义重采样；
6. TTS 有界队列，目标缓存 200–500ms；
7. 第一段优先，后续段背压；
8. 取消时优先停止播放，避免用户继续听旧答案；
9. 采集/播放 block 先试 10–20ms；
10. 最后再调温度、分段长度和音色参数。

### 资源预算

必须观察：

- CPU 总占用和各 worker 占用；
- GPU 显存、推理利用率和峰值；
- QwenTTS 生成实时比 RTF；
- 播放队列深度、underrun 次数；
- 线程/task 数量；
- 连续对话 10 分钟后的内存是否增长；
- 取消后模型请求和线程是否真正退出。

### 扬声器和蓝牙耳机的差异

**扬声器主通道**：

- 必须有播放参考信号；
- 必须验证 AEC/回声抑制；
- 必须区分“用户说话”和“系统自己播放”；
- AEC 未验证前，插话误触发时只能降级为 B 模式。

**蓝牙耳机兼容通道**：

- 先确认系统实际输入设备和输出设备；
- 记录蓝牙 profile、采样率、声道和设备切换时间；
- 不能假设耳机延迟和扬声器相同；
- 需要验证耳机麦克风回传是否稳定；
- 耳机可以作为较容易的全双工验收路径，但不能替代扬声器 AEC 验收。

### 验收节点 A5：低延迟和稳定性通过

建议工程目标（真实硬件不足时先作为目标，不得伪造实测）：

| 指标 | P50 目标 | P95 目标 | 说明 |
|---|---:|---:|---|
| 说话开始 → ASR partial | ≤150ms | ≤250ms | 以稳定 partial 事件计算 |
| 用户停止 → ASR final | ≤500ms | ≤800ms | 不能靠截断用户语句 |
| ASR final → Gemma 首 token | ≤500ms | ≤1000ms | warm 状态 |

| 首文本段 → QwenTTS 首 PCM | ≤800ms | ≤1500ms | 当前分段流目标 |

| 插话检测 → 播放确认停止 | ≤150ms | ≤250ms | 耳机先验收 |

- 无持续增长的内存、线程和队列；

- 无旧回合污染；
- 无连续 underrun；
- 任一 Provider 出错后能回到可继续说话状态。
