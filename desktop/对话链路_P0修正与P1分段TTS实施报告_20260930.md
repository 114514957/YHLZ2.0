# 对话链路 P0 修正与 P1 分段 TTS 实施报告

日期：2026-09-30。依据：台账0530、0531、0532；本轮结果已通过MCP追加台账0533并回读核验。

## 1. 先说结论

本轮不是再写一套方案，而是修正P0代码并新增可接现有Target链路的分段TTS适配层。

**已经证明（隔离测试）：**第一段LLM文本进入现有TargetVoiceChain之后，可以先提交TTS、先产生PCM并到达假播放端，再生成最后一段LLM文本。真实Qwen适配器配假模型的测试中，多段合成只建立一个模型工作实例。

**没有证明：**本机Gemma+真实Qwen的联合首声改善、扬声器/蓝牙的实际首声/静音时延、语音语义正确率、扬声器AEC双讲通过。没有加载真实模型，没有打开真实音频设备，没有重启生产服务。

新能力默认关闭，采用 `TargetVoiceCompositionConfig(segmented_tts_enabled=True)` 显式启用。旧入口保持可回退。

## 2. 当前两条链仍未完全合并

### A：音频直入入口

音频片段 → ConversationSession → Gemma input_audio → 内容回调/安全过滤 → 分段诊断。

已经修补音频回调和工厂注入分支。但是一次性 `voice_dialog_probe` 仍然是诊断工具：模型前关麦、整答后旧TTS子进程播放。这条诊断链不能作为全双工证明，分段列表也不等于分段已经被真机播放。

### B：现有Target持续输入/播放链

现有ASR/文本reasoner → TargetVoiceChain → 【新增可选SegmentedTTSProvider】→ 原有常驻Qwen provider → 原有TargetPlayback。

本轮适配层已接到Target组合根；开启配置后使用同一个Kernel、同一套turn/generation和既有取消接口。没有新建第二套对话状态机。

Target daemon当前默认入口仍是ASR/hybrid reasoner；它不因为本轮加了TTS适配器，就自动变成Gemma音频直入。下一阶段必须把A的原生音频输入、B的持续收音与播放统一到同一长寿命loop/Kernel。

## 3. 修正了哪些P0缺口

| 问题 | 原实现实际情况 | 本轮处理 |
|---|---|---|
| 350/600ms刷新 | 没有定时驱动；push重置最后delta时间，空闲判断不可达 | 新增tick；分段适配层和诊断入口20ms调用一次 |
| 首段定时 | 首段不参加超时刷新 | 首段和后续段都参与 |
| 长度上限 | 后段45不是硬上限；finish可能整块输出 | 首段≤20字符，后续≤45，finish遵守同样限制 |
| 短碎片饥饿 | 字数不足可能一直等 | 600ms硬年龄截止允许少于minimum的碎片输出 |
| 普通短句 | 过滤器固定保留长后缀 | 仅保留真正可能组成标记的后缀，普通短句即时放行 |
| 标记处理 | think/dev/native tool标记缺覆盖；blocked后buffer继续涨 | 增加已知标记；blocked/closed不累积；未完成标记在EOF丢弃 |
| daemon注入工厂 | _llm_injected绕过重建分支 | 工厂增加with_stream克隆；音频轮独立绑定本地Gemma内容回调 |
| 新轮清除取消 | clear可能复活旧轮共享bool | 增加每channel generation token；旧轮永远不能被新轮clear复活 |
| 流失败后回退 | 已朗读部分可能再从fallback重复朗读 | 已放行内容后不自动启动fallback；未放行且未取消才可回退 |
| probe首段计时 | 仅finish产生首段时计时为空 | push/tick/finish统一记首段时间 |

词法过滤是已知标记防护，不是完整语义识别。没有承诺可以消除任意形式的思考泄漏。

## 4. 分段步长：当前参数与真正含义

| 参数 | 当前值 | 说明 |
|---|---:|---|
| 首段minimum | 8字符 | 避免标点产生过碎请求；不是绝对必须等够8 |
| 首段target | 14字符 | 定时输出和标点附近的偏好目标 |
| 首段maximum | 20字符 | 无标点时按长度先发 |
| 后段minimum | 15字符 | 兼顾合成开销与语句完整性 |
| 后段maximum | 45字符 | 硬限制，不再把60当正常段长 |
| idle刷新 | 350ms | 距最后一个delta；已达到minimum才刷 |
| hard刷新 | 600ms | 距当前缓冲片段开始；不因新delta不断延后；短片段也刷 |
| 定时poll | 20ms | 无新delta时仍检查；事件循环忙时不保证硬实时 |
| 末尾finish | 有界排空 | 不把剩余内容一次无限长输出 |

字符步长、Qwen codec步数、PCM帧时长是三个不同量。`chunk_size=8`不等于8ms，不代表以上中文字符分段长度。

## 5. P1适配器如何工作

```text
LLM delta（上游应只交最终可见内容）
  → 已知标记词法过滤
  → TextChunker + 20ms tick
  → 有界文本段队列（8段；满时背压，不静默丢文本）
  → 原有provider.open(子speech_id)
  → push_text(这一段) + commit_text()
  → Qwen PCM → 20ms重打包 → 有界PCM事件队列（15帧）
  → 既有TargetPlayback
  → 子DONE + 事件流完整排空 + wait_stopped证明
  → 下一段（同一常驻工作进程）
```

- 根turn/session/provider_epoch保持不变；每段有独立子speech_id。
- 子READY/PCM_STREAM_END/DONE不伪装成整个回复结束。对Target只发一个逻辑READY、一个末尾PCM_STREAM_END和一个DONE。
- 子PCM序号从零重启时，逻辑PCM统一连续编号；跨段不足20ms的余量保留到后段，末尾才补齐。
- 子speech_id/epoch错误的PCM丢弃并计数。
- 取消时丢弃待合成段、清理适配器PCM队列、请求当前子合成停止；迟到PCM不转交播放。
- `cancel()`返回只表示请求已受理；`wait_stopped()`才是适配器的停止证据。停止未确认时不允许复用开新轮。
- PCM_STREAM_END不是底层worker复用边界。Qwen的tail verify、producer收尾和事件drain必须完成。
- Xiaoyi声线仍来自原有voice profile；适配器不选新音色、不下载模型、不建立第二个Qwen进程。
- 原生能力仍然 `text_stream=false`；这是工程分段流式，不是Qwen原生可追加文本声学生成，更不是单模型speech-to-speech。

### 队列预算必须区分层级

15个20ms帧约300ms，**只是适配器这一层PCM队列的上界**。它不包含正在处理的帧、底层Qwen自身队列、播放队列、系统/DAC/蓝牙缓存。

现有PlaybackConfig默认initial_buffer=300ms、max_queue_blocks=32、max_queue_duration=5000ms，本轮没有全局收紧。不能因为适配器队列是300ms，就宣称整条链已经达到500ms待播上限。

tail verify仍保留原设置，没有为了制造更快数字而全局关闭；它可能造成段间空洞。下一轮先量化耗时再设计对话模式的旁路/低优先级质量检查。

## 6. 工具轮的安全—延迟取舍

语音入口当前按既有策略提供CASUAL_SAFE_TOOLS。本轮没有擅自移除工具权限。

当HTTP请求提供了tools，内容先暂存：

1. 返回tool_calls：本轮中间话不播；等待工具执行后的回答。
2. 没调用工具：判定完成后才把本轮内容放行。
3. 无tools的回答轮：delta可以立即放行。

**影响：**即使本轮没真正调用工具，只要tools被提供，就可能仍要等整轮输出，抵消部分首声收益。这是明确尚未解决的瓶颈。

下一阶段应将闲聊快速通道与工具命令通道拆开：复用预召回记忆/人格后，无工具快速回答；明确要查资料/执行动作的请求走工具通道。必须独立验收命令识别、防误路由和工具权限，不把所有语音的工具一刀切关闭。

## 8. 如何启用、如何回退

组合根：`TargetVoiceCompositionConfig(qwen=原有配置, segmented_tts_enabled=True)`。关闭此项回到原整答提交行为。

扬声器输出探针已增加 `--segmented-tts` 开关，沿用默认Xiaoyi配置、原播放端和设备选择；`--help`不会加载模型/打开设备。真正运行探针会打开输出并启动Qwen工作实例：**不要在生产Qwen仍占GPU时直接运行另一份探针**，也不要凭旧设备编号就开始播放。

推荐先完成下一节的共享常驻服务验收入口，再在同一个已存在的工作实例上测真人链路。当前开关是开发入口，不是已经在生产默认开启。

## 9. 接下来的开发顺序及三个验收节点

### 节点A：共享常驻服务的联合流式

任务：将Gemma音频直入的turn请求接到Target生成租约和内容队列；后台转写由daemon长期loop持有，不能拖慢首声，也不能被一次性probe退出取消。一个播放端、一个Qwen工作实例，旧入口可回退。

输入输出时间戳：speech_end、LLM请求/首content、首segment、TTS提交、首PCM、播放回调首非静音、LLM_DONE。每轮携带turn_id、generation、speech_id、device route。指标必须区分计算到PCM与声学实际首声。

通过：至少20个warm轮，真实首段PCM/播放开始早于LLM_DONE；无重复加载/重复回答/泄漏工具中间话/迟到旧输出；常驻loop后台转写有完成或超时记录。未通过不进入全双工默认发布。

### 节点B：耳机/蓝牙插话与延迟

任务：先有线耳机，再蓝牙；量化输出开始前缓冲及总待播预算；插话确认后generation失效、LLM请求取消、TTS取消、播放停止、旧队列清理，新轮音频不丢。

通过目标（不是现有成绩）：用户声学结束到实际首声P50≤1.5s、P95≤2.5s；确认插话到实际静音P95≤250ms；记录开口到确认的检测延迟。分开cold/warm、闲聊/工具、扬声器/耳机，不用平均数隐藏慢尾。

蓝牙：记录真实input/output设备、采样率与路由；切换/断连后禁止旧device id默默恢复到错误设备，停止确认后按设备绑定规则重开。蓝牙硬件缓存无法从PCM入队时间推断。

### 节点C：主通道扬声器AEC双讲

任务：输出callback的真实播放样本作为回声参考，校准capture/playback时钟和对齐；持续收音，播放中真人打断可保留完整起始音频。

通过：只播系统声不被自己反复唤醒；播放中真人开口能打断；停声后无旧尾音污染；连续多轮不丢字、不积队列；AEC/参考缺失明确降级而非宣称Duplex C。测试覆盖近讲/远讲、不同音量/位置、短插话及蓝牙后切回扬声器。
