## 1. 当前到底打通到哪一步

当前不是“一个模型直接听语音再生成语音”的认证结果，而是现有组件链：

```text
未来真实用户语音入口：麦克风 → 输入处理 → ASR → partial / final
                                                ↓
本轮入口：固定中文文本 → WakeWordGate → TargetVoiceChain / SessionKernel
                                                ↓
                                      固定 Reasoner（非真实推理模型）
                                                ↓
                                      模拟 TTS（有效测试 PCM）
                                                ↓
                                      真实 SoundDevicePlaybackPort
                                                ↓
                                      模拟 sounddevice callback
```

- PCM：可以送去播放的数字音频采样；本轮模拟 TTS 生成了有效测试 PCM，不只是“完成”字符串。
- callback：声卡向程序要下一小段音频的回调；本轮回调由测试驱动，没打开声卡。
- generation：取消之后换一代编号，旧代音频不能混入新一轮。
- fail-closed：停止状态不明时宁可阻断下一轮，也不冒险让两轮声音同时播放。

| 能力 | 本轮状态 | 依据/限制 |
|---|---|---|
| 固定文本 → 门控 → 回复 → PCM → 队列 → 完成 | 软件验收通过 | 真实链与真实播放队列、模拟模型和声卡 |
| 合成中插话 → 停止确认 → 继续下一轮 | 软件验收通过 | 包括旧 PCM 拒绝、旧 lease 输出拒绝 |

## 2. 已定位并修复的两类根因

### 2.1 取消成功，但下一轮仍被“清理未完成”挡住

位置：`C:\Users\ACE_WAN——PROJECT\YHLZ\backend\target_chain.py`。

原问题包括两个相邻条件：

1. 新 final 进入时，把仍在正常运行、尚待观察终止的 TTS control 当成清理失败，所以无法正常覆盖前一轮。
2. 取消过程中，worker 的 finally 先挂上阻断标志；随后 TTS 与 Playback 都已确认停止，标志没有重新计算，下一轮仍抛 `TTS provider cleanup is not confirmed`。

修复：入口只把“已关闭且仍缺终止观察”的 control 当作残留清理；停止确认成功后重新计算门禁。**若之前真实停止失败，重复空闲 interrupt 不得把门禁洗白。**

通俗讲：不能让“已经停干净”还一直锁门，也不能让“没停干净”随便开门。

### 2.2 插话清了队列，等待中的生产者却把旧音频塞回来

位置：`C:\Users\ACE_WAN——PROJECT\YHLZ\backend\target_playback.py`。

原问题：队列满时生产者等空间；插话把队列清空；等待结束后 while 条件变为 false，旧逻辑直接重新入队，没有再次检查这一轮是否取消。

修复：获得锁后以及真正入队前重新检查取消信号、slot 是否取消、finish 状态、slot 身份。任一不满足就拒绝旧 PCM，不把它送到新一轮。

这解释的是软件上“停了还可能冒出旧内容”的风险，不代表本轮已经测过真实声卡里的残余声音。两类缺陷均有先失败、修复后通过的回归测试。

## 4. 适配器的新阻塞：名字重复 + 输出采样率不匹配

### 4.1 设备名字重复

`C:\Users\ACE_WAN——PROJECT\YHLZ\backend\target_device_binding.py` 目前仅用名字选设备。同一个 Realtek 扬声器以 MME、DirectSound、WASAPI 三种 host API 出现，名字完全相同；当前实现会报 `TARGET-DEVICE-AMBIGUOUS`。

这个报错不应简单删掉：它在防止程序偷偷选错设备。应增加区分字段，而不是匹配到第一个就用。

该绑定文件是其他工作 Agent 的未提交新增文件，本轮没有覆盖。以下为下一步实现合同，不是已实现功能。

### 4.2 24 kHz 音频与设备接受的格式不一致

实际执行的是 `sounddevice.check_output_settings(device=..., samplerate=..., channels=2, dtype='float32')`；没有开启输出流。

| 本次编号（非永久） | 名称 | host API | 24 kHz | 48 kHz | 44.1 kHz |
|---:|---|---|---|---|---|
| 3 | 扬声器 (Realtek(R) Audio) | MME | 接受 | 接受 | 接受 |
| 7 | 扬声器 (Realtek(R) Audio) | Windows DirectSound | 接受 | 接受 | 接受 |
| 8 | 扬声器 (Realtek(R) Audio) | Windows WASAPI | 拒绝 | 接受 | 拒绝 |
| 11 | Headphones (Realtek HD Audio 2nd output) | Windows WDM-KS | 拒绝 | 接受 | 接受 |

关键结论：本机当前 WASAPI 扬声器在 24 kHz 检查时报 `Invalid sample rate [PaErrorCode -9997]`，48 kHz 检查接受。

但是 `C:\Users\ACE_WAN——PROJECT\YHLZ\backend\target_playback.py` 的现有输入规范为 24 kHz mono PCM，并检查输入采样率必须等于 PlaybackConfig 的采样率。**不能只把 config 改成 48000；需要真正重采样，不能只改标签或把 24 kHz 样本按 48 kHz 播放。**

编号 11 是 `Headphones (Realtek HD Audio 2nd output)`；仅这个名字不能证明它是蓝牙。目前不把任何已枚举端点认证为蓝牙。

### 4.3 两条明确分开的推进路线

**路线 A：先证明真实扬声器能响。** 当前 MME Realtek 输出接受 24 kHz，可作为明确选择的输出基线；DirectSound 是另一条候选。先跑固定句，确认真模型和扬声器。格式接受不保证声卡真的打开成功，不保证低延迟，不保证声音从正确物理位置出来。

**路线 B：修正式输出适配器。** 保留模型侧 24 kHz 规范音频，输出侧通过有状态重采样适配设备接受的格式，再送物理播放端口。WASAPI 48 kHz 是查询接受的候选，不是已经完成或比其他 host API 更快的实测结论。

路线 A 是显式诊断配置，不能变成静默全局回退；路线 B 不能未测就替换用户主通道。

## 7. 延迟从哪里测，怎么降

以现有架构制定以下埋点设计，不只看一个总耗时猜原因：

```text
麦克风采集时间 → VAD 判定说完 → ASR final → 门控/排队完成
→ 真实 Reasoner 首段可播文本 → TTS 首 PCM → 播放缓冲就绪
→ 首次非零输出 callback → 物理可闻（单独测量/人工判断）
```

节点使用同一 trace/turn/generation 的单调时钟。分开记录冷启动/热态、软件/声学、扬声器/蓝牙，不能混成一组 p50/p95。

| 观测到的问题 | 优先行动 | 验收注意 |
|---|---|---|
| 冷启动明显慢 | 分开记录模型加载/预热与会话请求 | 不让预热消失在统计里；热态也要测 |
| 说完后才开始很久 | 测 VAD 端点与 ASR final 等待 | 避免靠误截断换取表面低延迟 |
| Reasoner 到首段很久 | 确认真实流式文本是否到达 TTS | 空 token 或回调事件不算可播文字 |
| TTS 首 PCM 慢 | 测首段长度、worker 等待、实际模型生成 | 不先用训练解决调度/接口问题 |
| 首 PCM 到播放慢 | 测预缓冲、积压、转换、输出调度 | 保留 underrun 指标，避免把卡顿后移 |
| 插话后还有旧声音 | 四端取消、转换尾部、队列和物理尾音分开看 | 软件确认不等于耳朵已静音 |

生产预缓冲默认 **300 ms**；模拟探针的低缓冲不能直接复制到生产。真实基线通过后，提议只改这一项，比较 300 → 200 → 120 ms，每档至少 20 轮固定文本；记录首音、underrun、异常和人工断裂反馈。数字是**实验档位，不是承诺**。发生不可接受断裂就回退，不同时改变模型、host API 与 chunk size。

本项目当前发现的是生命周期、队列、路由和格式边界问题，**本阶段不安排训练**。先让已有模型、设备、流式协议提供真实证据；训练需求由之后明确的识别/音色/语义缺陷驱动，不能作为这些软件错误的修复方式。也不凭“端到端模型”名称判断总延迟，候选实现必须在相同输入/输出和埋点口径下比较。

## 8. 何时才能叫全双工
