卷一：Demo 路线
===============================================================================

------------------------------------------------------------------------------
1.1 Demo 定位与验证目标
------------------------------------------------------------------------------
Demo 只验证 3 件事，其余能力全部不属于 Demo 验证范围：
  ① 端到端延迟可接受：用户说完话 → 听到回应 < 3s
  ② 口型/表情同步自然度：口型变化与 TTS 发声对齐
  ③ 语音链路稳定性：识别准、不卡顿、连续对话不崩

一句话：让"语音进 → AI 答 → 语音出 + 口型同步"这条单链路
跑得顺、看得见、不会在演示现场翻车。

------------------------------------------------------------------------------
1.2 Demo 范围：留什么 / 砍什么
------------------------------------------------------------------------------
【留】（单链路最小集合）
  - 进程：backend 单进程(FastAPI :8000) + desktop_avatar_py.py 官方桌宠
  - 链路：麦克风 → 回声消除/降噪 → VAD/打断 → FunASR(单一引擎)
        → 最简上下文(context_manager，记忆只保本轮对话)
        → DeepSeek(单一引擎) → Edge-TTS → 播放 + 口型同步
  - 通道：桌宠↔backend 只需一条 WebSocket（口型/表情/状态）

【砍】（demo 后迭代）
  插件系统 / 沙盒 / 防注入 / 记忆 v1+v2 / 知识图谱 / 多模态认知 /
  视觉 / B站直播 / VTS / tools 工具系统 / webui 服务托管 / gui_main 大面板 /
  /ws 与 /ws/stream 双通道 / Ollama / 声音克隆

------------------------------------------------------------------------------
1.3 必修问题（6 条，全部会在 Demo 出问题）
------------------------------------------------------------------------------
■ 问题 1：2 秒播放缓冲 —— 全链路最大延迟项
  现状: 音频攒 2 秒才出声；前面 0.2s 分片识别/流式生成全部白做。
  建议做法: 改"渐进播放"——TTS 首个完整分句到达后 300ms 内开始出声，
        后续分句无缝衔接；2 秒缓冲保留为"卡顿保底模式"(可选开关)。
  验收: 首字延迟 < 1s，全句 < 3s。
  备注: 一致性问题（见"重点"节）：前面所有环节（0.2s 分片识别、流式生成、并行合成）都是为了快，结果最后一步播放器把音频攒 2 秒才出声，前面所有优化全部白费。2秒缓冲 vs 低延迟目标，你打算怎么选？

■ 问题 2：采样率链路断裂（44.1kHz vs 16kHz）
  现状: 配置 SAMPLE_RATE=44100，FunASR/Whisper 标准输入 16k，
        直接喂会识别错乱；文档未定义重采样归属。
  建议做法: 两个重采样锚点，与引擎生命周期绑定：
        - 采集 44.1k → [asr_engine 入口重采样] → 16k 入 ASR
        - TTS 合成输出 → [tts_engine 出口重采样] → 44.1k 到播放设备
        不做进 audio_enhancer（它是降噪/增强管道，塞重采样破坏单一职责）。
  验收: 3 条测试音频，识别文本与原文一致率 ≥ 95%。

■ 问题 3：TTS 切句策略两处矛盾
  现状: 清单写"智能切句≤50字"，架构写"≥12字符或标点切句"。
  建议做法: 统一为单规则——优先按标点(。？！；)切；无标点达 12 字触发；
        单段上限 30 字。两份文档引用同一规则。
  验收: 长句(>100字)播报无 2s 以上静默空洞。

■ 问题 4：错峰加载 ASR↔TTS 造成对话中卡顿
  现状: STAGGERED_MODE 轮换加载，对话中"说完话→要TTS"时重新加载
        模型，停顿 1-3s，demo 现场像死机。
  建议做法: Demo 强制关闭错峰——STAGGERED_MODE 默认 False（配置项，
        不改代码逻辑），ASR(FunASR ~1GB) + TTS(edge-tts 无显存) 常驻共存；
        8GB 显存预算充足，实测峰值确认余量。低显存用户的错峰场景
        留到正式版再评估，Demo 阶段不做取舍犹豫。
  验收: 连续 10 轮对话中无 500ms 以上的模型加载停顿。

■ 问题 5：桌宠↔backend 通信契约缺失（联调黑洞）
  现状: 文档未定义桌宠如何连 backend、口型数据走什么格式。
  建议做法: Demo 前只补最小契约：
        - 连接: 桌宠启动时连 backend WS /ws/stream
        - 帧格式: {type: mouth_open|emotion|speech_start|speech_end, data, ts}
        - 心跳: 每 10s，3 次无响应判离线并提示
        - 重连: 指数退避 1s/2s/4s，上限 30s
  验收: 关掉 backend → 桌宠 10s 内显示离线 → 重启后自动恢复口型。

■ 问题 6：演示应急重置（保命后门）
  现状: 演示中对话错乱/LLM 说胡话时，只能重启进程——现场很狼狈。
  建议做法: 两级重置，不依赖语音识别（"/clear" 这类语音指令会被
        ASR 识别成乱码，不可靠）：
        - 热键: 全局快捷键（如 Ctrl+Shift+R）→ 调 /clear-history API
        - 自然词: ASR 后处理把"清空/重置/重新开始"映射为清上下文
  验收: 演示中无论对话错乱到何种程度，≤3s 恢复到干净状态，无需重启。

1.4 Demo 验收标准（对照表）
------------------------------------------------------------------------------
| 验收项          | 标准                                  | 检查方式            |
|-----------------|---------------------------------------|---------------------|
| 端到端延迟      | 说完话 → 出声 < 3s (P50)              | 计时脚本/录屏       |
| 首字延迟        | < 1s                                  | 同上                |
| 口型对齐误差    | < 300ms（肉眼无感错位）               | 录屏逐帧比对        |
| 识别正确率      | 3 条测试音频 ≥ 95%                    | 脚本断言            |
| 打断功能        | 说话可打断 AI，打断后 1s 内停声       | 人工测试            |
| 应急重置        | 错乱后 ≤3s 恢复干净状态，不重启       | 人工测试            |
| 稳定性          | 连续 10 轮对话无崩溃/无显存溢出       | 自动脚本            |
| 断网兜底        | Edge-TTS 不可用时降级 mock 音频不崩   | 断开网络测试        |
| 显存峰值        | < 4GB（8GB 卡留余量）                 | gpu_manager 监控    |

      （D1-D3）→ 再优化延迟（D4-D5）→ 再联调（D6）→ 最后验证（D7-D8）。

几句闲话（小建议）
------------------------------------------------------------------------------
● 完整性的小方法：按"开机→配置→加载→对话→记忆→异常→退出"把文档
  走一遍，缺的那一环往往就是坑。比如你的文档里没有"异常降级"这章，
  写代码时第一个崩的就是它——我也是这么崩过来的。
● 每个关键决定顺手写一行"为什么"，不然两周后的你自己也会看不懂。
  （2 秒缓冲这个矛盾就是这么来的：当时觉得对，后来没人记得为什么。）
● 现场功夫全在预演：先跑通、再故意搞破坏（拔网线、打断它说话）、
  最后掐表。三遍下来，现场基本就不会翻车了。
