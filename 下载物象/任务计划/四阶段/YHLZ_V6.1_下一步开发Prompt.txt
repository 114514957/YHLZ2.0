## 2. 本阶段开发判断（为什么做这个，不做那个）

### 为什么做"情绪表达 + 自主成长节律"

V6.0 完成了**连续性**（重启不断、历史可溯）。但伙伴仍然是"被动触发"的：
- 记忆整理需要显式 API 调用
- 成长事件需要显式 track
- 没有可计算的"情绪状态"表达互动感受

V6.1 让伙伴具备：
1. **情绪表达**：可计算、可解释的情绪状态（基于互动结果/关系/成功率的规则映射），用于更细腻的回应风格——但不改变核心人格
2. **自主成长节律**：handle 联动自动采集成长事件 + 定时/触发式记忆整理

### 为什么不做（V6.1 明确不包含）

- 不做具身化（虚拟形象/动作/视觉人格化）→ V7.x
- 不做 LLM 情绪理解（保持纯规则可解释）
- 不做真实设备控制
- 不做黑盒训练 / 自由协商

## 3. 本版本目标

**V6.1 Emotion Representation & Autonomous Growth Rhythm**

1. **情绪表达层**：`companion/emotion/`（情绪状态机 + 可计算规则 + 情绪审计）
   - 维度：积极度 (positivity) / 能量 (energy) / 亲密感 (warmth)
   - 规则：互动成功/失败/关系信任/创造完成 → 情绪更新（可解释）
   - 情绪 ≠ 人格：核心人格 base 不可变，情绪是表现层
   - 情绪审计：每次更新记录原因
2. **自主成长节律**：`companion/rhythm/`
   - handle 联动：每次委派后自动 track 成长事件
   - 记忆整理触发器：达到阈值（经历数/天数）自动 consolidate
   - 自动快照触发器：每日一次（配置开关）
3. **API**：`companion_emotion()` / `companion_emotion_adjust(context)` /
   `companion_emotion_audit()` / `companion_growth_rhythm()`
4. **配置**：`companion_emotion_*` / `companion_rhythm_*` 前缀

## 4. 架构设计要求

### 分层铁律（保持）

```
Interface → Service → Manager → Storage / Adapter
```

### 情绪表达层

```
backend/embodied/companion/emotion/
├── emotion_state.py     # 情绪状态 (positivity/energy/warmth + 可解释)
├── emotion_engine.py    # 情绪引擎 (规则更新 + 情境映射)
├── emotion_rules.py     # 情绪规则表 (情境 → 维度变化)
└── emotion_audit.py     # 情绪审计 (每次更新追踪)
```

- 情绪维度范围 [0,1]，更新步长配置驱动（禁止魔法数字）
- 情境白名单：success / failure / consecutive_fail / creative_done /
  creative_rejected / relationship_up / relationship_down / idle
- 情绪稳定规则：连续失败/成功有限幅（防剧烈波动）
- 情绪不写入持久化快照？——**应写入**（V6.0 快照扩展 emotion 域）

### 自主成长节律

```
backend/embodied/companion/rhythm/
├── growth_rhythm.py     # 成长节律 (handle 联动 + 触发器)
└── rhythm_audit.py      # 节律审计
```

- handle 联动：委派成功后自动 `track_event("experience_added")` +
  `track_event("experience_confirmed")`（当验证确认时）
- 整理触发器：经历数 ≥ 阈值 或 距上次整理 ≥ N 天 → 自动 consolidate
- 快照触发器：距上次快照 ≥ 1 天（配置开关 `companion_rhythm_daily_snapshot`）
- 所有自动行为记录审计（不静默）

### 快照扩展

V6.0 SNAPSHOT_DOMAINS 增加 `emotion` 域（向后兼容：旧快照无 emotion 域
→ 恢复时跳过该域即可，RestoreManager 已按域遍历）。

## 5. 开发任务

### P0（必须）

1. `emotion/emotion_state.py`：情绪状态（3 维 + 上次变化原因 + 稳定规则）
2. `emotion/emotion_rules.py`：情境 → 维度变化规则表（可解释）
3. `emotion/emotion_engine.py`：情绪引擎（update(context)/decay/stats）
4. `emotion/emotion_audit.py`：情绪审计
5. `rhythm/growth_rhythm.py`：handle 联动采集 + 自动整理/快照触发器
6. Service API：`companion_emotion*` / `companion_growth_rhythm`
7. 快照扩展 emotion 域（保存/恢复）
8. handle 联动：委派 → track 成长事件 + 情绪更新

### P1（尽力）

9. 情绪对回应的修饰规则（情绪高 → 建议措辞更热情，仅建议不强制）
10. 周报：growth_report 增加情绪趋势维度

## 6. 开发要求

### 必须

- 情绪是表现层，核心人格（base）不可变；禁止情绪引擎修改人格
- 全部规则可解释（reason 字段）
- 配置驱动（`companion_emotion_*` / `companion_rhythm_*`），禁止魔法数字
- 自动行为（整理/快照/采集）全部审计
- 快照向后兼容（旧快照无 emotion 域不报错）
- 中文 docstring / 类型注解 / RLock / 完整日志 / 测试 CRLF
- 版本断言批量更新用 Python 脚本

### 禁止

- 禁止破坏 V6.0 及以前 API
- 禁止情绪状态修改人格 base / 使命 / 核心价值
- 禁止 LLM 情绪理解（纯规则）
- 禁止跨层调用 / 静默吞异常 / 黑盒 / 临时方案
