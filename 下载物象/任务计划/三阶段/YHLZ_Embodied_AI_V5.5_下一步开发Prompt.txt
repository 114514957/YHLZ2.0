二、本阶段开发判断

为什么做 Companion Adaptive Personality:
- V5.0~V5.4 建立了完整智能闭环 (感知-策略-规划-执行-反馈-修正-学习)
- 但伙伴人格是静态的 (MainCompanionAgent.personality = "铁哥们" 固定)
- 现实 AI 伙伴需要: 人格自适应 (根据互动历史/情境调整语气与行为,
  但保持核心人格稳定)

V5.5 增强方向:
- 人格状态: 当前人格维度 (热情/耐心/幽默/严肃) 状态 (规则驱动)
- 情境适应: 根据任务类型/执行结果调整人格维度 (成功→鼓励, 失败→耐心)
- 互动记忆: 互动次数/成功失败比例 → 人格倾向统计 (可解释)
- 人格审计: 每次调整记录 (情境/调整/结果)

为什么不做 (本阶段边界):
- 不做跨进程分布式多 Agent (内部单进程)
- 不做 Agent 间自由对话/协商 (确定性规则 + 人格调整策略)
- 不做强化学习 / 神经网络 / 黑盒优化 (人格调整 = 规则统计)
- 不改 Agent Brain / Vision Interface / Memory Interface
- 不控制真实设备 / 机器人 / 自动驾驶
- 不做自我目标生成

三、本版本目标

YHLZ Embodied AI V5.5
Companion Adaptive Personality
伙伴自适应人格层

核心目标:
从:
    伙伴自我修正与学习 (V5.4)
升级:
    伙伴自适应人格 (V5.5)

保持:
    一个人格 / 一个核心意识 / 一个决策中心
    纯规则 + 确定性 + 可解释

四、本版本不包含 (明确边界)

- 禁止神经网络训练 / 梯度更新 / 黑盒优化 (人格调整 = 规则统计)
- 禁止自主修改策略内容
- 禁止绕过 Permission Layer (执行必须经 Permission)
- 禁止写入 Agent Memory
- 禁止真实设备控制
- 禁止修改 Agent Brain / Vision Interface / Memory Interface
- 禁止自我目标生成
- 禁止跨子系统调用 (只改 Embodied 模块)
- 禁止分布式多进程 Agent (内部单进程)

五、架构设计要求

分层: Interface → Service → Manager → Storage/Adapter (保持)

增强模块 (companion 包内):
- 新增 companion/personality.py: 自适应人格器 (人格维度状态/情境适应/
  互动记忆/人格审计)

配置项 (全部 backend/config.py, companion_* 前缀, COMPANION_* 环境变量):
- companion_personality_enabled (默认 True, 人格自适应开关)
- companion_personality_base (默认 "铁哥们", 基础人格)
- companion_personality_adjust_step (默认 0.1, 单次调整步长)

数据模型增强:
- PersonalityState: {base, dimensions: {warmth, patience, humor, serious},
  interactions, success_rate, last_adjust}
- CompanionResponse 增加: personality (人格状态)

API (Service 层新增, 保持 V5.4 兼容):
- companion_personality()  人格状态 (维度/互动统计/可解释)
- companion_adjust_personality(context)  人格调整 (情境 → 维度调整)
- companion_handle() 增强: 人格状态附带 (返回结构向后兼容)

六、开发任务

P0:
1. 人格维度状态: 热情/耐心/幽默/严肃 (0.0~1.0, 可解释)
2. 情境适应: 任务类型/执行结果 → 维度调整 (规则表, 步长可配)

P1:
6. 人格倾向分析: 长期互动 → 人格画像 (成功率高→鼓励型等)
7. 人格重置: 恢复到基础人格 (可配置)
8. 人格 Dry Run: 预演调整方案 (不生效, 复用 dry_run 风格)

七、开发要求

必须:
- 先读后写 / 接口先行 / 配置驱动 / 向后兼容
- 中文注释 (模块/类/函数 docstring) / 类型注解 / 完整日志
- RLock 线程安全 (人格状态共享)
- 单例 + reset (get_service/reset_service)
- Mock 优先 / 默认测试模式
- 异常分层隔离 (Service 捕获返回结构化错误)
- 无测试不交付 (每功能配单元测试)

禁止:

- 跨层调用 (Adapter 不调 Service)
- 临时方案进入主架构
- 静默吞异常
- 破坏 V5.4 既有 API (只新增不修改)
