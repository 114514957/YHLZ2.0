二、本阶段开发判断

为什么做 Companion Execution & Feedback Loop:
- V5.0~V5.2 建立了感知-策略-规划闭环 (数据管道)
- 但规划结果尚未闭环到执行与反馈 (规划输出 → 执行 → 反馈 → 调整)
- 现实 AI 伙伴需要: 完整闭环
  感知 → 策略 → 规划 → 执行 → 反馈 → 调整 (循环)

V5.3 增强方向:
- 执行集成: planning_agent 输出规划 → 执行 Agent (run_goal / execute_action)
- 反馈闭环: 执行结果 → 反馈分析 → 更新经验 (成功/失败 → 策略调整)
- 闭环循环: 感知-策略-规划-执行-反馈 完整循环 (上限可配)
- 执行审计: 每次执行记录 (目标/动作/结果/耗时)

为什么不做 (本阶段边界):
- 不做跨进程分布式多 Agent (内部单进程)
- 不做 Agent 间自由对话/协商 (确定性管道 + 规则依赖)
- 不做强化学习 / 神经网络 / 黑盒优化
- 不改 Agent Brain / Vision Interface / Memory Interface
- 不控制真实设备 / 机器人 / 自动驾驶
- 不做自我目标生成

三、本版本目标

YHLZ Embodied AI V5.3
Companion Execution & Feedback Loop
伙伴执行与反馈闭环层

核心目标:
从:
    伙伴感知与战略集成 (V5.2)
升级:
    伙伴执行与反馈闭环 (V5.3)

保持:
    一个人格 / 一个核心意识 / 一个决策中心
    纯规则 + 确定性 + 可解释

四、本版本不包含 (明确边界)

- 禁止神经网络训练 / 梯度更新 / 黑盒优化
- 禁止自主修改策略内容 (内容修改仍仅来自经验学习规则)
- 禁止绕过 Permission Layer (执行必须经 Permission)
- 禁止写入 Agent Memory
- 禁止真实设备控制
- 禁止修改 Agent Brain / Vision Interface / Memory Interface
- 禁止自我目标生成
- 禁止跨子系统调用 (只改 Embodied 模块)
- 禁止分布式多进程 Agent (内部单进程)

五、架构设计要求

分层: Interface → Service → Manager → Storage/Adapter (保持)

增强模块 (companion 包内):
- 新增 companion/executor.py: 执行协调器 (规划 → 执行 → 反馈 → 调整,
  闭环循环, 上限可配)
- companion/delegate.py 增强: 执行阶段委派 (规划结果 → 执行 Agent)
- companion/pipeline.py 增强: 闭环管道 (感知-策略-规划-执行-反馈)

配置项 (全部 backend/config.py, companion_* 前缀, COMPANION_* 环境变量):
- companion_loop_max_iterations (默认 3, 闭环循环上限)
- companion_execute_confirm (默认 False, 执行确认标记)
- companion_feedback_enabled (默认 True, 反馈闭环开关)

数据模型增强:
- CompanionResponse 增加: execution (执行明细) / feedback (反馈结果)
- ExecutionRecord: {goal, actions, result, latency_ms, status}

API (Service 层新增, 保持 V5.2 兼容):
- companion_execute(request)  执行入口 (规划 → 执行 → 反馈 → 闭环)
- companion_loop(request)     闭环循环 (感知-策略-规划-执行-反馈, 上限内)
- companion_handle() 增强: 闭环管道 (返回结构向后兼容)

七、开发要求

必须:
- 先读后写 / 接口先行 / 配置驱动 / 向后兼容
- 中文注释 (模块/类/函数 docstring) / 类型注解 / 完整日志
- RLock 线程安全 (闭环场景注意共享状态)
- 单例 + reset (get_service/reset_service)
- Mock 优先 / 默认测试模式
- 异常分层隔离 (Service 捕获返回结构化错误)
- 无测试不交付 (每功能配单元测试)

禁止:
- 硬编码 (魔法数字/路径/阈值全进 config)
- 跨层调用 (Adapter 不调 Service)
- 临时方案进入主架构
- 静默吞异常
- 破坏 V5.2 既有 API (只新增不修改)
