二、本阶段开发判断

为什么做 Long Horizon Planning Layer:
- V4.6 已让 AI 能"跨目标统筹规划" (一次规划多目标: 分组/共享/预算)
- 但 V4.6 输出的是"规划方案" (CrossGoalPlan), 不包含执行编排
- 现实任务是多阶段/长时间跨度的: 需要把规划落地为可执行的
  长期任务序列 (阶段划分 → 顺序编排 → 进度跟踪 → 战略调整)

例如:
- 仓库整理任务: 感知 → 搬运 → 归位 (多阶段长期任务)
- 巡逻任务: 多轮 scan+inspect 组合 (长时间跨度)
- 资源受限长期任务: 预算随执行动态调整 (战略执行管理)

V4.7 让 AI 从"跨目标统筹规划"进入"长期任务规划与战略执行管理":
- 阶段划分: 长期目标 → 阶段 (Phase) 序列 (感知阶段/执行阶段/收尾阶段)
- 顺序编排: 阶段间依赖 (前阶段输出 → 后阶段输入)
- 进度跟踪: 阶段执行状态 (pending/running/done/failed), 可恢复
- 战略调整: 阶段失败 → 重规划 (规则驱动, 可解释)

为什么不做 (本阶段边界):
- 不做端到端自动执行编排 (仍是规则 + 统计 + 阈值)
- 不做强化学习 / 神经网络 / 黑盒优化
- 不改 Agent Brain / Vision Interface / Memory Interface
- 不控制真实设备 / 机器人 / 自动驾驶
- 不做自我目标生成

五、架构设计要求

分层: Interface → Service → Manager → Storage/Adapter (保持)
新增模块建议:
- backend/embodied/longhorizon/  (长期任务规划层, 新建包)
  - mission.py     长期任务模型: LongHorizonMission (阶段序列/依赖/进度/状态机)
  - phasing.py     阶段划分器: 长期目标 → Phase 序列 (规则驱动, 可解释)
  - executor.py    执行编排器: 阶段顺序/依赖解析/进度跟踪/失败重规划
  - __init__.py    门面类 (Service 唯一接入点)
- backend/embodied/planning/ 保持 V4.6 不变 (作为阶段内子规划复用)

配置项 (全部 backend/config.py, embodied_* 前缀, EMBODIED_* 环境变量):
- embodied_mission_max_phases (默认 10)
- embodied_mission_retry_limit (默认 2, 阶段失败重试上限)
- embodied_mission_resume_enabled (默认 True, 支持断点恢复)

数据模型:
- LongHorizonMission: {mission_id, goals, phases, dependencies, progress,
  status: pending/running/done/failed, strategy_mode: rule_based}

API (Service 层新增, 保持 V4.6 兼容):
- long_horizon_plan(goals, budget)   长期任务规划 (阶段划分 + 顺序编排)
- long_horizon_phases(goals)         阶段划分分析
- long_horizon_progress(mission_id)  进度跟踪
- long_horizon_retry(mission_id, phase_id) 阶段重试 (失败 → 重规划)
- long_horizon_dry_run(goals)        预演 (复用 V4.5/V4.6 dry_run 风格)
