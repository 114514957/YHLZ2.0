二、本阶段开发判断

为什么做 Companion Coordination Enhancement:
- V5.0 建立了内部多 Agent 架构 (注册/路由/委派/汇总)
- 但委派是顺序串行执行, 无并发/超时控制; 路由是单一关键词规则
- 现实 AI 伙伴需要: 并发委派提升响应, 精确路由提升意图识别,
  协同审计与统计, 更细粒度能力映射

V5.1 增强方向:
- 并发委派: 无依赖专业 Agent 并行处理 (线程池, 可配置)
- 超时控制: 慢 Agent 超时降级 (不阻塞整体)
- 意图识别增强: 多关键词权重打分 (确定性加权, 可解释)
- 能力映射细化: 专业 Agent 精确对接 Service 方法 (细化 default agents)
- 协同统计: 每次委派的 Agent 组合 / 耗时 / 成功率统计

为什么不做 (本阶段边界):
- 不做跨进程分布式多 Agent (内部单进程)
- 不做 Agent 间自由对话/协商 (确定性路由 + 规则分派)
- 不做强化学习 / 神经网络 / 黑盒优化 (意图识别仍为规则加权)
- 不改 Agent Brain / Vision Interface / Memory Interface
- 不控制真实设备 / 机器人 / 自动驾驶
- 不做自我目标生成

五、架构设计要求

分层: Interface → Service → Manager → Storage/Adapter (保持)

增强模块 (companion 包内):
- companion/delegate.py  增强: 并发委派 (线程池) + 超时控制 + 耗时统计
- companion/router.py    增强: 关键词权重打分路由 (确定性加权)
- companion/__init__.py  增强: 细化默认专业 Agent 能力映射
- 新增 companion/stats.py: 协同统计 (委派组合/耗时/成功率)

配置项 (全部 backend/config.py, companion_* 前缀, COMPANION_* 环境变量):
- companion_delegate_workers (默认 4, 并发线程数)
- companion_agent_timeout (默认 10.0, 单 Agent 超时)
- companion_route_topk (默认 3, 路由打分取前 N)

数据模型增强:
- CompanionResponse 增加: dispatched_parallel (是否并发) /
  total_latency_ms / per_agent_latency_ms
- RouteResult 增加: score / weighted_keywords (可解释打分)

API (Service 层新增, 保持 V5.0 兼容):
- companion_stats()       协同统计 (委派次数/成功率/平均耗时/Top 组合)
- companion_handle() 增强: 并发委派 + 超时 (返回结构向后兼容)

六、开发任务

P0:
1. 并发委派: 无依赖专业 Agent 线程池并行 (顺序保持结果稳定)
2. 超时控制: 单 Agent 超时 → 标记 timeout 错误 (不阻塞整体)
3. 路由打分: 关键词权重 (确定性加权) + Top-K 路由 (可解释分数)
4. 协同统计: companion_stats() (组合/耗时/成功率)
5. 单元测试 (新增 >=100 用例, 目标专项 >= 1514)

P1:

   (如 long_horizon_agent → long_horizon_plan / track_progress)

8. 协同 Dry Run 增强: 预演含并发/超时模拟

七、开发要求

必须:
- 先读后写 / 接口先行 / 配置驱动 / 向后兼容
- 中文注释 (模块/类/函数 docstring) / 类型注解 / 完整日志
- RLock 线程安全 (线程池场景特别注意共享状态)
- 单例 + reset (get_service/reset_service)
- Mock 优先 / 默认测试模式
- 异常分层隔离 (Service 捕获返回结构化错误)
- 无测试不交付 (每功能配单元测试)

禁止:
- 硬编码 (魔法数字/路径/阈值全进 config)
- 跨层调用 (Adapter 不调 Service)
- 临时方案进入主架构
- 静默吞异常
- 破坏 V5.0 既有 API (只新增不修改)
