## 2. 本阶段开发判断（为什么做这个，不做那个）

### 为什么做"Constitution Engine"

V7.0 完成后 YHLZ 已有三层自治能力（成长治理/智能调度/表达存在），
但治理是分散的：
1. **无统一最高治理原则**（人机互补/身份边界/创造增强无集中定义）
2. **无治理冲突仲裁**（成长建议 vs 调度成本 vs 表达边界无优先级裁决）
3. **无治理审计总账**（各层审计分散，无统一治理视图）

V8.0 三主线：
1. **Constitution 定义层**：人机互补/身份边界/创造增强原则的
   机器可读定义 + 校验
2. **治理仲裁器**：跨层冲突仲裁（身份 > 安全 > 成长 > 调度 > 表达）
3. **治理总账**：统一治理审计（可查询/可回放）

### 为什么不做（V8.0 明确不包含）

- 不做 LLM 核心（纯规则保持）
- 不做自动应用成长（growth_auto_apply 保持 false）
- 不做云端成为核心（身份/记忆/安全永远本地）
- 不做 3D 渲染（表达保持状态机，推送接口可预留）

## 3. 本版本目标

**V8.0 YHLZ Constitution Engine**

1. **Constitution 定义** `companion/constitution/`
   - 治理原则表（可解释）：人机互补/身份边界/创造增强/安全优先
   - 原则校验器（行为 → 原则符合性判定）
2. **治理仲裁器** `constitution_arbiter.py`
   - 跨层冲突仲裁（优先级：身份 > 安全 > 成长 > 调度 > 表达）
   - 输出 {decision, reason, priority, layers}
3. **治理总账** `constitution_ledger.py`
   - 统一治理审计（跨层行为记录，可查询/可回放）
4. **快照增强**：constitution_state 域

## 4. 架构设计要求

### 分层铁律（保持）

```
Interface → Service → Manager → Storage / Adapter
```

### Constitution 定义层

```
backend/embodied/companion/constitution/
├── principles.py          (治理原则表 + 校验)
├── arbiter.py             (跨层冲突仲裁)
├── ledger.py              (治理总账)
└── __init__.py            (ConstitutionEngine 门面)
```

- 原则全部可解释（principle_id/rule/reason）
- 禁止魔法数字（全进 config）

### 治理仲裁器

- 优先级：identity > safety > growth > scheduling > expression
- 输入：跨层冲突事件（如成长建议 vs 成本限制）
- 输出：{decision, reason, priority, layers}

### 治理总账

- 记录：{time, layer, action, decision, reason, priority}
- 可查询/可回放（reuse 审计模式）

## 6. 开发要求

### 必须

- 原则校验纯规则（可解释）
- 仲裁优先级固定（身份 > 安全 > 成长 > 调度 > 表达）
- 总账全量记录（不可静默）
- 配置驱动（`companion_constitution_*` 前缀）
- 中文 docstring / 类型注解 / RLock / 完整日志 / 测试 CRLF
- 版本断言批量更新用 Python 脚本

### 禁止

- 禁止破坏 V7.0 及以前 API
- 禁止自动应用成长（growth_auto_apply 恒 false 语义）
- 禁止云端结果直接改变身份（验证铁律保持）
- 禁止跨层调用 / 静默吞异常 / 黑盒 / 临时方案
